# 01 · 架构与核心流程

## 1. 分层架构（自顶向下）

```
┌─────────────────────────────────────────────────────────────┐
│  cmd/skill-up/main.go        CLI 入口（极薄，ldflags 注入 version） │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│  internal/cli/ (Cobra 命令层)                                 │
│  run / validate / list-cases / report / import / debug / init│
│  职责：参数解析、配置加载、override 合成、调用 runner          │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│  internal/runner/  端到端编排                                 │
│  职责：iteration 工作区管理 → 构造 evaluator → 聚合 → 写报告  │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│  internal/evaluator/  单 Case 流水线编排（核心引擎）          │
│  职责：并发调度 + retry + 执行一个 case 的完整生命周期        │
└───────┬───────────────┬───────────────┬─────────────┬───────┘
        │               │               │             │
┌───────▼──────┐ ┌──────▼───────┐ ┌─────▼─────┐ ┌─────▼──────┐
│ internal/    │ │ internal/    │ │ internal/ │ │ internal/  │
│ agent/       │ │ judge/       │ │ runtime/  │ │ mcp/       │
│ 多引擎适配器  │ │ 3 种评分策略  │ │ 沙箱隔离   │ │ MCP 注册   │
└──────────────┘ └──────────────┘ └───────────┘ └────────────┘
        │               │               │
        └───────────────┴───────────────┴──→ pkg/transcript/（统一会话数据模型）
                                            internal/report/（多格式报告）
                                            internal/credential/（多源凭据解析）
                                            internal/observability/（OTel 追踪）
```

**分层的关键约束**（来自 [AGENTS.md](../AGENTS.md)）：
- `internal/` 是私有的，模块外不可 import。
- `pkg/skillup/`、`pkg/transcript/` 是 **semver 稳定的公开 API**，破坏性改动要升大版本。
- CLI 胶水代码放 `internal/cli/`，业务逻辑放对应的 `internal/<domain>/`。

> **Java 类比**：这套分层 ≈ Spring 项目的 controller → service → (strategy/adapter) → infrastructure。`internal/` = 不对外暴露的 service 实现；`pkg/` = 对外的 API/DTO 模块。

## 2. 核心数据流：一次 `skill-up run` 发生了什么

### 2.1 顶层 4 阶段（[internal/cli/run.go:123-166](../internal/cli/run.go#L123)）

```
Phase 1: 配置加载      loadAndPrepareConfig()
  ├── 找 eval.yaml（向上查 SKILL.md + evals/eval.yaml，或 --auto 识别 evals.json）
  ├── Loader 加载 eval.yaml + cases/*.yaml（路径相对 SKILL.md 目录解析）
  ├── include/exclude glob 过滤
  ├── 只校验「选中」的 case（被过滤掉的不阻塞运行）
  └── 应用 CLI override（--engine / --model / --runtime / --parallelism / --rk / --ek）

Phase 2: 凭据 + Agent   loadCredentialsAndAgent()
  ├── Resolver 加载凭据（.env + ~/.skill-up/credentials.yaml）
  ├── 解析 model ref（provider/name 切分，处理代理网关的字面模型 id）
  └── agent.DetectAgentWithInitParams() 工厂创建 Agent 适配器

Phase 3: 执行评测       executeEvaluation()
  └── runner.Evaluate()  →  见 2.2

Phase 4: 汇总           统计 pass/fail/error，决定退出码（0=全过，1=失败/错误，CI 友好）
```

### 2.2 Runner 层：iteration 循环（[internal/runner/runner.go:95-180](../internal/runner/runner.go#L95)）

```
对每个 iteration（默认 1 轮，--iteration N 跑 N 轮，--iteration 0 自动续号）：
  1. setupWorkspace()  在 <skill>-workspace/iteration-<N>/ 建产物目录
  2. newEvaluator(EvalOptions{...})  构造评测器（注入 config/loader/agent/并发度/是否带 baseline）
  3. ev.EvaluateAll(ctx, cases)      并发跑所有 case（见 2.3）
  4. WriteResults()                  分组(with/without skill) → 写 grading/benchmark/result/各格式报告
```

> **设计点**：workspace 默认放在 skill 目录**旁边**（`<skill>-workspace/`），而不是里面 —— 对齐 Anthropic eval 布局，也避免污染 skill 仓库。

### 2.3 Evaluator 层：Case 并发执行（[internal/evaluator/evaluator.go:180-237](../internal/evaluator/evaluator.go#L180)）

```
EvaluateAll():
  tasks = cases × {with_skill [, without_skill]}   # baseline 翻倍任务
  sem := chan struct{}{concurrency}                 # 信号量限并发
  for each task:  go func { sem<-{}; executeCase(); <-sem }   # WaitGroup 等待
```

- **并发模型**：`带缓冲 channel 当信号量 + sync.WaitGroup`，受 `cases.parallelism` 控制（CLI 可覆盖，上限 256）。
  > **Java 类比**：≈ 自己手撸的 `Semaphore` + `CountDownLatch`，等价于 `ThreadPoolExecutor` + `Future.allOf`。
- **baseline**：`benchmark.enabled=true` 时，同一 case 跑两遍（装 Skill / 不装 Skill），量化 Skill 增量价值 —— 这是**Agent Skill 版的 A/B 实验**。

### 2.4 单 Case 生命周期（核心！[internal/evaluator/evaluator.go:333](../internal/evaluator/evaluator.go#L333)）

这是整个项目最该讲清楚的一条链：

```
executeCase()  —— 带 retry 包装（按 retry_policy.retry_on ∈ {timeout,error}，指数退避 2^n 秒）
  └─ executeCaseOnce()  —— 一次完整尝试
       │
       ① 准备 Runtime（沙箱）
       │   prepareRuntimeForCase():  none/opensandbox/docker → Create() 建隔离 workspace
       │
       ② 装环境 + 装 Agent + 装 MCP + 装 Skill
       │   setupCaseEnvironment():
       │     - 跑 environment.setup_steps（自定义初始化命令）
       │     - agent.Install()（装 Agent CLI，幂等）
       │     - agent.InstallMCP()（注册 MCP server）
       │     - agent.InstallSkill()（把 SKILL.md 等装进引擎的 skill 目录，without_skill 配置跳过）
       │     - fixtures.UploadAll()（上传测试夹具：repo_fixture / files / git init）
       │
       ③ 执行 Agent
       │   单轮: agent.Run(ctx, rt, opts, messages) → SessionResult
       │   多轮: executeMultiTurn() → 每轮调 SessionResumer.RunTurn(resume sessionID)
       │        ├─ 模板替换 {{变量}}（上一轮 capture 的值注入下一轮 prompt）
       │        ├─ post_condition 门控（must_contain / on_fail: skip_remaining|fail）
       │        └─ regex / JSONPath 捕获响应值
       │
       ④ 收集产物
       │   - workspace diff（git baseline→HEAD，agent_judge 需要）
       │   - generated_files（agent 生成的文件）
       │   - collect_artifacts glob 下载
       │
       ⑤ expect 预检查（零成本短路）  runExpectPreCheck()
       │   must_contain / must_not_contain / exit_code / files_exist / golden_file / file_contains
       │   失败 → 直接 FAIL，跳过昂贵的 judge（省钱省时间）
       │
       ⑥ Judge 评分  runJudgePhase()
       │   judge.Input{Transcript, FinalMessage, WorkspaceDiff, GeneratedFiles, TurnResults, ...}
       │   → 工厂 NewJudge(judgeCfg) 按 type 路由：
       │       rule_based  : 纯 Go 声明式规则匹配（确定性，先 failure 短路再 success）
       │       script      : 跑外部评分脚本（退出码即结论，env 传 transcript）
       │       agent_judge : 起一个裁判 Agent，按 criteria 打分（阈值 ≥ pass_threshold 才 PASS）
       │   → Result{Status, AssertionResults[], Summary{pass_rate}}
       │
       ⑦ 合并 expect + judge 断言 → EvalResult{Status, Grading, TurnResults, ...}
```

**几个值得在面试强调的执行细节**：

1. **case 级 timeout 是 agent + judge 的总预算**（[evaluator.go:853-883](../internal/evaluator/evaluator.go#L853)）：用 `context.WithTimeout` 包住整次尝试，超时被识别成 `timeout` 重试理由，并在错误里**标注是哪个配置项**导致的（`case.constraints.timeout_seconds` vs `cases.defaults.timeout_seconds`），方便用户调参。
2. **错误不丢现场**：agent 执行失败时，仍会下载 glob 产物（[evaluator.go:456](../internal/evaluator/evaluator.go#L456)）；agent_judge 失败时用 `SessionResultError` 包裹保留裁判 session（[judge.go:156](../internal/judge/judge.go#L156)），仍能捞回 artifacts 排错。
3. **退出码语义**：agent 非零退出 ≠ 直接 FAIL。若配了 `expect.exit_code` 或 judge，会继续走评测；都没配才 FAIL（[evaluator.go:465-478](../internal/evaluator/evaluator.go#L465)）。
4. **judge 前移除 run skill**：agent_judge 时会先把被测 Skill 从引擎 skill 目录移除（[evaluator.go:719](../internal/evaluator/evaluator.go#L719)），防止裁判被被测 Skill 干扰，保证裁判中立。

## 3. 三条贯穿全项目的「数据契约」

这是理解架构的钥匙 —— 三条接口/类型把异构的子系统粘起来：

### 3.1 `Agent` 接口（执行层抽象）
[internal/agent/agent.go:132-148](../internal/agent/agent.go#L132) —— 7 个方法（`Name/Install/InstallMCP/InstallSkill/Run/Check/CheckCredentials`）+ 可选 `SessionResumer.RunTurn`。任何 Agent 引擎实现它，evaluator 就能驱动。

### 3.2 `judge.Input`（执行层 → 评测层的统一数据边界）
[internal/judge/judge.go:55-98](../internal/judge/judge.go#L55) —— 一个 struct 装下评测所需一切。三种 Judge 策略消费同一个 Input，**执行层和评测层彻底解耦**。换 Judge 策略不用动执行层。

### 3.3 `pkg/transcript.Transcript`（跨引擎统一会话模型）
[pkg/transcript/transcript.go](../pkg/transcript/transcript.go) —— `[]Message{Role, Content, Turn, ToolCall, ToolResult}`。不同 Agent 引擎的原生输出（Claude 的 JSONL、Codex 的 NDJSON 流、Qwen 的 Gemini schema）都被各自解析器归一成这个形状。这是**跨引擎可比**的基础，也是 semver 稳定的公开 API。

> **Java 类比**：这三条契约 ≈ 你定义的三个 SPI 接口 / DTO。`Agent` 是 SPI（多个实现），`judge.Input` 是 service 层和 strategy 层之间的 DTO 契约，`Transcript` 是跨系统的统一领域模型（DDD 里的共享内核）。

## 4. 配置如何驱动一切（eval.yaml）

一个最小的 `eval.yaml` 长这样（[examples/code-stats/evals/eval.yaml](../examples/code-stats/evals/eval.yaml)）：

```yaml
schema_version: v1alpha1
environment: { type: none }          # none / opensandbox / docker
engine:    { name: qodercli, model: { name: auto } }
skills:    [ { source: local_path, path: . } ]   # 装当前目录的 Skill
cases:
  files: [ evals/cases/analyze-directory.yaml, ... ]
  defaults: { timeout_seconds: 900, max_turns: 5 }
  parallelism: 2
  retry_policy: { max_retries: 2, retry_on: [error] }
benchmark: { enabled: true }         # 开 with/without skill 对比
judge: { type: script, script_path: evals/fixtures/scripts/check-stats.sh }
report:  { formats: [json, html] }
```

每个 case 文件定义 `input`(prompt/turns) + `context`(fixture/git) + `constraints` + `expect` + `judge`，**case 级可覆盖 eval 级**（见 [03-子系统详解.md](./03-子系统详解.md) 的配置合并语义）。
