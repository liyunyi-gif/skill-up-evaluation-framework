## 一、项目描述模板（按详略分三档）

### 档位 A：一行版（简历项目标题下的简介）
> **skill-up — Agent Skill 评测与演进框架**（Alibaba 开源，Go）：声明式 YAML 驱动，在 Claude Code / Codex / Qoder CLI 等多引擎上跑 Agent Skill 的评测用例，通过规则/脚本/LLM 裁判打分，产出结构化报告与 A/B 基线对比，支持 CI 集成与 OpenTelemetry 全链路追踪。

### 档位 B：STAR 三条版（推荐，简历主体）

> **skill-up：Agent Skill 评测与演进 CLI 框架** ｜ Go 1.25 · Alibaba 开源
>
> - **多引擎抽象与适配**：设计 `Agent` 接口 + 工厂 + 模板方法的四层适配架构（BaseAgent→CLIAgent→具体引擎），统一接入了 Claude Code / Codex / Qoder CLI / 通义千问 4 种异构 Agent CLI，并支持通过 `engine.custom`（local/http 双传输）零改源码扩展任意 Agent 服务。
> - **可插拔评分引擎**：基于策略模式实现 rule_based / script / agent_judge（LLM 裁判）三种评分策略，用 `judge.Input` 统一数据边界解耦执行层与评测层；针对 LLM 输出设计了四层兜底 JSON 解析 + 防作弊校验（结果数 = 标准数、evidence 必填），把 LLM 裁判的误判面降到最低。
> - **工程化与可观测**：实现 none/OpenSandbox/Docker 三后端的统一 Runtime 隔离层（进程组优雅终止、跨平台 Shell 抽象、符号链接 TOCTOU 防御），集成 OpenTelemetry 全链路 trace；支持 with/without Skill 基线 A/B 对比，将「Skill 有效性」量化为可复现指标。

### 档位 C：详细五条版（技术面/个人陈述用）
1. **定位**：Agent Skill（AI Agent 技能包）的「单元测试 + 回归测试」框架，把过去靠人肉试的 Skill 质量评估，产品化为可声明、可复现、可回归、可入 CI 的工程化流程。
2. **声明式评测 DSL**：自研 `v1alpha1` YAML schema（eval.yaml + cases/*.yaml），分层校验器（文档级/类型枚举/runtime 特化/case 级/去重/judge 合并），支持 case 级覆盖 eval 级、CLI override 叠加、子集校验正确性。
3. **多引擎适配**：四层组合（BaseAgent/CLIAgent/具体适配器/CustomAgent），别名归一化抽到无依赖叶子包消除常量同步；处理了跨引擎语义串味（如 qoder 专属 `auto` 模型）、兼容代理网关（合成 `skill-up-openai` provider）、跨平台 shebang/env -S 解析等真实工程问题。
4. **评分与判官**：三种 Judge 策略 + expect 零成本预检查短路；agent_judge 的 context_materializer 用 profile/mode 双维控制 prompt 体积（include 超限自动降级 file_ref）；不可信输入全链路脱敏（maskAPIKey）+ 路径穿越/SSRF/凭据泄漏防御。
5. **可观测 + 生态**：OpenTelemetry trace（含 linked trace topology 把子 Agent trace 挂成父子）+ 兼容 Anthropic grading/benchmark 格式（生态借力）+ GitHub Action 一键 CI。

## 三、高频面试问答（按「会问什么」组织）

### Q1：讲讲这个项目的架构 / 你负责的部分怎么设计的？
**答法**：先给分层（CLI→Runner→Evaluator→Agent/Judge/Runtime/Report），再讲「三条数据契约」（Agent 接口、judge.Input、Transcript）如何把异构子系统解耦。最后落到一个亮点（如 agent 适配的四层组合 或 judge 的统一边界）。
> 关键词：分层、接口隔离、策略模式、数据边界。

### Q2：为什么要抽象出这么一层 Agent 接口？直接调 Claude Code 不行吗？
**答**：因为要「跨引擎可比」。同一个 Skill 要在 Claude Code / Codex / Qoder CLI 上都跑一遍，证明它不依赖单一引擎。每个引擎的安装、命令、输出格式、session 机制都不同，不抽象就会每加一个引擎改一堆 if-else。抽象成 `Agent` 接口后，evaluator 只面向接口编程，新引擎只加一个适配器 + 工厂 case。
> 延伸：这是「开闭原则」+「依赖倒置」的落地。

### Q3：rule_based / script / agent_judge 怎么选？
**答**：按「确定性 + 成本」分层。
- 能用确定规则判的（关键字、文件存在、工具调用、退出码）→ rule_based，零成本、CI 友好、可复现。
- 需要复杂逻辑（跑测试套件、解析结构化输出）→ script，退出码即结论，语言任选。
- 开放式语义评测（代码质量、bug 定位准确性、文档可读性）才用 agent_judge，因为它贵且非确定。
- 设计上还有 expect 预检查做**第一层短路**：能零成本判的直接 FAIL，连 rule_based 都不跑，更别说 LLM。
> 这体现「成本意识」—— 不是无脑调大模型。

### Q4：用 LLM 当裁判，怎么保证它打分靠谱？
**答（分四点）**：
1. **prompt 工程**：强制 JSON 输出、强制 evidence、给响应模板骨架；配了 judge skill 时强制裁判先加载完整 rubric。
2. **输出鲁棒解析**：LLM 返回的 JSON 经常不规整，做了四层兜底（直接解析→提取围栏块→大括号配对状态机→引号修复）。故意不用正则提 JSON，因为嵌套+转义让正则很脆弱。
3. **防作弊校验**：结果数必须 == criteria 数（防少返回几条导致通过率虚高），每条 evidence 必填。
4. **阈值制**：pass_rate ≥ pass_threshold（默认 0.7）才 PASS，而不是要求全过 —— 容忍单条判定的波动。
> 这条最能体现「跟大模型真实打交道的工程经验」。

### Q5：怎么做并发的？怎么控制超时和重试？
**答**：
- **并发**：带缓冲 channel 当信号量 + WaitGroup，受 `cases.parallelism` 控制（1–256）。每个 case 一个 goroutine。
- **超时**：case 级 `context.WithTimeout`，是 agent + judge 的**总预算**；超时被识别成 `timeout` 重试理由，错误里标注是哪个配置项导致的（方便调参）。
- **重试**：`retry_policy.retry_on ∈ {timeout, error}`，指数退避 `2^n` 秒。
- **进程清理**：none runtime 用进程组，ctx cancel 先 SIGTERM 整组、1s 后 SIGKILL，防孙子进程逃逸。

### Q6：安全上做了什么？
**答（Custom Engine 是重点）**：因为自定义引擎是不可信的（返回任意 JSON/文件），做了全套护栏：
- 路径穿越 + 符号链接 TOCTOU 防御（每次 use 前重新 `EvalSymlinks`，关闭运行中种链接的窗口）；
- 凭据脱敏（maskAPIKey 对所有不可信字段全替换）；
- 凭据不能进命令行/URL（会出现在 ps/trace）；
- artifact 下载不跟随 3xx 重定向（防 SSRF）；
- 配置侧：识别敏感变量名 + 真实凭证形状（sk-ant-/ghp_/AKIA…），严格模式拒绝凭证进命令行字段。

### Q7：怎么保证评测可复现？
**答**：
- 声明式 YAML 配置（环境/引擎/模型/用例/判官全声明）；
- 每个 iteration 产物落盘（result.json/grading.json/benchmark.json + outputs/）；
- agent_judge 物化上下文到磁盘 + manifest.json 记录交付决策；
- iteration-N 目录自动续号，历史可追溯；
- OTel trace 串起全链路，带 case.id/engine/model/status 属性。

### Q8：with/without Skill 基线对比是干嘛的？
**答**：Agent Skill 的核心问题是「这个 Skill 到底有没有用」。benchmark.enabled=true 时同一批 case 跑两遍（装/不装），算通过率/token/耗时的 mean+stddev 和 delta。delta 直接量化 Skill 的增量价值。这是「Skill 版的 A/B 实验」，把主观判断变成可量化指标。

### Q9（Java 选手高频）：Go 和 Java 写这种项目的区别 / 你怎么上手的？
**答**：
- Go 没有 Spring 那套，依赖注入靠「构造器 + 接口」，更轻；
- 没有继承，用「组合 + 接口」（项目里 BaseAgent→CLIAgent 就是 embedding + 接口）；
- 错误处理是 `if err != nil` 而非 try-catch，但项目用了 error chain（`errors.Is/As`，如 `SessionResultError`）做类型化错误；
- 并发用 goroutine + channel，比 Java 线程池轻量（项目里信号量 + WaitGroup 是惯用法）；
- context 贯穿全链路做超时/取消传递（比 Java 的 InterruptedException 模型更系统）。

### Q10：这个项目最难 / 最有技术含量的部分是什么？
**答（任选一个深讲）**：
- **agent_judge 的工程化**：从 prompt 体积控制（context_materializer profile/mode）到输出鲁棒解析（四层兜底）到防作弊，是把「LLM 当组件」的完整工程实践。
- **Custom Engine 的安全**：不可信输入的系统性防御（TOCTOU/脱敏/SSRF），是少见的安全深度。
- **跨平台执行**：进程组优雅终止 + classifyExecError 四态 + shebang/env -S tokenizer + 跨平台路径转换，全是细节魔鬼。
