> 这一份是「能让你在面试里讲出深度」的素材。每条都标了：**是什么 / 为什么这么做 / Java 类比 / 简历话术**。

## A. 设计模式落地（不要只说名词，要能讲清「解决了什么」）

### A1. 策略模式 × 2 处

**① Judge 评分策略**（[internal/judge/factory.go:22-50](../internal/judge/factory.go#L22)）

```go
func NewJudge(cfg config.JudgeConfig, ag agent.Agent, rt runtime.Runtime) (Judge, error) {
    switch cfg.Type {
    case "rule_based":  return NewRuleBasedJudge(cfg), nil      // 纯 Go 规则，确定性
    case "script":      return &ScriptJudge{...}, nil            // 外部脚本，退出码即结论
    case "agent_judge": return NewAgentJudge(...), nil           // LLM 裁判，阈值制
    case "":            return nil, nil                          // 无 judge = 默认 PASS
    }
}
```

三个实现都满足 `Judge interface { Evaluate(ctx, Input) (*Result, error) }`，evaluator 不感知具体类型。
- **Java 类比**：Spring 里 `@Component` + `Map<String, JudgeStrategy>` 按 key 注入；这里是 switch + 构造器。
- **简历话术**：「设计并实现了基于策略模式的可插拔评分框架，规则/脚本/LLM 裁判三种策略共享统一输入契约，新增评分方式只需加一个 case 分支，零侵入上游。」

**② 自定义引擎传输策略**（[internal/agent/custom.go:128-160](../internal/agent/custom.go#L128)）

`customTransport` 接口有 `localTransport`（runtime 内执行命令）和 `httpTransport`（POST 远程服务）两实现，`selectTransport` 按配置路由，结果都归一到 `transportOutcome` 由同一个 `assembleResult` 装配。

### A2. 模板方法 + 工厂 + 适配器（Agent 适配层四层组合）

[internal/agent/](../internal/agent/) 的继承/组合关系：

```
BaseAgent（基础设施：凭据检查、env 合并、PATH 探测、shell 引用）
  ├── CLIAgent（CLI 类 Agent 的模板方法：InstallMCP/InstallSkill/Run/Check 骨架）
  │     ├── ClaudeCodeAgent / CodexAgent / QoderCLIAgent / QwenCodeAgent
  └── CustomAgent（故意不嵌 CLIAgent，直接嵌 BaseAgent —— 控制接口表面）
```

- **工厂**：`DetectAgent` 按 engine name 路由（[factory.go:12-34](../internal/agent/factory.go#L12)），别名归一化抽到无依赖的叶子包 `agentkind`（消除「两处常量列表手动同步」）。
- **适配器**：每个 Agent CLI 的安装/命令/输出格式都不同，适配器把它们翻译成统一的 `Agent` 接口 + `SessionResult`。
- **Java 类比**：Spring JDBC 的 `DataSource → JdbcTemplate → 各数据库 Driver`；这里是 `BaseAgent → CLIAgent → 各 Agent CLI`。

### A3. 值对象边界（数据契约固化协议）

`judge.Input`（执行层→评测层）和 `judge.Result/AssertionResult/ResultSummary`（评测层→报告层）是纯值对象，注释里明确写「unified data boundary」。换 Judge 不动执行层，换报告格式不动评测层。
- **Java 类比**：DDD 的值对象 + 端口/适配器架构里的端口契约。

### A4. 函数式选项模式（functional options）

`report.ComputeAnthropicBenchmark(name, path, withRuns, withoutRuns, WithTimestamp(ts))`（[benchmark_anthropic.go:137-187](../internal/report/benchmark_anthropic.go#L137)）—— Go 社区惯用的可扩展构造 API。
- **Java 类比**：Builder 模式的变体，但更轻。

## B. 工程深度亮点（这些最能区分候选人）

### B1. 「执行层 ↔ 评测层」解耦的统一数据边界 ⭐⭐⭐

一个 `judge.Input` 装下评测所需一切（transcript / final_message / workspace_diff / generated_files / turn_results / session_result）。三种 Judge 策略消费同一份输入。

**为什么重要**：这是整个项目架构的灵魂。它让「怎么执行」和「怎么评分」彻底独立演进。新增一种 Judge（比如未来的 embedding 相似度 judge）只需实现接口 + 工厂加 case；执行层加一种新引擎，Judge 完全无感。

> 面试可以这么讲：「我们把可扩展性落到了类型契约上，而不是停在口头抽象。上游只要能产出 Input，任何执行后端能接入；下游只要能消费 Result，任何报告层能接入。」

### B2. expect 预检查的「短路省钱」⭐⭐

[internal/evaluator/evaluator.go:540-565](../internal/evaluator/evaluator.go#L540)：在昂贵的 Judge（尤其 LLM 裁判）之前，先跑零成本的确定性检查（字符串包含/文件存在/退出码/golden 比对）。失败直接 FAIL 短路，跳过 Judge 的一次 LLM 调用。

**为什么重要**：体现了「成本意识」—— 不是无脑调大模型，而是分层：能确定性判的不花 LLM token。同时通过后的 expect 断言会**前置拼到 judge 断言**里一起计入通过率，保证报告完整。

### B3. agent_judge 的「LLM 输出鲁棒解析」⭐⭐⭐

LLM 当裁判返回的 JSON 经常不规整。skill-up 的 `extractJSON`（[internal/judge/agent_judge.go:229-259](../internal/judge/agent_judge.go#L229)）做了**四层兜底**：

1. 直接 `json.Unmarshal` 整段；
2. 失败 → 提取 ` ```json ... ``` ` 围栏块；
3. 还失败 → 大括号配对状态机扫描候选 JSON 对象（`findJSONObjectEnd` 故意不用正则，因为嵌套+转义让正则很脆弱）；
4. 最后 → `repairJSONQuotes` 修 LLM 常见的「evidence 文本里忘转义双引号」问题。

外加两个防作弊校验（[agent_judge.go:213-225](../internal/judge/agent_judge.go#L213)）：
- **结果数必须 == criteria 数**：防止 LLM 少返回几条导致「1/1 = 100%」虚高；
- **每条 evidence 非空**：强制可解释。

**为什么重要**：这是「跟大模型真实打交道的工程经验」—— 提示工程 + 输出容错 + 防作弊。面试很加分。

### B4. context_materializer 的「prompt 体积控制」⭐⭐

agent_judge 要把被测产出（transcript/diff/files）喂给裁判 Agent，但 prompt 不能无限大。设计了两维控制（[internal/judge/context_materializer.go](../internal/judge/context_materializer.go)）：

- **Profile**（`minimal`/`standard`）：批量预设每种材料的默认交付方式；
- **Mode**（`include`/`truncate`/`omit`/`file_ref`）：每种材料可单独覆盖。`include` 超过 `max_bytes`(默认 64KB) 自动降级为 `file_ref`（只在 prompt 里给路径，让裁判自己读）。

外加一个 `manifest.json` 记录每个材料的交付决策，用于报告和复现。

**为什么重要**：体现了「token 成本工程」—— 既控制 prompt 体积，又保留完整信息访问（file_ref）。

### B5. 不可信输入的安全护栏（Custom Engine 全链路）⭐⭐⭐

自定义引擎是**不可信的**（可能返回任意 JSON / 任意文件）。skill-up 做了一整套防护（[internal/agent/custom.go](../internal/agent/custom.go)）：

| 风险 | 防护 |
|------|------|
| 路径穿越 / 符号链接 TOCTOU | `workspacePath` 每次 use 前重新解析符号链接 + `EvalSymlinks`，关闭「运行中种外指链接」的窗口 |
| 凭据被 echo 回来 | `maskAPIKey` 对 FinalMessage/Stderr/Transcript/Engine/Model **所有不可信字段**脱敏（≥8 字符的 env value 全替换） |
| 凭据进命令行/URL | API key 不能渲染进 command/URL（会出现在 `ps`/trace） |
| artifact URL 重定向到内网 | HTTP artifact 下载**不跟随 3xx 重定向** |
| 内存耗尽 | multipart 上传总大小上限 256MB |

**为什么重要**：这是简历级**安全工程**展示 —— 对 TOCTOU、凭据泄漏、SSRF 的系统性防御，远超「我用了 https」。

### B6. 配置即代码的安全实践 ⭐⭐

[internal/customengine/customengine.go](../internal/customengine/customengine.go)：

- `sensitiveEnvNamePattern`：识别 `API_KEY/TOKEN/SECRET/PASSWORD` 等敏感变量名；
- `secretLiteralPatterns`：识别 `sk-ant-/sk-/ghp_/AIza/xox/AKIA/JWT` 等**真实凭证形状**；
- `resolveEnvRefsStrict`：命令行字段用**严格模式**，拒绝把凭证拼进命令行，并迭代展开防止 `${WRAPPER_VAR}` 间接走私；
- `normalizeKeyForSensitiveCheck`：`api-key/apiKey/bearerToken` 统一转 UPPER_SNAKE_CASE 再匹配，覆盖多种命名风格。

**为什么重要**：开源工具被各种用户配置，「防止用户把明文密钥写进会被日志/进程列表暴露的地方」是成熟产品的标配意识。

### B7. 跨平台 + 多源容错的执行细节 ⭐⭐

几个小而精的工程点，单独讲都很有料：

- **进程组 + 优雅升级**（none runtime，[none.go + none_exec_unix.go](../internal/runtime/)）：子进程设为进程组长，ctx cancel 时先 `SIGTERM` 整组，1 秒后升级 `SIGKILL`，防止超时命令的孙子进程（ping/sleep/git）逃逸继续改 workspace。
- **`classifyExecError`**：精心区分「ctx 取消 / 正常非零退出 / 管道延迟(ErrWaitDelay) / 真错误」四种情况，让超时与正常失败可区分。
- **Codex 三层 transcript 解析**（[codex.go:440-506](../internal/agent/codex.go#L440)）：stdout NDJSON 流 → session JSONL 文件 → last-message 文件，按「更长且自洽才覆盖」的规则融合 + 兜底。
- **超长 prompt 双模式交付**（[prompt_delivery.go](../internal/agent/prompt_delivery.go)）：≤32KB 内联 `-p`，超出走「写文件 + stdin」，绕开 ARG_MAX 上限。
- **nvm/node 引导**（[node_install.go](../internal/agent/node_install.go)）：干净容器没 node，生成 bash 脚本下 nvm（带 SHA256 校验 + gitee 镜像回退）装 Node 22，三套镜像（nvm/node/npm registry）全可环境变量覆盖（照顾中国大陆网络）。

### B8. with/without Skill 基线 A/B ⭐⭐

[internal/report/benchmark.go](../internal/report/benchmark.go)：`benchmark.enabled=true` 时同一批 case 跑两遍（装/不装 Skill），算 `mean + stddev`（4 指标：pass_rate/time/tokens）+ delta。

**为什么重要**：把「这个 Skill 到底有没有用」从主观判断变成**可量化的 A/B 实验**。这是 Agent Skill 评测框架的核心价值主张。

### B9. OpenTelemetry 全链路追踪 ⭐⭐

[internal/observability/observability.go](../internal/observability/observability.go)：

- 每个 `run → evaluate_all → case → agent.run → judge` 都是 span，带 `skill_up.engine/model/case.id/status` 属性；
- **linked trace topology**：能把子 Agent（被调用的真实 Agent CLI）的 trace 挂成父子关系（通过 env 注入子进程的 OTEL 配置）；
- 支持 OTLP gRPC/HTTP，环境变量驱动，不配则不启用（零开销）。

**为什么重要**：可观测性是后端基本功。能讲清「分布式 trace 怎么把跨进程的调用链串起来」很加分。

### B10. Anthropic 生态兼容（技术选型判断）⭐

输出 `grading.json` / `benchmark.json` / `eval_metadata.json` 兼容 Anthropic skill-creator/eval-viewer 格式；`skill-up import` 能把 Anthropic `evals.json` 转成本项目 YAML。

**为什么重要**：体现了「自研产品 vs 主流生态」的选型判断 —— 借力既有生态（用户能直接用 Anthropic 的 viewer），而不是从头造轮子。

## C. 工程实践（代码质量信号）

| 实践 | 体现 |
|------|------|
| **注释解释「为什么」而非「是什么」** | 全代码库一致风格，关键决策处都有 rationale 注释 |
| **错误信息可定位** | timeout 错误标注「哪个配置项」导致；judge 失败保留 session |
| **外部依赖全可 mock** | `openSandboxClient` / `dockerCommandRunner` / `var createOpenSandbox` 都是注入 seam |
| **表驱动测试为主** | Go 社区惯例，`go test -race` 必跑 |
| **build tag 隔离 e2e** | `make test`(单测) vs `make e2e`(端到端) 分离 |
| **不可变配置** | MCP 合并返回 deep copy，调用方无法反向改原配置 |
| **CI 门禁** | `make verify` = fmt-check → vet → revive → golangci-lint，Conventional Commits 强制 |
