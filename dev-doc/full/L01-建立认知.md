> 面向：Java 后端 / 全栈工程师，把 skill-up 这个 Go 项目写进简历、在面试中讲清楚。

## 1. 学习目标

学完本课，你应该能：

1. **一句话定位**：能用一句话向同事（非本项目的人）说清 skill-up 是什么，且**不把层级说错**（不说成「拓展 agent 能力的平台」）。

4. **误解纠正**：能识别并纠正至少 3 个关于 skill-up 的常见误解（能力边界、模型来源、用例来源）。
5. **面试口径**：能背出 30 秒面试版定位，知道哪些词该说、哪些词是红线。

## 3. 讲解

### 3.1 一句话定位：skill-up 是 Agent Skill 的「考试系统」

**skill-up 是 Alibaba 开源的一个 CLI 框架（Go 1.25），干一件事：给 AI Agent 的 Skill 写测试。**

更准确的一句（面试口径）：

> **skill-up 是 Agent Skill 的评测与质量保障框架** —— 你声明 YAML 用例，框架把 Skill 装进真实的 Agent 引擎，跑 prompt、收输出、用规则/脚本/LLM 裁判打分，最后产出结构化报告。

#### 先搞清楚「Skill」是什么

Agent（Claude Code / Codex / Qoder CLI 这类编程助手）本身只会一堆通用本事。**Skill 是给 Agent 装的「App / 技能包」**，通常就是一个带 `SKILL.md` 的目录，让 Agent 学会一件它原本不会的事（比如「按某套规范生成 API 文档」「部署到某套内部 K8s」）。

> 类比（你熟的）：Skill 之于 Coding Agent ≈ **应用插件**之于 IDE、≈ **Skill 模块**之于一个机器人。
> 拓展 Agent 能力边界的，是 Skill 本身，不是 skill-up。这一句先记住。

#### 两个最好用的类比

**类比 A：skill-up 之于 Skill ≈ JUnit 之于 Java 代码**

| | JUnit | skill-up |
|---|---|---|
| 被测对象 | Java 类/方法 | Agent Skill |
| 用例写法 | `@Test` 注解 + 断言 | YAML 声明 + expect/judge |
| 执行 | JUnit 引擎跑 | skill-up 框架跑 |
| 产出 | 测试报告（红/绿） | result.json / benchmark.json |
| 让代码更强？ | ❌ 只告诉你「没坏」 | ❌ 只告诉你「没坏」 |

**类比 B：skill-up 是 Skill 的「自动化考试系统」**

你（出题人）写用例 → skill-up（考务）组考：**装 Skill 进 Agent、发题、收卷** → **判卷**（rule/script/LLM 裁判打分）→ **发榜**（报告）。这个比喻贯穿整个 [doc/07 核心流程讲解](../../doc/07-核心流程讲解.md)，L02 跑通时你会逐个体感到。

> 关键认知（红线）：**skill-up 不让你的 Skill「更强」，它只让你知道「这个 Skill 到底行不行」**。
> 就像 JUnit 不会让你的 Java 代码跑得更快，它只告诉你哪里挂了。

### 3.2 它解决什么痛点（为什么需要它）

#### 没有 skill-up 的世界（痛点）

假设你写了一个 Skill，让 Agent 会「按公司规范生成数据库迁移脚本」。怎么验证它好不好用？

过去的做法：**人肉试**。

- 打开 Claude Code，装上 Skill，手动敲几个 prompt，看看输出像不像样；
- 改了 Skill，再手动敲一遍；
- 换个模型 / 换个引擎（Codex），再手动敲一遍；
- 三个月后回归，还得记得当初敲了啥 prompt —— **记不清了，结果不可复现**。

**这正是 JUnit 出现之前，Java 代码的测试方式**：写个 `main()` 手动 `System.out.println` 看结果。后来有了 JUnit，测试变成「可声明、可复现、可回归、进 CI」的工程产物。

> 对 Java 背景的你，这个痛点应该秒懂：**Skill 的质量过去没有 JUnit**。
> 没有可度量、可复现、可回归的工程化手段，全靠人肉试 → 脆弱、没法 review、进不了 CI。

#### skill-up 把这件事产品化成一个 CLI

它把 Anthropic 官方 [Agent Skills evaluation guide](https://agentskills.io/skill-creation/evaluating-skills) 里描述的「正确但靠手动的评测循环」 —— 写真实用例、with/without Skill 跑两遍、判分、汇总、迭代 —— 做成了一个**可复用的命令行工具**：

- 声明式 YAML 取代临时脚本目录；
- 自动化：沙箱搭建、Skill 安装、Agent 调用、打分、报告全包；
- 多引擎：`claude_code` / `codex` / `qodercli` / `qwen_code` 一套用例跨引擎对比；
- CI 友好：退出码 `0/1` 直接驱动流水线。

一句话：**它把「测 Skill」从手工作坊变成工程流水线**。

### 3.3 三者关系：Skill / skill-up / skill-upper（最绕的点，慢慢看）

这是整个项目最容易搞混的地方：**`skill-up` 和 `skill-upper` 名字像、方向相反**。先把三者角色摆清，再用方向图讲谁调谁。

#### 三者各是谁（一张表）

| | 是谁 | 干啥 | 拓展 agent 能力？ |
|---|---|---|---|
| **Skill** | 给 Agent 用的**能力模块**（一个带 `SKILL.md` 的目录） | 让 Agent 学会新本事 | ✅ 是它拓展 |
| **skill-up** | Skill 的**考试系统 / 质检框架**（Go CLI） | 跑用例、打分、出报告 | ❌ 只验证，不增加 |
| **skill-upper** | 仓库里**附带的一个 Skill** | 让 Agent 自动写/修测试用例 | ✅（因为它是 Skill） |

注意第三行：**skill-upper 自己就是一个 Skill**（所以它拓展能力），它的特别之处是「让 Agent 帮你写 skill-up 的测试用例」。

#### 方向图：谁调用谁（箭头别看反 ⚠️）

**关系① — skill-up（司机 → 车）**

```
   skill-up  ────启动/调用(当子进程)────▶  Claude Code / Codex
  (独立 Go 程序)                           (被测对象 / 工具)
        ▲                                     │
        └────────返回输出 / transcript─────────┘
   ★ skill-up 是主，它把 cc 当工具跑（不是被 cc 装进去）
```

**关系② — skill-upper（宿主 → 插件）**

```
   Claude Code / Codex  ────装载────▶  skill-upper
   (宿主)                              (一个 Skill / 车载 App)
                                          ▲
                          借用 cc 的模型能力，生成/迭代测试用例
   ★ cc 是主，skill-upper 是它的插件（被 cc 装进去）
```

> **一句话记忆**：**skill-up 是「司机」，cc/codex 是它开的「车」，skill-upper 是「车载 App」。**
> 司机不是被车装的，是司机在开车 —— 所以 skill-up 和 cc 的关系不是「没有」，而是「skill-up 在驱动 cc」。

#### 「哪件事归谁」表（这张表能解决 90% 的混淆）

| 你想干的 | 归谁 | 怎么干 |
|---|---|---|
| 生成测试用例 | **skill-upper**（关系②） | 在 cc 里、用 cc 的模型读 `SKILL.md` 写 YAML |
| 跑测评流程 | **skill-up**（关系①） | 自己的 Go 代码编排，**启动 cc 当被测对象** |
| 打分（rule/script） | **skill-up** 自己 | 纯代码，不需要模型 |
| 打分（agent_judge） | **skill-up** 起裁判 agent | 这一步才调模型 |

> Java 类比帮你固化：
> - **skill-up ≈ JUnit 引擎 + CI runner**（独立程序，驱动被测代码）；
> - **Skill ≈ 被测的 Java 业务代码**（被跑的对象）；
> - **skill-upper ≈ 一个帮你生成测试用例的 IDE 插件**（嵌在 IDE 里，借用 IDE 的能力干活）。

### 3.4 声明式哲学：声明「要什么」 vs 命令式「怎么做」

面试高频概念题：「skill-up 为什么是声明式框架？」这一节给你能讲清楚的答案。

#### 什么是声明式

> **声明式（declarative）= 你描述「要什么」（测什么、期望什么），框架负责「怎么跑」。配置是数据，执行逻辑固化在框架里。**

对照命令式（imperative）：你得一步步写「怎么做」。

#### 没有 skill-up，你得怎么干（命令式 / imperative）

```go
// 命令式：你得自己一步步写"怎么做"
box := createDocker("node:22")
box.run("npm install -g @anthropic-ai/claude-code")
box.copyIn("./my-skill", "~/.claude/skills/my-skill")
out := box.run("claude -p '生成 hello world 程序'")
if !strings.Contains(out, "Hello") { fail() }
// 还要自己写：并发、重试、超时、解析输出、出报告...
```

每次测试你都在重写这套「怎么做」的过程脚本 —— **脆弱、不可复现、没法 review**。
这就像 Java 里不写 JUnit，而是每个类都手写一个 `public static void main()` 去手动 `assert`，每个项目都重新发明一遍测试轮子。

#### 有了 skill-up（声明式）：你只写「要什么」

```yaml
# eval.yaml —— 声明环境 / 引擎 / 用例清单
schema_version: v1alpha1
environment: { type: none }
engine: { name: claude_code }
cases: { files: [evals/cases/hello.yaml] }

# cases/hello.yaml —— 声明输入和期望
input: { prompt: "生成 hello world 程序" }
expect: { must_contain: ["Hello"] }
```

然后 `skill-up run` —— **建沙箱、装 Agent、装 Skill、发 prompt、收输出、打分、出报告**这套「怎么做」全是框架内部固化的 Go 代码，你一行都不用写。

#### 「你声明」 vs 「框架执行」（声明式的本质）

| 你声明（YAML 数据） | 框架执行（代码，你不用管） |
|---|---|
| 测哪些用例、发什么 prompt | 怎么并发调度、重试、超时 |
| 期望输出（must_contain / 文件 / golden） | 怎么检查、短路、打分 |
| 用哪个引擎 / 模型 | 怎么装 Agent、启动子进程、解析输出 |
| 用哪种评分（rule / script / judge） | 怎么路由到对应打分器 |
| 要不要 A/B 对比 | 怎么跑两遍、算 delta |
| 要什么报告格式 | 怎么生成 json / html / junit |

> **左边是数据（声明），右边是逻辑（固化在框架）。** 这就是声明式的本质 —— 把「意图」和「执行」分开，意图变成可序列化的数据。

#### Java / 业界类比（你熟的）

skill-up 之于「测 Skill」 = 这些框架之于它们的领域：

| 框架 | 你声明 | 框架执行 |
|---|---|---|
| **Spring** | `@Configuration` / `application.yml` | 实例化、注入、代理、生命周期 |
| **SQL** | `SELECT ...` 要什么数据 | 优化器怎么查 |
| **Kubernetes** | YAML 描述期望状态 | 调谐到期望状态 |
| **Terraform** | HCL 描述基础设施 | 创建/更新资源 |
| **JUnit** | `@Test` + 断言描述期望 | 生命周期、执行、报告 |
| **skill-up** | YAML 描述评测用例 | 沙箱→执行→打分→报告 |

共同点：**你从不手写「怎么做」，只声明「要什么」。** 如果你写过 Spring 的 `application.yml` 或 K8s 的 Deployment YAML，skill-up 的 YAML 你会觉得很亲切。

#### 它不是「纯」声明式 —— 有命令式逃生舱

成熟框架的标志：**默认声明式，需要时能逃回命令式**。skill-up 有三处逃生舱：

| 逃生舱 | 什么时候用 |
|---|---|
| `judge: script` | 规则不够用？写个脚本（命令式）做复杂判定 |
| `environment.setup_steps` | 环境要特殊初始化？写命令式命令 |
| `engine.custom` | 要接私有 Agent？写模板 / HTTP 调用（命令式） |

> 类比：**Kubernetes 是声明式的，但有 init container 当逃生舱；Terraform 声明式，也有 provisioner。**
> skill-up 同款思路 —— **声明式是骨架，命令式是关节**，关键路径声明式，边缘场景留口子。

#### 声明式带来的最大红利：可工具化

这一点最容易被忽略，但却是 skill-upper 能存在的前提：

因为用例是**结构化数据**（YAML），而不是临时脚本，工具才能：
- **生成**它 —— skill-upper 读 `SKILL.md`，自动写 YAML 用例；
- **校验**它 —— `skill-up validate` 检查 schema 合法性；
- **转换**它 —— `skill-up import` 把 Anthropic 的 `evals.json` 转成本仓库的 YAML；
- **聚合**它 —— 报告系统汇总成 benchmark。

> **命令式脚本做不到这些** —— 这就是声明式带来的生态红利。
> 一句话：**正因为它声明式，skill-upper 才能存在；skill-upper 又反过来让声明式用例更好写。** 这是一个正向飞轮。

### 3.5 常见误解纠正（面试红线区）

这五个误解，面试官最爱用它们试你层级清不清楚。逐条对照。

#### 误解 ①：「skill-up 拓展 Agent 的能力边界」

❌ 错。**拓展能力的是 Skill 本身，skill-up 是质检层，只验证不增加。**

正确口径：「Agent Skill 的评测与质量保障框架」。别说成「拓展 agent 能力的平台」—— 差一个层级。
类比：JUnit 不让你的代码更强，只让你知道它没坏。

#### 误解 ②：「skill-up 是 Claude Code 的插件 / 被 cc 装进去」

❌ 方向反了。**skill-up 是司机，cc 是车** —— 是 skill-up 启动 cc 当子进程（关系①），不是 cc 装 skill-up。
被 cc 装进去的是 **skill-upper**（关系②），那是另一个东西。

> 这是面试里最致命的口误，一旦说反，基本判定你没搞懂架构。

#### 误解 ③：「skill-up 自己提供 AI 模型」

❌ 错。**skill-up 本身不提供模型**。
- 打分如果是 `rule_based` / `script`，**纯代码，一个模型都不调**；
- 只有 `agent_judge`（LLM 裁判）和「Agent 引擎跑 Skill」这两步才需要模型；
- 模型来自**你提供的 API Key**（按优先级解析：`flag` > `env` > `credentials.yaml`），引擎是 `claude_code` / `codex` / `qodercli` / `qwen_code` 任你选。

> 类比：JUnit 不提供「被测代码」，被测代码是你写的；skill-up 不提供模型，模型是你接的。

#### 误解 ④：「测试用例必须手写 YAML，门槛高」

❌ 半错。**用例必须存在**（声明式框架的输入是数据，没数据没法跑），**但不必须手写**。
- 你可以手写（传统方式）；
- 也可以让 **skill-upper 在 cc 里帮你生成**（推荐方式，关系②的用武之地）；
- 还可以 `skill-up import` 从 Anthropic 的 `evals.json` 导入。

> 一句话：**用例是「必须有的数据」，不是「必须手写的代码」**。这是声明式 + skill-upper 飞轮带来的好处。

#### 误解 ⑤（bonus）：「skill-up 和 skill-upper 是同一个东西的两个名字」

❌ 错。它俩是**方向相反**的两个存在（见 3.3）：
- `skill-up`：Go CLI 程序，独立运行，**驱动** cc（司机）；
- `skill-upper`：一个 Skill，**被** cc 装载（车载 App），帮 cc 写用例。

记住「司机/车/车载 App」就不会混。

## 5. 检查点自测（附答案要点）

先自己答，再对答案要点。答对 4 题以上算本课过关。

**Q1. skill-up 和 skill-upper 啥区别？谁嵌入谁？**

<details>
<summary>答案要点</summary>

- skill-up 是 Go CLI 框架（Skill 的考试系统），**独立运行**；skill-upper 是仓库附带的一个 **Skill**。
- 方向相反：skill-up **启动** cc 当子进程（司机→车）；cc **装载** skill-upper 当插件（宿主→插件）。
- 「嵌入」要分清：cc 嵌入的是 **skill-upper**，不是 skill-up。skill-up 是嵌入 cc 的「驱动者」。
- 一句话：司机（skill-up）/ 车（cc）/ 车载 App（skill-upper）。

</details>

**Q2. 为什么说 skill-up 是声明式框架？**

<details>
<summary>答案要点</summary>

- 声明式 = 描述「要什么」，框架负责「怎么跑」；配置是数据，逻辑固化在框架。
- 用户写 YAML 声明：测哪些用例、发什么 prompt、期望什么、用哪个引擎/评分。
- 框架内部 Go 代码负责：沙箱、安装、并发、重试、超时、打分、报告。
- 好处：可复现、可版本化、零代码门槛、**可工具化**（skill-upper 生成 / validate 校验 / import 转换）。
- 有三处命令式逃生舱：`judge: script` / `setup_steps` / `engine.custom` —— 声明式是骨架，命令式是关节。

</details>

**Q3. skill-up 和 Coding Agent（如 Claude Code）是什么关系？**

<details>
<summary>答案要点</summary>

- **skill-up 驱动 cc，不是被 cc 装载**。
- skill-up 把 cc 当作「被测对象 / 工具」，启动它当子进程、发 prompt、收 transcript。
- cc 是 skill-up 支持的多个引擎之一（`claude_code` / `codex` / `qodercli` / `qwen_code`）。
- 关键：skill-up 不拓展 cc 的能力，只验证装进 cc 的 Skill 行不行。

</details>

**Q4. skill-up 会拓展 Agent 的能力吗？它提供模型吗？**

<details>
<summary>答案要点</summary>

- **不拓展能力**。拓展能力的是 Skill 本身，skill-up 是下游质检层（≈ JUnit 之于代码）。
- **不提供模型**。`rule_based` / `script` 打分纯代码不调模型；只有 `agent_judge` 和「Agent 跑 Skill」才需要模型，且模型来自你提供的 API Key。
- 红线口径：别说「拓展 agent 能力的平台」，要说「Agent Skill 的评测与质量保障框架」。

</details>

**Q5. 没有 skill-up，你要怎么验证一个 Skill？这为什么是痛点？**

<details>
<summary>答案要点</summary>

- 过去靠**人肉试**：手动开 cc、装 Skill、敲 prompt、肉眼看输出；换引擎/换模型再敲一遍。
- 痛点：不可复现（记不清当初敲了啥）、不可度量（没客观分数）、不可回归、没法进 CI、没法 review。
- 类比：就像 JUnit 出现之前，Java 代码靠 `main()` 里手动 `println` 测试。
- skill-up 把这件事产品化成声明式 CLI：可复现、可版本化、CI 友好、跨引擎对比。

</details>

## 7. 小结 + 下一课预告

### 本课你必须带走的三句话

1. **skill-up 是 Agent Skill 的评测与质量保障框架**（≈ JUnit 之于 Java 代码、≈ 考试系统之于考生）—— 它**不拓展能力，只验证能力**。
2. **三者方向别搞反**：skill-up（司机，独立 CLI）**驱动** cc（车）；cc **装载** skill-upper（车载 App，一个 Skill）。
3. **声明式 = 写「要什么」（YAML 数据），框架负责「怎么跑」（固化逻辑）**；声明式带来的最大红利是**可工具化**，这也是 skill-upper 能存在的前提。

### 30 秒面试口径（背下来）

> 「skill-up 是 Agent Skill 的评测与质量保障框架，用 Go 写的声明式 CLI。用户用 YAML 声明『测什么、期望什么、用哪个引擎和评分方式』，框架负责沙箱、安装、执行、打分、报告全流程。它和 Claude Code 的关系是 **skill-up 驱动 cc**（把 cc 当被测对象），不是被 cc 装载。它不拓展 Agent 能力 —— 拓展能力的是 Skill 本身，skill-up 是下游质检层，类似 JUnit 之于 Java 代码。」

### 下一课预告：L02 · 动手跑通（从安装到第一份报告）

L01 你建好了心智模型，L02 我们让它「落地」：

- 安装 skill-up（或用 skill-upper 引导安装）；
- 看懂最小的 `eval.yaml` + 一个 case YAML；
- 跑一次 `skill-up run`，拿到第一份 `result.json` / `benchmark.json`；
- 对照本课的「考试系统」比喻，体感一遍：出题 → 组考 → 判卷 → 发榜。

> L02 之后，本课这些概念就不再是抽象话术，而是你能指着报告文件说「这就是发榜」的实在东西。
