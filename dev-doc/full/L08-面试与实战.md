## 一、学习目标

学完本课，你能：

1. **写出**三档（一行/STAR/详细）可直接贴进简历的 skill-up 项目描述，并知道哪档用在哪。
2. **答出** 10 道高频面试题的要点（架构 / 多引擎抽象 / judge 选型 / LLM 抗噪 / 并发超时 / 安全 / 可复现 / A-B / 声明式 / Java↔Go），并背得出一段 30 秒电梯演讲。
3. **完成**一个从 0 设计的 Capstone：自己写一个小 Skill + 完整评测套件（用例覆盖 rule_based/script/agent_judge + with/without A/B benchmark）。
4. **通过**毕业检查点：30 秒讲清项目、5 分钟画出架构图、独立写一个 eval 套件。
5. **诚实定位**项目身份（开源学习者/二次开发者，不是从零作者），不夸大、不翻车。

#### 技术栈「通俗讲解」速查（看着名词发懵时用）

> 被问「XX 是什么」时，用大白话 + Java 类比答。完整表见 [doc/05 第七节](../../doc/05-技术栈.md)。挑你简历上写到的几条背熟。

| 术语 | 大白话 | Java 类比 |
|---|---|---|
| **goroutine + channel** | 超轻量线程 + 线程安全队列 | 协程≈更轻的线程；channel≈`BlockingQueue` |
| **sync.WaitGroup** | 等一批任务全干完的计数器 | `CountDownLatch` |
| **context** | 贯穿调用链的「超时+取消」控制器 | `Future.cancel()` + `Thread.interrupt()` 统一版 |
| **OpenTelemetry** | 分布式追踪标准，画调用链 | **SkyWalking / Zipkin / Sleuth** |
| **Cobra / pflag** | Go 的 CLI 框架 | `Picocli` / `Spring Shell` |
| **LLM-as-a-Judge** | 让一个 LLM 给另一个 LLM 的输出打分 | 无（AI 专属） |
| **MCP** | 大模型调外部工具的开放协议 | OpenAPI 之于 HTTP |
| **策略/工厂/模板方法/适配器** | 你 Java 里那套设计模式 | 同 |

> ⚠️ **铁律**：简历上任何一条技术栈，**你必须能讲满 30 秒**。讲不出来的，降级到「了解」或删掉。面试官专盯「精通」问。

### A4. 高频面试 Q&A（10 题，每题给答案要点）

> 完整版（含延伸与追问）见 [doc/04 第三节](../../doc/04-简历素材与面试问答.md)。这里给**每题的核心答题骨架**，方便考前 30 分钟扫一遍。

#### Q1 · 架构 / 你负责的部分怎么设计的？
**要点（3 步递进）**：
1. **先分层**：CLI → Runner → Evaluator → （Agent / Judge / Runtime / Report）。
2. **再讲三条数据契约**：`Agent` 接口、`judge.Input`、`Transcript` —— 它们把异构子系统解耦。
3. **落到一个亮点**：Agent 四层适配（BaseAgent→CLIAgent→具体引擎→Custom）或 Judge 统一边界。
> 关键词：分层、接口隔离、策略模式、数据边界。

#### Q2 · 为什么抽象 Agent 接口？直接调 Claude Code 不行吗？
**要点**：因为要**跨引擎可比**。同一个 Skill 要在 Claude Code / Codex / Qoder CLI 上都跑，证明不依赖单一引擎。每个引擎的安装、命令、输出格式、session 机制都不同，不抽象就每加一个引擎改一堆 if-else。抽象后 evaluator 只面向接口编程，新引擎只加一个适配器 + 工厂 case。
> 一句话：开闭原则 + 依赖倒置的落地。

#### Q3 · rule_based / script / agent_judge 怎么选？
**要点（按「确定性 + 成本」分层）**：
- 能用确定规则判（关键字/文件存在/退出码）→ `rule_based`，零成本、CI 友好、可复现。
- 需要复杂逻辑（跑测试套件、解析结构化输出）→ `script`，退出码即结论，语言任选。
- 开放式语义评测（代码质量、bug 定位准确性）才用 `agent_judge`，贵且非确定。
- 还有 `expect` 预检查做**第一层短路**：能零成本判的直接 FAIL，连 rule_based 都不跑。
> 体现「成本意识」—— 不是无脑调大模型。

#### Q4 · 用 LLM 当裁判，怎么保证打分靠谱？（高频追问 ⭐）
**要点（分四点）**：
1. **prompt 工程**：强制 JSON 输出、强制 evidence、给响应模板骨架。
2. **输出鲁棒解析**：LLM 返回的 JSON 经常不规整，做了四层兜底（直接解析 → 提取 ```json 围栏 → 大括号配对状态机 → 引号修复）。故意不用正则，因为嵌套+转义让正则很脆弱。
3. **防作弊校验**：结果数必须 == criteria 数（防少返回几条导致通过率虚高），每条 evidence 必填。
4. **阈值制**：pass_rate ≥ pass_threshold（默认 0.7）才 PASS，容忍单条判定波动。
> 这条最能体现「跟大模型真实打交道的工程经验」。

#### Q5 · 怎么做并发？怎么控制超时和重试？
**要点**：
- **并发**：带缓冲 channel 当信号量 + WaitGroup，受 `cases.parallelism`（1–256）控制，每个 case 一个 goroutine。
- **超时**：case 级 `context.WithTimeout`，是 agent + judge 的**总预算**；超时被识别成 `timeout` 重试理由，错误里标注是哪个配置项导致。
- **重试**：`retry_policy.retry_on ∈ {timeout, error}`，指数退避 `2^n` 秒。
- **进程清理**：none runtime 用进程组，ctx cancel 先 SIGTERM 整组、1s 后 SIGKILL，防孙子进程逃逸。

#### Q6 · 安全上做了什么？
**要点（Custom Engine 是重点，因为它是不可信的）**：
- 路径穿越 + 符号链接 TOCTOU 防御（每次 use 前重新 `EvalSymlinks`）；
- 凭据脱敏（`maskAPIKey` 对所有不可信字段全替换）；
- 凭据不能进命令行/URL（会出现在 `ps`/trace）；
- artifact 下载不跟随 3xx 重定向（防 SSRF）；
- 配置侧识别敏感变量名 + 真实凭证形状（sk-ant-/ghp_/AKIA…），严格模式拒绝凭证进命令行。

#### Q7 · 怎么保证评测可复现？
**要点**：
- 声明式 YAML（环境/引擎/模型/用例/判官全声明）；
- 每个 iteration 产物落盘（result.json / grading.json / benchmark.json + outputs/）；
- agent_judge 物化上下文到磁盘 + manifest.json 记录交付决策；
- iteration-N 目录自动续号，历史可追溯；
- OTel trace 串起全链路，带 case.id/engine/model/status 属性。

#### Q8 · with/without Skill 基线对比是干嘛的？
**要点**：Agent Skill 的核心问题是「这个 Skill 到底有没有用」。`benchmark.enabled=true` 时同一批 case 跑两遍（装/不装），算通过率/token/耗时的 mean+stddev 和 delta。delta 直接量化 Skill 的增量价值 = **Skill 版的 A/B 实验**，把主观判断变成可量化指标。

#### Q9 · 为什么用声明式（YAML）而不是写代码？（概念题）
**要点**：
- 评测场景**高度模板化**（每个 case 都是「输入 → 期望 → 判官」），YAML 把重复结构固化成 schema，用户只填变量。
- 声明式带来**可复现**（配置即规格）、**可对比**（同一配置跨引擎跑）、**可入 CI**（退出码驱动）。
- 分层校验器在加载时就把错误挡住（文档级/类型枚举/runtime 特化/case 级/去重），相当于 `@Valid` 的强化版。
> 类比：JUnit 用注解声明测试，skill-up 用 YAML 声明评测 —— 都是「声明做什么，框架决定怎么做」。

#### Q10 ·（Java 选手高频）Go 和 Java 写这种项目的区别 / 你怎么上手的？
**要点（五点对比）**：
- Go 没有 Spring 那套，依赖注入靠「构造器 + 接口」，更轻；
- 没有继承，用「组合 + 接口」（项目里 BaseAgent→CLIAgent 就是 embedding + 接口）；
- 错误处理是 `if err != nil` 而非 try-catch，但项目用了 error chain（`errors.Is/As`）做类型化错误；
- 并发用 goroutine + channel，比 Java 线程池轻量（信号量 + WaitGroup 是惯用法）；
- context 贯穿全链路做超时/取消传递（比 InterruptedException 模型更系统）。
> 这题答得好，能直接消除面试官对「Java 转 Go」的顾虑。

### A5. 30 秒电梯演讲版（背这段 ⭐）

> 「skill-up 是 Alibaba 开源的 Agent Skill 评测框架，相当于 **Skill 版的 JUnit**。核心流程：读声明式 YAML 配置 → 工厂创建 Agent 适配器 → **并发跑每个用例**（带重试/超时）→ 单个用例内部：**建隔离沙箱 → 把 Skill 装进 Agent → 跑 prompt 收输出 → expect 预检查短路 → 再用 rule/script/LLM 裁判打分** → 最后汇总成 result.json / benchmark.json 报告，退出码驱动 CI。设计上用统一的 `judge.Input` 数据边界把**执行层和评测层解耦**，这也是它能在多引擎上做到跨引擎可比的关键。」

**怎么用**：
- 面试官问「介绍一下这个项目」→ 直接背这段。
- 招呼阶段破冰 → 砍掉中间细节，只留首尾两句。
- 背的时候**重点强调加粗词**，节奏感比内容更重要。

| 问题 | 参考回答思路 |

| 「TOCTOU 防御具体怎么做？」 | `workspacePath` 每次 use 前重新 `EvalSymlinks`，关闭「运行中种外指链接」窗口。详见 [dev-doc/deep/08](../deep/08-安全-CustomEngine不可信输入.md)。 |
| 「agent_judge 的 prompt 体积怎么控？」 | profile（minimal/standard）批量预设 + mode（include/truncate/omit/file_ref）单条覆盖，超 64KB 自动降级 file_ref，manifest.json 记录决策。详见 [dev-doc/deep/02](../deep/02-Judge三策略.md)。 |
| 「进程组怎么优雅终止？」 | 子进程设为进程组长，ctx cancel 先 SIGTERM 整组、1s 后 SIGKILL，防孙子进程逃逸。详见 [dev-doc/deep/04](../deep/04-并发重试超时.md)。 |
| 「如果要加一个新引擎，你要改哪几处？」 | 加一个具体 Agent 适配器（实现 Agent 接口）+ 工厂加一个 case + 别名归一化（如需）。** evaluator/Judge/Runtime 全无感** —— 这就是抽象的价值。 |

> 🎯 **模拟面试后**：录音回放，标出「卡壳/含糊/超时」的点，回去翻 `/dev-doc/deep/` 对应模块补课。**至少模拟 2 轮**再上真面。

## 四、讲解 B：Capstone 实战项目

> 这是毕业硬性交付。**不做的，等于没学完**。
> 时间预估：**4~8 小时**（含跑通 + 调试 + 写文档）。

### B0. 目标与交付物

**目标**：从 0 设计一个小 Skill + 完整评测套件，证明你**真的会用 skill-up**（而不只是读懂了）。

**交付物清单**（提交到自己的 Git 仓库）：

├── evals/
│   ├── eval.yaml                    ← Step 3+4
│   └── cases/

- ✅ `benchmark.enabled: true`（with/without A/B 对比）

### B1. 步骤 1 · 选题

**建议 A（推荐，对 Java 工程师最贴）**：**Conventional Commit 规范检查 Skill**
> 一个检查 git commit message 是否符合 `type(scope): subject` 规范的 Skill。理由：① 你天天写 commit，业务懂；② 规则清晰（正例反例好造）；③ 能覆盖三种 judge。

**建议 B**：**代码格式检查 Skill**（检查 Go/Java 文件命名、import 顺序、TODO 残留等）

**建议 C**：**自己工作里真实需要的一个小 Skill**（最推荐 —— 真实需求做出来能直接用，面试讲得也最自然）

> 选好后，把选题写一句话发给自己：「我要做一个 ___ Skill，它帮用户 ___」。说不清楚就别动手。

---

### B2. 步骤 2 · 写 SKILL.md

以「Conventional Commit 检查」为例，最小可用版本：

```markdown
---
name: commit-lint
description: Checks whether a git commit message follows Conventional Commits format
  (type(scope): subject). Use whenever the user asks to validate, lint, or review
  a commit message before committing.
version: 1.0.0
---

# Commit Lint Skill

Checks git commit messages against Conventional Commits.

## Rule
A valid commit message MUST:
1. Start with a type: feat | fix | docs | style | refactor | perf | test | chore | build | ci
2. Optionally a scope in parentheses: `feat(api):`
3. A colon and space, then a subject
4. Subject in lowercase imperative, ≤ 72 chars, no trailing period

## Format
```
type(scope): subject

optional body
```

## Examples
- ✅ `feat(auth): add OAuth2 login`
- ✅ `fix: handle nil pointer in parser`
- ❌ `update` (no type)
- ❌ `Fixed the bug.` (capital + period)

## Process
1. Read the commit message from the user (or `git log -1`)
2. Validate against the rule above
3. If invalid, explain which rule broke and suggest a fix
4. Output: `PASS` / `FAIL: <reason>` on the first line
```

> 完整范例参考 [examples/code-stats/SKILL.md](../../examples/code-stats/SKILL.md)。注意 frontmatter 的 `description` 要写全触发词，这是 Agent 决定何时调起 Skill 的依据。

---

### B3. 步骤 3 · 设计 5~8 个 eval case（正例 / 反例 / 边界）

核心原则：**正例、反例、边界各占约 1/3**。下面给 commit-lint 的 8 个用例骨架（每个都配 `expect` 预检查）：

| # | 用例 id | 类型 | 输入（prompt） | 期望（expect 预检查） |
|---|---|---|---|---|
| 1 | `valid-feat-scope` | 正例 | 「检查这条 commit：`feat(auth): add OAuth2 login`」 | must_contain `PASS` |
| 2 | `valid-fix-no-scope` | 正例 | 「`fix: handle nil pointer`」 | must_contain `PASS` |
| 3 | `invalid-no-type` | 反例 | 「`update readme`」 | must_contain `FAIL` |
| 4 | `invalid-trailing-period` | 反例 | 「`fix: handle nil pointer.`」 | must_contain `FAIL` |
| 5 | `edge-merge-commit` | 边界 | 「`Merge branch 'main'`」（合并提交豁免） | must_contain `PASS` 或 `SKIP` |
| 6 | `edge-long-subject` | 边界 | subject > 72 字符 | must_contain `FAIL` |
| 7 | `edge-chinese-subject` | 边界 | 「`docs: 修复 README 拼写`」（中文 subject） | 视你的规则定 PASS/FAIL |
| 8 | `invalid-capital` | 反例 | 「`Feat: add login`」（type 大写） | must_contain `FAIL` |

**单个 case 的 YAML 写法**（以 case 1 为例）：

```yaml
id: valid-feat-scope
title: Valid feat commit with scope passes

input:
  prompt: |
    Check this commit message against Conventional Commits:
    "feat(auth): add OAuth2 login"
    Reply with PASS or FAIL on the first line, then explain.

expect:
  must_contain:
    - "PASS"
  must_not_contain:
    - "FAIL"

judge:
  type: rule_based
  success:
    - output_contains: { all: ["PASS"] }
  failure:
    - output_contains: { any: ["FAIL"] }
```

> 用例 id 默认 = 文件名（去掉 .yaml）。`expect` 是零成本预检查，先于 judge 跑。详见 [doc/06 第 6 节](../../doc/06-快速上手.md)。

---

### B4. 步骤 4 · 配三种 judge（关键练习）

**① rule_based**（最便宜，case 1/2 用）：见上例。适合「输出里有/没某关键字」的判定。

**② script**（case 3/4/6 用，跑结构化判定）：

```yaml
judge:
  type: script
  script_path: evals/fixtures/scripts/check-commit.sh
  timeout_seconds: 30
```

脚本通过环境变量拿数据（`EVAL_FINAL_MESSAGE` / `EVAL_TRANSCRIPT_PATH` / `EVAL_EXIT_CODE`），退出码 0=PASS。范例见 [examples/code-stats 的 check-stats.sh](../../examples/code-stats/evals/fixtures/scripts/check-stats.sh)。

```bash
#!/bin/bash
# check-commit.sh
FINAL_MESSAGE="${EVAL_FINAL_MESSAGE:-}"
echo "$FINAL_MESSAGE" | grep -qE '^(PASS|FAIL)' || { echo "FAIL: no verdict"; exit 1; }
echo "$FINAL_MESSAGE" | grep -qi '^PASS' && { echo "PASS"; exit 0; }
exit 1
```

**③ agent_judge**（case 7 中文语义题用，最贵）：

```yaml
judge:
  type: agent_judge
  model: qwen3-plus           # 或你有的模型
  criteria:
    - "correctly identified whether the commit message is valid"
    - "explained the specific rule that passed or failed"
    - "suggested a fix when invalid"
  pass_threshold: 0.7
```

> 🪟 **Windows 注意**：`.sh` 脚本需 Git Bash（设 `SKILL_UP_Bash=D:\Git\bin\bash.exe`），或改用 `.ps1`。详见 [doc/06 第 9 节常见坑](../../doc/06-快速上手.md)。

---

### B5. 步骤 5 · 跑 benchmark（with/without Skill 对比）

`eval.yaml` 开启 benchmark：

```yaml
schema_version: v1alpha1

environment:
  type: none

engine:
  name: claude_code          # 或 qodercli / codex（你有哪个引擎的 key）
  model:
    name: sonnet             # 按实际填

cases:
  files:
    - evals/cases/valid-feat-scope.yaml
    - evals/cases/invalid-no-type.yaml
    # ... 其余用例
  defaults:
    timeout_seconds: 600
    max_turns: 5
  parallelism: 2
  retry_policy:
    max_retries: 2
    retry_on: [error]

benchmark:
  enabled: true              # ⭐ 关键：跑两遍（装/不装 Skill）

report:
  formats: [json, html]
```

跑：

```bash
skill-up validate            # 先全量校验
skill-up run                 # 正式跑（含 with/without 两轮）
```

**怎么读结果**：看 `benchmark.json` 里的 `delta` —— `pass_rate` 的 delta 为正，说明装了 Skill 后通过率提升，**这就是你 Skill 的增量价值**。如果 delta 接近 0 或为负，说明你的 Skill 没用或起了反作用，回去改 SKILL.md。

> 这一步跑通，你就在简历上有了**「我用 skill-up 给自己写的 Skill 做了 A/B 实验，证明它把通过率从 X% 提到 Y%」**的硬数据。

### B6. 步骤 6 · 用 skill-upper 迭代修复

如果跑出失败 case，别手动改，用仓库自带的 **skill-upper**（对话式闭环）：

```bash
# 装进你的 Agent（Codex / Claude Code）
npx skills add https://github.com/alibaba/skill-up/tree/main/skills/skill-upper -g -a claude-code -y
```

然后在 Agent 里说：

```
Use skill-upper to evaluate my commit-lint Skill. Read SKILL.md, run the
existing eval cases, and for each failure: diagnose whether it's a Skill
bug or a case bug, propose a fix, and re-run until green.
```

skill-upper 会替你跑「诊断 → 改 → 再跑」的闭环。详见 [doc/06 第 7 节](../../doc/06-快速上手.md)。

> 这一步的价值：你**体验了 skill-up 的完整生命周期**（写 Skill → 写用例 → 跑 → 诊断 → 迭代），这是面试讲「我怎么用这个框架」的真实素材。

### B7. Capstone 评估标准（rubric，自评用）

| 维度 | 满分 3 | 及格 2 | 不足 1 |
|---|---|---|---|
| **Skill 设计** | SKILL.md 清晰、规则明确、有正反例 | 基本可用，规则略模糊 | 无法判定输啥 |

| **Judge 覆盖** | 三种全配 + expect | 两种 + expect | 只有一种 |

| **README** | 含 Skill 说明 + 跑法 + 结论 | 有但简略 | 没有 |
| **迭代证据** | 用 skill-upper 修过并留痕 | 手动修过 | 没修 |

> **毕业线**：总分 ≥ 12/18，且 Judge 覆盖 ≥ 2 分、benchmark ≥ 2 分（这两项是硬指标）。

## 七、课程回顾（L01 → L08 一句话串起来）

| 课 | 一句话 |
|---|---|
| **L01 定位** | skill-up 是 Agent Skill 的「考试系统」—— 不增加能力，只验证能力（≈ JUnit 之于 Java 代码）。 |
| **L02 架构** | 分层 CLI→Runner→Evaluator→Agent/Judge/Runtime/Report，靠三条数据契约解耦。 |
| **L03 核心流程** | `run` 命令端到端：读配置 → 建 Agent → 并发跑 case → 7 小步（沙箱→装 Skill→Run→收产物→expect→Judge→出分）→ 报告。 |
| **L04 核心技术点** | 设计模式落地（策略/工厂/模板方法/适配器）+ 工程亮点（数据边界、短路省钱、LLM 容错、TOCTOU 防御）。 |
| **L05 子系统** | Judge 三策略 / Agent 四层适配 / Runtime 三后端 + Report A/B —— 三大子系统各自深入。 |
| **L06 快速上手** | 装好 → 写 eval.yaml + 一个 case → `validate` → `run` → 看 result.json（Windows 适配）。 |
| **L07 源码深挖** | `executeCaseOnce` 7 步逐行 + 声明式哲学 + 并发/安全/配置的源码级理解（`dev-doc/deep/` 8 篇）。 |
| **L08 面试与实战** | **把所学变成简历能讲的 + 手里能演示的**（面试 Q&A + Capstone）—— 你刚完成。 |

**一句话串起来**：从一个「考试系统」的定位出发 → 拆出分层架构 → 跑通端到端流程 → 提炼技术亮点 → 下钻三大子系统 → 自己动手跑 → 吃透源码 → 最后变成简历和作品。

恭喜，你毕业了。🎓

### 2. 贡献 upstream（真实开源经历 ⭐）
- 给 [alibaba/skill-up](https://github.com/alibaba/skill-up) 提 PR：补测试用例、修文档、加一个新引擎适配器、加一个 expect 断言类型。

### 3. 关注 MCP / Agent 生态（前瞻布局）
- **MCP（Model Context Protocol）**：大模型调外部工具的开放协议，是 Agent 生态的「USB 标准」。skill-up 已支持 mocked/real × stdio/http，理解它就理解了 Agent 工具链。
- **Agent Skill 工程化**：随着 Claude Code / Codex / Qoder 这类 Coding Agent 普及，「Skill 质量」会变成新工种（类似 SRE 之于 DevOps）。你现在学的评测框架，就是这块的基础设施。
- **LLM 评测方法论**：深入读 Anthropic 的 eval 设计文档（skill-up 兼容其格式），理解「LLM-as-a-Judge」的学术背景（论文：*Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena*）。

### 4. 转化到工作（落地价值）
- 把 Capstone 思路用到工作里：给团队的 AI 功能写评测用例；给内部 prompt 写 A/B 基线。
- 一旦你在公司里推动过一次「Agent Skill 评测」，简历就能写「主导搭建了内部 Agent 质量保障体系」—— 这是真东西。

### 5. 持续打磨简历
