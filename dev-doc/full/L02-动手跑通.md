# L02 · 动手跑通（安装 → 写 eval.yaml + case → validate → run → 看懂报告）

> 第 1 课我们看了「skill-up 是什么、为什么这么设计」。这一课不谈理论，**全程动手**：装好、写最小用例、跑通、读懂报告。
> 🪟 你在 Windows 上，全文用 🪟 标出 Windows 专属注意点，命令默认给 PowerShell / cmd 可直接复制的版本。

---

## 1. 学习目标

学完本课，你能独立做到：

1. 在 **Windows 原生**环境用源码构建出 `skill-up.exe`，并用 `--version` 验证。
2. 说清 `eval.yaml`（入口配置）和 `cases/*.yaml`（单个用例）**各自声明什么**，并能手写一个最小可跑的用例。
3. 走完 `validate` → `run` → 看报告的**完整闭环**，分清 PASS / FAIL / ERROR 三态和退出码 0 / 1。
4. 给自己的一个小 Skill 写 2 个 `rule_based` 用例并跑通。
5. 会用 `--format html` 看网页报告，遇到常见报错知道去哪查。

## 3. 讲解

### 3.1 🪟 先做选择：Windows 原生 还是 WSL2？

skill-up 在 Windows 上「能干的事」分两档。先用这张表决定今天用哪一档：

| 你想干的事 | Windows 原生（cmd / PowerShell） | WSL2（Linux 子系统） |
|---|:---:|:---:|
| 构建 / 单元测试（`go build`、`go test`） | ✅ | ✅ |
| `none` runtime（本机直接跑命令） | ✅（走 cmd.exe） | ✅ |
| `opensandbox` runtime（远程 Linux 沙箱） | ✅（远端是 Linux） | ✅ |
| `.ps1` / `.cmd` 脚本评分 | ✅ | — |
| `.sh` 脚本评分 | ✅（需 Git Bash） | ✅ |
| **跑真实 Agent**（Claude Code / Codex / Qoder CLI） | ⚠️ **受限**（Agent 靠 bash+node 引导，cmd.exe 跑不起来） | ✅ **推荐** |
| `validate` / `list-cases`（不启动 Agent） | ✅ | ✅ |

**一句话结论**（也是本课的策略）：

- 今天我们做的是 **构建 + validate + list-cases**（不启动 Agent），**Windows 原生完全够用**。
- 等你要真刀真枪「装 Agent → Agent 执行 → 打分」时（练习 2 / 练习 3 如果用真实引擎），切到 **WSL2** 最省心，省去路径 / 凭据 / bash 引导的折腾。

> 🪟 **Java 类比**：就像你写 Spring Boot 时，本地 IDE 跑单元测试没问题，但要跑集成测试（连真实 MySQL / Redis）时，很多人也喜欢丢进 Docker 或 WSL——道理一样：**隔离一个干净的 Linux 环境少踩坑**。

### 3.2 安装 skill-up

#### 🪟 方式 B（推荐给你）：Windows 本地从源码构建

你本机有 Go（项目要求 **Go 1.25+**，见 [`go.mod`](../../go.mod) 第 3 行 `go 1.25.0`）。在仓库根目录开 PowerShell：

```powershell
.\bin\skill-up.exe --version
```

能看到版本号就 OK。

> 🪟 如果提示 `go: command not found`：去 <https://go.dev/dl/> 装 1.25+，装完重开终端。
> 🪟 构建产物是 `bin\skill-up.exe`（带 `.exe`）。后面为了简洁，我统一写成 `skill-up`，你自己换成 `.\bin\skill-up.exe` 或把 `bin\` 加进 PATH。

#### 方式 A（备选 / 给 Mac/Linux 同事）：脚本装二进制


### 3.3 核心概念：两个文件，各司其职

要评测一个 Skill，你只需要写两类文件，它们都放在 Skill 目录下的 `evals/` 里：

```text
my-skill/
  SKILL.md              ← 你的 Skill 定义（Markdown + frontmatter）
  evals/                ← 评测根目录
    eval.yaml           ← 【入口配置】环境 / 引擎 / 用例清单 / 全局 judge
    cases/              ← 【用例目录】一个文件一个用例
      hello-world.yaml
    fixtures/           ← 可选：测试资源
      scripts/          ←   评分脚本（.sh / .ps1）
      repos/            ←   仓库模板（repo_fixture 用）
```

**它们分别声明什么？**（这道题后面自测会问，先记住）

| 文件 | 角色 | 声明什么 | Java 类比 |
|------|------|---------|----------|
| `eval.yaml` | **入口配置**（整个评测的 `application.yml`） | 运行环境（`environment.type`）、Agent 引擎（`engine.name`）、要跑哪些用例（`cases.files`）、全局 judge / 超时 / 并发 | Spring Boot 的 `application.yml` + JUnit 的 `@TestConfiguration` |
| `cases/*.yaml` | **单个用例**（一个 `@Test` 方法） | 发给 Agent 的 `input.prompt`、期望输出 `expect`（关键字断言）、可选 `judge`（脚本/LLM 评分） | 一个 `@Test` 方法 + `assertThat(...)` |

> 💡 **零配置自动装 Skill**：当 `evals/eval.yaml` 所在目录**往上能找到 `SKILL.md`** 时，skill-up 会**自动安装当前这个 Skill**，不用在 `eval.yaml` 里手写 `skills:` 路径。这是最省事的玩法。

### 3.4 Step-by-step：写最小用例 → 校验 → 跑 → 看输出

我们照着官方示例的「骨架」写一个 **hello-world** 最小用例。先看一眼现成示例长什么样，再自己造。

#### 3.4.1 先「抄作业」：看现成示例的结构

仓库里有一个完整可跑的示例 [`examples/code-stats/`](../../examples/code-stats/)，它的 `evals/` 结构如下：

```text
examples/code-stats/evals/
├── eval.yaml                       # 入口：environment=none, engine=qodercli, 3 个 case, 全局 script judge
├── evals.json                      # skill-creator 格式（另一套工具用，本课忽略）
├── cases/
│   ├── analyze-directory.yaml      # 用例 1：分析目录
│   ├── top-extensions.yaml         # 用例 2：找 top 扩展名
│   └── current-directory-format.yaml
└── fixtures/
    ├── scripts/check-stats.sh      # 评分脚本（退出码 0=PASS）
    └── repos/sample-project/       # 仓库模板（main.go / util.go / README.md）
```

它的 [`eval.yaml`](../../examples/code-stats/evals/eval.yaml) 关键字段：

```yaml
schema_version: v1alpha1
environment:
  type: none              # 本机直接跑，不要隔离容器
engine:
  name: qodercli          # 用 Qoder CLI 当 Agent 引擎
  model:
    name: auto
cases:
  files:                  # 用例清单（路径相对 eval.yaml）
    - evals/cases/analyze-directory.yaml
    - evals/cases/top-extensions.yaml
    - evals/cases/current-directory-format.yaml
  parallelism: 2          # 并发跑 2 个
judge:                    # 全局默认 judge（每个 case 也能单独覆盖）
  type: script
  script_path: evals/fixtures/scripts/check-stats.sh
```

一个用例（[`analyze-directory.yaml`](../../examples/code-stats/evals/cases/analyze-directory.yaml)）关键字段：

```yaml
id: analyze-directory
title: Analyze code stats for evals directory
input:
  prompt: |               # 发给 Agent 的 prompt
    Analyze the current directory using the code-stats requirements. ...
context:
  repo_fixture: evals/fixtures/repos/sample-project   # 仓库模板
expect:                   # 零成本预检查（不用写 judge 也有）
  must_contain: ["Files by Extension", "Total Files", "Total Lines"]
  must_not_contain: ["error", "Error"]
judge:                    # 覆盖全局 judge
  type: script
  script_path: evals/fixtures/scripts/check-stats.sh
```

> 注意路径规则：`cases.files` 里的项**相对 `eval.yaml`**；而 `repo_fixture` / `script_path` 这类 fixture 引用**相对 `SKILL.md` 所在目录**（所以写成 `evals/fixtures/...`）。这是新手的第一个坑，先记住。

#### 3.4.2 自己动手：最小 eval.yaml + hello-world case

新建一个练习目录 `my-skill/`（随便放哪都行），结构如下：

```text
my-skill/
  SKILL.md              ← 先建一个最小的
  evals/
    eval.yaml
    cases/
      hello-world.yaml
```

**`SKILL.md`**（最小占位，让 skill-up 能自动发现并装这个 Skill）：

```markdown
---
name: my-skill
description: 一个练手用的最小 Skill
---

# my-skill

收到请求时，生成一个 Hello World 程序。
```

**`evals/eval.yaml`**（入口配置）：

```yaml
schema_version: v1alpha1

environment:
  type: none                 # 不需要隔离容器，直接本机跑

engine:
  name: claude_code          # 用 Claude Code 当 Agent 引擎（需配 ANTHROPIC_API_KEY）

cases:
  files:
    - evals/cases/hello-world.yaml
```

> 💡 没写的字段走默认：JSON 报告、超时 300s、`max_turns` 10、并发 1。

**`evals/cases/hello-world.yaml`**（用例）：

```yaml
input:
  prompt: |
    Please generate a Hello World program

expect:
  must_contain:
    - "Hello"
    - "World"
  must_not_contain:
    - "error"
```

> 💡 用例 `id` 默认 = 文件名（`hello-world`）。`expect` 是**零成本预检查**：输出里必须有 Hello/World、不能有 error——这种简单断言不用写 judge。

#### 3.4.3 校验：`validate`（不启动 Agent）

```powershell
# 在 my-skill 目录下
skill-up validate
```

成功输出：

```text
✓ eval.yaml is valid (loaded 1 case(s))
```

> **`validate` 检查什么**：`eval.yaml` 和**每一个**引用到的 case 文件都能解析、必填字段齐全、取值在允许范围内。它检查**全量**用例，不受 `--include-case-name` 过滤影响。这一步**不需要凭据**，因为它不启动 Agent——所以本课练习 1 在 Windows 原生就能跑。

#### 3.4.4 列用例：`list-cases`（也不启动 Agent）

```powershell
skill-up list-cases
```

输出（4 列：`ID / Title / Tag / Prompt`）：

```text
ID                    Title                           Tag              Prompt
hello-world                                             hello-world      Please generate a Hello World program
```

> 没写 `title` 时显示 `id`；`tag` 没写就空着。这一步同样**不需要凭据**。

#### 3.4.5 正式跑：`run`

> ⚠️ 这一步要启动真实 Agent，**需要凭据**（见 [3.7 凭据怎么给](#37-凭据怎么给)）。如果你现在没有 ANTHROPIC_API_KEY，可以先跳过本节，直接做练习 1（只 validate / list-cases），等有 key 了再回来跑。

```powershell
skill-up run
```

成功输出长这样：

```text
Running 1 case(s) with agent claude_code
[Runner] Running 1 cases with agent claude_code
[Evaluator] Skill installed: my-skill
[Evaluator] Running case hello-world (with_skill): ...
[Evaluator] Case hello-world: PASS (pass_rate: 100.0%)
[INFO] Results written to ./my-skill-workspace/iteration-1
```

> 🪟 **跑真实 Agent 的 Windows 限制**：`claude_code` / `codex` / `qodercli` 这些引擎靠 **bash + Node/nvm** 引导启动，`cmd.exe` 跑不起来。如果你在 Windows 原生跑 `run` 报「Agent 起不来」类错误，**切到 WSL2** 就好了（见 [3.1 选择表](#31-先做选择windows-原生-还是-wsl2)）。`validate` / `list-cases` 不受此限制。

### 3.5 看懂输出（产物 + 三态 + 退出码）

跑完会在 Skill 目录**旁边**生成 `<skill-name>-workspace/`：

```text
my-skill-workspace/
└── iteration-1/                    ← 第 1 轮（--iteration N 会生成 N 个目录）
    ├── result.json                 ← 【事实源】完整原始数据（最权威）
    ├── benchmark.json              ← 汇总统计（含 with/without skill 对比）
    ├── report.html                 ← 人类可读网页报告（需 --format html）
    └── hello-world/                ← 每个用例一个子目录
        └── with_skill/
            ├── grading.json        ← 这个用例的打分结果
            └── outputs/            ← Agent 生成的文件
```

#### 三个文件，看什么？

| 文件 | 看哪个字段 | 含义 |
|------|-----------|------|
| `grading.json`（单用例） | `summary.pass_rate` | 通过率（0.0 ~ 1.0），1.0 = 全过 |
|                    | `expectations[].passed` / `evidence` | 每条断言是否过、失败原因 |
| `result.json`（全局，事实源） | `case_results[].grading.status` | **PASS / FAIL / ERROR**（三态，见下） |
| `benchmark.json`（汇总） | `run_summary.with_skill.pass_rate.mean` | 全部用例的平均通过率 |

#### 三态：PASS / FAIL / ERROR（必须分清）

| 状态 | 含义 | Java 类比 |
|------|------|----------|
| **PASS** | 所有断言都通过 | 测试绿条 ✅ |
| **FAIL** | 至少一条断言没过（**Agent 跑完了，但答得不对**） | `assertThat` 抛 AssertionError |
| **ERROR** | **执行本身挂了**（超时、Agent 崩溃等），根本没到断言环节 | 抛了 `RuntimeException`，连测试逻辑都没跑完 |

> 分清 FAIL 和 ERROR 是关键：ERROR 是「**评测基础设施**出问题」（Agent 没起来、超时、引擎崩了），FAIL 是「**Skill 行为**不对」。排错方向完全不同。

#### 退出码：0 / 1

| 退出码 | 含义 | 用途 |
|:------:|------|------|
| `0` | 所有用例都 PASS | CI 里 `&&` 串下一步 |
| `1` | 至少有一个 FAIL **或** ERROR | CI 里让 pipeline 挂掉 |

> 🪟 **PowerShell 看退出码**：`echo $LASTEXITCODE`（cmd 用 `%ERRORLEVEL%`）。
> 💡 在 CI（GitHub Actions / Jenkins）里直接靠退出码判断成功失败，不用解析输出——和 Maven/Gradle 的 `-B` 模式一样。

### 3.6 常用命令速查

| 命令 | 作用 | 要凭据？ |
|------|------|:------:|
| `skill-up validate [path]` | 校验 `eval.yaml` + **全量**用例 | 否 |
| `skill-up run [path]` | 跑评测（默认只校验**选中**的用例） | 是 |
| `skill-up list-cases [path]` | 列出所有用例 | 否 |
| `skill-up report <result.json>` | 从已有结果**重生成**报告（不重跑） | 否 |
| `skill-up import <evals.json>` | 把 Anthropic 格式 `evals.json` 转成本项目 YAML | 否 |
| `skill-up init` | 生成用户配置模板（OTel / runtime_kwargs） | 否 |
| `skill-up debug judge <input.json>` | 单独调试 judge 模块 | 否 |
| `skill-up debug report <input.json>` | 单独调试 report 模块 | 否 |

#### `run` 常用 flag

```bash
skill-up run --include-case-name "basic-*"      # 只跑匹配的用例（glob，可重复）
skill-up run --exclude-case-name "*-flaky"      # 排除（可重复）
skill-up run --engine codex --model openai/gpt-4 # 临时换引擎/模型（格式 provider/name）
skill-up run --parallelism 4                     # 并发（允许范围 1–256）
skill-up run --format html --format junit        # 多种报告（可重复；json 是默认，写了也是 no-op）
skill-up run --iteration 3                       # 跑 3 轮（每轮一个 iteration-N/ 目录）
skill-up run --iteration 0                       # 自动续号（接上一次）
skill-up run --dry-run                           # 只看会跑哪些用例，不真跑
skill-up run --auto                              # 自动探测 evals/，可直接吃 Anthropic evals.json
skill-up run -v                                  # debug 日志；-vv = trace
```

> 🪟 `--dry-run` 很有用：它**不启动 Agent**（不需凭据），只打印「这次会跑哪些用例、用什么引擎」。第一次配 config 时先用它过一眼最稳。

> **`validate` vs `run` 的校验范围**（容易混淆）：
> - `validate` 检查**全量**用例（不管 `--include/exclude-case-name`）。
> - `run` 只校验**过滤后选中**的用例——所以一个 eval 里可以同时放「快速 smoke 子集」和「重的用例」，跑 smoke 时重的那个就算配错了也不挡路。

### 3.7 凭据怎么给

优先级（**高 → 低**）：

```text
--api-key 参数  >  环境变量  >  ~/.skill-up/credentials.yaml
```

按引擎对应的环境变量：

| 引擎 (`engine.name`) | 环境变量 |
|----------------------|---------|
| `claude_code` | `ANTHROPIC_API_KEY` |
| `codex` | `OPENAI_API_KEY` |
| `qodercli` | `QODER_PERSONAL_ACCESS_TOKEN` |

```powershell
# 🪟 Windows PowerShell 设环境变量（只对当前会话）
$env:ANTHROPIC_API_KEY = "sk-ant-..."

# 运行时直接传（优先级最高，盖过环境变量）
skill-up run --api-key sk-ant-...
```

> 🪟 注意：Linux/Mac 写 `export VAR=...`，**Windows PowerShell 用 `$env:VAR = "..."`**，cmd 用 `set VAR=...`。别抄错。
> 💡 想持久化：用 `setx ANTHROPIC_API_KEY "sk-..."`（cmd），或 PowerShell 的 `[Environment]::SetEnvironmentVariable(...)`。**但 setx 写进注册表后不泄漏到当前会话**，要重开终端。

### 3.8 skill-upper：不想手写 YAML？用对话式玩法

仓库自带一个 **skill-upper** Agent Skill，装进你的 AI Agent（Codex / Claude Code）后，**用自然语言对话**就能：创建用例 → 运行 → 看报告 → 诊断失败 → 修 Skill/用例 → 再跑，闭环迭代。

```bash
# 装进 Codex（全局）
npx skills add https://github.com/alibaba/skill-up/tree/main/skills/skill-upper -g -a codex -y

# 装进 Claude Code（全局）
npx skills add https://github.com/alibaba/skill-up/tree/main/skills/skill-upper -g -a claude-code -y
```

> 你**不需要先装 skill-up**——skill-upper 跑的时候会检查 `skill-up` 命令在不在，不在就引导 Agent 帮你装。

然后在 Agent 里打开你的 Skill 项目，直接说：

```text
Use skill-upper to evaluate this Skill. Read SKILL.md, create realistic
eval cases, validate, run skill-up, and summarize the biggest failures.
```

> 🪟 **什么时候用 skill-upper**：你已经有 Claude Code / Codex 能用，且**不想一个个手写 YAML**。它本质是「让 AI 帮你写评测」——和 Cursor / Copilot 帮你写 JUnit 测试一个意思。本课为了让你理解机制，**先手写**；理解了之后，日常用 skill-upper 提效。

## 4. 动手练习（3 个递进）

> 三个练习从「不用凭据」到「跑真实 Agent」递进。没凭据也能做完练习 1。

### 练习 1（不需凭据）：构建 + 验证现成示例

1. 在仓库根目录构建：
   ```powershell
   go build -o bin/skill-up.exe ./cmd/skill-up
   .\bin\skill-up.exe --version
   ```
2. 跑官方示例的 `list-cases`（不启动 Agent）：
   ```powershell
   .\bin\skill-up.exe list-cases .\examples\code-stats\evals\eval.yaml
   ```
   **期望**：看到 3 个用例（`analyze-directory` / `top-extensions` / `current-directory-format`）。
3. 跑官方示例的 `validate`（不启动 Agent）：
   ```powershell
   .\bin\skill-up.exe validate .\examples\code-stats\evals\eval.yaml
   ```
   **期望**：`✓ eval.yaml is valid (loaded 3 case(s))`。
4. 再试 `--dry-run`，看「会跑哪些用例」而不真跑：
   ```powershell
   .\bin\skill-up.exe run .\examples\code-stats\evals\eval.yaml --dry-run
   ```

**完成标志**：list-cases 列出 3 条、validate 通过、dry-run 打印出用例计划。

### 练习 2（需凭据）：给自己的 Skill 写 2 个 rule_based 用例并跑通

1. 按 [3.4.2](#342-自己动手最小-evalyaml--hello-world-case) 建一个自己的 `my-skill/`（含 `SKILL.md` + `evals/eval.yaml` + 2 个 case 文件）。
2. 写两个用例，都用 `rule_based` judge（最便宜，纯关键字检查）：
   - **case A**（应通过）：prompt 让 Skill 输出某内容，`success` 断言输出包含关键短语。
   - **case B**（应失败，故意制造一个不通过的，体会 FAIL 长什么样）。
   
   模板（写在 case 文件的 `judge` 块里）：
   ```yaml
   judge:
     type: rule_based
     success:
       - output_contains: { all: ["Hello", "World"] }
     failure:
       - output_contains: { any: ["error", "Error"] }   # 命中任一就 FAIL
   ```
3. 先 `validate`，再 `run`：
   ```powershell
   skill-up validate
   skill-up run
   ```
4. 打开 `my-skill-workspace/iteration-1/<case-id>/with_skill/grading.json`，对比 case A（PASS）和 case B（FAIL）的 `summary.pass_rate` 和 `expectations[].evidence`。

> 🪟 跑真实引擎要凭据 + 可能要 WSL2（见 [3.4.5](#345-正式跑run) 的 Windows 限制）。没条件的话，至少把**配置写对 + validate 通过**，体会「声明式」的部分。
> 💡 故意写一个「应失败」的用例很重要——只有见过 FAIL，你才知道报告里失败原因长什么样、怎么排错。

### 练习 3：用 `--format html` 看网页报告

1. 在练习 2 基础上，重跑并指定 html：
   ```powershell
   skill-up run --format html
   ```
2. 用浏览器打开 `my-skill-workspace/iteration-1/report.html`。
3. 或者**不重跑**，从已有结果重生成（省 token）：
   ```powershell
   skill-up report .\my-skill-workspace\iteration-1\result.json --format html
   ```
4. 试着一次出多种格式：
   ```powershell
   skill-up report .\my-skill-workspace\iteration-1\result.json --format json --format junit --format html
   ```
   会生成 `report.json` / `report.xml`（JUnit，CI 用）/ `report.html`。

**完成标志**：能在浏览器里看到带用例列表、通过率、失败详情的可视化报告。

## 5. 检查点自测

先自己答，再对照下面的答案。

1. `eval.yaml` 和 case 文件分别声明什么？
2. 退出码 `0` 和 `1` 分别代表什么？CI 里怎么用？
3. **PASS / FAIL / ERROR** 三态的区别？ERROR 意味着什么？
4. Windows 上跑**真实 Agent**（claude_code 等）有什么限制？怎么绕？
5. 凭据的三种给法和优先级是什么？

<details>
<summary>👉 点开看答案</summary>

1. **`eval.yaml`** = 入口配置（环境 / 引擎 / 用例清单 / 全局 judge）；**case 文件** = 单个用例（prompt / expect 断言 / 可选 judge）。类比：前者是 Spring Boot 的 `application.yml`，后者是一个 `@Test` 方法。
2. `0` = 全部 PASS；`1` = 至少一个 FAIL **或** ERROR。CI 里直接靠退出码让 pipeline 过/挂，不用解析输出文本（🪟 PowerShell 用 `$LASTEXITCODE`，cmd 用 `%ERRORLEVEL%`）。
3. **PASS** 全过；**FAIL** = Agent 跑完了但断言没过（**Skill 行为**有问题）；**ERROR** = 执行本身挂了（超时 / Agent 崩溃，**评测基础设施**有问题）。排错方向不同：ERROR 先查 Agent/超时/凭据，FAIL 先查 Skill 逻辑。
4. 真实 Agent 靠 **bash + Node/nvm** 引导，`cmd.exe` 跑不起来。绕法：要么在 Windows 上**自己装好 Node + Agent CLI**，要么（更省心）**切到 WSL2**。`validate` / `list-cases` / `--dry-run` 不受此限制。
5. `--api-key` 参数（最高） > 环境变量（`ANTHROPIC_API_KEY` 等） > `~/.skill-up/credentials.yaml`（最低）。
</details>

## 6. 常见坑

| 问题 | 解法 |
|------|------|
| `command not found: skill-up` / `skill-up.exe` | 把 `bin\` 加进 PATH，或全程用 `.\bin\skill-up.exe` 全路径调用 |
| 🪟 `.sh` 脚本评分失败（script judge） | 设 `SKILL_UP_BASH=D:\Git\bin\bash.exe`（指向 Git Bash，**不要**指向 `C:\Windows\System32\bash.exe` 那个 WSL shim，会被拒绝），或改用 `.ps1` 脚本 |
| 🪟 真实 Agent（claude_code/codex/qodercli）跑不起来 | 用 WSL2 跑（见 [3.1](#31-先做选择windows-原生-还是-wsl2)）；或本机自装 Node + Agent CLI |
| `validate` 报 `loaded 0 case(s)` | 检查 `cases.files` 路径——它是**相对 `eval.yaml`** 的 |
| case 里 `repo_fixture` / `script_path` 找不到 | 这类 fixture 路径**相对 `SKILL.md` 所在目录**（不是相对 `eval.yaml`），写成 `evals/fixtures/...` |
| 中文 `expect` 总失败 | 模型输出语言和断言语言要对齐（英文 prompt → 英文断言），中文断言尤其容易因大小写/全半角不一致挂 |
| 改了配置没生效 | 先 `skill-up validate`，看报错；再看是不是改错文件了（有 `evals.json` 和 `eval.yaml` 两套，别改错） |
| 🪟 `setx` 设了环境变量但当前会话没有 | `setx` 写注册表，**不泄漏到当前会话**，要重开终端；或直接用 `$env:VAR=...` 临时设 |
| opensandbox 报鉴权错 | 没设 `OPENSANDBOX_API_KEY` |
