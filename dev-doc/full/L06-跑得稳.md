## 1. 学习目标

学完本课后，你应当能讲清：

1. **并发模型**：skill-up 用「信号量（带缓冲 channel）+ WaitGroup + 预分配结果数组」做 fan-out/fan-in，为什么不用线程池（goroutine + 信号量 = 虚拟线程池），`parallelism` 怎么从 CLI/YAML/默认值三层汇合到 1-256。
2. **超时的「总预算」设计**：case 级超时覆盖 agent + judge 两段，超时错误还会标注是哪个 YAML 旋钮导致的；为什么不能把超时拆成分阶段。
3. **进程组优雅终止**：`Setpgid` + 负 PID 杀整棵进程树、SIGTERM→1s→SIGKILL 升级、`done` channel 防 PID 复用 TOCTOU、Windows 靠 `WaitDelay` 兜底。
4. **Runtime 抽象**：一个 13 方法的接口怎么把「本机进程组 / 远端 HTTP 沙箱 / 本地 Docker」三后端藏起来；为什么 docker 要 shell out CLI 而不用官方 SDK。
5. **跨平台 Shell**：`platform.Shell` 三元组怎么让「Windows 宿主 + POSIX 命令 + Git Bash 调度」这种混合状态变得可控，命令永远经 bash（除非用户连 Git Bash 都没装）。

## 3. 讲解

### 3.1 并发模型：`EvaluateAll`

核心代码在 [`internal/evaluator/evaluator.go:180-237`](../../internal/evaluator/evaluator.go)（`EvaluateAll` 方法）。这是整份代码里最值得在面试里画出来的一段。

#### 3.1.1 任务展开：`cases × {with_skill, without_skill}`

```go
// evaluator.go:195-206
configCount := 1
if e.withBaseline {
    configCount = 2
}

tasks := make([]task, 0, len(cases)*configCount)
for _, c := range cases {
    tasks = append(tasks, task{caseCfg: c, configName: "with_skill"})
    if e.withBaseline {
        tasks = append(tasks, task{caseCfg: c, configName: "without_skill"})
    }
}
```

- `e.withBaseline` 来自 eval.yaml 的 `benchmark.enabled: true`。
- 关键设计：**把「同一个 case 跑两次（带技能 / 不带技能）」做成两个独立 task**，而不是 case 内部的两阶段。好处是两条任务可以**并发跑**（受同一个信号量约束），跑完再由 `groupResultsByCase` 按 caseID 聚回一对，用来算 A/B 基线对比。
- `task` 结构体（[`evaluator.go:113-116`](../../internal/evaluator/evaluator.go)）只有两个字段：`caseCfg *config.CaseConfig` + `configName string`。

> **Java 类比**：相当于把 `List<Case>` flatMap 成 `List<Task>`，每个 Task 带一个 `variant` 标签（`"with_skill"` / `"without_skill"`），类似 Stream API 的 `flatMap(c -> Stream.of(new Task(c, "with"), new Task(c, "without")))`。

#### 3.1.2 三个并发原语 + 预分配结果数组

```go
// evaluator.go:208-212
results := make([]EvalResult, len(tasks))
sem := make(chan struct{}, e.concurrency)
totalCases := len(tasks)

var wg sync.WaitGroup
```

一行一个原语，每个都对应一个 Java 概念：

| Go 原语 | 作用 | Java 类比 |
|---|---|---|
| `results := make([]EvalResult, len(tasks))` | **预分配数组**：每个 goroutine 写自己的槽位 `results[idx]`，互不重叠，无需加锁 | `EvalResult[] results = new EvalResult[n]`，比 `synchronizedList.add()` 快得多 |
| `sem := make(chan struct{}, e.concurrency)` | **带缓冲 channel 当信号量**：缓冲大小 = 并发上限，写满就阻塞 | `java.util.concurrent.Semaphore(concurrency)` |
| `var wg sync.WaitGroup` | 等所有 goroutine 跑完 | `CountDownLatch(n)` 或 `CompletableFuture.allOf(...).join()` |

**为什么用「索引分区」代替「共享 slice + mutex」？** 因为每个 goroutine 用自己的下标 `idx` 写数组，天然无竞争，连原子操作都不需要。这是 Go 并发编程的经典技巧：**避免共享可变状态，而不是加锁保护它**。

#### 3.1.3 循环里起 goroutine：先抢令牌再 `go`

```go
// evaluator.go:213-233
for i, t := range tasks {
    wg.Add(1)
    sem <- struct{}{}          // (A) 主 goroutine 在这里阻塞，直到有空闲令牌
    caseNum := i + 1
    go func(idx int, tk task, cn int) {
        defer wg.Done()
        defer func() { <-sem }()  // (B) 子 goroutine 退出时归还令牌
        if e.observer != nil {
            e.observer.OnCaseStart(cn, totalCases, tk.caseCfg.ID, tk.caseCfg.Title)
        }
        results[idx] = e.executeCase(ctx, tk.caseCfg, tk.configName, nil, nil)
        if e.observer != nil {
            res := results[idx]
            passRate := float64(-1)
            if res.Grading != nil {
                passRate = res.Grading.Summary.PassRate
            }
            e.observer.OnCaseComplete(cn, totalCases, tk.caseCfg.ID, res.Status, passRate)
        }
    }(i, t, caseNum)
}
wg.Wait()
```

四个值得抠的细节：

**(A) `sem <- struct{}{}` 在 `go` 之前，且在主 goroutine 里。**
这一步**在主 goroutine 阻塞**，不是在子 goroutine 里。意思是：当并发数达到上限，**主 goroutine 会停下来不继续 `go`**，把「在飞的任务数」精确锁在 `e.concurrency`。

如果把 `sem <- struct{}{}` 放进子 goroutine，会发生什么？主 goroutine 会瞬间 `go` 出 N 个 goroutine，每个再去抢令牌——结果 N 个 goroutine 全创建了（占内存、给调度器压力），只是挤在信号量前排队。当前写法「先抢令牌再 go」更省资源。

**(B) `defer func() { <-sem }()` 在子 goroutine 里。**
保证**无论 `executeCase` 是正常返回还是 panic，令牌都会归还**。注意 defer 的 LIFO 顺序：`defer wg.Done()` 先注册，`defer func() { <-sem }()` 后注册，所以**先归还令牌，再 `Done`**——这个顺序是安全的：如果先 `Done`（`wg.Wait()` 返回）再归还令牌，`sem` 可能还没满，调用方复用 `sem` 会出问题。

**闭包变量捕获：`go func(idx int, tk task, cn int)(i, t, caseNum)`。**
这是 Go 最经典的坑：循环里直接闭包捕获 `i`、`t`，Go 1.22 之前所有 goroutine 会共享同一份变量，大概率全拿到最后一个值。这里用「把变量作为函数参数传进去」的方式，**在 `go` 的瞬间拍快照**，每个 goroutine 拿到自己的副本。

> **Java 类比**：相当于 lambda 捕获外层变量必须 effectively final 的限制。Java 编译器会强制你这么干，Go 没这个限制所以更容易踩坑，这里用参数化规避。

**`ProgressObserver` 回调（[`evaluator.go:43-46`](../../internal/evaluator/evaluator.go)）。**
接口注释明确写了「Implementations must be safe for concurrent use」（必须线程安全）。它有两个方法 `OnCaseStart` / `OnCaseComplete`，生产实现 `uiProgressObserver` 把回调转给终端进度条。用接口注入而不是直接调 `ui.XXX`，是为了**把进度展示和评测逻辑解耦**——测试时可以传 mock observer。

#### 3.1.4 `wg.Wait()` 之后无锁返回

```go
// evaluator.go:234-236
wg.Wait()
return results, nil
```

`wg.Wait()` 阻塞到所有 `wg.Done()` 调用完，此时 `results` 数组每个槽位都填好了，直接返回。**无锁、无 copy、无 channel drain**——这是 Go 并发编程里最干净的「fan-out → fan-in」模式之一。

> **Java 类比总结**：这套 `Semaphore + CountDownLatch + 预分配数组槽位` ≈ Java 的 `ThreadPoolExecutor(semaphore) + Future.allOf(latch) + 结果数组`，但 Go 用 channel + WaitGroup 把代码量压到了 20 行。

#### 3.1.5 `parallelism` 来源链：CLI > eval.yaml > 默认 1，上限 256

并发数不是写死的，而是**三层配置覆盖 + 硬上限校验**。来源链：

```
--parallelism (CLI)  >  cases.parallelism (eval.yaml)  >  默认 1
                            ↓ 校验
                     1 ≤ parallelism ≤ 256
```

关键代码：

```go
// evaluator.go:151-155（NewEvaluator 兜底）
concurrency := opts.Concurrency
if concurrency <= 0 {
    concurrency = 1
}
```

```go
// internal/cli/run.go:529-546（CLI 覆盖 + 校验，节选）
parallelismFlag := cmd.Flags().Lookup("parallelism")
if parallelismFlag == nil || !parallelismFlag.Changed {
    return nil  // 没传 --parallelism，保留 eval.yaml 的值
}
parallelism, err := strconv.Atoi(parallelismFlag.Value.String())
...
if parallelism < 1 {
    return fmt.Errorf("invalid --parallelism %d: must be >= 1", parallelism)
}
if parallelism > maxParallelismOverride {   // maxParallelismOverride = 256（run.go:35）
    return fmt.Errorf("invalid --parallelism %d: must be <= %d", parallelism, maxParallelismOverride)
}
evalCfg.Cases.Parallelism = parallelism
```

三个要点：

1. **`parallelismFlag.Changed`**：Cobra 提供的标志，告诉你这个 flag 是用户**显式传了**还是只是默认值。只有显式传了才覆盖 eval.yaml——避免「CLI 默认值 0 覆盖了 YAML 里的 8」这种事故。
2. **下界校验 `< 1`**：拒绝 0 和负数，在**配置阶段就报错**比运行时静默修正更明确。
3. **上界 `maxParallelismOverride = 256`**：工程经验值，再大容易把本地 Agent CLI（claude_code/codex 这些进程）打爆，也会瞬间打爆模型 API 的 RPM/TPM 配额。**面试可讲**：这是「保护下游」的限流，相当于 Sentinel 的并发数限流。

### 3.2 重试：`executeCase` 的 attempt 循环

核心代码在 [`evaluator.go:289-331`](../../internal/evaluator/evaluator.go)。

```go
// evaluator.go:289-291
func (e *defaultEvaluator) executeCase(ctx context.Context, caseCfg *config.CaseConfig, ...) EvalResult {
    maxAttempts := max(e.evalCfg.Cases.RetryPolicy.MaxRetries+1, 1)
```

#### 3.2.1 `maxAttempts = MaxRetries + 1`

`RetryPolicy`（`internal/config/schema.go:138-141`）：

```go
type RetryPolicy struct {
    MaxRetries int      `yaml:"max_retries,omitempty"`
    RetryOn    []string `yaml:"retry_on,omitempty"` // timeout, error
}
```

- `MaxRetries` 是「**额外**重试次数」，所以总尝试次数 `maxAttempts = MaxRetries + 1`（首次 + 重试 N 次）。
- `max(..., 1)` 兜底：即使没配或配 0，**至少跑一次**。

> **Java 类比**：Spring 的 `@Retryable(maxAttempts = 3)` 里 `maxAttempts` 是「总次数」（含首次），skill-up 用「重试次数」（不含首次），所以 +1。两种惯例都常见，关键是文档清楚。

#### 3.2.2 attempt 循环：每次都重建超时 context

```go
// evaluator.go:292-328
var result EvalResult
for attempt := 1; attempt <= maxAttempts; attempt++ {
    attemptCtx, cancel, timeoutSource, timeoutSec := withCaseTimeout(ctx, ...)
    result = e.executeCaseOnce(attemptCtx, caseCfg, configName, overrideRT, overrideAgent)
    if errors.Is(attemptCtx.Err(), context.DeadlineExceeded) && ctx.Err() == nil {
        annotateCaseTimeoutError(&result, timeoutSource, timeoutSec)
    }
    cancel()

    retryReason, ok := retryReasonForResult(result)
    if !ok || !retryAllowed(e.evalCfg.Cases.RetryPolicy, retryReason) || attempt == maxAttempts {
        return result
    }

    logging.WarnContextf(ctx, "Runner: case %s (%s) attempt %d/%d hit %s, retrying after %s",
        caseCfg.ID, configName, attempt, maxAttempts, retryReason, retryBackoffDelay(attempt))
    if err := sleepWithContext(ctx, retryBackoffDelay(attempt)); err != nil {
        return result
    }
}
```

四个关键点：

**(1) 每次尝试都调 `withCaseTimeout` 重建 context。**
**为什么不在循环外建一次？** 因为超时是「**单次尝试**的预算」，不是「所有重试加起来的总预算」。第一次跑超时了（context 已经 `DeadlineExceeded`），第二次重试必须用**新的 context** 才能真的再跑一次。所以每次循环都 `withCaseTimeout` 新建一个 `attemptCtx`，跑完 `cancel()` 释放。

**(2) `retryReasonForResult` 只认 `StatusError`（[`evaluator.go:897-905`](../../internal/evaluator/evaluator.go)）。**

```go
func retryReasonForResult(result EvalResult) (string, bool) {
    if result.Status != judge.StatusError || result.Error == nil {
        return "", false
    }
    if isTimeoutError(result.Error) {
        return "timeout", true
    }
    return "error", true
}
```

**只有 `StatusError` 才考虑重试**：PASS / FAIL / SKIP 都不重试。这是个重要设计——**FAIL（断言不过）是确定性失败，重试也不会变**，重试只对「不确定的执行错误」（超时、进程崩、网络抖动）有意义。

**(3) `retryAllowed` 是白名单制（[`evaluator.go:885-895`](../../internal/evaluator/evaluator.go)）。**

```go
func retryAllowed(policy config.RetryPolicy, reason string) bool {
    if reason == "" || policy.MaxRetries <= 0 {
        return false
    }
    for _, allowed := range policy.RetryOn {
        if strings.EqualFold(allowed, reason) {
            return true
        }
    }
    return false
}
```

YAML 里 `retry_on: [timeout]` 表示只重试超时；`retry_on: [timeout, error]` 都重试；**不写 `retry_on` 则什么都不重试**（即使 `MaxRetries > 0`）。`strings.EqualFold` 大小写不敏感，写 `Timeout` / `TIMEOUT` 都行。

**(4) `retryBackoffDelay` 指数退避 + 可取消 sleep（[`evaluator.go:939-956`](../../internal/evaluator/evaluator.go)）。**

```go
func retryBackoffDelay(attempt int) time.Duration {
    if attempt < 1 {
        attempt = 1
    }
    return time.Duration(1<<attempt) * time.Second   // 2^attempt 秒
}

func sleepContext(ctx context.Context, delay time.Duration) error {
    timer := time.NewTimer(delay)
    defer timer.Stop()

    select {
    case <-ctx.Done():
        return ctx.Err()
    case <-timer.C:
        return nil
    }
}
```

`1<<attempt` = 2 的 attempt 次方：attempt=1 → 2s，attempt=2 → 4s，attempt=3 → 8s，attempt=4 → 16s。经典指数退避——重试失败往往是因为下游过载（API 限流、容器还没起好），指数退避给下游恢复时间，同时避免重试本身又打爆下游。

> **Java 类比**：Spring Retry 的 `@Backoff(delay = 1000, multiplier = 2)`，或 Resilience4j 的 `ExponentialBackoff`。

**关键：sleep 是可取消的。** 不是 `time.Sleep(delay)`，而是 `select { ctx.Done() / timer.C }`。如果用户在重试等待期间按了 Ctrl+C（父 context 被取消），`time.Sleep` 会**继续睡完**才退出，而 `sleepContext` 会**立刻在 `<-ctx.Done()` 分支返回**。这是 Go 写「可中断 sleep」的标准范式。

`executeCase` 用的是 `var sleepWithContext = sleepContext`（[`evaluator.go:35`](../../internal/evaluator/evaluator.go)）这个**变量**——是个可替换的函数指针，方便测试 mock（测试里不想真等 2 秒就替换掉）。

#### 3.2.3 重试决策的三个退出条件

```go
// evaluator.go:310-313
retryReason, ok := retryReasonForResult(result)
if !ok || !retryAllowed(e.evalCfg.Cases.RetryPolicy, retryReason) || attempt == maxAttempts {
    return result
}
```

| 条件 | 含义 |
|---|---|
| `!ok` | 不是 Error 状态（PASS/FAIL/SKIP），没有重试理由 |
| `!retryAllowed(...)` | 是 Error，但 `retry_on` 白名单不包含该理由 |
| `attempt == maxAttempts` | 重试次数用完了 |

三个条件 `||` 短路，从左到右依次判断，符合「快速失败」原则。

### 3.3 超时控制：`withCaseTimeout` —— case 级总预算

#### 3.3.1 优先级：case 级 > defaults 级

```go
// evaluator.go:873-883
func withCaseTimeout(ctx context.Context, defaultTimeoutSec, caseTimeoutSec int) (context.Context, context.CancelFunc, string, int) {
    if caseTimeoutSec > 0 {
        c, cancel := context.WithTimeout(ctx, time.Duration(caseTimeoutSec)*time.Second)
        return c, cancel, "case.constraints.timeout_seconds", caseTimeoutSec
    }
    if defaultTimeoutSec > 0 {
        c, cancel := context.WithTimeout(ctx, time.Duration(defaultTimeoutSec)*time.Second)
        return c, cancel, "cases.defaults.timeout_seconds", defaultTimeoutSec
    }
    return ctx, func() {}, "", 0
}
```

- **优先 case 自己的 `constraints.timeout_seconds`**，没配（=0）才回退到 `cases.defaults.timeout_seconds`，都没配就**不设超时**（返回原 ctx + 空 cancel）。
- 返回值里的 `string`（source）和 `int`（seconds）：**为了给超时错误信息标注「哪个配置项导致的」**——下文 3.3.3 讲。

#### 3.3.2 「超时是 agent + judge 的总预算」——核心设计

看 `executeCase` 里超时是怎么用的（[`evaluator.go:294-295`](../../internal/evaluator/evaluator.go)）：

```go
attemptCtx, cancel, timeoutSource, timeoutSec := withCaseTimeout(...)
result = e.executeCaseOnce(attemptCtx, ...)  // 整个 once 都在这个 ctx 下
```

而 `executeCaseOnce` 内部会顺序做：1. 准备 runtime；2. `Agent.Run`；3.（可选）`Judge.Evaluate`。**这三步全部跑在同一个 `attemptCtx` 下**。

意味着：如果 timeout=60s，Agent 跑了 55s，judge 就只剩 5s——一旦超时，整个 attempt 失败，触发 `timeout` 重试理由。证据在 `handleExecutionResult`（[`evaluator.go:907-911`](../../internal/evaluator/evaluator.go)）的注释里：

```go
// handleExecutionResult finalises the EvalResult when the agent run returned an
// error. Any execErr (including ctx.DeadlineExceeded) terminates the case as
// ERROR: the case timeout is treated as a single budget for agent + judge, so
// we do not try to salvage partial output by running the judge against a
// truncated agent transcript.
```

**为什么这么设计？** 假设超时是「agent 单独的预算」，agent 跑超时了还让 judge 去评一个被截断的输出，judge 会基于残缺数据打分，可能给一个本应失败的 case 打 PASS——**总预算模式下，超时 = 整个 attempt 失败 = 触发重试**，语义干净。

> **Java 类比**：相当于给「整个 HTTP 请求处理链路」设一个总 timeout（包括下游调用 + 业务逻辑 + 持久化），而不是每步分别设 timeout。Spring Cloud Gateway 的 `timeout` 就是这种总预算语义；也类似 EJB 的 `@TransactionAttribute(timeout)` 把超时绑在整个事务上，而不是单个 SQL。

#### 3.3.3 `annotateCaseTimeoutError`：超时错误信息标注来源

```go
// evaluator.go:859-867
func annotateCaseTimeoutError(result *EvalResult, source string, seconds int) {
    if result == nil || result.Error == nil || source == "" || seconds <= 0 {
        return
    }
    if !errors.Is(result.Error, context.DeadlineExceeded) {
        return
    }
    result.Error = fmt.Errorf("%w (case timeout %ds via %s)", result.Error, seconds, source)
}
```

把原始的 `context.DeadlineExceeded` 包成：

```
context deadline exceeded (case timeout 60s via case.constraints.timeout_seconds)
```

三个看点：

1. **`%w` 包装错误**（不是 `%s`）：保留原始错误链，下游 `errors.Is(err, context.DeadlineExceeded)` 仍然能匹配。这是 Go 1.13 的错误包装范式。
2. **`via case.constraints.timeout_seconds`**：直接告诉用户「去改这个 YAML 字段」。这是**可定位性（debuggability）**——超时错误不仅报「超时了」，还报「是哪个配置项设的超时」。
3. **多重 guard**：防御式编程，避免把空 source 拼进去生成奇怪的错误信息。

调用方的判断（[`evaluator.go:305`](../../internal/evaluator/evaluator.go)）：

```go
if errors.Is(attemptCtx.Err(), context.DeadlineExceeded) && ctx.Err() == nil {
    annotateCaseTimeoutError(&result, timeoutSource, timeoutSec)
}
```

**`ctx.Err() == nil` 这个条件非常关键**：它排除「父 context 超时」的情况。如果调用 `EvaluateAll` 的人在外面套了一个 `context.WithTimeout(parentCtx, 5*time.Minute)`，那个父超时触发的 `DeadlineExceeded` **不应该**被标成「case timeout」——那会误导用户去改 case 的 YAML，而真正的问题是整体运行时间太长。所以只有「**case 自己的 deadline 触发，且父 context 还活着**」才标注。

> 注释（[`evaluator.go:296-304`](../../internal/evaluator/evaluator.go)）专门解释了为什么 `annotate` 必须在 `cancel()` 之前调用：`cancel()` 会把 `attemptCtx.Err()` 改写成 `context.Canceled`，覆盖掉原本的 `DeadlineExceeded`，于是超时标注就丢了。**顺序错了，错误信息就变了**——这是很容易踩的坑，源码用注释 explicit 标了出来。

### 3.4 进程清理：`NoneRuntime.Exec` 的进程组 SIGTERM→SIGKILL

这是最容易在面试里被追问「孙子进程怎么办」的部分。代码在 [`internal/runtime/none.go`](../../internal/runtime/none.go) + 两个平台分支文件 [`none_exec_unix.go`](../../internal/runtime/none_exec_unix.go) / [`none_exec_other.go`](../../internal/runtime/none_exec_other.go)。

#### 3.4.1 问题背景：为什么 `exec.CommandContext` 不够用？

Go 标准库的 `exec.CommandContext` 在 ctx 取消时**只 kill 直接子进程**。但 skill-up 的执行模型是：

```
skill-up (Go 进程)
  └─ shell (bash/cmd)            ← exec.Command 直接启动的
       └─ agent CLI (claude_code)
            └─ git / sleep / ping / node ...   ← 孙子进程
```

如果只 kill shell，**孙子进程会变成孤儿继续跑**，可能：继续写 workspace 文件污染下一个 case；占着端口/锁让下个 case 起不来；在 CI 里挂住让整个 pipeline 卡死。所以必须**杀整棵进程树**。

#### 3.4.2 POSIX 实现：进程组 + SIGTERM → 1s → SIGKILL

[`internal/runtime/none_exec_unix.go`](../../internal/runtime/none_exec_unix.go)（build tag `//go:build unix`）：

```go
// none_exec_unix.go:18
const noneExecKillGrace = 1 * time.Second

// none_exec_unix.go:31-58
func configureProcessGroup(cmd *exec.Cmd, done <-chan struct{}) {
    cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}      // ① 子进程成为新进程组 leader
    cmd.Cancel = func() error {                                // ② ctx 取消时调
        if cmd.Process == nil {
            return nil
        }
        pid := cmd.Process.Pid
        if err := signalGroupOrProcess(cmd, pid, syscall.SIGTERM); err != nil {
            return err
        }
        // ③ 起独立 goroutine，1s 后还没退就升级 SIGKILL
        go func() {
            timer := time.NewTimer(noneExecKillGrace)
            defer timer.Stop()
            select {
            case <-done:                                       // 进程已退出，停止升级
            case <-timer.C:
                _ = signalGroupOrProcess(cmd, pid, syscall.SIGKILL)
            }
        }()
        return nil
    }
}

// none_exec_unix.go:62-67
func signalGroupOrProcess(cmd *exec.Cmd, pid int, sig syscall.Signal) error {
    if err := syscall.Kill(-pid, sig); err != nil {            // ★ 负 PID = 给整组发信号
        return cmd.Process.Signal(sig)                         // 失败回退到只发主进程
    }
    return nil
}
```

逐点拆：

**(1) `Setpgid: true` —— 新进程组 leader。**
让子进程成为新进程组的 leader（PGID = 子进程 PID）。此后该进程及其所有后代都属于同一个进程组。这是 POSIX 的 `setpgid(0, 0)` 系统调用，等价于 shell 里的 `setsid`。

> **Java 类比**：Java 的 `ProcessHandle` 在 JDK 9+ 才有，且跨平台支持有限（Windows 上 `descendants()` 经常返回空）。Go 在系统编程上的优势——直接调系统调用，行为可预测。

**(2) `syscall.Kill(-pid, sig)` —— 负 PID = 整组。**
`kill(2)` 系统调用的约定：PID 为负数时，信号发给「绝对值那个 PGID」的所有成员。所以 `-pid` 就是「给整棵进程树发信号」，包括所有孙子进程。fallback `cmd.Process.Signal(sig)` 作为组信号失败的兜底（极少触发）。

**(3) SIGTERM 先行，1s 后 SIGKILL 升级。**
`cmd.Cancel` 是 Go 1.20+ `exec.Cmd` 的新字段：当 ctx 取消时被调用。先发 **SIGTERM**（优雅终止信号），让 shell 和孩子们有时间跑 trap handler、释放锁、flush 数据。如果 1s（`noneExecKillGrace`）后还没退出，**升级到 SIGKILL**（不可捕获、不可忽略）强制杀。

> 这是 Unix 进程管理的标准最佳实践，等价于 Kubernetes 的 `terminationGracePeriodSeconds` + SIGTERM/SIGKILL 流程，也等价于 `docker stop` 默认 10s grace。

**(4) 为什么 SIGKILL 在 goroutine 里「out of band」发？**
`cmd.Cancel` 必须快速返回（让 `os/exec` 框架继续干活），不能阻塞 1s 等升级。所以把「等 1s 再 SIGKILL」扔进一个 goroutine 异步执行。注释（[`none_exec_unix.go:43-46`](../../internal/runtime/none_exec_unix.go)）写得很清楚。

**(5) `done` channel 防 PID 复用（TOCTOU 安全）。**
这是个**TOCTOU（time-of-check-time-of-use）安全**细节：如果进程被杀后，操作系统把那个 PID 复用给了一个完全无关的新进程，再发 SIGKILL 就会误杀。所以 `runCmd`（[`none.go:289-295`](../../internal/runtime/none.go)）在 `cmd.Wait()` 返回后 `defer close(done)`，通知升级 goroutine「进程已经回收，别再发信号」：

```go
// none.go:289-295
func runCmd(cmd *exec.Cmd, done chan<- struct{}) error {
    defer close(done)                       // ★ Wait 返回后立刻 close，停止升级定时器
    if err := cmd.Start(); err != nil {
        return err
    }
    return cmd.Wait()
}
```

`select { case <-done: case <-timer.C: }`——谁先到听谁的：`done` 先到（进程提前退出）就停 timer，`timer.C` 先到（1s 到了进程还在）就发 SIGKILL。优雅且安全。

#### 3.4.3 Windows 实现：无进程组，靠 `WaitDelay`

[`internal/runtime/none_exec_other.go`](../../internal/runtime/none_exec_other.go)（build tag `//go:build !unix`）：

```go
//go:build !unix

package runtime

import "os/exec"

// configureProcessGroup 在没有 POSIX 进程组的平台上是 no-op。
func configureProcessGroup(_ *exec.Cmd, _ <-chan struct{}) {}
```

**Windows 没有 `setpgid` / `kill(-pid)` 等价物**，这里是个空函数。那 Windows 上孙子进程怎么办？答案在 [`none.go`](../../internal/runtime/none.go) 的 `Exec` 函数里——**两个平台都设置了 `cmd.WaitDelay`**：

```go
// none.go:23-31
// noneExecWaitDelay bounds how long Exec waits after ctx-cancel before
// forcibly closing the child's stdio pipes. On POSIX,
// configureProcessGroup kills the whole tree on cancellation so a short
// grace is enough. On Windows there is no process group equivalent and
// a Git Bash grandchild (ping/sleep/git) can still hold the stderr pipe;
// this delay ultimately closes it so the pipe-reader goroutines unblock
// and Exec returns within the deadline.
noneExecWaitDelay = 2 * time.Second

// none.go:216
cmd.WaitDelay = noneExecWaitDelay
```

`cmd.WaitDelay` 是 Go 1.20+ 的另一个新字段：`cmd.Wait()` 在子进程退出后，最多再等 `WaitDelay` 时间让 stdio 管道排空；超时就**强制关闭管道**，让 `Wait` 返回。

**为什么 Windows 需要这个？** 因为 Git Bash 的 `ping`/`sleep`/`git` 孙子进程会**占着 stderr 管道不放手**（即使 shell 父进程已经退出），导致读 stderr 的 goroutine 永远阻塞。`WaitDelay` 强制关管道，goroutine 解除阻塞，Exec 才能返回。

> **数值关系**：`noneExecKillGrace = 1s` < `noneExecWaitDelay = 2s`。注释明说：POSIX 上 1s 内进程组必死，2s 时关管道只是兜底；Windows 上没有组杀，只能靠 2s 关管道。两个常量**必须协同**，是典型的「魔法数字必须成对维护」。

#### 3.4.4 build tag 切换：Go 跨平台编译的经典范式

两个文件用 `//go:build unix` 和 `//go:build !unix` 互斥的 build tag，编译时 Go 工具链**自动选择对应平台的实现**：

- `none_exec_unix.go`：在 linux/darwin/freebsd 等 POSIX 系统编译进二进制；
- `none_exec_other.go`：在 windows 上编译进二进制。

两个文件**函数签名完全一致**（都是 `configureProcessGroup(cmd *exec.Cmd, done <-chan struct{})`），调用方 `none.go` 不用关心平台差异，直接 `configureProcessGroup(cmd, done)` 即可。

> **Java 类比**：相当于 Maven 的 `<profiles>` 或 GraalVM 的 `@TargetPlatform`，但 Go 的 build tag 是**源码级、零运行时开销**，更接近 C 的 `#ifdef`。Java 跨平台通常靠「JVM 抹平」，Go 靠「编译期选择」。

#### 3.4.5 `classifyExecError`：四态错误分类

[`none.go:307-334`](../../internal/runtime/none.go)，把 `cmd.Run()` 的错误翻译成 `(exitCode, error)` 对：

```go
// 优先级（注释 none.go:300-306）：
//   nil err                            → (0, nil)              // 正常退出 0
//   *exec.ExitError + ctx.Err() == nil → (exitCode, nil)       // 命令非零退出，业务失败
//   *exec.ExitError + ctx.Err() != nil → (exitCode, ctxErr)    // 被 ctx 杀，但包了 ExitError
//   exec.ErrWaitDelay (no ExitError)   → (0, nil)              // 进程正常退 0，只是管道滞后
//   non-ExitError                      → (-1, ctxErr or err)   // 启动失败之类
func classifyExecError(ctx context.Context, runErr error) (int, error) {
    if runErr == nil {
        return 0, nil
    }
    // ★ ctx 取消时强制返回 -1，无论 OS 报什么 exit code
    if ctxErr := ctx.Err(); ctxErr != nil {
        return -1, ctxErr
    }
    var exitErr *exec.ExitError
    if errors.As(runErr, &exitErr) {
        return exitErr.ExitCode(), nil
    }
    if errors.Is(runErr, exec.ErrWaitDelay) {
        return 0, nil
    }
    return -1, runErr
}
```

四种状态总结：

| 场景 | exitCode | error | 含义 |
|---|---|---|---|
| `runErr == nil` | 0 | nil | 正常成功 |
| ctx 被取消/超时 | **-1** | ctxErr | 被框架杀掉（无论 OS 报什么码） |
| `*exec.ExitError`（ctx 还活着） | 真实退出码 | nil | 脚本本身失败（业务错误） |
| `exec.ErrWaitDelay`（无 ExitError） | 0 | nil | 进程正常退出，只是管道慢关 |

两个精妙处：

**(1) ctx 取消时强制 -1。** 注释（[`none.go:311-316`](../../internal/runtime/none.go)）解释：POSIX 上被信号杀的进程报 -1 是惯例；但 **Windows bash 的 `sleep 1` 被 ctx 杀会报 exit 1**——和脚本正常失败无法区分。所以无论平台，只要 `ctx.Err() != nil`，统一改成 -1，作为「被 context 杀」的规范信号。下游 `Exec` 函数的 switch（[`none.go:247-269`](../../internal/runtime/none.go)）就靠这个识别。

**(2) `exec.ErrWaitDelay` 当作 exit 0。** 这是个**关键的宽容设计**：进程已经正常退出（没有 ExitError），只是 stdio 管道被后台孙子占着没及时关闭。如果把这当 exec 失败，会让「Agent 本身跑成功了，只是后台有个 sleep 没退」的 case 被误判为失败。所以源码选择**信任已捕获的输出，按 exit 0 处理**。

> **Java 类比**：相当于你在 `Process.waitFor()` 之后还要区分「进程正常 exit」、「进程被 `destroyForcibly` 杀」、「Future.cancel 触发的中断」——Go 这里用四种错误类型表达，比 Java 的 `InterruptedException` 单一信号更精细。

#### 3.5.2 工厂 `NewRuntime` + 构造期 Shell 校验（fail-fast）

```go
// runtime.go:216-238
func NewRuntime(cfg Config) (Runtime, error) {
    var (
        rt  Runtime
        err error
    )
    switch cfg.Type {
    case "none":
        rt = &NoneRuntime{cfg: cfg}
    case "opensandbox":
        rt, err = NewOpenSandboxRuntime(cfg)
    case "docker":
        rt, err = NewDockerRuntime(cfg)
    default:
        return nil, errors.New("unknown runtime type: " + cfg.Type)
    }
    if err != nil {
        return nil, err
    }
    // ★ 构造期立刻校验 Shell，坏配置 fail-fast
    if err := rt.Shell().Validate(); err != nil {
        return nil, fmt.Errorf("invalid %s runtime shell: %w", cfg.Type, err)
    }
    return rt, nil
}
```

两个设计点：

1. **`switch` 而非 map/registry**：三后端是闭集，未来不会动态扩展，用 switch 最直白。
2. **构造期 `rt.Shell().Validate()`**：拿到 Runtime 实例后**立刻**校验它的目标 shell 描述合法（比如 Windows 上配了个 cmd 但又填了 `BashPath`，会被 `platform.Shell.Validate` 直接拒掉）。**fail-fast**——坏配置在 `NewRuntime` 就报错，而不是等到第一次 `Exec` 才崩。

> **Java 类比**：类似 Spring 在 `ApplicationContext.refresh()` 阶段就把 bean 配置错误暴露，不等到第一次注入使用。

#### 3.5.3 `RequiresProcessSandbox`：分层防御

三后端的返回值差异是核心：

| 后端 | 返回值 | 含义 |
|---|---|---|
| `NoneRuntime` | **`true`** | 命令在主机直接跑，Agent 必须自己再套一层进程沙箱兜底 |
| `OpenSandboxRuntime` | `false` | 远端容器已隔离，Agent 不必重复套 |
| `DockerRuntime` | `false` | 本地容器已隔离，同上 |

谁消费这个值？Codex/Qwen Code 等 Agent 在决定要不要开自己的进程沙箱时调它。这是典型的**分层防御**——每层独立判断是否需要再隔离一次。

### 3.6 三后端实现

#### 3.6.1 `NoneRuntime`：本机进程组 + 临时目录隔离

定位（[`none.go:43-47`](../../internal/runtime/none.go)）：`NoneRuntime executes commands directly on the host with an isolated temp workspace.`

**没有进程级隔离**，靠两点兜底：(1) 每次跑用独立临时目录 `os.MkdirTemp("", "skill-up-*")` 避免文件串；(2) 进程组 + SIGTERM/SIGKILL 保证超时命令能被收掉（3.4 节已详述）。仅用于信任场景（本地开发、CI、被测 Skill 已知安全）。

`Exec` 函数（[`none.go:200-283`](../../internal/runtime/none.go)）的核心流程：

```go
// none.go:205-232（节选）
shell := platform.Host()                          // ① 选 shell（platform.Host 决定）
cmd := shell.Cmd(ctx, command)
done := make(chan struct{})
configureProcessGroup(cmd, done)                  // ② 进程组（POSIX 才有，Windows no-op）
cmd.WaitDelay = noneExecWaitDelay                 // ③ WaitDelay：ctx 取消后最多等 2s 强关管道
...
env := mergeEnv(r.cfg.Env, opts.Env)              // ④ 合并 env：主机 env ← cfg.Env ← opts.Env ← shell.Env
env = append(env, shell.Env...)
cmd.Env = env

exitCode, execErr := classifyExecError(ctx, runCmd(cmd, done))  // ⑤ 分类错误
```

> **Java 类比**：相当于 `ProcessBuilder.directory(workspace).command("bash", "-c", cmd).start()`，但多了进程组、WaitDelay、错误分类三道工序。

#### 3.6.2 `OpenSandboxRuntime`：远端 HTTP API + 批量上传并发下载

定位：把命令送到 Alibaba OpenSandbox 远端服务跑，**最强隔离 + 集中化镜像管理**。

**两个并发传输设计针对不同瓶颈**：

- **批量上传（每批 128 个文件，[`opensandbox.go:305-358`](../../internal/runtime/opensandbox.go)）**：瓶颈是 **fd**——每个上传要打开本地文件读，一次性传几千个 Skill 仓库文件会撑爆 `ulimit -n`。所以分批，每批结束用 `defer` 统一关掉这批的 fd。
- **并发下载（worker pool，默认 8 个，[`opensandbox.go:411-464`](../../internal/runtime/opensandbox.go)）**：瓶颈是**网络**——每个文件一次 HTTP GET，串行慢。所以并发，fail-fast（第一个错就 `cancel()` 整批）。

```go
// opensandbox.go:411-464（并发下载 worker pool 节选）
ctx, cancel := context.WithCancel(ctx)
defer cancel()

jobs := make(chan opensandbox.FileInfo)
errCh := make(chan error, 1)                       // ★ buffer 1，第一个错误就 cancel
var wg sync.WaitGroup
for range parallelism {
    wg.Go(func() {                                 // Go 1.25+ 的 wg.Go
        for file := range jobs {
            if err := r.downloadSearchResult(ctx, ...); err != nil {
                select {
                case errCh <- err:                 // 第一个错误塞进去
                    cancel()                       // 然后立刻 cancel 整个 ctx
                default:                           // 后续错误直接丢弃
                }
                return
            }
        }
    })
}
```

> **Java 类比**：上传 ≈ `Stream` + 分批处理防 OOM；下载 ≈ `ExecutorService.invokeAll` + `Future` 第一个异常就 `shutdownNow`。两套机制针对不同资源约束。

**可测试性设计**：`openSandboxClient` 是个接口（生产用真实 SDK，测试用 fake）+ `var createOpenSandbox` 是包级函数变量（测试里 `t.Cleanup` 替换成假工厂）。这是 Go 风格的「接口 + 包级变量」两件套，等效 Spring 的 `@MockBean`。

#### 3.6.3 `DockerRuntime`：shell out docker CLI（非 SDK）

定位（[`docker.go:44-58`](../../internal/runtime/docker.go)）：`DockerRuntime executes commands inside a local Docker container.` 生命周期是 `docker create` → `docker start` → `docker exec` / `docker cp` → `docker rm -f`。

**关键设计选择：shell out 调 `docker` CLI，不用 Docker SDK**。原因：

1. **依赖轻**：CLI 几乎所有开发机都装了，SDK 要拉一堆 transitive deps。
2. **可手动复现**：用户能直接 `docker exec -it <id> sh` 进去排障，看到的和代码跑的一致。
3. **测试简单**：mock 一个函数字段（`run dockerCommandRunner`）就行，无需起真容器。
4. **行为可预测**：CLI stderr 的前缀（`Error response from daemon:`）稳定，便于 `dockerExecLayerError` 分类。

代价：每次调用 fork 一个 docker 进程，比 SDK 直接走 HTTP 慢一点。但 skill-up 不是高频调用，几秒一次 `docker exec` 完全可接受。

**`Exec` 用 `sh -c` 而非 `bash -c`（[`docker.go`](../../internal/runtime/docker.go)）**：兼容最小镜像（alpine 默认没装 bash，只有 busybox sh）。skill-up 的所有 shell 片段（setup_steps、judge 脚本）都刻意保持 POSIX 兼容，所以 `sh` 够用。distroless 镜像不支持——整个评测生命周期都是 shell 驱动的，没 `/bin/sh` 跑不动。

**安全设计亮点**：`allow_declared`（FQDN 白名单出网）在 docker 后端**直接拒绝**（[`docker.go`](../../internal/runtime/docker.go) 构造期校验），注释写「Refuse loudly instead of silently allowing」。**绝不静默降级到不安全状态**——用户以为白名单生效了，实际全放行才是灾难。

> **Java 类比**：相当于选 ProcessBuilder 调 `docker` 命令还是选 `docker-java` 客户端库——前者依赖少行为直观，后者类型安全但重。也类似 **Testcontainers**：Testcontainers 也是 shell out docker，提供容器级隔离，只是 skill-up 把它内化成了 Runtime 接口的一个实现。

### 3.7 `platform.Shell` 跨平台抽象

[`internal/platform/`](../../internal/platform/) 整个包只做一件事：**把「宿主是什么 OS、用哪个 shell、怎么引用参数」集中到一处**，让 `runtime/` 包不再散落 `runtime.GOOS` 分支。

#### 3.7.1 三元组：`GOOS` + `Family` + `BashPath`

```go
// platform.go:44-50
type Shell struct {
    GOOS   string
    Family ShellFamily
    BashPath string   // Windows 上跑 POSIX 命令时，bash.exe 的绝对路径
}

type ShellFamily string

const (
    ShellPOSIX ShellFamily = "posix"   // sh 兼容
    ShellCmd   ShellFamily = "cmd"     // Windows cmd.exe
)
```

**为什么是三元组？**

- `GOOS`：目标文件路径风格、行分隔符、`exec.LookPath` 行为都依赖它。
- `Family`：决定参数引用规则（POSIX 单引号 vs Windows 双引号 + CommandLineToArgvW）。
- `BashPath`：**Windows 上跑 POSIX 命令时必须知道 bash.exe 在哪**。Windows 自带 `cmd.exe` 不懂 POSIX 语法，但用户可能装了 Git Bash。

这三者解耦后能表达「Windows 主机 + POSIX 命令语言 + Git Bash 调度」这种混合状态——skill-up 在 Windows 上跑评测的关键。

#### 3.7.2 `Validate`：构造期拒绝矛盾组合（[`platform.go:53-75`](../../internal/platform/platform.go)）

```go
func (s Shell) Validate() error {
    if s.GOOS == "" {
        return errors.New("shell GOOS must not be empty")
    }
    switch s.Family {
    case ShellPOSIX:
        if s.GOOS == GOOSWindows && s.BashPath == "" {
            return errors.New("windows POSIX shell requires BashPath")
        }
    case ShellCmd:
        if s.GOOS != GOOSWindows {
            return fmt.Errorf("cmd shell requires windows GOOS, got %q", s.GOOS)
        }
        if s.BashPath != "" {
            return errors.New("cmd shell must not set BashPath")
        }
    ...
    }
    return nil
}
```

拒绝：Windows + POSIX 但没 bash 路径；cmd 但 GOOS 不是 Windows；cmd 又设了 BashPath。**被 `NewRuntime` 在工厂里立刻调用**，坏配置 fail-fast。

#### 3.7.3 `Quoter()`：自动选引用函数（[`platform.go:78-89`](../../internal/platform/platform.go)）

```go
func (s Shell) Quoter() (func(string) string, error) {
    if err := s.Validate(); err != nil {
        return nil, err
    }
    if s.Family == ShellCmd {
        return shellquote.QuoteWindows, nil          // cmd → CommandLineToArgvW 规则
    }
    if s.GOOS == GOOSWindows {
        return quoteForBashDoubleQuote, nil          // Windows + POSIX → bash 双引号
    }
    return shellquote.QuotePOSIX, nil                 // 其他 → POSIX 单引号
}
```

三种引用策略，按 Shell 描述自动选。**为什么 Windows + POSIX 要单独一套？** 因为命令最终是 `bash -c "<command>"`，参数要塞进 bash 双引号字符串里，bash 双引号语义（`$VAR` 展开、`` `cmd` `` 执行）必须被转义；但 `bash.exe` 是 Windows 进程，`CommandLineToArgvW` 规则又同时生效。两套规则叠加，单独写一个 `quoteForBashDoubleQuote`（[`platform.go:115-128`](../../internal/platform/platform.go)，只转义 `\ " $ \`` 四个字符）最清晰。

#### 3.7.4 命令永远经 bash（即便宿主是 Windows）

这是整个抽象的**最终效果**：

1. evaluator / agent 调 `rt.Exec(ctx, "set -eu; npm install", opts)`。
2. `NoneRuntime.Exec` 调 `platform.Host().Cmd(ctx, command)` → 在 Windows 上变成 `bash.exe -c "set -eu; npm install"`。
3. 命令字符串是 POSIX 语法，bash 能直接执行，**完全绕过 cmd.exe 的语法不兼容问题**。
4. Windows 上还会自动注入 `MSYS_NO_PATHCONV=1` 等 env，防止 Git Bash 的 MSYS 层把 `/x/y` 这种「看起来像 Unix 路径」的参数自动改成 `C:\Program Files\Git\x\y`。
5. 只有在用户机器上**完全没装 Git Bash** 时，才退化到 cmd.exe fallback。

**`DiscoverBash` 还会显式排除 WSL 的 `bash.exe`**（`bash_windows.go`）：WSL 的 bash 在 PATH 上排很靠前，但它期望 Linux 路径（`/mnt/c/...`），把 Windows 路径喂给它直接失败。所以必须显式排除——这是踩过坑才写得出的代码。

> **Java 类比**：相当于你写了一套基于 Bash 的部署脚本，跨平台跑靠「在 Windows 上偷偷用 Git Bash」实现。这种「目标方言优先于宿主方言」的设计，类似 JVM 让 Java 代码无视底层 OS 差异——只不过这里「虚拟机」是 bash 本身。

**关键陷阱（接口注释 [`runtime.go:149-152`](../../internal/runtime/runtime.go)）**：`Shell()` 返回的是**目标 shell**（命令实际跑的那个 shell），不是 skill-up 进程所在主机的 shell。比如你在 Windows 笔记本上跑 skill-up 评测一个 Docker 镜像，`platform.Host()` 是 Windows，但 `DockerRuntime.Shell()` 永远返回 `Linux/POSIX`——因为命令是在 Linux 容器里执行的。调用方做参数引用时**必须**用 `rt.Shell().Quoter()`，否则会把 Windows 风格引用喂给 Linux bash。

   ```
                                                                  │
                                                                  ▼
                                                            defer close(done)
   ```

   ```
   os/exec 框架:  ctx.Done() 触发 ──► 调 cmd.Cancel
   ```

## 5. 检查点自测

### Q1：skill-up 怎么做并发？为什么不用线程池？

**答**：用 goroutine + 带缓冲 channel 当信号量。`EvaluateAll`（[`evaluator.go:180-237`](../../internal/evaluator/evaluator.go)）先把 cases × {with_skill, without_skill} 展开成任务列表，每个任务起一个 goroutine；并发上限用 `sem := make(chan struct{}, concurrency)` 控制——主 goroutine 在 `sem <- struct{}{}` 阻塞，子 goroutine 退出时 `<-sem` 归还令牌；用 `sync.WaitGroup` 等全部完成。结果用预分配数组 `results[idx]` 写，每个 goroutine 写自己的槽位，无锁。

为什么不用「线程池」？Go 的 goroutine 是用户态轻量级线程（2KB 起始栈），开几十万个也不心疼；而 Java 式线程池主要为了复用昂贵的内核线程。skill-up 的任务数通常几十到几百，直接每任务一 goroutine + 信号量限流，代码更直观。**信号量本质上是「虚拟的线程池」，只是调度交给 Go runtime。**

### Q2：case 超时为什么是「总预算」（agent + judge 共用一个 deadline）？

**答**：`withCaseTimeout`（[`evaluator.go:873-883`](../../internal/evaluator/evaluator.go)）返回的 `attemptCtx` 同时绑定了 `Agent.Run` 和后续的 `Judge.Evaluate`。`handleExecutionResult`（[`evaluator.go:907-911`](../../internal/evaluator/evaluator.go)）的注释明说：超时直接判 ERROR，**不试图用截断输出跑 judge**。

原因：judge 基于残缺 transcript 打分会误导（给本应失败的 case 打 PASS）。总预算模式下「超时 = 整次失败 = 触发 timeout 重试」，语义干净。而且错误信息会标注来源（`annotateCaseTimeoutError`，[`evaluator.go:859-867`](../../internal/evaluator/evaluator.go)）：`context deadline exceeded (case timeout 60s via case.constraints.timeout_seconds)`，用户直接知道去改哪个 YAML 字段。

### Q3：孙子进程怎么不逃逸？为什么 `exec.CommandContext` 不够用？

**答**：`exec.CommandContext` 在 ctx 取消时只 kill 直接子进程，但 skill-up 的进程树是 `shell → agent CLI → git/sleep/ping`，孙子进程会变孤儿继续跑，污染 workspace、占端口、卡 CI。

解决方案在 [`none_exec_unix.go`](../../internal/runtime/none_exec_unix.go)（POSIX）：`cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` 让子进程成为新进程组 leader，然后 `cmd.Cancel` 里用 `syscall.Kill(-pid, SIGTERM)` 给**整组**发信号（负 PID = 组信号）。SIGTERM 后启一个 goroutine 等 1s（`noneExecKillGrace`），没退就升级 `SIGKILL`。goroutine 用 `done` channel 知道进程何时被回收，**避免给被操作系统复用的 PID 误发信号**（TOCTOU 安全）。

Windows 没有 `setpgid`/`kill(-pid)` 等价物（[`none_exec_other.go`](../../internal/runtime/none_exec_other.go) 是空实现），靠 `cmd.WaitDelay = 2s` 在子进程退出后强制关闭 stdio 管道，让读管道的 goroutine 解除阻塞。两个平台用 build tag `//go:build unix` / `!unix` 切换。

### Q4：三种 Runtime 怎么选？依据是什么？

**答**：看**隔离强度需求**和**环境可用性**：

- `none`：本机直接跑，**无隔离**，靠临时目录 + 进程组兜底。用于本地开发、CI、被测 Skill 已知安全的信任场景。`RequiresProcessSandbox()` 返回 `true`，要求 Agent 自己再套一层进程沙箱。
- `docker`：本地容器，**OS 级隔离**（`--network none` 断网）。用于不信任被测 Skill、但又没有远端沙箱服务的场景。需要本机装了 docker CLI。
- `opensandbox`：Alibaba 远端沙箱服务，**最强隔离 + 集中管控**。用于生产评测、多租户、需要审计的场景。需要 `OPENSANDBOX_BASE_URL` / `OPENSANDBOX_API_KEY`。

选择是**配置驱动**的：eval.yaml 里 `environment.type: none|docker|opensandbox`，工厂 `NewRuntime`（[`runtime.go:216-238`](../../internal/runtime/runtime.go)）switch 分发。三后端实现同一个 13 方法接口，evaluator 调用方完全不感知差异。

### Q5：为什么 Docker 后端用 shell out CLI 而不用官方 Docker SDK？

**答**：四个理由：

1. **依赖轻**：CLI 几乎所有开发机都装了，SDK 要拉一堆 transitive deps，构建变慢。
2. **可手动复现**：用户能直接 `docker exec -it <id> sh` 进去排障，看到的和代码跑的一致——这对调试失败的 case 非常关键。
3. **测试简单**：mock 一个函数字段（`run dockerCommandRunner`）就行，不用 mock SDK 的复杂 client。
4. **行为可预测**：CLI stderr 的前缀（`Error response from daemon:`）稳定，便于 `dockerExecLayerError` 基于前缀分类「基础设施故障 vs 业务失败」。

代价是每次调用 fork 一个 docker 进程，比 SDK 直接走 HTTP 慢一点，但 skill-up 不是高频调用（几秒一次 `docker exec`），完全可接受。这是**「依赖少 + 行为直观」优先于「类型安全 + 性能」**的工程权衡——类似 Java 里选 ProcessBuilder 调命令行工具 vs 选重客户端库。

## 7. 小结 + 下一课预告

### 小结

skill-up 的「跑得稳」是一套**层层包装**的设计，一根 `context.Context` 把四件事串成一条线：

1. **并发层**（`EvaluateAll`）：信号量（channel 当令牌桶）+ WaitGroup + 预分配结果数组，fan-out/fan-in 无锁。并发度三层配置（CLI > YAML > 默认 1）+ 硬上限 256 保护下游。
2. **重试层**（`executeCase`）：`maxAttempts = MaxRetries + 1`，只有 `StatusError` 才考虑重试（FAIL 是确定性失败不重试），白名单制 `retry_on`，指数退避 `2^n` 秒，可取消 sleep。
3. **超时层**（`withCaseTimeout`）：case 级总预算覆盖 agent + judge，超时错误标注是哪个 YAML 旋钮导致的（可定位性）。
4. **进程清理层**（`NoneRuntime.Exec`）：进程组 `Setpgid` + 负 PID 杀整棵树，SIGTERM→1s→SIGKILL 升级，`done` channel 防 PID 复用 TOCTOU，Windows 靠 `WaitDelay` 兜底，build tag 分平台。

底下还垫了一层 **Runtime 抽象**：13 方法接口屏蔽本机/容器/远端三后端，`platform.Shell` 三元组屏蔽 Linux/macOS/Windows 三平台，命令永远经 bash（除非用户连 Git Bash 都没装）。整层的设计目标是——**让 evaluator 写一次代码，跨任意后端、任意宿主 OS 都能跑同一个不可信 Skill**。

> **面试一句话**：这套设计是 Go 在系统编程上比 Java 显式且可控的地方——`context.Context` 一根线从用户 Ctrl+C 传到底层 `kill -9`，比 Java 的 `Thread.interrupt()`（几乎没人响应）+ 注解模型（`@Retryable`/`@Timeout` 隐式生效）更显式、更可控、更可调试。

### 下一课预告：L07 · 输出报告与安全

本课讲的是「怎么跑得稳」，下一课往上走一层，讲「**跑完了怎么交付 + 怎么不泄密**」：

- **输出报告**：EvalResult 怎么聚合成 case 报告 / iteration 报告 / 整体报告；JSON / Markdown / HTML 三种格式怎么生成；A/B baseline 对比（with_skill vs without_skill）怎么算。
- **安全**：评测不可信 Skill 时的威胁模型——命令注入、路径穿越（Zip Slip）、敏感信息泄漏（API key 进日志）、网络出网管控（`network_policy: deny_all` / `allow_declared` 白名单）；以及 `maskCommand`、`safeLocalTarget`、`overlayEnvList` 字面透传等防御点。

这两块合起来，就是 skill-up 作为「可交付、可审计、可信」评测平台的最后一块拼图。
