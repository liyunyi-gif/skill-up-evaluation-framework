# L03 · 核心流程：skill-up run 端到端时序 + 单 case 7 步生命周期 + 三条数据契约

> 面向：Java 后端/全栈工程师，用 skill-up 项目给简历加分、准备面试。
> 本课是整个系列的「脊梁」——把 `skill-up run` 敲下去之后到底发生了什么，一次讲透。

---

## 1. 学习目标

学完本课，你应该能够：

1. **画出端到端时序图**：从 `skill-up run` 命令进入，到产出 `result.json` / `benchmark.json` 的 4 个阶段（配置 → 凭据 → 并发执行 → 汇总退出码），能用一张图讲清楚每层的职责。
2. **讲清单 case 的 7 步生命周期**：建沙箱 → 装环境/Skill/MCP/夹具 → Agent.Run → 抓产物 → expect 短路 → Judge 打分 → 合并出分，每一步能指出对应的源码位置（file:line）和「为什么这么做」。
3. **说出三条贯穿全项目的数据契约**（`Agent` 接口 / `judge.Input` / `transcript.Transcript`），并解释它们为什么是架构的「钥匙」。
4. **解释并发模型**：skill-up 用「带缓冲 channel 当信号量 + `sync.WaitGroup`」控制并发，能用 Java 的 `Semaphore` / `CountDownLatch` / `ThreadPoolExecutor` 做类比。
5. **掌握 3 个面试加分点**：A/B 对照（`without_skill` 跳过装 Skill）、expect 短路省钱、`judge.Input` 解耦执行层与评测层。

### 3.1 分层架构图（自顶向下）

> **Java 类比**：这套分层 ≈ Spring 项目的 `controller → service → (strategy/adapter) → infrastructure`。
> - `internal/cli/` ≈ Controller（接 HTTP/CLI 请求，做参数解析）
> - `internal/runner/` + `internal/evaluator/` ≈ Service（业务编排核心）
> - `agent` / `judge` ≈ SPI + Strategy（多实现、多策略）
> - `pkg/` ≈ 对外稳定的 API/DTO 模块（`pkg/transcript/` 是 semver 稳定的公开契约）

**关键约束**（来自 `AGENTS.md`）：
- `internal/` 是私有的，模块外不可 import。
- `pkg/skillup/`、`pkg/transcript/` 是 **semver 稳定的公开 API**，破坏性改动要升大版本。
- CLI 胶水放 `internal/cli/`，业务逻辑放对应的 `internal/<domain>/`。

### 3.2 `skill-up run` 的 4 阶段（顶层时序）

入口是 [`internal/cli/run.go`](../../internal/cli/run.go) 的 `runEval` 函数（`run.go:123-166`）。它把整个流程划成 4 个 Phase，每个 Phase 一个辅助函数：

```go
// internal/cli/run.go:123
func runEval(cmd *cobra.Command, args []string) error {
    // --- Phase 1: Configuration ---
    cases, evalCfg, loader, err := loadAndPrepareConfig(ctx, cmd, args, span)  // run.go:139

    if maybeRunDryRun(cmd, cases, evalCfg) { return nil }                      // run.go:144

    // --- Phase 2: Credentials & agent ---
    ag, resolver, runnerParams, err := loadCredentialsAndAgent(cmd, evalCfg)   // run.go:149

    // --- Phase 3: Run evaluation ---
    results, err := executeEvaluation(cmd, cases, evalCfg, loader, resolver, runnerParams, ag) // run.go:155

    // --- Phase 4: Summary ---
    passed, failed, errored := countResultStatus(results)                      // run.go:162
    ui.Summary(passed, failed, errored)
    return exitStatusError(cmd.ErrOrStderr(), results)                         // run.go:165
}
```

| Phase | 函数 | 干什么 | Java 类比 |
|---|---|---|---|
| 1 配置 | `loadAndPrepareConfig` (`run.go:170`) | 读 `eval.yaml` + `cases/*.yaml` → include/exclude glob 过滤 → **只校验选中的 case** → 应用 CLI override（`--engine`/`--model`/`--runtime`/`--parallelism`） | Spring 启动读 `application.yml` + 校验 `@ConfigurationProperties` |
| 2 凭据+Agent | `loadCredentialsAndAgent` (`run.go:238`) | 加载凭据（`.env` + `~/.skill-up/credentials.yaml`）→ 按 engine 名字**工厂创建 Agent 适配器**（`agent.DetectAgentWithInitParams`，`run.go:268`） | `@Bean` 工厂方法 + 多源 `@Value` 解析 |
| 3 执行评测 | `executeEvaluation` (`run.go:278`) | 构造 Runner → 调 `run.Evaluate()` 跑所有 case | Service 调用业务核心 |
| 4 汇总退出码 | `exitStatusError` (`run.go:347`) | 统计 pass/fail/error → 决定退出码（`0`=全过 / `1`=失败或错误，**CI 友好**） | Spring Boot 的 `ExitCodeGenerator` |

#### Phase 1 的一个重要细节：只校验选中的 case

[`loadAndPrepareConfig`](../../internal/cli/run.go) 在 `run.go:189-195` 有一段关键注释：

> *Validate only the selected cases (after filters) ... an invalid case that was filtered out must not block the run.*

也就是说，如果你用 `--include-case-name "basic-*"` 过滤了一堆 case，**被过滤掉的 case 即使配置错了也不会阻塞本次运行**（要全量校验用 `skill-up validate`）。这避免了「一个坏 case 卡住整个 CI」。

#### Phase 4 退出码语义

`exitStatusError`（`run.go:347-372`）有个细节值得注意：**它跳过 `without_skill` 的结果**（`run.go:352-354`）。

```go
for _, result := range results {
    if result.Configuration == "without_skill" {
        continue  // baseline 不影响退出码
    }
    // ... 统计 hasFail / hasError
}
```

为什么？因为 `without_skill` 是「对照组」，本来预期就可能跑挂（agent 没装 Skill 表现差）。如果让对照组的失败把 CI 染红，那就违背了「A/B 实验」的初衷——退出码只反映「装了 Skill 的正式跑」的健康度。

> **Java 类比**：相当于 JUnit 的 `@Test` 主测试决定 CI 红绿，而 `@Disabled` / baseline 对照不计入。

### 3.3 Runner 层：iteration 工作区（`runner.go:95-180`）

[`Runner.Evaluate`](../../internal/runner/runner.go)（`runner.go:95`）是 Phase 3 的真正实现。核心是 **iteration 循环**：

```go
// runner.go:140
for i := range runCount {
    runNumber := startIteration + i
    r.setupWorkspace(ctx, workspaceDir, skillName, runNumber)                  // runner.go:142
    ev := newEvaluator(evaluator.EvalOptions{ ... })                           // runner.go:153
    results, err := ev.EvaluateAll(ctx, cases)                                  // runner.go:168
    r.WriteResults(ctx, results, reportName, skillDir, runNumber, opts.Formats) // runner.go:175
}
```

3 个设计点：

1. **iteration 工作区**：`--iteration N` 跑 N 轮，每轮写到 `<skill>-workspace/iteration-<N>/`；`--iteration 0`（默认）自动续号（`runner.go:127-133`，调 `nextIterationNumber` 扫目录找 `max(N)+1`）。
2. **workspace 放在 skill 目录旁边**（`runner.go:121-126`）：`<skill>-workspace/` 和 `<skill>/` 是兄弟目录，**不污染 skill 仓库**，对齐 Anthropic eval 布局。
3. **`newEvaluator` 是个包级变量**（`runner.go:36` 的 `var newEvaluator = evaluator.NewEvaluator`）——这是 Go 里常见的「可替换工厂」技巧，测试时可以替换成 mock evaluator，不真跑 agent。

`WriteResults`（`runner.go:191`）负责把结果分组成 `with_skill` / `without_skill`（`groupResultsByCase`，`runner.go:283`），写 `result.json`（事实源）+ `benchmark.json`（含 A/B 基线对比，`runner.go:210-216`）+ 可选 `html`/`junit`。

> **Java 类比**：iteration 循环 ≈ Spring Batch 的 `Step` 循环；workspace 隔离 ≈ 每个 batch run 用独立的工作目录。

### 3.4 Evaluator 并发模型：信号量 + WaitGroup

[`EvaluateAll`](../../internal/evaluator/evaluator.go)（`evaluator.go:180`）是并发调度的核心。先把 case 列表展开成 task 列表，再用「信号量 + WaitGroup」并发跑：

```go
// evaluator.go:195-206 —— 展开 task 列表（baseline 翻倍）
configCount := 1
if e.withBaseline {
    configCount = 2
}
tasks := make([]task, 0, len(cases)*configCount)
for _, c := range cases {
    tasks = append(tasks, task{caseCfg: c, configName: "with_skill"})          // :202
    if e.withBaseline {
        tasks = append(tasks, task{caseCfg: c, configName: "without_skill"})   // :204
    }
}

// evaluator.go:208-234 —— 并发执行
results := make([]EvalResult, len(tasks))
sem := make(chan struct{}, e.concurrency)   // 信号量：带缓冲 channel
var wg sync.WaitGroup
for i, t := range tasks {
    wg.Add(1)
    sem <- struct{}{}                        // 获取「令牌」（满则阻塞）
    go func(idx int, tk task) {
        defer wg.Done()
        defer func() { <-sem }()             // 归还「令牌」
        results[idx] = e.executeCase(ctx, tk.caseCfg, tk.configName, nil, nil)
    }(i, t, caseNum)
}
wg.Wait()                                    // 等所有 goroutine 完成
```

#### 为什么用 channel 当信号量？

Go 没有 Java 那种现成的 `Semaphore`，社区惯用「带缓冲 channel」模拟：

- `sem := make(chan struct{}, N)` 创建一个容量 N 的 channel。
- `sem <- struct{}{}`：往里塞一个空结构体，**如果 channel 满了就阻塞**——相当于「获取许可」。
- `<-sem`：从里面取一个出来——相当于「释放许可」，腾出位置给下一个 goroutine。

这跟 Java 的 `java.util.concurrent.Semaphore` 语义完全一致：

```java
// Java 等价写法
Semaphore sem = new Semaphore(N);
sem.acquire();      // ≈ sem <- struct{}{}
try { ... } finally { sem.release(); }   // ≈ defer func(){ <-sem }()
```

`sync.WaitGroup` 则等价于 Java 的 `CountDownLatch`：

```go
wg.Add(1)    // ≈ latch = new CountDownLatch(n); （循环里累加）
defer wg.Done()  // ≈ latch.countDown()
wg.Wait()    // ≈ latch.await()
```

合起来，这套并发模型 ≈ Java 的 `ThreadPoolExecutor`（限并发）+ `Future.allOf` / `CountDownLatch`（等全部完成）。受 `cases.parallelism` 控制（CLI 可覆盖，上限 256，见 `run.go:35` 的 `maxParallelismOverride`）。

#### A/B baseline：`with_skill` vs `without_skill`

注意上面 `tasks` 展开逻辑（`evaluator.go:202-205`）：当 `benchmark.enabled=true` 时，**同一个 case 会生成两个 task**——一个 `with_skill`，一个 `without_skill`。它们用**完全相同**的 prompt / 夹具 / setup_steps / MCP，**唯一的变量就是有没有装 Skill**。这就是典型的 **A/B 对照实验**（详见 3.6 步骤②）。

### 3.5 单 case 7 步生命周期（核心中的核心）

这是整个项目最该讲清楚的一条链。入口是 [`executeCaseOnce`](../../internal/evaluator/evaluator.go)（`evaluator.go:333`）。作者在函数签名上留了一句注释：

> *orchestrates the full case lifecycle (runtime prep → agent run → judge → finalize); splitting further would obscure the linear flow*

——**故意不拆这个函数**，因为拆了反而看不见「线性」这条主线。下面把它拆成 7 步逐段讲。

#### 外壳：`executeCase`（重试包装，`evaluator.go:289-331`）

在讲 7 步之前，先看它的外层 retry 包装。`executeCaseOnce` 自己不重试，重试是父函数 `executeCase` 做的：

```go
// evaluator.go:289
func (e *defaultEvaluator) executeCase(...) EvalResult {
    maxAttempts := max(e.evalCfg.Cases.RetryPolicy.MaxRetries+1, 1)  // :290
    for attempt := 1; attempt <= maxAttempts; attempt++ {            // :293
        attemptCtx, cancel, timeoutSource, timeoutSec := withCaseTimeout(...) // :294
        result = e.executeCaseOnce(attemptCtx, ...)                  // :295
        // 关键：先标注超时，再 cancel()
        if errors.Is(attemptCtx.Err(), context.DeadlineExceeded) && ctx.Err() == nil {
            annotateCaseTimeoutError(&result, timeoutSource, timeoutSec)        // :306
        }
        cancel()                                                     // :308
        retryReason, ok := retryReasonForResult(result)              // :310
        if !ok || !retryAllowed(...) { return result }               // :311
        sleepWithContext(ctx, retryBackoffDelay(attempt))            // :325
    }
}
```

3 个值得记的点：

1. **总尝试次数 = `max_retries + 1`**（`evaluator.go:290`）：YAML 里 `max_retries: 2` 表示「最多重试 2 次」，加上首次 = 3 次。`max(..., 1)` 兜底至少跑一次。
   > **Java 类比**：Spring Retry 的 `@Retryable(maxAttempts = 3)` 里 `maxAttempts` 是**包含首次**的总次数。

2. **超时是 case 级总预算**（`withCaseTimeout`，`evaluator.go:873-883`）：优先用 `case.constraints.timeout_seconds`，其次用 `cases.defaults.timeout_seconds`，都没配就不限时。**这个 ctx 一路传给 agent 和 judge，是两者的总预算**。

3. **只重试 ERROR，不重试 FAIL**（`retryReasonForResult`，`evaluator.go:897-905`）：FAIL 是「评测结论」（再跑大概率还是 FAIL），ERROR 才是「执行故障」（超时/panic/网络抖动），值得重试。
   > **Java 类比**：Spring Retry 的 `@Retryable(include = {TimeoutException.class})` 用异常类型当白名单；Go 没检查异常，这里用字符串分类。

#### 现在进入 `executeCaseOnce` 的 7 步（`evaluator.go:333-481`）

```
executeCaseOnce
  ① prepareRuntimeForCase      建隔离沙箱（none/docker/opensandbox）
  ② setupCaseEnvironment       装环境/Skill/MCP/夹具（A/B 关键在这）
  ③ Agent.Run / executeMultiTurn  发题收卷（Skill 真的执行）
  ④ collectGlobArtifacts + workspace diff   抓产物
  ⑤ runExpectPreCheck          expect 预检查（零成本短路）
  ⑥ runJudgePhase              Judge 打分（rule_based/script/agent_judge）
  ⑦ 合并 expect + judge 断言    → EvalResult
```

---

##### 步骤 ① 建沙箱（`evaluator.go:375-388`）

```go
// evaluator.go:375
var rt runtime.Runtime
if overrideRT != nil {
    rt = overrideRT
} else {
    rt, err = e.prepareRuntimeForCase(ctx, caseCfg, configName, runAgent)  // :380
    if err != nil { /* ERROR 直接返回 */ }
    defer func() { _ = rt.Close() }()   // :387  用完即关
}
```

`prepareRuntimeForCase`（`evaluator.go:968-990`）做三件事：调 `runtime.NewRuntime(rtCfg)` 工厂建沙箱 → `rt.Create(ctx)` 真正起容器/建目录 → `setupCaseEnvironment`（步骤②）。失败时**先 `rt.Close()` 再返回错误**，避免资源泄漏。

- `runtime.Runtime` 是个接口（`internal/runtime/runtime.go`），实现有 `none`（本机直接跑）/ `docker` / `opensandbox`（远程容器）三种。`NewRuntime` 是工厂方法。
- **每个 case 一个独立 workspace**，用完 `defer rt.Close()` 关掉——case 之间互不污染。

> **Java 类比**：相当于 `try (Sandbox sandbox = SandboxFactory.create(config)) { ... }`（try-with-resources），`rt.Close()` 就是 `AutoCloseable.close()`。

---

##### 步骤 ② 装环境 + 装 Agent + 装 MCP + 装 Skill + 上传夹具（`evaluator.go:992-1031`）

这是 A/B 测试机制的核心。[`setupCaseEnvironment`](../../internal/evaluator/evaluator.go)（`evaluator.go:992`）按顺序装 5 样东西：

```go
// (a) 跑 setup_steps（自定义 shell 初始化命令）—— evaluator.go:993
for i, step := range e.evalCfg.Environment.SetupSteps {
    result, err := rt.Exec(ctx, step.Run, runtime.ExecOptions{})
    // 失败要带 i+1（步骤序号）和原始命令，方便定位
}

// (b) 装 Agent CLI（claude-code / codex CLI 等）—— evaluator.go:1003
if e.evalCfg.Environment.Type != "none" {
    ag.Install(ctx, rt)
}

// (c) 注册 MCP servers（外部工具协议）—— evaluator.go:1009
ag.InstallMCP(ctx, rt, mcpCfg)

// (d) 【A/B 关键】with_skill 才装 Skill，without_skill 跳过！—— evaluator.go:1013
if configName != "without_skill" && e.loader != nil {
    for _, skillRef := range e.evalCfg.Skills {
        ag.InstallSkill(ctx, rt, skillCfg)
    }
}

// (e) 上传夹具（repo / context.files / git init / apply_diff）—— evaluator.go:1023
e.fixtures.UploadAll(ctx, rt, caseCfg, e.skillDir, fixtureBaseDir)
```

**步骤 (d) 是整个 skill-up 框架的灵魂**（`evaluator.go:1013`）：

```go
if configName != "without_skill" && e.loader != nil {
```

这一行 `if` 实现 A/B 对照：
- `with_skill` 任务：装上 `SKILL.md`，看 agent「有技能」时表现。
- `without_skill` 任务：**完全跳过 `InstallSkill`**，看 agent「裸跑」时表现。

两次执行的其他条件（prompt、夹具、setup_steps、MCP）完全一致，**唯一变量就是有没有 Skill**。技能净收益 = `with_skill - without_skill`。这是评测一个 Skill 是否真有用的**唯一可靠方法**——直接看 `with_skill` 绝分会受「agent 本身能力」干扰（强 agent 不带 Skill 也行）。

> **Java 类比**：JMH 基准测试的 `@Benchmark` + 对照组，或 A/B test 平台「实验组 / 对照组」分桶。本质都是控制变量法。

步骤 (e) 的夹具上传顺序也很讲究（`fixtures.go:275-282`）：先拷仓库 → `git init` → 切到目标分支 → 写 inline 文件 → 最后 `apply_diff` 打 patch。注释原话：

> *Order matters: the git repo must exist and be on the right branch before inline context.files are written ... apply_diff runs last, on top of both.*

否则 `git switch` 会把刚写的 inline 文件覆盖掉。

##### 步骤 ③ 发题收卷：`Agent.Run` / `executeMultiTurn`（`evaluator.go:392-478`）

- **`Agent.Run`** 是 `Agent` 接口的核心方法（`agent.go:143`）：`Run(ctx, rt, opts, messages) (*SessionResult, error)`。每个 agent 适配器（claude-code、codex、qoder_cli、custom）各自实现，本质是**起子进程跑 agent CLI**。
- **多轮分支**（`evaluator.go:398-409`）：case 定义了 `input.turns` 且 agent 实现了 `SessionResumer` 接口（`agent.go:72-74`）才走多轮。`SessionResumer.RunTurn` 在 turn 之间传递 `sessionID` 续接会话。
- **`SessionResumer` 是可选接口**：编译期检查（`agent.go:151-155`）确保只有 `ClaudeCodeAgent` / `QoderCLIAgent` / `CodexAgent` 实现了它。

> **Java 类比**：`Agent` 是 SPI（Service Provider Interface），多个实现；`SessionResumer` 是可选扩展接口（类似 Java SPI 的 `Optional` 能力探测）。`runAgent.(agent.SessionResumer)` 的类型断言 ≈ Java 的 `if (agent instanceof SessionResumer sr)`。

##### 步骤 ④ 抓产物：`collectGlobArtifacts` + workspace diff（`evaluator.go:456`）

case 跑完后，要把沙箱里的产物（生成的文件、改动的代码）拉出来给 judge 看。两条机制：

**④-a workspace diff**（`prepareWorkspaceArtifacts`，`evaluator.go:1134`）：只有 `judge.type == agent_judge` 时才需要（`judgeNeedsWorkspaceDiff`）。
- **Run 之前**调 `prepareWorkspaceDiffState`：在沙箱里 `git init` + `git add --all` + `git commit` 打 baseline。
- **Run 之后**调 `collectWorkspaceDiff`：`git diff --cached <baseline>` 算出 agent 改了哪些代码，并排除 agent 自己生成的产物文件。

**④-b glob artifacts**（[`collectGlobArtifacts`](../../internal/evaluator/artifacts_collect.go)，`evaluator.go:456` 调用）：按 `collect_artifacts` glob 匹配下载产物文件。这步有 3 个极考究的设计：

```go
// artifacts_collect.go:73
dctx := context.WithoutCancel(ctx)                            // 脱离父 cancel！
dctx, cancel := context.WithTimeout(dctx, collectArtifactsTimeout) // 60s 自己挂新超时
defer cancel()
```

1. **位置极其关键**（`evaluator.go:456`）：它在 `handleExecutionResult` 的 early-return **之前**，也在 `defer rt.Close()` **之前**。意思是：**即使 agent 失败、超时，也要把沙箱里的产物拉出来**——失败 case 的现场最有价值，丢了就没法调试。
2. **`context.WithoutCancel`**（`artifacts_collect.go:73`，Go 1.21 新 API）：case context 可能已经因为超时被 cancel，但产物收集必须跑完。所以**脱离父 cancel**，自己挂个 60s 新超时（`collectArtifactsTimeout = 60 * time.Second`，`artifacts_collect.go:25`）。
3. **任何错误只 `Warn` 不 fail**（`artifacts_collect.go:60-61` 注释：`never fails the case`）：产物收集永远不能让 case 从 PASS 变 ERROR，最多丢失调试信息。

> **Java 类比**：相当于 `try-catch-finally` 的 finally 块里强制 flush 日志和 dump 线程；或者 Chaos Engineering 工具失败时自动 collect core dump。`context.WithoutCancel` ≈ Java 里「父线程中断了，但 finally 块里的 IO 必须跑完」。

##### 步骤 ⑤ expect 预检查：零成本短路（`evaluator.go:540-565`）

到这步 agent 已跑完、产物已收集。接下来是 **expect 预检**——一个零成本、确定性的硬门控。逻辑在 [`evaluateCaseSession`](../../internal/evaluator/evaluator.go)（`evaluator.go:492`）里调用：

```go
// evaluator.go:518
if failed := e.runExpectPreCheck(ctx, caseCfg, configName, judgeInput, turnsTotal, result); failed {
    return *result   // expect 失败 → 直接 FAIL，跳过 judge！
}
// expect 通过（或没配 expect）才往下走 judge
finalResult := e.runJudgePhase(...)  // :527
```

`runExpectPreCheck` 本体（`evaluator.go:540-565`）调用 `judge.CheckExpect`（`judge/expect.go`）——全是**纯字符串/文件检查**：

| 规则 | 含义 |
|---|---|
| `must_contain` | `final_message` 必须包含某些子串 |
| `must_not_contain` | 必须不包含 |
| `exit_code` | 进程退出码必须等于指定值 |
| `files_exist` / `files_not_exist` | workspace 里某些文件必须存在/不存在 |
| `golden_file` | 输出和 golden 文件比对 |
| `file_contains` | 指定文件里必须包含某些串 |

**关键设计：expect 失败立刻 FAIL，跳过 judge**。为什么？

- judge（尤其 `agent_judge`）要**再调一次 LLM**，又贵又慢（一次评测动辄几美元、几十秒）。
- expect 是免费的纯函数（字符串 `Contains` + `os.Stat`），跑一次几毫秒。
- 如果 expect 已经判定 FAIL（比如 agent 输出根本没提到那个 bug），再花 judge 的钱纯属浪费。

`judge/expect.go` 开头的注释把这层意图说得很清楚：

> *Expect is a zero-cost, deterministic gate that runs BEFORE any judge. If any expect check fails, the case is immediately marked FAIL and the (potentially expensive) judge execution is skipped entirely.*

> **Java 类比**：Servlet Filter 链里的短路——认证不通过直接 401，不进 Controller；或者 Spring Security Filter 的 `AccessDeniedHandler`。expect 是 Filter，judge 是 Controller。

**⑥-a `judge.Input` —— 执行层与评测层的统一边界**

[`judge.Input`](../../internal/judge/judge.go)（`judge.go:55-98`）是**所有 judge 实现共用的入参**。三种 judge 拿到的是同一个 struct：

- `rule_based`：纯字段判断（`MustContain` 等），等价于 expect 的进阶版。
- `script`：起一个外部脚本，把 Input 序列化成环境变量 / JSON 喂进去（`evaluator.go:633-641` 把 transcript 落临时文件，路径通过 `EVAL_TRANSCRIPT_PATH` 环境变量传给脚本）。

> **Java 类比**：策略模式（Strategy）。`Judge` 是 Strategy 接口（`judge.go:31-33` 的 `Evaluate(ctx, in Input) (*Result, error)`），`Input` 是 Context 对象，`rule_based` / `script` / `agent_judge` 是三个 `ConcreteStrategy`。`NewJudge`（`judge/factory.go:22`）是工厂方法，按 `type` 字段路由。

**⑥-b `runJudgePhaseWithSpan` 的兜底**

```go

**「没配 judge 默认 PASS」**（`evaluator.go:620-626`）是条宽松兜底：YAML 里完全没写 `judge:` 块，case 跑完就算 PASS。意味着 skill-up 允许「只看 agent 能不能跑起来，不评分」。

**⑥-c 裁判中立：judge 前移除 run skill**

`newJudgeForCase`（`evaluator.go:670`）建裁判时做了一件**非常重要的事**：

    return nil, err
}
```

`removeDefaultRunSkillsBeforeJudge`（`evaluator.go:719-754`）：
- 只在 `configName == "with_skill"` 且 `judge.type == agent_judge` 时触发（`evaluator.go:726`）。
- 把 run 阶段装的 default skill（被测的 `SKILL.md`）**从 skill 目录里 `rm -rf` 掉**。
- 目的：**让裁判 agent 看不到被测 skill**，避免裁判「作弊」——否则裁判可能直接用被测 skill 给出高分，评测就失去意义了。

**裁判中立原则**：裁判不能既当运动员又当裁判。这是评测公平性的底线。

##### 步骤 ⑦ 合并 expect + judge 断言（`evaluator.go:527-535`）

最后一步在 `evaluateCaseSession` 末尾：

### 3.6 三条贯穿全项目的「数据契约」（架构钥匙）

这是理解架构的钥匙——三条接口/类型把异构的子系统粘起来。**面试时能把这三条讲清楚，基本就证明你真懂这个项目了。**

#### 契约 1：`Agent` 接口（执行层抽象）

[`internal/agent/agent.go`](../../internal/agent/agent.go) `:133-148`，7 个方法 + 可选 `SessionResumer`：

```go
type Agent interface {
    Name() string
    Install(ctx, rt) error                              // 装 Agent CLI（幂等）
    InstallMCP(ctx, rt, mcpCfg) error                   // 注册 MCP server
    InstallSkill(ctx, rt, skillCfg) error               // 装 Skill（A/B 关键）
    Run(ctx, rt, opts, messages) (*SessionResult, error) // 跑 agent（核心）
    Check(ctx, rt) error                                // 检查 agent 可用性
    CheckCredentials(ctx) error                         // 检查凭据
}
// 可选接口（agent.go:72-74）：
type SessionResumer interface {
    RunTurn(ctx, rt, opts, message, sessionID) (*SessionResult, error)  // 多轮续接
}
```

**为什么是钥匙**：任何 Agent 引擎（claude_code / codex / qodercli / custom）只要实现这 7 个方法，evaluator 就能驱动它。这是典型的 **SPI（Service Provider Interface）**——把「调用方」和「实现方」彻底分开。

> **Java 类比**：`Agent` ≈ SLF4J 的 `Logger` 接口、JDBC 的 `Driver` 接口、Spring 的 `BeanPostProcessor`。多实现 + 工厂发现（`agent.DetectAgentWithInitParams` ≈ `DriverManager.getConnection`）。`SessionResumer` ≈ Java SPI 的可选能力扩展。

#### 契约 2：`judge.Input`（执行层 → 评测层的统一数据边界）

[`internal/judge/judge.go`](../../internal/judge/judge.go) `:55-98`——一个 struct 装下评测所需一切：

```go
type Input struct {
    CaseID         string
    Transcript     transcript.Transcript   // 完整会话
    FinalMessage   string                  // 最后一条 assistant 消息
    ExitCode       int                     // 进程退出码
    WorkspacePath  string                  // 沙箱根目录
    WorkspaceDiff  string                  // agent 改了哪些代码
    GeneratedFiles []string                // agent 生成的文件
    SessionResult  *agent.SessionResult    // 完整原始结果
    TurnResults    []InputTurnResult       // 多轮每轮结果
    TurnsExecuted  int
    TurnsTotal     int
    // ...
}
```

**为什么是钥匙**：三种 judge 策略（`rule_based` / `script` / `agent_judge`）消费**同一个 Input**，执行层和评测层彻底解耦：
- 换 judge 策略（比如加个 `vector_similarity`）不用动执行层。
- 加新 agent（比如 `cursor` 适配器）不用动 judge。
- 构造一个 `judge.Input` 就能单测任何 judge，不需要真跑 agent——**可测试性极好**。

> **Java 类比**：策略模式的 Context 对象；或者 Spring MVC 的 `ModelAndView`——controller 把数据塞进 ModelAndView，view 解析器（不同 judge）拿同一份数据自己渲染。也像 DDD 里的「应用层 DTO 契约」。

#### 契约 3：`pkg/transcript.Transcript`（跨引擎统一会话模型）

[`pkg/transcript/transcript.go`](../../pkg/transcript/transcript.go) `:43`——`type Transcript []Message`，其中 `Message`（`:18-25`）：

```go
type Message struct {
    Role       Role            `json:"role"`        // user/assistant/tool_call/tool_result/error
    Content    string          `json:"content"`
    Turn       int             `json:"turn"`        // 第几轮
    ToolCall   *ToolCallInfo   `json:"tool_call"`   // 工具调用
    ToolResult *ToolResultInfo `json:"tool_result"` // 工具返回
    Timestamp  *time.Time      `json:"timestamp"`
}
```

**为什么是钥匙**：不同 Agent 引擎的原生输出格式天差地别——Claude 是 JSONL、Codex 是 NDJSON 流、Qwen 是 Gemini schema。**各自的解析器都把这些归一成 `Transcript` 这一个形状**。这是**跨引擎可比**的基础：judge 和 report 只认 `Transcript`，不用关心底下是哪个引擎。这也是 semver 稳定的公开 API（破坏性改动要升大版本）。

> **Java 类比**：DDD 里的「共享内核（Shared Kernel）」或「统一领域模型」。相当于把 Kafka / RabbitMQ / RocketMQ 的不同消息格式统一映射成一套内部事件模型。

### 3.7 三个面试加分点（背下来，能讲就是亮点）

#### 加分点 1：A/B 对照——`without_skill` 跳过装 Skill

- **机制**：`EvaluateAll` 对每个 case 生成两个 task（`evaluator.go:202-205`），`setupCaseEnvironment` 里 `if configName != "without_skill"` 决定**装不装 skill**（`evaluator.go:1013`）。其他条件完全一致。
- **意义**：技能净收益 = `with_skill - without_skill`。直接看绝对分会受「agent 本身能力」干扰（GPT-5 不带 skill 也强）。A/B 对照是评测 Skill 价值的**唯一可靠方法**。
- **一句话**：「我用 `if configName != "without_skill"` 一行代码实现了 A/B 实验的分桶，控制变量法测 Skill 的净收益。」

#### 加分点 2：expect 短路省钱

- **机制**：`runExpectPreCheck`（`evaluator.go:540-565`）在 judge 之前跑免费的字符串 / 文件检查，任一失败立刻 FAIL 并跳过 judge。
- **意义**：judge（尤其 `agent_judge`）要调 LLM，又贵又慢（一次几美元）。expect 把「明显错得离谱」的 case 先挡掉，省 90% 不必要的 judge 调用。
- **一句话**：「我设计了零成本的 expect 预检查短路，把昂贵的 LLM 裁判调用挡在后面，单次评测成本降一个数量级。」

#### 加分点 3：`judge.Input` 解耦执行层与评测层

- **机制**：`judge.Input`（`judge.go:55-98`）是所有 judge 实现共用的入参 struct，由 `evaluateCaseSession`（`evaluator.go:503-516`）一次性组装。
- **意义**：执行层和评测层只通过这一个 struct 通信。加新 agent 不动 judge；加新 judge 不动 agent。可单测、可观测。
- **一句话**：「我用一个 DTO struct 当执行层和评测层的统一边界，等于策略模式里的 Context 对象，让两边独立演进。」

## 5. 检查点自测（5 题带答案）

先自己想答案，再对照下面的参考答案。

<details>
<summary>👉 点开看答案</summary>

**Q1：case 级 timeout 是什么的总预算？为什么？**

答：是 **agent + judge 的总预算**，不是单个 agent 或单个 judge 的。`executeCase`（`evaluator.go:294`）通过 `withCaseTimeout` 包一层 `context.WithTimeout`，这个 ctx 一路传给 `executeCaseOnce` → `Agent.Run` → `j.Evaluate`。如果 agent 跑超时，ctx 已 `DeadlineExceeded`，judge 调用时第一个 ctx 检查就会失败。设计目的：避免「agent 卡 5 分钟超时，judge 又调 LLM 卡 5 分钟」总耗时失控。注释在 `evaluator.go:907-911` 写得很清楚：`the case timeout is treated as a single budget for agent + judge`。

**Q2：expect 失败为什么直接短路？**

答：因为 judge（尤其 `agent_judge`）要**再调一次 LLM**，又贵又慢（一次几美元、几十秒）。expect 是免费的纯函数（字符串 `Contains` + `os.Stat`），跑一次几毫秒。如果 expect 已经判定 FAIL（比如 agent 输出根本没提到那个 bug），再花 judge 的钱就是浪费。所以 `runExpectPreCheck`（`evaluator.go:518-520`）失败直接 return，跳过 judge。

**Q3：`judge.Input` 为何能解耦执行层和评测层？**

答：因为它是**所有 judge 实现共用的唯一入参**（`judge.go:55-98`），由 evaluator 一次性组装（`evaluator.go:503-516`）。三种 judge（rule_based / script / agent_judge）拿的都是同一个 struct。换 judge 不动执行层，加新 agent 不动 judge；还能构造 Input 单测任何 judge，不用真跑 agent。对应设计模式是策略模式：`Judge` 是 Strategy 接口（`judge.go:31-33`），`Input` 是 Context 对象。

**Q4：`without_skill` 是怎么实现 A/B 的？**

答：`EvaluateAll` 对每个 case 生成两个 task——`with_skill` 和 `without_skill`（`evaluator.go:202-205`）。在 `setupCaseEnvironment` 里有一行 `if configName != "without_skill"`（`evaluator.go:1013`）决定**装不装 Skill**。两次执行的其他条件（prompt、setup_steps、MCP、夹具）完全一致，唯一变量就是有没有 Skill。净收益 = `with_skill - without_skill`。这是控制变量法在评测里的标准做法。

**Q5：并发用什么原语？**

答：**带缓冲 channel 当信号量 + `sync.WaitGroup`**（`evaluator.go:209, 212`）。`sem := make(chan struct{}, concurrency)` 创建容量为 N 的 channel，`sem <- struct{}{}` 获取许可（满则阻塞），`<-sem` 释放许可；`wg.Add/Done/Wait` 等所有 goroutine 完成。等价于 Java 的 `Semaphore`（限并发）+ `CountDownLatch`（等全部完成）+ `ThreadPoolExecutor`。受 `cases.parallelism` 控制（CLI 可覆盖，上限 256）。

</details>
