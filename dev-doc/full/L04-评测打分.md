## 1. 学习目标

学完本课，你应该能做到：

1. **讲清三种 Judge 策略的原理与差异**：rule_based（纯 Go 声明式断言）、script（外部脚本退出码即结论）、agent_judge（LLM 当裁判 + 阈值制），并能在面试里讲清「为什么是这三个，不是两个或四个」。
2. **为不同评测场景选对 Judge**：关键字/工具调用 → rule_based；复杂逻辑/跑测试套件 → script；开放式语义（代码质量、bug 定位）→ agent_judge；并理解「确定性 + 成本」的分层思路。
3. **讲清 LLM 裁判怎么抗噪**：`extractJSON` 四层兜底解析、防作弊校验（结果数=criteria 数 + evidence 非空）、阈值制 vs 全过制的取舍。
4. **解释 expect 预检查的「短路省钱」**：为什么在昂贵的 Judge 之前先跑零成本确定性检查，以及它和 Judge 的断言是怎么合并进报告的。
5. **看懂 context_materializer 的 prompt 体积控制**：profile × mode 双维度 + `include` 超 64KB 自动降级为 `file_ref`，背后是「token 成本工程」思维。

## 3. 讲解

### 3.1 Judge 在流水线里的位置：expect 预检查 → Judge

评测不是一步到位的。完整的「执行 → 评分」链路是这样的（参见 `internal/evaluator/evaluator.go`）：

```
[组装 judge.Input（执行层产物 → 评测层契约）]
        ↓
[expect 预检查]   ← 零成本、确定性，跑在 Judge 之前
   ├─ 失败 → 直接 FAIL，跳过 Judge（省钱！）
   └─ 通过 → 继续
        ↓
[Judge.Evaluate（本课主角）]
   ├─ rule_based  ─→ 纯 Go 内存计算
   ├─ script      ─→ 子进程，退出码即结论
   └─ agent_judge ─→ 起一个独立 agent session 当裁判
        ↓
[judge.Result → grading.json]
```

> **Java 类比**：Judge 这一层相当于 JUnit 的 `Assert` + 自定义 `TestRule`，但比 JUnit 多了「用 LLM 当裁判」和「跑外部脚本」两种扩展形态。`expect` 相当于 JUnit 的 `assumeXXX()`——不满足前提条件就跳过后续昂贵判定。

关键设计：expect 通过后，它的断言会**前置拼到 Judge 断言**里一起计入通过率（保证报告完整，能看到「expect 检查了什么」）。

### 3.2 数据边界：`judge.Input` / `Result`（执行层↔评测层统一契约）

#### 为什么说它是「统一契约」

所有策略共享同一个抽象（[`judge.go:30-33`](../../internal/judge/judge.go#L30)）：

```go
// judge.go:30-33
type Judge interface {
    Evaluate(ctx context.Context, in Input) (*Result, error)
}
```

**一个方法、一个输入、一个输出。** 三种实现（`RuleBasedJudge` / `ScriptJudge` / `AgentJudge`）面对的是同一个数据契约。这意味着：

- 执行层（evaluator）只要按 `Input` 字段把产物组装好，不关心下游是哪种 Judge。
- 任何一种 Judge 都不能「额外要字段」。某条信息没在 `Input` 里，要么扩展 `Input`，要么不用它。
- 新增一种 Judge（比如未来的 embedding 相似度 judge）只需实现接口 + 工厂加一个 `case` 分支，执行层零改动。

> **Java 类比**：这是教科书级 **策略模式（Strategy）**。相当于 Spring 里 `interface JudgeStrategy { Result evaluate(Input in) }`，三个 `@Component` 实现共享同一个上下文对象。Go 没有构造器重载，靠「函数 + switch」实现工厂；Spring 靠 `Map<String, JudgeStrategy>` 按 key 注入——殊途同归。

#### `Input`：执行层往评测层送的「全量证据包」

[`judge.go:55-98`](../../internal/judge/judge.go#L55)，核心字段：

| 字段 | 类型 | 含义 | 谁会用 |
|---|---|---|---|
| `Transcript` | `transcript.Transcript` | Agent 完整交互记录（含 tool_call） | rule_based 的 `tool_called`、agent_judge 的评审材料 |
| `FinalMessage` | `string` | 最后一轮 assistant 文本 | expect 的 `must_contain`、rule_based 的 `output_contains`、script 通过 env 传 |
| `ExitCode` | `int` | engine 进程退出码 | expect `exit_code`、rule_based `exit_code`、script env `EVAL_EXIT_CODE` |
| `WorkspacePath` | `string` | case 工作区绝对路径 | `files_exist`、script 的 `cwd` |
| `SkillDir` | `string` | SKILL.md 所在目录 | `golden_file`、`attachment` 相对路径基准 |
| `WorkspaceDiff` | `string` | 跑完后的 git diff | agent_judge 的评审材料 |
| `GeneratedFiles` | `[]string` | Agent 新建的文件路径列表 | agent_judge 的评审材料 |
| `TurnResults` | `[]InputTurnResult` | 每轮结果（多轮用） | rule_based 的轮级断言 |

注意 `InputTurnResult`（[`judge.go:36-49`](../../internal/judge/judge.go#L36)）里同时携带了 `Response`、`Transcript`、`Status`、`Reason` —— **多轮场景下，rule_based 可以针对「第 3 轮响应里是否包含 X」做断言**，这是单轮评测系统做不到的。

> **设计巧思**：`Transcript` 是包级类型 `pkg/transcript.Transcript`，跨「执行层 ↔ 评测层」复用，避免重复定义。Java 里相当于把 DTO 抽到公共 API 模块，两边共用——这就是**值对象（Value Object）**边界的意义：固化协议，换 Judge 不动执行层，换报告格式不动评测层。

#### `Result`：直接对应 `grading.json` 的「评分报告」

[`judge.go:112-142`](../../internal/judge/judge.go#L112)，四类 `Status`（[`judge.go:19-28`](../../internal/judge/judge.go#L19)）语义要分清：

- `PASS`：所有断言通过。
- `FAIL`：有断言没过（**业务失败**——被评测对象做错了）。
- `SKIP`：主动跳过（如多轮 post_condition 触发 `skip_remaining`）。
- `ERROR`：执行异常（agent 调用炸了、脚本起不来——**评测系统自己出了问题**）。

> **区分 FAIL vs ERROR 是关键设计**：混在一起会让「系统不稳定」伪装成「agent 能力差」，污染数据。Java 里相当于 `AssertionError`（业务断言失败）vs `RuntimeException`（系统异常）。

三个构造器是 Result 的「工厂方法」，避免每个策略自己手算 Summary。最值得讲的是 `NewResult`（[`judge.go:213-252`](../../internal/judge/judge.go#L213)）的两个边界语义：

```go
if total > 0 {
    passRate = float64(passed) / float64(total)
} else {
    passRate = 1.0 // no assertions = vacuous pass（空真）
}
```

1. **零断言 = 空真（vacuous pass）**：`passRate=1.0`。「没要求」等于「无义务」，默认 PASS。这是 evaluator 里「没配置 Judge 就默认 PASS」的基础。
2. **`nil` 切片转 `[]AssertionResult{}`**：保证 `grading.json` 里永远是数组而不是 `null`，前端展示更稳定。

#### `SessionResultError`：错误链里抢救 Session

[`judge.go:154-182`](../../internal/judge/judge.go#L154)。`agent_judge` 跑到一半 LLM 调用失败时，**虽然返回了 error，但 session 已经产生了 transcript / artifacts**。直接把 error 往上抛，这些产物就丢了——调试时无从下手。

`SessionResultError` 把 session 用 error 链携带上去，调用方用 `errors.As` 提取（[`judge.go:176-182`](../../internal/judge/judge.go#L176)）：

```go
func SessionResultFromError(err error) *agent.SessionResult {
    var withSession *SessionResultError
    if errors.As(err, &withSession) {
        return withSession.Session
    }
    return nil
}
```

> **Java 类比**：相当于把附加上下文塞进 `Throwable.addSuppressed()` 或自定义异常的 `attachment` 字段。Go 没有异常链语法糖，靠 `Unwrap()`（[`judge.go:168-173`](../../internal/judge/judge.go#L168)）配合 `errors.As` 实现。

### 3.3 工厂 `NewJudge` + `MergeJudgeConfig`（策略模式 + case 级覆盖）

#### `NewJudge`：type 字段 switch 派发

[`factory.go:22-50`](../../internal/judge/factory.go#L22)，标准的简单工厂：

```go
func NewJudge(cfg config.JudgeConfig, ag agent.Agent, rt runtime.Runtime) (Judge, error) {
    switch cfg.Type {
    case "rule_based":
        return NewRuleBasedJudge(cfg), nil
    case "script":
        if cfg.ScriptPath == "" {
            return nil, errors.New("script judge requires script_path")
        }
        return &ScriptJudge{ScriptPath: cfg.ScriptPath, TimeoutSeconds: derefInt(cfg.TimeoutSeconds), Runtime: rt}, nil
    case "agent_judge":
        if ag == nil {
            return nil, errors.New("agent_judge requires an Agent")
        }
        return NewAgentJudgeWithContextAndSkills(ag, rt, cfg.Model, cfg.Criteria, cfg.PassThreshold, cfg.Context, derefInt(cfg.TimeoutSeconds), SkillInfosFromRefs(cfg.Skills)), nil
    case "":
        return nil, nil  // 没配置 → 调用方默认 PASS
    default:
        return nil, fmt.Errorf("unknown judge type: %q", cfg.Type)
    }
}
```

要点：
1. **依赖注入**：`ag`（agent）和 `rt`（runtime）由外部传入，不在这里 new。便于测试 mock。
2. **必备参数校验**：`script` 要 `ScriptPath`、`agent_judge` 要 `Agent`，缺失即报错。
3. **空 type 返回 `nil, nil`**：约定「无 Judge = 默认 PASS」，调用方在 evaluator 里处理。
4. **`derefInt`**（[`factory.go:53-58`](../../internal/judge/factory.go#L53)）：把 `*int` 拍平，nil → 0。`TimeoutSeconds` 在 schema 里是 `*int`（「未配置」语义需要它），到具体 Judge 里则是 `int`（0 表示用默认）。

> **Java 类比**：相当于 `JudgeFactory.create(cfg, agent, runtime)`。Spring 里更常见的写法是 `Map<String, JudgeStrategy>` 按 key 注入——`applicationContext.getBean(cfg.getType(), JudgeStrategy.class)`。Go 没有 Spring 容器，靠 switch 显式派发，编译期就能发现拼写错误，反而更稳。

#### `MergeJudgeConfig`：case 级覆盖 eval 级

[`factory.go:68-87`](../../internal/judge/factory.go#L68)，这段语义要仔细品：

```go
func MergeJudgeConfig(global, caseLevel config.JudgeConfig) config.JudgeConfig {
    // If case has a type, use it entirely
    if caseLevel.Type != "" {
        merged := caseLevel
        if merged.Model == "" { merged.Model = global.Model }
        if merged.PassThreshold == nil { merged.PassThreshold = global.PassThreshold }
        if merged.TimeoutSeconds == nil { merged.TimeoutSeconds = global.TimeoutSeconds }
        merged.Context = MergeJudgeContextConfig(global.Context, caseLevel.Context)
        return merged
    }
    return global  // No case-level judge, use global
}
```

**核心设计选择——「case 配了 Type 就是全量覆盖」**：

- 一旦 case 写了 `judge.type: script`，它就**不会**继承全局的 `rule_based` 规则，连 `Criteria` / `Success` / `Failure` / `ScriptPath` 也都只看 case 自己的。
- **只有三个字段会回退**：`Model`、`PassThreshold`、`TimeoutSeconds`（它们是「跨策略通用的旋钮」）。

为什么这么设计？看注释（[`factory.go:62-67`](../../internal/judge/factory.go#L62)）：避免「全局 rule_based + case script」这种混搭把字段串到一起出怪 bug。**全量覆盖语义最清晰。**

> **Java 类比**：Spring 的 `@PropertySource` 多级覆盖是「逐字段 merge」；这里是「分类型整体替换 + 少量共享默认值」，更接近「模板方法里 hook 方法被子类整个重写」的语义。

#### `MergeJudgeContextConfig`：context 字段的逐项 merge

[`factory.go:91-123`](../../internal/judge/factory.go#L91)：和上面相反，context 是**逐字段 merge** 而非整体替换。原因：context 调节的是「评审材料怎么送」（profile / mode / limits / attachments），这些是「细节旋钮」，逐项 merge 更灵活。

细节里的工程功夫：
- `Limits`（[`factory.go:125-145`](../../internal/judge/factory.go#L125)）：只在 case 显式设了 `> 0` 的值时才覆盖，避免 case 的「未配置」清掉 global 的合理值。
- `Attachments` **整体替换**（[`factory.go:119-121`](../../internal/judge/factory.go#L119)）：因为 attachments 是个 list，逐项 merge 语义不清。**注意克隆**：`append([]config.JudgeContextAttachment(nil), caseLevel.Attachments...)` —— 避免共享底层数组导致后续误改。
- `cloneJudgeContextConfig`（[`factory.go:147-158`](../../internal/judge/factory.go#L147)）做深拷贝：顶层 struct 解引用、`Limits` 指针单独拷、`Attachments` 切片单独 append 一份。

> **Java 类比**：相当于 `Cloneable` + 手动深拷贝 List。不可变配置是 Java 后端的基本功（避免下游误改上游对象），这里完全一致。

### 3.4 expect 预检查：零成本短路省钱

#### 设计目标

[`expect.go:1-8`](../../internal/judge/expect.go#L1) 的注释把意图说得明明白白：

> Expect is a zero-cost, deterministic gate that runs BEFORE any judge. If any expect check fails, the case is immediately marked FAIL and the (potentially expensive) judge execution is skipped entirely.

**「省钱」是关键**：agent_judge 要再起一个 LLM 调用，可能花几毛到几块钱；script 要起子进程；哪怕 rule_based 也要算多轮。**如果用例连「必须包含 hello」都没满足，那还浪费钱跑 Judge 干嘛？**

#### 7 类 check 实现

`CheckExpect`（[`expect.go:48-90`](../../internal/judge/expect.go#L48)）按固定顺序收集 failures：

| 规则 | 实现位置 | 说明 |
|---|---|---|
| `must_contain` | [`expect.go:128-139`](../../internal/judge/expect.go#L128) | 全包含检查，`strings.Contains` |
| `must_not_contain` | [`expect.go:142-153`](../../internal/judge/expect.go#L142) | 反向 |
| `exit_code` | [`expect.go:157-168`](../../internal/judge/expect.go#L157) | `*int` 为 nil 视为「未配置」 |
| `files_exist` | [`expect.go:171-190`](../../internal/judge/expect.go#L171) | 调 `fileExistsInWorkspace`（`safePath` + `os.Stat`） |
| `files_not_exist` | [`expect.go:193-212`](../../internal/judge/expect.go#L193) | 反向 |
| `golden_file` | [`expect.go:216-249`](../../internal/judge/expect.go#L216) | 全文比对 + 首差异偏移提示 |
| `file_contains` | [`expect.go:252-279`](../../internal/judge/expect.go#L252) | 读文件检查 `strings.Contains` |

特点：
1. **纯函数**（除了文件相关的 `os.Stat` / `os.ReadFile`，无副作用）。
2. **不短路**：和 rule_based 不同，expect 会跑完所有规则，收集全部 failures——因为它很便宜，且报告完整更好。

#### `safePath`：路径穿越防御

[`judge.go:302-313`](../../internal/judge/judge.go#L302)：

```go
func safePath(workspace, rel string) (string, error) {
    abs := filepath.Join(workspace, rel)
    clean := filepath.Clean(abs)
    workspaceClean := filepath.Clean(workspace)
    if clean == workspaceClean { return clean, nil }
    if !strings.HasPrefix(clean, workspaceClean+string(filepath.Separator)) {
        return "", fmt.Errorf("path %q escapes workspace", rel)
    }
    return clean, nil
}
```

凡是 case 配置里写的相对路径（`files_exist: ["../../etc/passwd"]`、`golden_file: "../../../secret"`）都会被这层挡住。**评测框架尤其需要这种防御**：用例文件来自用户/三方仓库，必须假设它们不可信。

注意它是**前缀比对 + `filepath.Separator`**，而不是简单的 `strings.HasPrefix(clean, workspaceClean)`——否则 `/tmp/work` 会被 `/tmp/work-evil` 匹配上。这是个经典坑，skill-up 写得很规范。

#### `ToAssertionResults` + `diffHint`

- `ToAssertionResults`（[`expect.go:96-121`](../../internal/judge/expect.go#L96)）：把规则结果转成 `AssertionResult`。**每类规则一条**（多条失败合并 evidence），不会因为 `must_contain` 配了 5 个 keyword 就出 5 行。注意 text 前缀 `expect.`——报告里一眼能区分「这条是 expect 产生的」vs「这条是 Judge 产生的」。
- `diffHint`（[`expect.go:286-300`](../../internal/judge/expect.go#L286)）：golden_file 不一致时给个差异提示。朴素双指针扫到第一个不同字符，截前后各 20 字符。**为什么不直接上 `diff` 库？** 因为 expect 是「零成本」层，引入外部依赖不划算，一段提示足够人定位问题——「够用就好」的工程判断。

### 3.5 策略一：`rule_based`（纯 Go 声明式断言）

#### 核心算法：先 failure 短路，再 success 全检

这是 rule_based 最值得讲的设计（[`rule_based.go:33-67`](../../internal/judge/rule_based.go#L33)）：

```go
func (j *RuleBasedJudge) Evaluate(_ context.Context, in Input) (*Result, error) {
    var allAssertions []AssertionResult

    // 1. Check failure rules first — any match is immediate FAIL.
    for _, rule := range j.Failure {
        ar := evaluateAssertion(rule, in)
        if ar.Passed {
            // A failure rule "passed" means the bad pattern WAS found → FAIL.
            allAssertions = append(allAssertions, AssertionResult{
                Text:     "failure: " + ar.Text,
                Passed:   false,
                Evidence: "failure rule matched: " + ar.Evidence,
            })
        }
    }

    // Short-circuit: if any failure rule matched, return immediately.
    if len(allAssertions) > 0 {
        return NewResult(allAssertions, in.TurnsExecuted, in.TurnsTotal), nil
    }

    // 2. Check success rules — all must pass.
    for _, rule := range j.Success {
        ar := evaluateAssertion(rule, in)
        allAssertions = append(allAssertions, ar)
    }
    ...
}
```

#### failure 语义反转（重点！）

注意上面那段代码：**failure 规则「命中」时，`ar.Passed` 是 `true`**（因为底层 `evalOutputContains` 不知道自己被用于 failure 还是 success），但 `RuleBasedJudge` 在外层**把它的 Passed 反转成 `false`**！

代码里的注释（[`rule_based.go:40-44`](../../internal/judge/rule_based.go#L40)）说得很直白：

> A failure rule "passed" means the bad pattern WAS found → FAIL.

举例：
- 配置 `failure: [{output_contains: {any: ["panic", "fatal error"]}}]`
- 实际输出里出现了 "panic"
- `evalOutputContains` 返回 `Passed: true`（「any 命中了」）
- `RuleBasedJudge` 反转 → `Passed: false`，记录 `text: "failure: output_contains.any: ..."`

**这个反转让 `evaluateAssertion` 保持「语义纯粹」（passed = 条件成立），由调用方决定「条件成立是好事还是坏事」。** 这是策略模式里「复用底层算子」的经典做法——`evalOutputContains` 写一份，success 和 failure 都能用，避免代码重复。

> **Java 类比**：相当于一个 `Predicate<Input>` 返回 `true/false`，外层用 `predicate.negate()` 或在 `if` 里反转语义。短路逻辑相当于 `if (anyMatch(failures)) return FAIL; else if (allMatch(successes)) return PASS; else return FAIL;` 的 Stream 短路。

#### 多轮定位 `lookupTurn`

[`rule_based.go:315-338`](../../internal/judge/rule_based.go#L315)：

```go
func lookupTurn(turnNum int, turns []InputTurnResult, ruleName string) (*InputTurnResult, *AssertionResult) {
    if turnNum >= 1 {
        for i := range turns {
            if turns[i].TurnNumber == turnNum {
                tr := &turns[i]
                if tr.Status != "completed" {
                    ar := AssertionResult{
                        Text:     fmt.Sprintf("%s[turn=%d]", ruleName, turnNum),
                        Passed:   false,
                        Evidence: fmt.Sprintf("turn %d has status %q (reason: %s); assertion requires completed turn", turnNum, tr.Status, tr.Reason),
                    }
                    return nil, &ar
                }
                return tr, nil
            }
        }
    }
    ...
}
```

设计要点：
- **第二个返回值是 `*AssertionResult`**（指针）：nil 表示「找到了且状态 OK」，非 nil 表示「已经为你准备好失败断言了，直接用」。
- **状态校验**：即使轮次存在，如果 `Status != "completed"`（如 `skipped` / `failed`），也直接生成失败断言。这避免了「用第 3 轮的失败响应当成功响应检查」的逻辑漏洞。
- **1-based index**：配置里写 `turn: 0` 或负数直接失败。

> **Java 类比**：这种「返回 `Optional<Failure>`」的写法相当于 `Either<AssertionResult, InputTurnResult>`，Go 没有 Either，用双返回值模拟。

#### `argsMatch`：tool 参数部分匹配

[`rule_based.go:294-306`](../../internal/judge/rule_based.go#L294)：

```go
func argsMatch(expected, actual map[string]any) bool {
    for k, ev := range expected {
        av, ok := actual[k]
        if !ok { return false }
        // Compare as strings for flexibility (YAML values may deserialize differently).
        if fmt.Sprintf("%v", ev) != fmt.Sprintf("%v", av) {
            return false
        }
    }
    return true
}
```

两点设计：
1. **只校验 expected 里出现的字段**：actual 多出来的字段忽略（部分匹配）——「我只关心这个参数对不对」。
2. **字符串化比较**：YAML 里 `1.0` 可能解析成 `float64(1)`，JSON 里可能是 `int(1)`，直接 `==` 不等。`fmt.Sprintf("%v", ...)` 把两者都拍成 `"1"` / `"1"`，绕开类型不一致问题。

> **代价**：`fmt.Sprintf` 比 `==` 慢，但断言匹配不在热路径，可接受。Java 里类似 `Objects.toString(a).equals(Objects.toString(b))`。

#### 9 种断言类型

按 `evaluateAssertion`（[`rule_based.go:75-102`](../../internal/judge/rule_based.go#L75)）的 switch 顺序：`output_contains`(all/any/not)、`exit_code`、`tool_called`、`files_exist`、`files_not_exist`、`turn_response_contains`、`turn_response_not_contains`、`tool_called_in_turn`、`tool_not_called_in_turn`。

其中 `evalOutputContains`（[`rule_based.go:109-175`](../../internal/judge/rule_based.go#L109)）特别值得注意：一条规则可以**混合** `all` / `any` / `not` 三种语义：

```yaml
output_contains:
  all: ["null pointer", "fix"]
  any: ["fixed", "patched"]
  not: ["TODO"]
```

### 3.6 策略二：`script`（退出码即结论、env 传参、跨平台派发）

#### 极简且语言中立的契约

[`script.go:17-23`](../../internal/judge/script.go#L17) 的注释写明：

> Script contract:
> - Working directory: case workspace root
> - Environment variables: EVAL_TRANSCRIPT_PATH, EVAL_FINAL_MESSAGE, EVAL_EXIT_CODE
> - Exit code 0 → PASS, non-0 → FAIL
> - stdout → evaluation evidence, stderr → debug info

这个契约最大的好处是**语言中立**：用户可以用 Python / Bash / PowerShell / Node 写评分脚本，只要遵守「退出码 = 结论」即可。这相当于把「评分逻辑」外置成「用户插件」。

#### 统一 none runtime

[`script.go:62-74`](../../internal/judge/script.go#L62)：

```go
func (j *ScriptJudge) runtime(ctx context.Context) (evalruntime.Runtime, func(), error) {
    if j.Runtime != nil {
        return j.Runtime, func() {}, nil
    }
    rt, err := evalruntime.NewRuntime(evalruntime.Config{Type: "none", Delete: true})
    ...
}
```

**`Runtime` 字段是关键**：脚本不是直接在 host 上跑，而是被**上传到 runtime**（可能是 docker、可能是远程、可能是本地 none）里执行。这和「被执行的 Agent 跑在同一个 runtime 里」保持一致——评分脚本看到的工作区、文件系统、shell 跟被评测对象一模一样，**避免环境差异带来的判定偏差**。无注入 runtime 时，现场建临时 `none` runtime，让本地/容器/远程走同一代码路径。

#### Evaluate 流程 + buildResult

[`script.go:76-146`](../../internal/judge/script.go#L76) 步骤：`planScript` 决定怎么跑 → 创建临时目录 → 上传脚本 → 上传 transcript → 构造命令+cwd+env → `rt.Exec` → 处理结果（超时/非零退出/零退出）。

env 传参（[`script.go:115-123`](../../internal/judge/script.go#L115)）：

```go
result, err := rt.Exec(ctx, command, evalruntime.ExecOptions{
    Cwd:        cwd,
    TimeoutSec: int(timeout.Seconds()),
    Env: map[string]string{
        "EVAL_TRANSCRIPT_PATH": transcriptEnv,
        "EVAL_FINAL_MESSAGE":   in.FinalMessage,
        "EVAL_EXIT_CODE":       strconv.Itoa(in.ExitCode),
    },
})
```

`buildResult`（[`script.go:149-161`](../../internal/judge/script.go#L149)）：**一个脚本 = 一条断言**。stderr 会被附在 evidence 末尾（`[stderr: ...]`），方便排查但不会盖过 stdout 的结论。

#### 跨平台派发 `planScript`（精华所在）

[`interpreter.go:47-65`](../../internal/judge/interpreter.go#L47)：POSIX 极简，Windows 复杂。

```go
func planScript(scriptPath string, shell platform.Shell) (scriptPlan, error) {
    ...
    if shell.GOOS != platform.GOOSWindows {
        return scriptPlan{
            uploadName: "script",
            command: func(remoteScript string) string {
                q := shellquote.QuotePOSIX(remoteScript)
                return "chmod 700 " + q + " && " + q   // 交给 shebang
            },
            cleanupCommand: func(dir string) string { return "rm -rf " + shellquote.QuotePOSIX(dir) },
            envPath: identityEnvPath,
        }, nil
    }
    return planWindowsScript(scriptPath, shell)
}
```

- **POSIX**：上传脚本原样不改名，`chmod 700` + 执行。**所有解释器选择交给内核的 shebang 机制**（`#!/usr/bin/env python3` 内核直接派发）。Go 代码不掺和。
- **Windows**：内核不认 shebang，所以要在 Go 代码里根据**扩展名 + shebang**决定怎么调解释器（`.ps1`→pwsh/powershell、`.cmd/.bat`→`cmd /c`、`.sh`→必须 bash）。

`scriptPlan` 是个「行为包」（[`interpreter.go:19-35`](../../internal/judge/interpreter.go#L19)），用三个闭包打包：`command(remoteScript)` / `cleanupCommand(dir)` / `envPath(p)`。**`envPath` 是个细节亮点**：Windows `.sh` 走 Git Bash 时，路径要 `filepath.ToSlash` 转成正斜杠，否则 `cat "$EVAL_TRANSCRIPT_PATH"` 会失败（[`script.go:106-114`](../../internal/judge/script.go#L106)）。

> **shebang 解析器**（`parseShebang` + `parseEnvShebang` + `tokenizeShebangSplitString`）：实现了 `/usr/bin/env` + GNU `env -S` split-string（含一个处理引号/转义的小型 tokenizer 状态机）。为什么不用正则？注释说得很清楚：嵌套大括号 + 转义引号让正则脆弱，状态机才健壮。**这种细节就是工程经验和「业余评测框架」的分水岭。**
>
> **Java 类比**：这种「用闭包打包一组相关行为」等价于返回一个实现 `ScriptPlan` 接口的匿名类。Go 没有匿名类，但函数是一等公民，写起来更轻。

### 3.7 策略三：`agent_judge`（LLM 当裁判）

整个流程：**物化上下文 → 构造 prompt → Agent.Run → 解析 JSON → 校验防作弊 → 阈值判定**。

#### 主流程 Evaluate

[`agent_judge.go:116-176`](../../internal/judge/agent_judge.go#L116)，分步讲：

**Step 1**：空 criteria 直接返回 PASS（[`agent_judge.go:117-119`](../../internal/judge/agent_judge.go#L117)）——无标准 = 无义务 = vacuous pass。

**Step 2**：context 超时（[`agent_judge.go:121-126`](../../internal/judge/agent_judge.go#L121)）。**注意 `parentCtx := ctx`** —— 在套 timeout 之前**先快照父 ctx**。后面要靠它判断「是 judge 自己超时，还是 case 上游超时」。

**Step 3**：物化评审材料（[`agent_judge.go:128-131`](../../internal/judge/agent_judge.go#L128)）。

**Step 4**：构建 prompt（[`agent_judge.go:134-135`](../../internal/judge/agent_judge.go#L134)）。

**Step 5**：调 Agent.Run（[`agent_judge.go:143-157`](../../internal/judge/agent_judge.go#L143)）：

```go
sessionResult, err := j.Agent.Run(ctx, j.Runtime, agent.ExecOptions{ArtifactDir: in.ArtifactDir}, messages)
parentExpired := parentCtx.Err() != nil   // 立刻快照
if err != nil {
    annotated := err
    if !parentExpired { annotated = j.annotateTimeoutError(ctx, err) }
    if !canRecoverAgentJudgeResult(err, sessionResult) {
        return nil, &SessionResultError{Err: ..., Session: sessionResult}
    }
    // 能恢复就继续
}
```

**`parentExpired` 立刻快照**是个并发竞争窗口问题（[`agent_judge.go:137-142`](../../internal/judge/agent_judge.go#L137) 注释）：如果 case timeout 和 judge timeout 设置得很接近，Run 返回后再延迟读 `parentCtx.Err()`，父 timer 可能恰好触发，误判成「父超时」。

**Step 6**：解析 JSON + 校验（[`agent_judge.go:159-173`](../../internal/judge/agent_judge.go#L159)）：四层兜底解析 + 防作弊校验。

**Step 7**：阈值判定 `buildResult`。

#### 阈值制 vs 全过制

[`agent_judge.go:178-197`](../../internal/judge/agent_judge.go#L178)：

```go
result := NewResult(assertions, in.TurnsExecuted, in.TurnsTotal)
result.JudgeSession = sessionResult
result.JudgeContext = buildContextMetadata(sessionResult, materialized, prompt)
if len(assertions) > 0 && result.Summary.PassRate >= j.PassThreshold {
    result.Status = StatusPass
} else if len(assertions) > 0 {
    result.Status = StatusFail
}
```

关键区别：
- `NewResult` 默认「有 failed 就 FAIL」（**全过制**，rule_based 用这个）。
- `AgentJudge` **覆盖 Status**：只要 `PassRate >= PassThreshold`（默认 0.7，[`agent_judge.go:19`](../../internal/judge/agent_judge.go#L19)），即使有 failed 也算 PASS。
- 这是个**软判定**模型，承认 LLM 裁判的噪声。

> **Java 类比**：相当于把 JUnit 的 `assertTrue` 改成了「10 个 assert 过 7 个就算测试通过」。这种软判定在模糊评测（代码风格、文档质量）场景是合理的。

#### `extractJSON` 四层兜底（重点！）

[`agent_judge.go:229-259`](../../internal/judge/agent_judge.go#L229)，LLM 输出从来不可靠，所以这是个层层降级的解析链：

```go
func extractJSON(output string, v any) error {
    candidates := []string{output}                        // Layer 1: 直接当 JSON 解
    if fenced := extractFencedJSON(output); fenced != "" { // Layer 2: 抽 ```json ... ``` 围栏
        candidates = append(candidates, fenced)
    }
    for _, candidate := range candidates {                 // 先试标准 Unmarshal
        if err := json.Unmarshal([]byte(candidate), v); err == nil { return nil }
    }
    for _, candidate := range findJSONObjectCandidates(output) {  // Layer 3: 扫所有「像 JSON 对象」的子串
        if err := json.Unmarshal([]byte(candidate), v); err == nil { return nil }
    }
    repaired := repairJSONQuotes(output)                   // Layer 4: 引号修复后再扫一遍
    if repaired != output {
        for _, candidate := range findJSONObjectCandidates(repaired) {
            if err := json.Unmarshal([]byte(candidate), v); err == nil { return nil }
        }
    }
    return fmt.Errorf("no valid JSON found in agent output (length=%d)", len(output))
}
```

- **Layer 1 + 2**：直接解 + 围栏抽取（[`agent_judge.go:318-331`](../../internal/judge/agent_judge.go#L318)，LLM 经常用 ```` ```json ```` 包装）。
- **Layer 3**：`findJSONObjectCandidates` + `findJSONObjectEnd`（[`agent_judge.go:364-401`](../../internal/judge/agent_judge.go#L364)）是个**字符级状态机**，四个状态维度（双引号字符串、单引号字符串、转义、嵌套深度）。注释解释了**为什么不用正则**：嵌套大括号 + 转义引号让 regexp 脆弱。
- **Layer 4**：`repairJSONQuotes`（[`agent_judge.go:270-316`](../../internal/judge/agent_judge.go#L270)）处理 LLM 最常犯的错——在 JSON 字符串里写未转义的双引号。启发式：在字符串里遇到 `"` 时，看后面（跳空白后）是不是 JSON 结构字符（`:` / `,` / `}` / `]`）：是→闭合字符串；否→加 `\` 转义。

> **核心思想**：LLM 输出永远会有 5%-20% 的格式问题，要么惩罚用户重跑（贵），要么代码兜底（便宜）。skill-up 选了后者，且把兜底逻辑写得**完全无副作用**（纯字符串处理 + 最终用 `encoding/json` 校验合法性）。
>
> **Java 类比**：相当于写了一个容错的 `JsonParser`，类似 Jackson 的 `DeserializationFeature.FAIL_ON_TRAILING_TOKENS=false` 但更激进。

#### 防作弊校验

[`agent_judge.go:213-225`](../../internal/judge/agent_judge.go#L213)：

```go
func validateAgentJudgeResponse(criteria []string, results []CriterionResult) error {
    // A short response inflates pass_rate because NewResult uses the returned
    // count as the denominator (e.g. 1-of-1 returned = 100% even if 3 were sent).
    if len(results) != len(criteria) {
        return fmt.Errorf("agent_judge: expected %d criterion results, got %d", len(criteria), len(results))
    }
    for i, cr := range results {
        if strings.TrimSpace(cr.Evidence) == "" {
            return fmt.Errorf("agent_judge: criterion %d %q has empty evidence", i+1, cr.Criterion)
        }
    }
    return nil
}
```

两条防作弊规则：

1. **结果数必须 == criteria 数**：LLM 偷懒只返回 1 条 → 1/1 = 100% → 假 PASS。必须强制 `len(results) == len(criteria)`。
2. **每条 evidence 非空**：LLM 直接 `{"passed": true, "evidence": ""}` 蒙混 → 拒绝。

这两条规则配合 prompt 里的 `You MUST NOT pass a criterion without specific evidence.`（[`agent_judge.go:454`](../../internal/judge/agent_judge.go#L454)）形成两道防线——**prompt 引导 + 代码强制**。另外 prompt 模板里**预填 criterion 字段**（[`agent_judge.go:519-534`](../../internal/judge/agent_judge.go#L519)），强制 LLM 用我们提供的原文，避免它改写后绕开数量匹配。

> **面试加分点**：这种「不信 LLM」的设计思维在 Java 后端工程师做 AI 应用时特别要学习——**不能把 LLM 输出当可信数据源，必须当不可信输入处理**。

#### `canRecoverAgentJudgeResult`：容错策略

[`agent_judge.go:423-435`](../../internal/judge/agent_judge.go#L423)：

- err 为 nil 或 sessionResult 为 nil 或 final message 为空 → 不能恢复。
- `errors.Is(err, context.Canceled)`（用户主动取消）→ **永不恢复**。
- 其他情况（含 `DeadlineExceeded`）→ **可以恢复**，只要有 final message。

这是个 trade-off：严格起见应该一遇错就抛，但 LLM API 经常在已生成完整输出后才报「连接重置」，丢弃输出等于浪费一次成功调用。**容错策略让评测更稳定。**

### 3.8 `context_materializer`（为什么物化、profile×mode 双维、自动降级）

#### 为什么需要「物化」

[`context_materializer.go:85-87`](../../internal/judge/context_materializer.go#L85) 注释：

> MaterializeJudgeContext writes agent_judge materials to disk and uploads readable copies into the runtime workspace.

LLM 裁判需要看到 final_message / transcript / diff / 生成的文件才能评分。但这些产物有四个特点：
1. **体积大**：transcript 可能几十 KB 到几 MB。
2. **来源分散**：在 host 内存里、在工作区里、在 artifact dir 里。
3. **要送到 runtime 里**：裁判 agent 在 runtime（可能 docker）里跑，得让 agent 能读到。
4. **prompt 体积有限**：全 inline 进 prompt 会爆 token。

物化的本质就是：**把这些产物按「投递策略」写成文件 + 上传到 runtime + （可选）inline 进 prompt**。

#### profile × mode 双维度

`resolveJudgeContext`（[`context_materializer.go:151-197`](../../internal/judge/context_materializer.go#L151)）实现「双维度配置」：

**维度一：profile（预设套餐）**，两种（[`context_materializer.go:162-172`](../../internal/judge/context_materializer.go#L162)）：

```go
switch profile {
case judgeContextProfileMinimal:    // "minimal"
    effective.finalMessageMode = judgeContextModeTruncate
    effective.transcriptMode = judgeContextModeOmit
    effective.workspaceDiffMode = judgeContextModeOmit
    effective.generatedFilesMode = judgeContextGeneratedOmit
default:                             // "standard"（默认）
    effective.finalMessageMode = judgeContextModeInclude
    effective.transcriptMode = judgeContextModeFileRef
    effective.workspaceDiffMode = judgeContextModeFileRef
}
```

- **minimal**：只给 final_message 截断版，其他全关。**省钱模式**（裁判只看输出文本）。
- **standard**：final_message 全文 inline，transcript / diff 用 file_ref（写在文件里、prompt 里只放路径）。

**维度二：mode（每材料的精细控制）**，五种（[`context_materializer.go:24-32`](../../internal/judge/context_materializer.go#L24)）：

| mode | 含义 |
|---|---|
| `include` | 文件 + inline 进 prompt |
| `omit` | 不投递 |
| `truncate` | 截断到 max_bytes 后 inline |
| `file_ref` | 文件上传到 runtime，prompt 里只放路径 |
| `index` | 仅 generated_files 用，只列文件名 |

case 级配置非 `""` 就覆盖 profile 设的默认。

#### 自动降级：`include` 超 max_bytes 退化为 `file_ref`

`materializeText`（[`context_materializer.go:229-232`](../../internal/judge/context_materializer.go#L229)）：

```go
if mode == judgeContextModeInclude && len([]byte(content)) > maxBytes {
    mode = judgeContextModeFileRef
    material.Mode = mode
}
```

**默认 `maxBytes = 64KB`**（[`context_materializer.go:33`](../../internal/judge/context_materializer.go#L33)）。一旦 inline 内容超 64KB，自动改成 file_ref——**避免 prompt 撑爆 token 上限**。这是个非常工程化的设计：用户写 `mode: include` 表示「我希望 inline」，但系统在边界情况下自动降级，不报错、不打断评测。

**结合 LLM 的工具调用能力**：裁判 agent 看到路径后会主动调 `read_file` 工具按需读取——既能看到完整内容，又不撑爆 prompt。这是「AI Agent 系统设计」的经典模式：**让模型自己决定何时拉取上下文**。

> **Java 类比**：相当于把一个 List 全量序列化改成懒加载 + 分页，避免 OOM。

#### manifest.json：材料清单 + 路径安全

最后会写一份 `manifest.json`（[`context_materializer.go:134-145`](../../internal/judge/context_materializer.go#L134)），记录每个材料的 mode / bytes / truncated 等元信息。这份 manifest 同时被 `Result.JudgeContext.Manifest` 引用，所以报告里能看到「裁判看到了什么、用什么模式、是否被截断」——完全透明可追溯。

attachment 的路径安全（[`context_materializer.go:421-442`](../../internal/judge/context_materializer.go#L421)）：`resolveAttachmentPath` 强制附件路径必须在 `SkillDir` 或 `WorkspacePath` 之内（用 `isWithin`，基于 `filepath.Rel`）。用户配置里写 `attachment: [{path: "/etc/passwd"}]` 会被拒绝——又是路径遍历防御。

### 3.9 三种策略选型决策树

按「确定性 + 成本」分层：

```
我要评测什么？
│
├─ 关键字 / 工具调用 / 文件产出 / 退出码  →  rule_based（零成本、完全确定）
│      缺点：只能判「有没有」，不能判「好不好」
│
├─ 复杂逻辑判定 / 跑测试套件 / 多步验证    →  script（低成本、确定，退出码即结论）
│      优点：语言中立，Python/Bash/PS 都行
│      缺点：要自己写脚本，跨平台有坑
│
└─ 开放式语义（代码质量 / bug 定位 / 文档通顺度）  →  agent_judge（高成本、非确定，阈值制）
       优点：能判「好不好」，接近人类判断
       缺点：贵（一次 LLM 调用）、有噪声（靠阈值+四层兜底+防作弊扛）
```

**省钱组合拳**：先用 `expect` 零成本拦掉明显失败的 case，再让昂贵的 `agent_judge` 只评「值得评」的 case。agent_judge 一次调用几分钱，跑 1000 个 case 就是几十块——expect 把「明显错误的 case」提前拦下，能省掉大量 LLM 调用。这是个 **ROI 极高的工程优化**。

> **Java 类比**：相当于 Servlet Filter 链式短路、Spring Security 的 `AccessDecisionManager` 早退——能便宜挡住的就不要进昂贵的下游。

### 练习 1：为一个 case 写 rule_based 规则（success + failure）

假设你有一个 Skill，让 Agent 修一个 null-pointer bug。写一段 `evals/cases/fix-nullpointer.yaml`，要求：
- 终态输出**必须**包含 `"null pointer"` 和 `"fix"` 两个词，且**至少**包含 `"fixed"` / `"patched"` 之一。
- 终态输出**绝不能**出现 `"panic"` / `"fatal error"`（出现即判 FAIL）。
- 工作区里必须生成补丁文件 `fix.patch`。

参考答案（对照 [`rule_based.go`](../../internal/judge/rule_based.go) 的语义）：

```yaml
id: fix-nullpointer
turns:
  - user: "请定位并修复这段代码里的 null pointer 问题"
judge:
  type: rule_based
  failure:
    - output_contains:
        any: ["panic", "fatal error"]
  success:
    - output_contains:
        all: ["null pointer", "fix"]
        any: ["fixed", "patched"]
    - files_exist:
        - "fix.patch"
```

**自检**：把 `failure` 块和 `success` 块的位置互换，结果会变吗？（提示：看 [`rule_based.go:37-53`](../../internal/judge/rule_based.go#L37)，failure 永远先评，命中即短路。）

### 练习 2：写一个 `.sh` / `.ps1` script judge（退出码判 PASS）

写一个脚本，检查工作区里生成的 `result.txt` 是否包含字符串 `"OK"`：包含则退出 0，否则退出 1。

**Bash 版** `judges/check_ok.sh`：

```bash
#!/usr/bin/env bash
# 契约：cwd = workspace 根目录；退出码 0=PASS 非 0=FAIL；stdout=evidence
set -euo pipefail
if grep -q "OK" result.txt; then
  echo "result.txt contains OK"
  exit 0
else
  echo "result.txt missing OK" >&2   # stderr 作为 debug info
  exit 1
fi
```

**PowerShell 版** `judges/check_ok.ps1`：

```powershell
# Windows 上 .ps1 自动走 powershell.exe，shebang 写 pwsh 才走 PowerShell Core 7+
$ErrorActionPreference = "Stop"
if (Select-String -Path result.txt -Pattern "OK" -Quiet) {
    Write-Output "result.txt contains OK"
    exit 0
} else {
    [Console]::Error.WriteLine("result.txt missing OK")
    exit 1
}
```

YAML 配置：

```yaml
judge:
  type: script
  script_path: judges/check_ok.sh      # Windows 用 .ps1
  timeout_seconds: 15
```

**自检**：你的 `.sh` 在 Windows Git Bash 下能跑吗？路径里的反斜杠要不要转？（提示：看 [`script.go:106-114`](../../internal/judge/script.go#L106)，`envPath: filepath.ToSlash` 专门处理这个。）

### 练习 3：配一个 agent_judge（criteria + pass_threshold）

为一个「代码审查」Skill 配 LLM 裁判：让裁判判断 Agent 是否（1）定位了 bug、（2）给出了修复方案、（3）修复方案不引入新问题。要求 3 条里过 2 条就算 PASS（阈值 0.7）。

```yaml
judge:
  type: agent_judge
  model: claude-sonnet             # 裁判用的模型（可省，用全局默认）
  pass_threshold: 0.7              # 3 条过 2 条 = 0.67 < 0.7 会 FAIL，过 3 条 = 1.0 PASS；实际要过 3 条
  timeout_seconds: 120
  criteria:
    - "输出明确指出了 null-pointer dereference 的具体位置"
    - "输出给出了可执行的修复方案（patch 或代码片段）"
    - "修复方案没有引入明显的回归风险（如新增未判空的字段访问）"
  context:
    profile: standard              # final_message inline，transcript/diff 用 file_ref
    # transcript: truncate         # 可逐项覆盖 profile
    limits:
      max_bytes: 32768             # 超 32KB 自动降级 file_ref
```

**自检**：如果裁判只返回了 1 条 result（偷懒），会发生什么？（提示：看 [`agent_judge.go:213-225`](../../internal/judge/agent_judge.go#L213) 的 `validateAgentJudgeResponse`。）如果裁判返回的 JSON 里有未转义的双引号呢？（提示：看 [`agent_judge.go:270-316`](../../internal/judge/agent_judge.go#L270) 的 `repairJSONQuotes`。）

## 5. 检查点自测

**Q1：三种 judge 怎么选？**

> 按「确定性 + 成本」分层：关键字/工具调用/文件产出 → rule_based（零成本、完全确定）；复杂逻辑/跑测试套件 → script（低成本、退出码即结论）；开放式语义（代码质量、bug 定位）→ agent_judge（高成本、非确定、阈值制）。先用 expect 零成本拦掉明显失败，再让昂贵的 agent_judge 只评「值得评」的 case。

**Q2：LLM 裁判返回的 JSON 不规整怎么办？**

> `extractJSON`（[`agent_judge.go:229-259`](../../internal/judge/agent_judge.go#L229)）四层兜底：① 直接 `json.Unmarshal`；② 抽 ```` ```json ```` 围栏；③ `findJSONObjectEnd` 大括号配对状态机扫候选（不用正则，因为嵌套+转义让正则脆弱）；④ `repairJSONQuotes` 修未转义双引号。核心思想：LLM 输出有 5%-20% 格式问题，代码兜底比让用户重跑便宜。

**Q3：为什么 agent_judge 要校验「结果数 = criteria 数」？**

> 防作弊（[`agent_judge.go:213-225`](../../internal/judge/agent_judge.go#L213)）。`NewResult` 用返回的 result 数做分母，如果 LLM 偷懒只回 1 条，1/1 = 100% 会虚高成假 PASS。所以必须强制 `len(results) == len(criteria)`，外加每条 evidence 非空（避免全标 passed 不举证）。配合 prompt 里预填 criterion 原文 + `MUST NOT pass without evidence`，形成「prompt 引导 + 代码强制」双防线。

**Q4：expect 短路省了什么？**

> 省掉了一次（可能很贵的）Judge 调用（[`expect.go:1-8`](../../internal/judge/expect.go#L1)）。agent_judge 一次调用几分钱，跑 1000 个 case 就是几十块。expect 是零成本确定性检查（字符串/文件/退出码/golden 比对），连「必须包含 hello」都没满足的 case 直接 FAIL 短路，跳过 Judge。通过后的 expect 断言会前置拼到 judge 断言里一起计入通过率，保证报告完整。

**Q5：rule_based 的 failure 规则语义为什么是反的？**

> 因为底层 `evalOutputContains` 等 `evalXxx` 函数是「语义纯粹」的——`Passed=true` 表示「条件成立」，它们不知道自己被用于 success 还是 failure（[`rule_based.go:38-46`](../../internal/judge/rule_based.go#L38)）。`RuleBasedJudge` 在外层反转：failure 规则「命中」（条件成立）= 坏模式被找到 = FAIL，把 `Passed` 反转成 `false`。这让底层算子写一份就能被 success/failure 复用，避免代码重复——策略模式里「复用底层算子」的经典做法。

## 7. 小结 + 下一课预告

### 小结

skill-up 的 Judge 子系统用**一个接口**（`Judge.Evaluate(Input) (*Result, error)`）+ **三种实现**（rule_based 内存算 / script 子进程跑 / agent_judge LLM 裁判），配合五大工程手段：

1. **expect 预检查短路省钱**——零成本确定性检查挡在昂贵 Judge 之前。
2. **safePath 路径安全**——`filepath.Separator` 前缀比对防 `../../` 穿越到工作区外。
3. **MergeJudgeConfig 分级覆盖**——case 配了 Type 就全量覆盖，只回退三个通用旋钮。
4. **extractJSON 四层兜底 + 防作弊双校验**——把「不可信的 LLM 输出」工程化成「可解析、不可作弊」的结构化结果。
5. **profile×mode 双维物化 + 自动降级**——`include` 超 64KB 自动退化为 `file_ref`，既控 prompt 体积又保留完整信息访问。

这套设计把「模糊的 AI 评测」工程化成了「可复现、可调试、可省钱」的流水线，可以直接搬到任何「AI 输出质量评测」系统里复用——这就是简历上能写的那句「设计并实现了基于策略模式的可插拔评分框架」。
