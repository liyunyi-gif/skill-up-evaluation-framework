# L05 · 引擎适配与配置

> **本课主题**：skill-up 怎么「接住」各种 Coding Agent 引擎（claude-code / codex / qodercli / qwen_code / 你自定义的引擎），以及整套 `eval.yaml` 配置是怎么被加载、填默认、分层校验的。
>
> 学完这课，你在面试里能讲清两件事：**① 多引擎适配层的架构（接口 + 工厂 + 模板方法 + 组合优于继承）**；**② 配置即代码（schema + 默认值单一事实源 + 多阶段分层校验）**。前者是 GoF 设计模式的活样板，后者是工程严谨度的体现——都是 Java 后端面试的高频考点。

---

## 1. 学习目标

学完本课，你能：

1. **画出多引擎适配层的四层组合图**（`Agent 接口 → BaseAgent → CLIAgent → 具体引擎`，外加 `CustomAgent` 走组合），并用 Spring JDBC 的 `DataSource → JdbcTemplate → Driver` 类比讲清楚每一层的职责。
2. **讲清 `Agent` 接口的 7 个方法**为什么是这 7 个（3 准备 + 1 计算 + 2 自检 + 1 元信息），以及 `SessionResumer` 为什么拆成**可选接口**而不是塞进 `Agent` 里。
3. **能独立加一个新引擎**：照着 `factory.go` 说出要改的 3 处（agentkind 常量 + 新引擎文件 + 工厂 switch 分支），并解释「为什么改这 3 处就够了」（开闭原则）。
4. **解释配置加载的完整数据流**：`eval.yaml → YAML tag 绑定到 Go struct → //go:embed defaults.yaml 注入默认 → 分层校验器多阶段把关 → 不可变对象进业务层`，并讲清 `run` 和 `validate` 命令在校验范围上的差异。
5. **复述 3 个面试亮点细节**：Claude 双写 `ANTHROPIC_AUTH_TOKEN`、Codex 合成 `skill-up-openai` provider、Codex MCP 桥接脚本——用它们证明你不只是「会用 API」，而是「懂底层踩坑」。

## 3. 讲解

### 3.1 为什么需要 Agent 抽象

skill-up 的核心业务是「**评测**」：同一道题，喂给 N 个 Agent，比谁答得好。如果 evaluator 直接写死调用：

```go
// 反面教材：evaluator 直接 exec
output := exec.Command("claude", "-p", prompt).Output()
```

会发生什么？

1. **每加一个引擎就要改 evaluator**：加 codex 改一遍，加 qoder 改一遍……业务逻辑和引擎调用**强耦合**。
2. **没法横向对比**：evaluator 不知道「这是个 claude 结果还是 codex 结果」，没法统一打分。
3. **测试困难**：单测里没法 mock 一个假引擎。

正确做法是引入**抽象接口**，让 evaluator 永远只依赖接口：

```go
// evaluator 只认这个接口
result, err := agent.Run(ctx, runtime, opts, messages)
```

底下到底是 claude 还是 codex？evaluator **不关心**。这就是经典的**开闭原则（对扩展开放，对修改关闭）+ 依赖倒置原则（依赖抽象，不依赖具体）**。

> **Java 类比**：这和 JDBC 的设计哲学一模一样。`DataSource` 是接口，业务代码只调 `dataSource.getConnection()`；底下连 MySQL 还是 PostgreSQL，由具体 `Driver` 决定。skill-up 的 `Agent` 接口 = `DataSource`，4 个引擎 = 4 个 Driver。Java 同学应该立刻能 get 到。

### 3.2 Agent 接口：7 个方法的契约

源码：[`internal/agent/agent.go:133-148`](../../internal/agent/agent.go#L133)

```go
type Agent interface {
    Name() string
    Install(ctx context.Context, rt Runtime) error
    InstallMCP(ctx context.Context, rt Runtime, mcpCfg runtime.MCPConfig) error
    InstallSkill(ctx context.Context, rt Runtime, skillCfg runtime.SkillConfig) error
    Run(ctx context.Context, rt Runtime, opts ExecOptions, messages []transcript.Message) (*SessionResult, error)
    Check(ctx context.Context, rt Runtime) error
    CheckCredentials(ctx context.Context) error
}
```

这 7 个方法对应「**评测一个 Agent 需要的全部副作用**」，可以分成 4 组：

| 分组 | 方法 | 干什么 | 何时被调 |
|------|------|--------|----------|
| **元信息** | `Name()` | 返回引擎名（`claude_code` 等） | 全链路埋点、报告 |
| **准备 ×3** | `Install(ctx, rt)` | 在 runtime 里装好 CLI（npm/curl） | eval 开始前的 setup |
| | `InstallMCP(ctx, rt, cfg)` | 把 MCP server 注册进 agent | setup 阶段 |
| | `InstallSkill(ctx, rt, cfg)` | 把被测 skill 同步进引擎 skill 目录 | setup 阶段 |
| **计算 ×1** | `Run(ctx, rt, opts, messages)` | **核心**：跑一次 agent，拿回 `SessionResult` | 每个 case 的执行步 |
| **自检 ×2** | `Check(ctx, rt)` | 查 CLI 在不在 PATH（`command -v claude`） | setup 前诊断 |
| | `CheckCredentials(ctx)` | 查 API token 设置了没 | setup 前 |

**为什么是这 7 个，不多不少？**

- skill-up 评的就是 **skill**，所以必须能把 skill 装到 agent 里 → `InstallSkill`。
- 现代 Coding Agent 要配 **MCP 工具**（文件系统、自定义工具）→ `InstallMCP`。
- 引擎跑在 **runtime 沙箱**里（可能没预装）→ `Install` + `Check`。
- 调用要凭证 → `CheckCredentials`。
- 真正跑 prompt 拿结果 → `Run`。

少了任何一个，evaluator 就得自己补逻辑，又把引擎细节泄漏回业务层。这是**接口设计「最小完备」原则**：每个方法对应一类不可合并的副作用。

> **Java 类比**：这就是 JDBC `Connection` 接口的思路——`createStatement / close / commit / rollback`，每个方法对应一类操作，不能少，多了又限制实现。

#### SessionResumer：可选能力接口

源码：[`internal/agent/agent.go:65-74`](../../internal/agent/agent.go#L65)

```go
// SessionResumer is an optional interface that agents may implement to support
// multi-turn conversation evaluation.
type SessionResumer interface {
    RunTurn(ctx context.Context, rt Runtime, opts ExecOptions,
            message transcript.Message, sessionID string) (*SessionResult, error)
}
```

**关键设计**：它和 `Agent` 是**两个接口**，不是把 `RunTurn` 塞进 `Agent` 里。

为什么？因为「能不能续接上一轮对话」是**部分引擎**才有的能力：claude-code 有 `--resume`，codex 有 `exec resume`，qodercli 有 `-r`；但 qwen_code 和 CustomAgent **不支持**多轮。

如果把 `RunTurn` 放进 `Agent`，qwen_code 就得写一个永远返回 `errors.New("not supported")` 的空实现——**接口臃肿**（ISP，接口隔离原则）。拆成可选接口后，evaluator 用**类型断言**探测能力：

```go
if resumer, ok := agent.(SessionResumer); ok {
    resumer.RunTurn(...)   // 支持多轮
} else {
    agent.Run(...)         // 退化成单轮
}
```

源码用**编译期断言**锁死「哪几个引擎实现了 SessionResumer」，见 [`internal/agent/agent.go:150-155`](../../internal/agent/agent.go#L150)：

```go
var (
    _ SessionResumer = (*ClaudeCodeAgent)(nil)
    _ SessionResumer = (*QoderCLIAgent)(nil)
    _ SessionResumer = (*CodexAgent)(nil)
)
```

这种 `var _ Interface = (*Type)(nil)` 是 Go 的**静态自检惯用法**：编译期就保证类型实现了接口，**不用等到运行时调用才发现漏方法**。等价于 Java 的 `class Foo implements Bar` 显式声明，但用「赋值给空白变量」模拟，更灵活。

> **Java 类比**：这种「核心接口 + 可选能力接口」的拆法，在 Java 里就像 `Collection`（核心）+ `RandomAccess`（标记接口，表示支持快速随机访问）。不是每个 Collection 都 `RandomAccess`，调用方用 `instanceof` 探测。

### 3.3 四层组合：BaseAgent → CLIAgent → 具体引擎

Go 没有 `extends`，复用靠**结构体嵌入（embedding）**——等价于 Java 的「组合 + 语言级委托」，但比继承更灵活。整个适配层是 4 层组合：

```
                    ┌─────────────────────────────────────────┐
   evaluator ──────►│  Agent 接口 (7 方法) + SessionResumer    │  ← 契约
                    └─────────────────┬───────────────────────┘
                                      │ 被这几个实现满足
            ┌─────────────┬───────────┴───────────┬─────────────┐
            ▼             ▼                       ▼             ▼
       ClaudeCode     Codex                  QoderCLI       QwenCode     CustomAgent
            └─────┬───────┴───────────┬────────┴────────┬──────┘             │
                  │ 嵌入 CLIAgent      │ 嵌入            │ 嵌入               │ 嵌入 BaseAgent
                  ▼                   ▼                 ▼                    ▼
              ┌──────────────────────────────────────────────┐  ┌────────────────────┐
              │  CLIAgent (模板方法层)                        │  │  BaseAgent          │
              │  InstallMCP/InstallSkill/Run/Check            │  │  (直接嵌入，跳过 CLI)│
              └──────────────────────┬───────────────────────┘  └────────────────────┘
                                     │ 嵌入
                                     ▼
              ┌──────────────────────────────────────────────┐
              │  BaseAgent (基础设施层)                       │
              │  Name / SkillPath / CheckCredentials          │
              │  mergeExecOptionsEnv / probeAndMergePATH      │
              │  installSkillDefault                          │
              └──────────────────────────────────────────────┘
```

#### 第 1 层：BaseAgent（基础设施）

源码：[`internal/agent/agent.go:157-162`](../../internal/agent/agent.go#L157)

```go
type BaseAgent struct {
    Cfg     Config
    Version string
}
```

它挂在 `Config`（[`agent.go:95-121`](../../internal/agent/agent.go#L95)，一坨字段：Name/RunCmd/SkillPath/APIKey……）之上，提供**所有引擎都需要**的基础方法：

| 方法 | 行号 | 作用 |
|------|------|------|
| `Name()` | [`agent.go:188`](../../internal/agent/agent.go#L188) | 返回 `Cfg.Name` |
| `SkillPath()` | [`agent.go:193`](../../internal/agent/agent.go#L193) | 返回引擎读 skill 的目录 |
| `CheckCredentials(ctx)` | [`agent.go:198`](../../internal/agent/agent.go#L198) | 按 provider（openai/anthropic）查对应 env |
| `credentialEnvVars(...)` | [`agent.go:240`](../../internal/agent/agent.go#L240) | 把 API key/baseURL 拼进 env map |
| `mergeExecOptionsEnv(...)` | [`agent.go:332`](../../internal/agent/agent.go#L332) | 合并多个 env 来源进 `ExecOptions.Env` |
| `probeAndMergePATH(...)` | [`agent.go:349`](../../internal/agent/agent.go#L349) | 跑探针命令，把 `~/.local/bin` 加进 PATH |
| `installSkillDefault(...)` | [`agent.go:257`](../../internal/agent/agent.go#L257) | 默认 skill 安装（拷目录） |

**这里有个伏笔**：`installSkillDefault` 故意**挂在 BaseAgent 而不是 CLIAgent** 上。注释（[`agent.go:252-256`](../../internal/agent/agent.go#L252)）写得很直白：

> Defined on BaseAgent so both CLIAgent and CustomAgent share it via embedding,
> without making CustomAgent inherit the rest of CLIAgent.

这是为后面「CustomAgent 不嵌 CLIAgent」埋的——把共享方法**下推到最底层**，避免被迫继承一整套 CLI 行为。

#### 第 2 层：CLIAgent（模板方法）

源码：[`internal/agent/cli.go:19-22`](../../internal/agent/cli.go#L19)

```go
type CLIAgent struct {
    BaseAgent
}
```

它只为「**通过 CLI 调用**」的引擎提供模板方法骨架，定义了 4 个流程：

| 方法 | 行号 | 干什么 |
|------|------|--------|
| `InstallMCP` | [`cli.go:24`](../../internal/agent/cli.go#L24) | 用 `text/template` 渲染 `InstallMCPCmd` 模板，逐个 server 调 `rt.Exec` |
| `InstallSkill` | [`cli.go:81`](../../internal/agent/cli.go#L81) | 模板没配 → 走 `installSkillDefault`；配了就渲染 |
| `Run` | [`cli.go:125`](../../internal/agent/cli.go#L125) | **最关键的模板方法**：拼 instruction → 渲染 RunCmd → 执行 |
| `Check` | [`cli.go:186`](../../internal/agent/cli.go#L186) | 跑 `command -v claude` 探测 CLI 是否在 PATH |

以 `CLIAgent.Run` 为例（[`cli.go:125-158`](../../internal/agent/cli.go#L125)），它是经典的模板方法骨架：

```go
func (a *CLIAgent) Run(ctx context.Context, rt Runtime, opts ExecOptions,
                       messages []transcript.Message) (*SessionResult, error) {
    if err := requireBashTargetShell(rt); err != nil { return nil, ... }   // ① Windows 必须 bash
    start := time.Now()
    instruction := BuildInstructionFromMessages(messages)                  // ② messages 拼成单串
    cmd := fmt.Sprintf(a.Cfg.RunCmd, shellQuote(instruction))              // ③ %s 模板渲染
    opts = a.mergeExecOptionsEnv(ctx, opts, ...)                           // ④ 合并 env
    result, err := rt.Exec(ctx, cmd, opts)                                 // ⑤ 真正执行
    sessionResult := &SessionResult{ Engine: a.Name(), ExitCode: result.ExitCode, ... }
    return sessionResult, nil                                              // ⑥ 错误处理
}
```

**注意**：这是「通用 Run」——只把 stdout 当 final message，**不解析 transcript**。但 4 家引擎的输出格式完全不同（claude 有 stream-json、codex 有 NDJSON events、qwen 有 Gemini-shape JSONL），所以 **4 个具体引擎全都重写了 Run**。`CLIAgent.Run` 实际只起**默认基线**作用。

> **Java 类比**：这就是 `JdbcTemplate.execute(String sql)` 的位置——给你个能直接跑 SQL 的兜底；但真要拿结构化结果，你得用 `query(sql, RowMapper)` 这种更具体的方法（对应每个引擎自己重写的 Run）。**模板方法 + 钩子（hook）**模式的活用。

#### 第 3 层：4 个具体引擎（嵌入 CLIAgent）

每个引擎的写法极其规整，4 个文件长得几乎一样。以 Claude 为例（[`internal/agent/claude_code.go:22-46`](../../internal/agent/claude_code.go#L22)）：

```go
type ClaudeCodeAgent struct {
    CLIAgent
}

func NewClaudeCodeAgent(cfg Config) *ClaudeCodeAgent {
    if cfg.Name == "" { cfg.Name = "claude-code" }
    cfg.CheckCmd = "command -v claude"
    cfg.SkillPath = ".claude/skills"
    return &ClaudeCodeAgent{
        CLIAgent: CLIAgent{BaseAgent: NewBaseAgent(cfg)},
    }
}
```

`CodexAgent`（[`codex.go:23`](../../internal/agent/codex.go#L23)）、`QoderCLIAgent`（[`qodercli.go:18`](../../internal/agent/qodercli.go#L18)）、`QwenCodeAgent`（`qwen_code.go`）结构完全一致，只是构造时填的默认值（`CheckCmd` / `SkillPath` / `RunCmd` / 安装命令）不同。

**为什么这样写「好」**：

1. `New*Agent` 是**便利构造函数**（Java 里叫 static factory method），把「默认值 + 嵌入初始化」一次性封死。
2. 想加第 5 个引擎？复制一份文件，改 5 个常量即可，**不动任何已有代码**——开闭原则。
3. 每个引擎**按需重写**任意方法（4 个都重写了 `Run` / `Install` / `InstallMCP`），不重写的就用 CLIAgent 模板。

#### 第 4 层（特殊）：CustomAgent 故意不嵌 CLIAgent

这是整个适配层**最值得讲的设计决策**。源码：[`internal/agent/custom.go:65-79`](../../internal/agent/custom.go#L65)

```go
// CustomAgent embeds BaseAgent directly (not CLIAgent) so it inherits only
// shared agent infrastructure — Name, credential helpers, exec-options merge,
// installSkillDefault. Run / Install / InstallMCP / InstallSkill / Check /
// CheckCredentials are all defined explicitly, so future additions to CLIAgent
// do not accidentally leak in with the wrong semantics for a custom engine.
type CustomAgent struct {
    BaseAgent   // ← 注意：嵌的是 BaseAgent，不是 CLIAgent！
}
```

为什么？Custom Engine 的执行模型**根本不是 CLI**——它可能是本地命令、可能是 HTTP 服务、可能压根没有「安装」这个概念。如果让它嵌 CLIAgent，将来给 CLIAgent 加方法时会**意外漏进来**：对一个 HTTP 引擎来说，「跑 InstallMCP 命令」这种语义完全是错的。

于是 CustomAgent 把所有方法都**显式实现**了一遍（[`custom.go:89-114`](../../internal/agent/custom.go#L89)）：

```go
func (a *CustomAgent) Install(_ context.Context, _ Runtime) error { return nil }       // no-op
func (a *CustomAgent) InstallMCP(...) error { /* 只打日志，不装 */ }
func (a *CustomAgent) InstallSkill(...) error { return a.installSkillDefault(...) }    // 复用 BaseAgent 的
func (a *CustomAgent) Check(...) error { return nil }                                  // no-op
func (a *CustomAgent) CheckCredentials(...) error { return nil }                       // no-op
func (a *CustomAgent) Run(...) (*SessionResult, error) { /* 大量逻辑：local/http 双 transport */ }
```

5 个 no-op 看起来「浪费」，但这是**用代码自证意图**：「Custom Engine 没有安装/检测概念，只是占个位返回 nil」。比「继承了一堆错误行为」安全得多。

> **Java 类比（重点记忆）**：整个四层组合对应 Spring JDBC 的经典分层——
>
> | skill-up | Java/Spring 类比 | 职责 |
> |----------|------------------|------|
> | `Agent` 接口 | `javax.sql.DataSource` | 契约 |
> | `CLIAgent`（模板方法） | `JdbcTemplate` | 通用流程骨架 |
> | `ClaudeCodeAgent` 等 4 个 | 各家 JDBC `Driver`（MySQL/PG/Oracle） | 具体实现 |
> | `BaseAgent`（基础设施） | `AbstractDataSource` | 最底层通用能力 |
> | `CustomAgent`（不嵌 CLIAgent） | 自定义 NoSQL DataSource（直接实现接口，不走 JdbcTemplate） | 组合优于继承 |
> | `DetectAgent`（工厂） | `DriverManager.getConnection` | 工厂 + 路由 |
>
> CustomAgent 不嵌 CLIAgent，等价于 MyBatis 这种非 JDBC 模板的 ORM，**直接实现 `DataSource`** 而不是继承 `AbstractDataSource`——只复用真正需要的基础能力，避免被模板类默认行为绑架。这是 **Effective Java Item 18「组合优于继承」**的经典体现。

### 3.4 工厂：DetectAgent + agentkind 别名归一化

光有接口和实现还不够，还要有个**集中创建**的入口——这就是工厂模式。

#### agentkind：消除「两处常量同步」的叶子包

源码：[`internal/agentkind/agentkind.go`](../../internal/agentkind/agentkind.go)

这是一个**只有常量**的叶子包，存在的唯一理由看包注释（[`agentkind.go:1-8`](../../internal/agentkind/agentkind.go#L1)）：

> It is a tiny leaf package with no internal dependencies so both
> internal/agent (factory dispatch) and internal/config (validation) can
> import the same source of truth without creating an import cycle —
> previously the list was duplicated in both packages with a "keep in sync"
> comment.

```go
const (
    ClaudeCode      = "claude_code"
    ClaudeCodeAlias = "claude-code"
    Codex           = "codex"
    QoderCLI        = "qodercli"
    QoderAlias      = "qoder"
    QoderCLIAlias   = "qoder-cli"
    QwenCode        = "qwen_code"
    QwenCodeAlias   = "qwen-code"
    QwenAlias       = "qwen"
)
```

**为什么需要它？** `internal/agent`（工厂分发）和 `internal/config`（校验「是不是合法引擎」）都要用这份清单。如果放在 `agent` 包，`config` 就要 import `agent`；但 `agent` 又可能间接依赖 `config`——**循环依赖**，Go 编译器直接拒绝。

**解法**：把常量抽到**最底层的叶子包**（无任何内部依赖），谁都能 import 它，它不依赖任何人。

**亮点设计**：

- 每个引擎同时给 `_` 和 `-` 两种写法（`claude_code` / `claude-code`），因为 YAML 历史上两种都有人写。
- `IsBuiltin(name)`（[`agentkind.go:38-41`](../../internal/agentkind/agentkind.go#L38)）用 map 查表，O(1)。
- **消除「keep in sync」注释**是关键：注释不能保证同步，编译器才能。

> **Java 类比**：这相当于把「协议号 / MIME 类型」这种跨模块共享常量放到 `commons-lang3` 之类的叶子 jar——谁都能依赖它，它不依赖任何人。**Maven 依赖树里的叶子 jar**。

#### DetectAgent：纯路由

源码：[`internal/agent/factory.go:12-34`](../../internal/agent/factory.go#L12)

```go
func DetectAgent(engineName string, cfg Config) (Agent, error) {
    if cfg.Name == "" { cfg.Name = engineName }
    switch engineName {
    case agentkind.QoderCLIAlias, agentkind.QoderAlias, agentkind.QoderCLI:
        return NewQoderCLIAgent(cfg), nil
    case agentkind.ClaudeCodeAlias, agentkind.ClaudeCode:
        return NewClaudeCodeAgent(cfg), nil
    case agentkind.Codex:
        return NewCodexAgent(cfg), nil
    case agentkind.QwenCode, agentkind.QwenCodeAlias, agentkind.QwenAlias:
        return NewQwenCodeAgent(cfg), nil
    default:
        if cfg.Custom != nil {
            return NewCustomAgent(cfg), nil
        }
        return nil, &UnsupportedAgentError{Name: engineName}
    }
}
```

就是个**大 switch**——但有几个细节：

1. **别名归一**：每个 case 列出所有别名（`QoderCLIAlias, QoderAlias, QoderCLI`），不管用户写哪种，都路由到同一个 `NewXxxAgent`。
2. **default 走 Custom**：引擎名不是内置的，但 `cfg.Custom != nil`（用户在 YAML 里配了 `engine.custom` 块），就当 Custom Engine 处理。
3. **彻底不支持 → `UnsupportedAgentError`**：这是个**可导出的错误类型**（不是普通 `errors.New`），上游可以 `errors.As(err, &UnsupportedAgentError{})` 精准识别并给友好提示。

> **Go 错误处理惯用法**：错误类型化 > 字符串匹配。这相当于 Java 里 throw 一个自定义异常类型（`UnsupportedAgentException`），而不是 throw `new RuntimeException("unsupported ...")`——catch 端能精确处理，不用 parse 异常消息。

#### DetectAgentWithInitParams：处理「auto」串味

源码：[`internal/agent/factory.go:39-77`](../../internal/agent/factory.go#L39)

这个函数比 `DetectAgent` 多做一步：把「凭据解析后的初始参数」映射到 Config。最有意思的是**「auto」模型剥离**（[`factory.go:45-47`](../../internal/agent/factory.go#L45)）：

```go
model := params.Model
// "auto" is a QoderCLI-specific model tier; strip it for other built-in
// engines so they don't need to hard-code awareness of it.
if model == "auto" && !isQoderCLIEngine(engineName) && params.Custom == nil {
    model = ""
}
```

为什么？`qodercli` 有个「auto」模型档位（自动选 lite/efficient/performance/ultimate），但**别的引擎不懂「auto」是啥**。如果原样把 `"auto"` 传给 claude-code，它会把 `"auto"` 当 model 名发给 Anthropic API，直接 400。

**两种处理思路对比**：

- **错的**：让每个引擎都写一行 `if model == "auto" { model = "" }`——4 处重复，未来加引擎还会忘。
- **对的**：在**工厂层一次性剥离**，下游引擎永远看不到「auto」。

但 **Custom Engine 保留「auto」**（`params.Custom == nil` 的判断）——因为 custom engine 是用户自定义的，`auto` 可能是它自己定义的合法档位，由用户通过 `${model}` 自己解读。**「内置归一，自定义透传」**的边界划得非常清晰。

> **面试金句**：「我在工厂层做了一次『方言归一』——把 qodercli 私有的 model 档位剥离掉，下游引擎就不用每个都写 awareness 逻辑。这种『脏活集中在入口做一次』是工厂模式的核心价值之一。」

#### 亮点 1：Claude 双写 `ANTHROPIC_AUTH_TOKEN`

源码：[`internal/agent/claude_code.go:119-128`](../../internal/agent/claude_code.go#L119)

```go
envVars := a.credentialEnvVars(credential.EnvAnthropicAPIKey, credential.EnvAnthropicBaseURL)
// Some Anthropic-compatible proxies only validate `Authorization: Bearer <token>`
// and do not recognise the `x-api-key` header...
if a.Cfg.APIKey != "" {
    envVars[credential.EnvAnthropicAuthToken] = a.Cfg.APIKey
}
```

**故事**：Anthropic 官方有**两套**鉴权 header：

- `x-api-key: <key>`——官方 SDK 默认（设 `ANTHROPIC_API_KEY` 时走这个）。
- `Authorization: Bearer <token>`——设 `ANTHROPIC_AUTH_TOKEN` 时切换到这个。

问题：**很多企业内部代理（anthropic-proxy 网关）只认 Bearer，不认 x-api-key**。只设 `ANTHROPIC_API_KEY`，请求会被代理拒掉。

**解法**：把**同一个 API key 同时写到两个 env 变量**——官方 API 两个都接受，代理也能找到 Bearer。**一份凭证，双 header 兼容**。

> **Java 类比**：相当于 Spring Security 里同时配 `BasicAuth` 和 `Bearer Token` 过滤器，让一套凭证穿过不同鉴权网关。这种「**兼容性高于纯粹性**」的工程权衡，面试可以重点讲。

#### 亮点 2：Codex 合成 `skill-up-openai` provider

源码：[`internal/agent/codex.go:40`](../../internal/agent/codex.go#L40)（常量）+ `codex.go:397` 附近（逻辑）

故事背景：codex CLI 默认用 OpenAI 的 `/responses` 端点（`wire_api="responses"`），但很多兼容服务（阿里 dashscope、idealab）**只支持 `/chat/completions`**。如果直接配 `base_url`，codex 会忽略它，继续打官方 `api.openai.com`，返回 400。

**错误思路**：把 provider 名设为 `"openai"`——codex 内置了 `"openai"` 定义，**合并覆盖行为跨版本不稳定**。

**正确思路**（[`codex.go:39-40`](../../internal/agent/codex.go#L39) 注释）：用 `skill-up-` 前缀造一个**全新的 provider 名**，强制 codex 从零创建定义（不存在合并问题），并通过 `wire_api="chat"` 强制走 `/chat/completions`：

```go
codexOpenAIOverrideProvider = "skill-up-openai"
```

最终拼出 5 个 `-c` 参数：
```bash
codex exec --json \
  -c 'model_provider="skill-up-openai"' \
  -c 'model_providers.skill-up-openai.base_url="https://..."' \
  -c 'model_providers.skill-up-openai.wire_api="chat"' \
  ...
```

**`skill-up-` 前缀**还有个好处：在 codex 日志/命令行里一眼能看出「这是 skill-up 合成的」，方便排错。**给合成物加命名空间前缀**是个非常实战的工程习惯。

#### 亮点 3：Codex MCP 桥接脚本

源码：`internal/agent/codex.go:152` 附近

故事：codex 的 `codex mcp add` **不支持 `--header`** 给 HTTP MCP server 加自定义 header。但评测时我们要测带鉴权 header 的 MCP server，怎么办？

**思路**：用**中间人桥接脚本**——用 `npx mcp-remote` 做 HTTP MCP client，由它带 header，再用 stdio 把协议转给 codex。生成的命令大致：

```bash
codex mcp add my-server \
  -- 'sh' '-c' 'exec npx mcp-remote "$1" --header "Authorization: Bearer xxx" 2>/dev/null' \
  'mcp-remote' \
  https://mcp.example.com/sse
```

精彩之处：用 **shell `-c` + `--` 分隔符**把「stdio 命令」伪装成本地程序，但实际它内部转 HTTP。`$1` 是 shell 位置参数指向 endpoint URL，`2>/dev/null` 静音噪音。这是**「用组合代替修改」**的极致——codex 不支持？外面套一层 shell 脚本就行。**适配器模式的终极体现**。

### 3.6 transcript 归一：把 4 种 JSON 翻译成同一份

`SessionResult.Transcript`（[`agent.go:60`](../../internal/agent/agent.go#L60)）是个统一结构。但 4 家 Agent 的**原始输出格式完全不同**，适配层要把它们翻译成统一的 `[]transcript.Message`（`{Role, Content, Turn, ToolCall, ToolResult}`）。

| 引擎 | 原始格式 | session 文件位置 |
|------|----------|------------------|
| claude_code | stream-json（NDJSON，type=user/assistant/tool_call/...） | `~/.claude/projects/<wskey>/*.jsonl` |
| qodercli | **同 claude schema**（历史 fork 红利） | `~/.qoder/projects/<wskey>/*.jsonl` |
| codex | NDJSON events（thread.started/turn.started/item.completed/...） | stdout + `~/.codex/sessions/*<thread_id>*.jsonl` |
| qwen_code | **Gemini schema**（role ∈ {user, model}，parts 数组） | `~/.qwen/projects/<wskey>/chats/*.jsonl` |

**三套解析策略**：

1. **Claude / Qoder 共享 `parseSessionFile`**：因为 qodercli 是 claude 的 fork，session 文件 schema 完全一样，直接复用同一个解析器。**最妙的是 token 聚合用 `max` 而不是累加**——源码注释讲了一个细节：Claude session 文件里每条 assistant 事件的 usage 是**累计快照**（running meter）而非每行 delta，所以 `input_tokens` 在很多行里完全相同（缓存命中），`output_tokens` 单调递增。直接 sum 会**重复计算**，用 max 取高峰水位才对。这是**只有真解析过真实数据才知道的坑**。

2. **Codex 双解析器 + 两阶段关联**：codex 有 stdout NDJSON 和 session 文件两个数据源。**threadID 从 stdout 解析**（`thread.started` 事件），然后用它去找 session 文件。只有 session 文件的 transcript **更长**（信息更全）时才覆盖 stdout 的结果。`command_execution` 用 map 关联 started/completed 事件（靠 ID 配对 tool_call 和 tool_result）——这是**事件溯源（event sourcing）**模式的标准做法。

3. **Qwen Gemini schema 翻译**：qwen_code 是 Gemini CLI 的 fork。注意 `Role` 在 Gemini 里是 `"model"` 而不是 `"assistant"`，解析器用 `ev.Type` 而不是 `ev.Message.Role` 判定，绕开命名差异。`Parts` 是异构数组（text/functionCall/functionResponse），用 switch 翻译成统一的 `transcript.Message`。

> **面试金句**：「适配层最难的不是接口设计（那就是个适配器模式），而是把 4 家完全不同的输出格式（stream-json / NDJSON / Gemini jsonl）归一成同一份 transcript。比如 Claude 的 token 是累计快照不是增量，直接 sum 会算错——这种坑只有真解析过真实 session 文件才知道。」

### 3.7 配置系统：eval.yaml 怎么变成运行时对象

讲完引擎，来看**驱动整次评测的配置系统**。`internal/config` 包负责把 `eval.yaml` 文档变成 Go 里**强类型、带默认、被校验过、不可变**的对象。

> **一句话类比**：配置是 skill-up 的「**类型系统**」。对 Java 工程师，它相当于 **Spring Boot 的 `@ConfigurationProperties` + `@Valid` + 默认值注入**的组合——只不过这里全部用纯 Go 手写，没有反射魔法。

#### eval.yaml v1alpha1 schema：9 个顶层字段

源码：[`internal/config/schema.go:10-21`](../../internal/config/schema.go#L10)

```go
type EvalConfig struct {
    SchemaVersion string          `yaml:"schema_version"`
    Environment   Environment     `yaml:"environment"`
    MCP           MCPConfig       `yaml:"mcp"`
    Skills        []SkillRef      `yaml:"skills"`
    Engine        EngineConfig    `yaml:"engine"`
    Cases         CasesConfig     `yaml:"cases"`
    Judge         JudgeConfig     `yaml:"judge"`
    Benchmark     BenchmarkConfig `yaml:"benchmark"`

```

这 9 个字段就是 eval.yaml 的**全部顶层 key**，对应「一个评测任务」的全部维度：

| 字段 | 维度 | 一句话 |
|------|------|--------|
| `schema_version` | 版本 | 必须 `v1alpha1`（k8s 式 API 版本化） |
| `environment` | 在哪跑 | `none` / `opensandbox` / `docker` 三种运行时 |
| `mcp` | 工具集 | MCP server 列表，eval 级声明，case 级可覆盖 |
| `skills` | 被测技能 | 装哪些 Skill（`local_path` / `registry`） |
| `engine` | 谁来跑 | Agent 引擎（claude_code/codex/custom）+ 模型 |
| `cases` | 跑什么 | case 文件列表 + 默认值 + 并发度 + 重试 |
| `judge` | 怎么判 | `rule_based` / `script` / `agent_judge`（详见 L04） |
| `benchmark` | 对不对比 | 启用 baseline 对比（A/B） |
| `report` | 怎么输出 | `json` / `junit` / `html` |

> **Java 类比**：这就是 Spring `@ConfigurationProperties(prefix = "eval")` 的 root bean。每个字段是嵌套 POJO，YAML tag 等价于字段绑定。

**v1alpha1 版本化**：校验在 [`validator.go:57-61`](../../internal/config/validator.go#L57)，缺字段报错，写 `v1beta1` / `v1` / `v2` 全部拒绝。`v1alpha1` 是 **Kubernetes API 风格**的版本号：`v` 前缀 + 主版本号 + `alpha`（实验性，可能 break）+ 序号。skill-up 选它因为**还在快速演进**，提前承诺兼容会变成技术债。**版本号字段的存在本身就是设计契约**——它是未来 schema 演进的基础设施。

#### CaseConfig：单个测试用例

源码：[`internal/config/schema.go:252-281`](../../internal/config/schema.go#L252)

case 文件是独立 YAML，通过 `eval.yaml` 的 `cases.files` 引用。一个 case 描述「给 agent 一个输入，检查它的输出」：

```go
type CaseConfig struct {
    ID          string      `yaml:"id"`
    Title       string      `yaml:"title"`
    Input       Input       `yaml:"input"`
    Constraints Constraints `yaml:"constraints"`
    Expect      Expect      `yaml:"expect"`
    Judge       JudgeConfig `yaml:"judge,omitempty"`
    MCP         MCPConfig   `yaml:"mcp,omitempty"`
    // ...
    SourceFile string `json:"-" yaml:"-"`   // ← 最特别的字段
}
```

**输入的两种互斥形态**（[`schema.go:283-287`](../../internal/config/schema.go#L283)）：

```go
type Input struct {
    Prompt string `yaml:"prompt,omitempty"`
    Turns  []Turn `yaml:"turns,omitempty"`
}
```

- `prompt`：单轮对话。
- `turns`：多轮对话，每轮有自己的 `post_condition` 和 `capture`。

两者**必须二选一**（XOR 约束），校验在 [`validator.go:116-121`](../../internal/config/validator.go#L116)：既不能都没有，也不能同时有。

**最特别的字段 `SourceFile`**：tag 是 `json:"-" yaml:"-"`——**永远不会被序列化**，纯粹是 loader 加载时注入的「元数据」。它的存在是为了让**去重校验能在 case 子集上正确工作**（后面讲）。这相当于 JPA 的 `@Transient`——字段只在运行时存在，不参与持久化。

#### Loader：以 SKILL.md 为锚点的路径解析

源码：[`internal/config/loader.go`](../../internal/config/loader.go)

Loader 有三个关键设计：

**(1) `filepath.Abs` 必须先做**（[`loader.go:43-60`](../../internal/config/loader.go#L43)）。注释明说：

> evalPath is normalized with filepath.Abs so EvalDir is absolute; otherwise a
> relative path like ./evals/eval.yaml yields Dir chains such as "." and breaks
> skill root resolution (e.g. InstallSkill target becomes ".qoder/skills/.").

用户在 skill 根目录执行 `skill-up run ./evals/eval.yaml`：

- 不调 `Abs`：`evalDir = "./evals"`，上一级是 `.`——**target 拼成 `.qoder/skills/.`**，路径错乱。
- 调了 `Abs`：`evalDir = "/abs/path/to/skill/evals"`，正确找到 SKILL.md。

**教训**：Go 的 `filepath.Dir` 对相对路径是「字面切分」，不返回绝对路径。任何依赖 `Dir` 链做路径解析的代码，**第一步必须 Abs**。

**(2) `FindSkillDir` 向上查最多 10 层**（[`loader.go:214-229`](../../internal/config/loader.go#L214)）：

```go
const maxSkillDirSearchDepth = 10   // loader.go:17

func FindSkillDir(startDir string) (string, bool) {
    dir := filepath.Clean(startDir)
    for depth := 0; depth <= maxSkillDirSearchDepth; depth++ {
        if _, err := os.Stat(filepath.Join(dir, "SKILL.md")); err == nil {
            return dir, false   // 找到了
        }
        parent := filepath.Dir(dir)
        if parent == dir { break }   // 到达文件系统根
        dir = parent
    }
    return filepath.Dir(startDir), true   // fallback，不报错
}
```

- `SKILL.md` 是「技能根」的锚点——类似 Node 的 `package.json`、Go 的 `go.mod`，是**项目根标识符**。
- 找不到时**不报错**，返回 fallback + `Warnf`——「宽容失败」设计。
- 硬上限 10 层，防止在巨型仓库里无限向上找。

**(3) `LoadCaseConfig`：路径相对 skillDir、id 文件名兜底、SourceFile 注入**（[`loader.go:108-133`](../../internal/config/loader.go#L108)）：

```go
func (l *Loader) LoadCaseConfig(casePath string) (*CaseConfig, error) {
    fullPath := filepath.Join(l.skillDir, casePath)   // ① 相对 skill 根
    // ... read + unmarshal ...
    if cfg.ID == "" {
        cfg.ID = stripExt(filepath.Base(casePath))    // ② id 文件名兜底
    }
    cfg.SourceFile = casePath                         // ③ 注入原始路径
    return &cfg, nil
}
```

三个细节：

- **case 路径相对 skill 根**，不相对 eval.yaml 所在目录——让「在 skill 目录里跑」和「显式传 `evals/eval.yaml`」行为一致。
- **id 文件名兜底**：没写 `id:` 就用文件名（去扩展名）。`cases/basic-test.yaml` → id = `basic-test`。这是「**约定大于配置**」——Rails、Spring Boot 的核心哲学。
- **`SourceFile` 注入**：记录「这个 case 从 cases.files 哪个条目加载来」，供去重校验用。注意存的是**用户写的原始字符串**（`cases/basic.yaml`），不是 `fullPath`——错误消息对用户更友好。

#### 默认值：`//go:embed` 让文档和代码不漂移

源码：[`internal/config/defaults.go`](../../internal/config/defaults.go)

默认值只填 4 个（`timeout_seconds` / `max_turns` / `parallelism` / `report.formats`），其他字段保留零值让 validator 拒绝（避免默认值**掩盖配置错误**）。这 4 个默认值来自 `//go:embed defaults.yaml`：

```go
//go:embed defaults.yaml
var defaultsYAML []byte        // defaults.go:69-70
```

```yaml
# internal/config/defaults.yaml
schema_version: v1alpha1
environment:
  type: none
cases:
  defaults:
    timeout_seconds: 300
    max_turns: 10
  parallelism: 1
report:
  formats: [json]
```

**`//go:embed` 的意义**：

1. **编译期嵌入**：`defaults.yaml` 在 `go build` 时被嵌入二进制，运行时不依赖文件系统。
2. **文档与代码不漂移**：README 写「默认超时 300s、max_turns 10、parallelism 1」，这同一份 yaml 也是代码默认值源——**改一处，两边同步**。
3. **没有「魔法数字」**：`300` / `10` / `1` 不散落在 Go 代码里，集中在 yaml 里。

> **Java 类比**：`//go:embed` 类似 Spring Boot 的 `@Value("classpath:defaults.yaml")`。但 Go 的 embed 是**编译期**完成，运行时零开销，不会因为打包漏了 yaml 而崩溃。

**deep copy 保证不可变**（[`defaults.go:21-58`](../../internal/config/defaults.go#L21)）：`DefaultEvalConfig()` 每次返回 deep copy（用 yaml Marshal/Unmarshal 做拷贝，取巧但有效，零反射代码）。`init()` 里如果编译期嵌入的 yaml 解析不了，直接 **panic 让 CI 红**——开发者 bug，运行时没法救。

#### 分层校验器：多阶段、子集、延迟

`validator.go` 是 config 包最复杂的文件。核心思想是「**分层校验、各司其职**」——不同类型的校验在不同阶段做，避免一个巨型函数。

| 阶段 | 函数 | 校验内容 | 何时触发 |
|------|------|---------|---------|
| **文档级** | `ValidateEvalConfig` | schema_version、environment.type、engine.name、cases.files 非空 | 加载后立即 |
| **类型枚举** | `isValidRuntimeType` 等 | Type 字段是合法枚举 | 文档级内 |
| **runtime 特化** | `validateDockerEnvironment` | docker 必须 image、workspace_mount 绝对 | 文档级内 |
| **网络策略** | `validateNetworkPolicy` | network_policy 配置合法性 | 文档级内 |
| **case 级** | `ValidateCaseConfig` | input 互斥、turn 完整、capture、per-turn rules | 加载每个 case |
| **去重** | `duplicateCaseErrors` | 路径归一化后去重、case id 去重 | `ValidateCases` 入口 |
| **judge 合并** | `ValidateCasesWithEvalDefaults` | 用 eval 级 judge 默认合并 case 级后校验 | case 校验后 |
| **延迟（customengine）** | `ResolveCustomEngineConfig` | engine.custom 块、env 引用、敏感字段 | CLI override 后 |

以 `ValidateEvalConfig`（[`validator.go:53-106`](../../internal/config/validator.go#L53)）为例，它的核心模式是**错误累积**：

```go
func (v *Validator) ValidateEvalConfig(cfg *EvalConfig) error {
    var errs []string   // ← 一次性收集所有错误
    if cfg.SchemaVersion == "" {
        errs = append(errs, "schema_version is required")
    } else if cfg.SchemaVersion != "v1alpha1" {
        errs = append(errs, fmt.Sprintf("schema_version must be 'v1alpha1', got '%s'", cfg.SchemaVersion))
    }
    // ... environment / engine / cases / judge ...
    if len(errs) > 0 {
        return fmt.Errorf("validation errors:\n  - %s", strings.Join(errs, "\n  - "))
    }
    return nil
}
```

**为什么累积而不是发现第一个就 return？** 对用户友好得多——「修一个跑一次 → 修下一个」是糟糕体验，**一次性看到全部错误**才能高效修复。错误格式统一：`validation errors:\n  - err1\n  - err2`，每条缩进对齐。

**runtime 特化校验**有「前置门（preflight gate）」的注释（[`validator.go:70-75`](../../internal/config/validator.go#L70)）：

> Docker-runtime fields that would otherwise silently pass `skill-up validate`
> and only fail later when NewDockerRuntime constructs the container — catch
> them at the preflight gate.

把运行期错误**提前到加载期**。同一个校验在 `runtime/docker.go` 里也会做（运行期兜底），但**两层防御**比单层稳。

#### 子集校验正确性：run vs validate

这是配置系统里**最精巧**的设计点之一。三个层次的入口（[`validator.go:352-397`](../../internal/config/validator.go#L352)）：

| 入口 | 范围 | 用途 |
|------|------|------|
| `ValidateAll` | eval + 全部 cases | `skill-up validate` |
| `ValidateCasesWithEvalDefaults` | 任意 case 子集 + eval 默认 | `skill-up run` 过滤后 |
| `ValidateCases` | 仅 case 子集 | 内部组合 |

注释明说（[`validator.go:359-367`](../../internal/config/validator.go#L359)）：

> `skill-up run` calls this with only the cases left after include/exclude
> filters, so an invalid unselected case never blocks a filtered run;
> `skill-up validate` passes every case (via ValidateAll) for full-suite
> validation.

**关键问题**：去重逻辑如果依赖「全量 cases 的顺序索引」，过滤后的子集就会漏判。怎么解决？靠前面 loader 注入的 `SourceFile`——它是**每个 case 自带的元数据**，子集校验依然正确。去重时还会做 **`path.Clean` 归一化**（[`validator.go:437`](../../internal/config/validator.go#L437)）：`cases/a.yaml` 和 `./cases/a.yaml` 经 Clean 后是同一个文件。这就是「**子集校验正确性**」的关键。

#### 延迟校验：engine.custom 等 `--engine` override 后

注释反复强调（[`loader.go:79-82`](../../internal/config/loader.go#L79)、[`validator.go:84-86`](../../internal/config/validator.go#L84)）：

> Custom engine env resolution and validation are intentionally deferred:
> the final engine name is only known after CLI overrides (--engine), so
> the caller invokes ResolveCustomEngineConfig once that is settled.

**为什么延迟？** 考虑这个场景：

```yaml
engine:
  name: claude_code        # ← 加载期看到这个名字（内置引擎）
  custom:
    transport: local       # ← claude_code 是内置引擎，custom 块本该被忽略
    local:
      command: broken-cmd  # ← 但用户可能 --engine my-custom override
```

如果加载期立即校验 custom，用户用 `--engine claude_code` 时会被 broken-cmd 阻塞——但这个 custom 块根本不会被使用。**只有 `--engine` 应用后，才知道 custom 是否生效**。

所以流程是：

```
LoadEvalConfig (不校验 custom)
    ↓
ValidateEvalConfig (校验除 custom 外的全部)
    ↓
resolveEvalConfig (应用 --engine override)
    ↓
ResolveCustomEngineConfig (校验 custom)
```

> **Java 类比**：等价于 Spring 的 `@ConditionalOnProperty(name = "engine.name", havingValue = "custom")`。skill-up 没有 IoC 容器，所以靠**显式的两阶段调用**实现 late binding。

## 5. 检查点自测

答得上才算过。先自己想，再核对答案。

### Q1：为什么 CustomAgent 不嵌 CLIAgent？

**答**：因为 Custom Engine 的执行模型**根本不是 CLI**（可能是本地命令、HTTP 服务，没有「安装」概念）。如果嵌 CLIAgent，将来给 CLIAgent 加方法时会**意外漏进来**——对 HTTP 引擎来说，「跑 InstallMCP 命令」这种语义完全是错的。所以 CustomAgent 只嵌 BaseAgent（共享 Name / 凭据 / env 合并 / installSkillDefault 这些最基础能力），其余方法**显式实现**（5 个 no-op + Run）。这是 **Effective Java Item 18「组合优于继承」**的体现——控制接口表面，避免被模板类默认行为绑架。

### Q2：agentkind 为什么是叶子包？

**答**：因为 `internal/agent`（工厂分发）和 `internal/config`（校验「是不是合法引擎」）都要用这份引擎名清单。如果放在 `agent` 包，`config` import `agent` 但 `agent` 可能又间接依赖 `config`——**循环依赖**，Go 编译器拒绝。抽成**无任何内部依赖的叶子包**（`agentkind`），谁都能 import 它，它不依赖任何人。包注释明说：以前这份清单在两个包里各抄一份，挂着「keep in sync」注释——**注释不能保证同步，编译器才能**。

### Q3：case 文件路径相对什么解析？

**答**：相对 **skill 根目录**（SKILL.md 所在目录），不相对 eval.yaml 所在目录。源码在 [`loader.go:111`](../../internal/config/loader.go#L111)：`fullPath := filepath.Join(l.skillDir, casePath)`。注释说明原因：让「在 skill 目录里跑」和「显式传 `evals/eval.yaml`」两种调用方式**行为一致**。注意 `skillDir` 是 `NewLoader` 里先 `filepath.Abs` 再 `FindSkillDir` 向上找 SKILL.md 得到的——所以 case 路径最终解析成绝对路径。

### Q4：分层校验有哪些阶段？

**答**：7 个阶段（按数据流顺序）：

1. **文档级**：schema_version / environment.type / engine.name / cases.files 非空。
2. **类型枚举**：Type 字段是合法枚举（none/opensandbox/docker）。
3. **runtime 特化**：docker 必须 image、workspace_mount 绝对路径。
4. **网络策略**：network_policy 配置合法性（deny_all / allow_declared）。
5. **case 级**：input 互斥、turn 完整、post_condition、capture。
6. **去重**：case 文件路径归一化后去重、case id 去重。
7. **延迟（customengine）**：engine.custom 块校验，等 `--engine` override 后。

每个阶段只做自己擅长的检查，避免一个巨型函数——这等价于 Java 里 `@NotNull` / 自定义 `@ConstraintValidator` / `@Valid` 级联 / `@GroupSequence` 分阶段的组合。

### Q5：run 和 validate 的校验范围有何不同？

**答**：

- **`skill-up validate`** 走 `ValidateAll`，校验 **eval + 全部 cases**，目标是「整套配置能不能用」。
- **`skill-up run`** 走 `ValidateCasesWithEvalDefaults`，只校验 **过滤后选中的 case 子集**——未选中的 case 即使有问题也不阻塞本次 run。

**关键设计**：去重逻辑依赖每个 case 自带的 `SourceFile` 元数据（loader 注入），而不是「全量 cases 的顺序索引」，所以**子集校验依然正确**——不会因为过滤掉某个 case 而漏判重复。这是「子集校验正确性」的精妙之处。

## 7. 小结 + 下一课预告

### 本课小结

本课覆盖了 skill-up 的**两大基础设施**：

1. **多引擎适配层**（`internal/agent/`）：用「**Agent 接口 + DetectAgent 工厂 + BaseAgent/CLIAgent 模板方法 + 4 引擎具体实现 + CustomAgent 组合**」这套结构，把「4 家完全不同的 Coding Agent CLI + 用户自定义引擎」统一成一个稳定的 7 方法接口。核心是三个 GoF 模式落地——**适配器**（统一接口）、**工厂**（集中路由 + 别名归一）、**模板方法**（共享流程骨架）。最值得讲的设计决策是 **CustomAgent 故意不嵌 CLIAgent**（组合优于继承），以及 transcript 归一时 **token 用 max 而非 sum**（累计快照语义）。

2. **配置系统**（`internal/config/`）：把 `eval.yaml` 从「字符串文档」变成「**强类型 + 默认值 + 多阶段校验 + 不可变 + 安全脱敏**」的运行时对象。核心是「**配置即代码**」——`//go:embed defaults.yaml` 让文档和代码不漂移；分层校验器把 95% 的错误挡在运行前；`SourceFile` 元数据保证子集校验正确；延迟校验让 `engine.custom` 等 `--engine` override 后才生效。

**一句话记忆**：agent 包是「**适配器 + 工厂 + 模板方法**」三件套；config 包是「**schema + embed 默认 + 分层校验**」三件套。两者通过 `agentkind` 叶子包解耦。

### 下一课预告：L06 跑得稳

引擎接好了、配置加载了，下一课讲「**怎么让评测跑得稳**」：

- **并发控制**：信号量限流、worker pool，怎么在 `parallelism=N` 下既快又不炸。
- **重试策略**：`RetryPolicy`（max_retries / retry_on），超时和错误分别怎么重试。
- **超时控制**：`context.WithTimeout` 的使用，为什么 session 解析要用 `context.WithoutCancel`（本课 3.6 提过伏笔）。
- **进程组管理**：超时后怎么 kill 整个进程组（SIGTERM→SIGKILL 升级），避免孤儿进程。
- **Runtime 三后端**（none / opensandbox / docker）怎么隔离，为 L07 的沙箱安全打基础。

这些是「**让系统在生产里稳**」的硬功夫，面试里和「高并发」「容错」强相关。去 [L06 跑得稳](./L06-跑得稳.md)。
