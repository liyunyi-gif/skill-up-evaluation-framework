# 05 · 配置加载与分层校验（eval.yaml v1alpha1 + Loader + Validator）

> 一句话定位：**配置是 skill-up 的「类型系统」**——`eval.yaml` 描述「在什么环境里、用什么 Agent、跑哪些 case、怎么判分」，整个运行期行为都由这份文档驱动；`internal/config` 包负责把 YAML 文档变成 Go 里**强类型、带默认、被校验过、不可变**的对象，并在加载阶段就把 95% 的错误挡在 `validate` 之前。

这是典型的「**配置即代码（Configuration as Code）**」思路：YAML 不是被运行时随手读的字符串，而是先经过 schema 对齐、默认值注入、分层校验、敏感字段脱敏，再以「干净对象」的形式进入业务层。对 Java 工程师来说，可以把它理解成 **Spring Boot 的 `@ConfigurationProperties` + `@Valid` + `ConfigurationPropertiesBindingPostProcessor`** 的组合：先把扁平 YAML 绑定到 POJO，再做 JSR-303 Bean Validation，再做 `Binder` 默认值注入——只不过这里全部用纯 Go 手写，没有反射魔法。

本文按「**schema → 默认值 → 路径解析 → 分层校验 → MCP 合并 → customengine 安全**」的数据流顺序逐段拆解，所有引用都标注 `文件名:行号`，可点击核对。

---

## 1. 配置驱动一切：为什么 skill-up 要花一整个包做配置

skill-up 是一个**评测框架**，不是一次性脚本。同一份 eval.yaml 会被 4 个不同入口消费：

| CLI 命令 | 入口 | 用到的 config 子集 |
|---------|------|-------------------|
| `skill-up validate` | `cli/validate.go:11` | 全量校验（eval + 所有 case + customengine） |
| `skill-up run` | `cli/run.go:74` | 加载 + 过滤后只校验选中 case |
| `skill-up list-cases` | `cli/listcases.go` | 只读 case 列表 |
| `skill-up --auto` | `cli/run.go:807` | 自动发现 eval.yaml 或 Anthropic evals.json |

如果配置校验散落在各业务模块（runtime 在 `NewDockerRuntime` 才发现 image 缺失、agent 在启动时才发现 engine.name 非法），用户会得到「**跑到一半才报错**」的糟糕体验，CI 里尤其致命。`internal/config` 的核心目标就是：

1. **类型对齐**：用 Go struct + YAML tag 把扁平 YAML 变成强类型对象（schema.go）
2. **文档与代码不漂移**：默认值用 `//go:embed defaults.yaml` 嵌入，README 里写的默认值和代码里跑的默认值是**同一份源**（defaults.go）
3. **早失败（fail-fast）**：能在加载期发现的错误绝不留到运行期（validator.go）
4. **不可变（immutable）**：合并/拷贝都走 deep copy，调用方拿到的对象不会被别人悄悄改掉（mcp_merge.go、defaults.go）
5. **安全**：把「凭证进命令行」这种典型事故在校验期直接拒绝（customengine.go）

## 2. eval.yaml v1alpha1 完整 schema 逐段讲

### 2.1 顶层结构：`EvalConfig` 9 个字段

```go
// internal/config/schema.go:11-21
type EvalConfig struct {
    SchemaVersion string          `yaml:"schema_version"`
    Environment   Environment     `yaml:"environment"`
    MCP           MCPConfig       `yaml:"mcp"`
    Skills        []SkillRef      `yaml:"skills"`
    Engine        EngineConfig    `yaml:"engine"`
    Cases         CasesConfig     `yaml:"cases"`
    Judge         JudgeConfig     `yaml:"judge"`
    Benchmark     BenchmarkConfig `yaml:"benchmark"`
    Report        ReportConfig    `yaml:"report"`
}
```

这 9 个字段就是 eval.yaml 的**全部顶层 key**，对应「一个评测任务」的全部维度。语义分组：

| 字段 | 维度 | 一句话 |
|------|------|--------|
| `schema_version` | 版本 | 必须 `v1alpha1`，k8s 式 API 版本化 |
| `environment` | 在哪跑 | `none` / `opensandbox` / `docker` 三种运行时 |
| `mcp` | 工具集 | MCP server 列表，eval 级声明，case 级可覆盖 |
| `skills` | 被测技能 | 安装哪些 Skill（`local_path` / `registry`） |
| `engine` | 谁来跑 | Agent 引擎（claude_code/codex/custom） + 模型 |
| `cases` | 跑什么 | case 文件列表 + 默认值 + 并发度 + 重试策略 |
| `judge` | 怎么判 | `rule_based` / `script` / `agent_judge` |
| `benchmark` | 对不对比 | 启用 baseline 对比（A/B） |
| `report` | 怎么输出 | `json` / `junit` / `html` |

> Java 类比：这就是 Spring `@ConfigurationProperties` 的 root bean。每个字段都是一个嵌套 POJO，YAML tag 等价于 `@ConfigurationProperties(prefix = ...)` 的字段绑定。

### 2.2 `Environment`：运行时环境（15 字段 + 类型转换器）

```go
// internal/config/schema.go:24-39
type Environment struct {
    Type                  string            `yaml:"type"` // none, opensandbox, docker
    Image                 string            `yaml:"image,omitempty"`
    SandboxTemplate       string            `yaml:"sandbox_template,omitempty"`
    WorkspaceMount        string            `yaml:"workspace_mount,omitempty"`
    Env                   map[string]string `yaml:"env,omitempty"`
    SetupSteps            []SetupStep       `yaml:"setup_steps,omitempty"`
    UseServerProxy        bool              `yaml:"use_server_proxy,omitempty"`
    ReadyTimeoutSeconds   int               `yaml:"ready_timeout_seconds,omitempty"`
    SandboxTimeoutSeconds int               `yaml:"sandbox_timeout_seconds,omitempty"`
    Entrypoint            []string          `yaml:"entrypoint,omitempty"`
    Metadata              map[string]string `yaml:"metadata,omitempty"`
    Kwargs                map[string]string `yaml:"kwargs,omitempty"`
    NetworkPolicy         string            `yaml:"network_policy,omitempty"` // deny_all, allow_declared
    AllowedEgress         []string          `yaml:"allowed_egress,omitempty"` // FQDN/wildcard egress allowlist
}
```

**字段含义**：
- `Type`：**唯一必填**（除 `none` 外的运行时类型）；枚举值在 `validator.go:24-28` 集中定义（`runtimeTypeNone` / `runtimeTypeOpenSandbox` / `runtimeTypeDocker`）。
- `Image` / `SandboxTemplate`：docker 需要 image，opensandbox 二选一（image 或 sandbox template）。
- `WorkspaceMount`：容器内挂载点，docker 模式下**必须是绝对路径**（`validator.go:582` 校验）。
- `Env` / `SetupSteps`：容器启动时的环境变量与初始化命令。
- `NetworkPolicy` / `AllowedEgress`：网络隔离策略，`deny_all` 或 `allow_declared`（白名单）。

**最值得关注的是 `ToRuntimeConfig()`** ——这是「配置层 → 运行时层」的**适配器方法**：

```go
// internal/config/schema.go:42-65
func (e Environment) ToRuntimeConfig() runtime.Config {
    setupSteps := make([]runtime.SetupStep, len(e.SetupSteps))
    for i, s := range e.SetupSteps {
        setupSteps[i] = runtime.SetupStep{Run: s.Run}
    }

    return runtime.Config{
        Type:            e.Type,
        Image:           e.Image,
        WorkspaceMount:  e.WorkspaceMount,
        Env:             e.Env,
        SetupSteps:      setupSteps,
        SandboxTemplate: e.SandboxTemplate,
        UseServerProxy:  e.UseServerProxy,
        ReadyTimeout:    time.Duration(e.ReadyTimeoutSeconds) * time.Second,
        SandboxTimeout:  time.Duration(e.SandboxTimeoutSeconds) * time.Second,
        Entrypoint:      e.Entrypoint,
        Metadata:        e.Metadata,
        Kwargs:          e.Kwargs,
        NetworkPolicy:   e.NetworkPolicy,
        AllowedEgress:   e.AllowedEgress,
        Delete:          true,   // ← 硬编码
    }
}
```

**为什么要在 config 层做转换？** 因为 `internal/runtime` 是下游消费者，它不应该知道 YAML 的存在。这一层做的就是：
1. **单位转换**：`ReadyTimeoutSeconds int` → `ReadyTimeout time.Duration`（秒→`time.Duration`）。Java 里类似 `@DurationUnit(ChronoUnit.SECONDS)`。
2. **类型翻译**：`[]SetupStep` → `[]runtime.SetupStep`（config 的 SetupStep 只有 `Run` 一个字段，runtime 的 SetupStep 可能有更多内部字段）。
3. **硬编码默认**：`Delete: true`——所有运行时用完即删，由 config 层一次性决定，下游不能改。

> Java 类比：这就是 Spring 的 `Converter<SourceType, TargetType>` 或 MapStruct 的 `@Mapping`。config 层的 `Environment` 是「**用户视图**」，`runtime.Config` 是「**内部视图**」，两者解耦。

### 2.3 `MCPConfig` / `MCPServer`：工具服务声明

```go
// internal/config/schema.go:72-86
type MCPConfig struct {
    Servers []MCPServer `yaml:"servers"`
}

type MCPServer struct {
    Name      string   `yaml:"name"`
    Mode      string   `yaml:"mode"`                // mocked, real
    Transport string   `yaml:"transport,omitempty"` // stdio, http
    Command   string   `yaml:"command,omitempty"`   // for stdio MCP servers
    Args      []string `yaml:"args,omitempty"`      // for stdio MCP servers

```

**字段含义**：
- `Name`：MCP server 唯一标识，**合并时的 key**（见 §7）。
- `Mode`：`mocked`（用 fixture 模拟）或 `real`（真实 MCP server）。MVP 阶段**case 级只能用 `mocked`**（`mcp_merge.go:57`）。
- `Transport`：`stdio`（子进程）或 `http`（远端）。
- `Command` / `Args`：stdio 模式下的启动命令。
- `Endpoint`：http 模式下的服务地址。
- `ConfigRef`：mocked 模式下指向 fixture 的引用，`filesystem` 这个内置 server 例外（`mcp_merge.go:60`）。

### 2.4 `SkillRef`：被测技能的来源

### 2.5 `EngineConfig`：Agent 引擎配置（核心）

```go
// internal/config/schema.go:96-106
type EngineConfig struct {
    Name    string      `yaml:"name"` // claude_code, codex, custom
    Version string      `yaml:"version,omitempty"`
    Entry   string      `yaml:"entry,omitempty"`
    Model   ModelConfig `yaml:"model"`
    // Kwargs carries agent-specific key/value options. Each agent reads only
    // the keys it understands; unknown keys are ignored. Recognised keys are
    // documented per agent (e.g. codex honours "bypass_sandbox").
    Kwargs map[string]string    `yaml:"kwargs,omitempty"`
    Custom *customengine.Config `yaml:"custom,omitempty"`
}

// internal/config/schema.go:109-114
type ModelConfig struct {
    Provider string            `yaml:"provider"` // anthropic, openai, azure, ollama
    Name     string            `yaml:"name"`
    BaseURL  string            `yaml:"base_url,omitempty"`
    Params   map[string]string `yaml:"params,omitempty"`
}
```

**几个关键设计**：

1. **`Name` 是必填**，但 `validator.go:80` 只校验非空——**真正的「是否合法引擎」校验是延迟的**（见 §6.6 和 §8）。原因：`--engine` CLI override 会改这个名字，加载期还不知道最终值。

2. **`Kwargs` 是「松散契约」**：注释明确说「each agent reads only the keys it understands; unknown keys are ignored」。这是 Go 里常见的**可选能力（optional capabilities）模式**——不同 agent 支持不同 kwargs（如 codex 认 `bypass_sandbox`），统一用一个 `map[string]string` 承载，避免每加一个 agent 就改 schema。Java 里等价于 Spring 的 `@ConditionalOnProperty` 或 SPI 机制。

3. **`Custom *customengine.Config`** 是**指针**，关键设计：
   - 指针可以区分「未声明（nil）」和「声明了空块（非 nil 但字段为零值）」。
   - 只有 `Name` 不是内置引擎时才走 custom 分支（`customengine.go:194`）。

内置引擎清单在**单独的 leaf 包** `internal/agentkind/agentkind.go:12-34`：

```go
const (
    ClaudeCode      = "claude_code"
    ClaudeCodeAlias = "claude-code"
    Codex           = "codex"
    QoderCLI        = "qodercli"
    QoderAlias      = "qoder"
    QoderCLIAlias   = "qoder-cli"
    QwenCode        = "qwen_code"
    QwenCodeAlias   = "qwen-code"
    QwenAlias       = "qwen"
)
```

**为什么独立成 leaf 包？** `agentkind.go:1-8` 的包注释说得明明白白：「previously the list was duplicated in both packages with a 'keep in sync' comment」。`internal/agent`（工厂分发）和 `internal/config`（校验）都要用这份清单，如果放在任一边都会造成循环依赖。**抽成无依赖的 leaf 包**是 Go 解决循环依赖的标准套路。

### 2.7 `JudgeConfig`：评测策略（schema 最复杂的部分）

```go
// internal/config/schema.go:144-163
type JudgeConfig struct {
    Type       string              `json:"type" yaml:"type"` // rule_based, script, agent_judge
    ScriptPath string              `json:"script_path,omitempty" yaml:"script_path,omitempty"`
    Model      string              `json:"model,omitempty" yaml:"model,omitempty"`
    Criteria   []string            `json:"criteria,omitempty" yaml:"criteria,omitempty"`
    Skills     []SkillRef          `json:"skills,omitempty" yaml:"skills,omitempty"`
    Context    *JudgeContextConfig `json:"context,omitempty" yaml:"context,omitempty"`
    // PassThreshold is the minimum pass rate for agent_judge.
    // Nil means "not configured", so the judge layer applies its default of 0.7.
    // When set explicitly, the value must be in the inclusive range [0.0, 1.0].
    PassThreshold *float64 `json:"pass_threshold,omitempty" yaml:"pass_threshold,omitempty"`
    // TimeoutSeconds bounds a single judge invocation in seconds ...
    TimeoutSeconds *int   `json:"timeout_seconds,omitempty" yaml:"timeout_seconds,omitempty"`
    Success        []Rule `json:"success,omitempty" yaml:"success,omitempty"`
    Failure        []Rule `json:"failure,omitempty" yaml:"failure,omitempty"`
}
```

**两个用指针的字段值得专门讲**：

- `PassThreshold *float64`：注释明确说「Nil means not configured, so the judge layer applies its default of 0.7」。如果用 `float64`，零值 `0.0` 会被误解成「阈值 0」，导致所有 case 都 pass——**这是配置驱动系统里最经典的「零值歧义」陷阱**。Go 没有 Java 那种 `Float` 包装类，所以用 `*float64` 显式区分「未设置」和「设置了 0」。

- `TimeoutSeconds *int`：同样的理由，`0` 既可能表示「无超时」也可能表示「没配置」，用 `*int` 消除歧义。注释还说明了不同 judge 类型对 `0` 的语义不同（script 回退到 30s 默认，agent_judge 视为「无 judge 级 deadline」）。

> Java 工程师的直觉：Go 里 `*T` ≈ Java 的 `Optional<T>`，但**没有 `Optional` 那么啰嗦**，且**可空性不会泄漏到类型签名**（一个坑）。这里用指针是为了让 `omitempty` 在 YAML 序列化时能正确省略字段——nil 指针会被省略，`*p == 0` 不会。

`Judge` 的 `Type` 枚举在 `validator.go:16-20`：
```go
const (
    judgeTypeRuleBased    = "rule_based"
    judgeTypeScript       = "script"
    judgeTypeAgentJudge   = "agent_judge"
    maxRetryPolicyRetries = 10
)
```

每种 type 对应的必填字段不同（`validator.go:228-240`）：
- `script` → `script_path` 必填
- `agent_judge` → `model` 和 `criteria` 必填

这是典型的「**判别联合（discriminated union）**」：用 `type` 字段做判别，其余字段的有效性取决于 type。Go 没有原生 sum type，靠校验器手写实现；Java 里类似 Jackson 的 `@JsonTypeInfo(use=Id.NAME, include=As.PROPERTY, property="type")` + `@JsonSubTypes`。

`JudgeContextConfig` / `JudgeContextLimits` / `JudgeContextAttachment` 是 agent_judge 的「**喂什么材料给判官 LLM**」配置（profile/final_message/transcript/workspace_diff/generated_files），字段较多但不复杂，展开见 `schema.go:166-187`。

## 3. `CaseConfig` 详解：单个测试用例

case 文件是独立 YAML，通过 `eval.yaml` 的 `cases.files` 列表引用。一个 case 描述「给 agent 一个输入，检查它的输出」。

```go
// internal/config/schema.go:253-281
type CaseConfig struct {
    ID          string      `yaml:"id"`
    Title       string      `yaml:"title"`
    Description string      `yaml:"description"`
    Tag         string      `yaml:"tag"` // trigger_test, functional_test
    Input       Input       `yaml:"input"`
    Context     Context     `yaml:"context"`
    Constraints Constraints `yaml:"constraints"`
    Expect      Expect      `yaml:"expect"`
    Judge       JudgeConfig `yaml:"judge,omitempty"`
    MCP         MCPConfig   `yaml:"mcp,omitempty"`
    CollectArtifacts []string `yaml:"collect_artifacts,omitempty"`

    // SourceFile is the cases.files entry this case was loaded from ...
    // excluded from marshalling. Duplicate-case validation keys off it ...
    SourceFile string `json:"-" yaml:"-"`
}
```

**最特别的字段**：`SourceFile string` 带的 tag 是 `json:"-" yaml:"-"`——这意味着它**永远不会被序列化**，纯粹是 loader 在加载时注入的「元数据」。它的存在是为了让**去重校验能在 case 子集上正确工作**（见 §6.5）。

> Java 类比：这就是 JPA 里 `@Transient` 注解的等价物——字段只在运行时存在，不参与持久化。

### 3.1 `Input`：输入的两种互斥形态

```go
// internal/config/schema.go:284-287
type Input struct {
    Prompt string `yaml:"prompt,omitempty"`
    Turns  []Turn `yaml:"turns,omitempty"`
}
```

**互斥校验**在 `validator.go:116-121`：
```go
if cfg.Input.Prompt == "" && len(cfg.Input.Turns) == 0 {
    errs = append(errs, "input.prompt or input.turns is required")
}
if cfg.Input.Prompt != "" && len(cfg.Input.Turns) > 0 {
    errs = append(errs, "input.prompt and input.turns are mutually exclusive")
}
```

- `prompt`：单轮对话，一句话丢给 agent。
- `turns`：多轮对话，每轮有自己的 `post_condition` 和 `capture`。

两者**必须二选一**——既不能都没有，也不能同时有。这是「**XOR 约束**」，Java 的 Bean Validation 里要写自定义注解，Go 里就是两行 if。

### 3.2 `Turn` / `PostCondition` / `CaptureRule`：多轮对话的核心

```go
// internal/config/schema.go:290-296
type Turn struct {
    Role           string         `yaml:"role"` // user
    Content        string         `yaml:"content"`
    PostCondition  *PostCondition `yaml:"post_condition,omitempty"`
    Capture        []CaptureRule  `yaml:"capture,omitempty"`
    TimeoutSeconds int            `yaml:"timeout_seconds,omitempty"`
}

// internal/config/schema.go:299-304
type PostCondition struct {
    MustContainAny []string `yaml:"must_contain_any,omitempty"`
    MustContainAll []string `yaml:"must_contain_all,omitempty"`
    MustNotContain []string `yaml:"must_not_contain,omitempty"`
    OnFail         string   `yaml:"on_fail,omitempty"` // skip_remaining, fail
}

// internal/config/schema.go:307-311
type CaptureRule struct {
    Variable string `yaml:"variable"`
    Pattern  string `yaml:"pattern,omitempty"`
    JSONPath string `yaml:"jsonpath,omitempty"`
}
```

**`PostCondition.OnFail`** 是 case 控制流的「**短路开关**」：`fail`（默认，直接判 fail）或 `skip_remaining`（跳过后续 turn，但保留当前结果）。校验在 `validator.go:597-612`：
```go
if pc.OnFail != "" && pc.OnFail != "fail" && pc.OnFail != "skip_remaining" {
    errs = append(errs, fmt.Sprintf("%s.on_fail must be empty, \"fail\", or \"skip_remaining\", got %q", prefix, pc.OnFail))
}
if len(pc.MustContainAny) == 0 && len(pc.MustContainAll) == 0 && len(pc.MustNotContain) == 0 {
    errs = append(errs, prefix+" must include at least one of must_contain_any, must_contain_all, or must_not_contain")
}
```

后者是「**至少填一个**」约束——空的 PostCondition 没意义。

**`CaptureRule`** 用来从 agent 回复里**抽变量**，给后续 turn 用。`Pattern`（正则）和 `JSONPath` 是**互斥**的两种抽取方式，校验在 `validator.go:615-643`：
```go
hasPattern := cr.Pattern != ""
hasJSONPath := cr.JSONPath != ""
if !hasPattern && !hasJSONPath {
    errs = append(errs, prefix+" must specify exactly one extractor: pattern or jsonpath")
} else if hasPattern && hasJSONPath {
    errs = append(errs, prefix+" must specify exactly one extractor: pattern or jsonpath (both set)")
}
// Regex pattern must compile
if hasPattern {
    if _, err := regexp.Compile(cr.Pattern); err != nil {
        errs = append(errs, fmt.Sprintf("%s.pattern is invalid regex: %v", prefix, err))
    }
}
```

值得注意：**正则在这里就 compile 一次**，而不是每次匹配时反复 compile——这是 Go 里 `regexp.MustCompile` 的标准优化（compile 一次，多次 `Match`）。

`captureVariablePattern = ^[A-Za-z_][A-Za-z0-9_]*$`（`validator.go:594`）：变量名必须是合法标识符，避免后面 `${var}` 模板替换时出现歧义。

### 3.3 `Context`：测试夹具（fixture）

```go
// internal/config/schema.go:314-318
type Context struct {
    RepoFixture string            `yaml:"repo_fixture,omitempty"`

// internal/config/schema.go:321-326
```

三种夹具来源，**互不冲突可组合**：
- `RepoFixture`：复用一个完整的 git 仓库镜像（一般在 `evals/fixtures/` 下）。

这是「**fixture 三选 N**」的灵活设计，case 作者按需组合。

### 3.4 `Constraints` / `Expect`：执行限制与基础断言


### 3.5 case 级覆盖 eval 级：MCP 和 Judge 的覆盖语义

- **MCP**：按 name 整条替换或追加，详见 §7。

## 4. v1alpha1 版本化设计：k8s 式 API 约定

### 4.1 `schema_version` 强制为 `v1alpha1`

校验在 `validator.go:57-61`：
```go
if cfg.SchemaVersion == "" {
    errs = append(errs, "schema_version is required")
} else if cfg.SchemaVersion != "v1alpha1" {
    errs = append(errs, fmt.Sprintf("schema_version must be 'v1alpha1', got '%s'", cfg.SchemaVersion))
}
```

这是**最严格**的版本约束：缺字段报错，写 `v1beta1` / `v1` / `v2` 全部拒绝。

### 4.2 为什么遵循 k8s API 约定

`v1alpha1` 是 **Kubernetes API 风格的版本号**：
- `v` 前缀
- `1` 是主版本号
- `alpha` 表示「**实验性，可能在 minor 版本间 break**」
- 数字后缀 `1` 是 alpha 序号

| 阶段 | 含义 | 兼容性承诺 |
|------|------|-----------|
| `alpha` (`v1alpha1`) | 实验性，默认可能禁用 | **不承诺**，随时可能 break |
| `beta` (`v1beta1`) | 预发布，默认启用 | 同一 beta 期内兼容 |
| `GA` (`v1`) | 正式发布 | 长期兼容 |

**为什么 skill-up 选 `v1alpha1`？** 因为它**还在快速演进**，字段可能会调整。提前承诺兼容会变成技术债——这是开源项目早期常见的版本策略。

### 4.3 字段/常量集中，预留升级路径

所有枚举值都**集中在 validator.go 顶部**（`validator.go:16-34`）：
```go
const (
    judgeTypeRuleBased    = "rule_based"
    judgeTypeScript       = "script"
    judgeTypeAgentJudge   = "agent_judge"
    maxRetryPolicyRetries = 10
)

const (
    runtimeTypeNone        = "none"
    runtimeTypeOpenSandbox = "opensandbox"
    runtimeTypeDocker      = "docker"
)

const (
    customTransportLocal = "local"
    customTransportHTTP  = "http"
)
```

**好处**：
1. 一个 place to change——以后从 `v1alpha1` 升到 `v1beta1`，新增字段/枚举只改一处。
2. 避免散落的字符串字面量（"none" / "docker" / "rule_based"）——这是 bug 温床。
3. 配合 `isValidRuntimeType` / `isValidJudgeType` 等枚举校验函数（`validator.go:559-591`），新增枚举值只改 const + switch。

### 4.4 未来升级路径（设计推断）

当 `v1alpha1` 升 `v1beta1` 时，可以：
1. 新增 `schema_version: v1beta1` 分支
2. 在 loader 里做 **版本路由**：`v1alpha1` 走旧 schema，`v1beta1` 走新 schema
3. 必要时做 **webhook 式迁移**：把旧文档自动转换为新版本（k8s 的标准做法）

当前还没这套机制，但 `schema_version` 字段的存在已经为它**预留了入口**——这是版本化设计的关键：**先把版本号钉死，未来才能分支**。

## 5. Loader：以 SKILL.md 为锚点的路径解析

### 5.1 `NewLoader`：为什么必须 `filepath.Abs`

```go
// internal/config/loader.go:43-60
func NewLoader(evalPath string) *Loader {
    absEvalPath := evalPath
    if abs, err := filepath.Abs(evalPath); err == nil {
        absEvalPath = abs
    }

    evalDir := filepath.Dir(absEvalPath)
    skillDir, fallback := FindSkillDir(evalDir)
    if fallback {
        logging.Warnf("SKILL.md not found within %d levels above %s; falling back to %s", maxSkillDirSearchDepth, evalDir, skillDir)
    }

    return &Loader{
        evalPath: absEvalPath,
        evalDir:  evalDir,
        skillDir: skillDir,
    }
}
```

**注释明说**了 `filepath.Abs` 的必要性（`loader.go:40-42`）：
> evalPath is normalized with filepath.Abs so EvalDir is absolute; otherwise a relative path like ./evals/eval.yaml yields Dir chains such as "." and breaks skill root resolution (e.g. InstallSkill target becomes ".qoder/skills/.")

**场景**：用户在 skill 根目录下执行 `skill-up run ./evals/eval.yaml`。
- 不调 `Abs`：`evalDir = filepath.Dir("./evals/eval.yaml") = "./evals"`，`FindSkillDir("./evals")` 上一级是 `.`——**`InstallSkill` 的 target 会拼成 `.qoder/skills/.`**，路径错乱。
- 调了 `Abs`：`evalDir = "/abs/path/to/skill/evals"`，`FindSkillDir` 上一级是 `/abs/path/to/skill`，正确找到 SKILL.md。

**教训**：Go 的 `filepath.Dir` 对相对路径的处理是「**字面切分**」，不会返回绝对路径。任何依赖 `Dir` 链做路径解析的代码，**第一步必须 Abs**。

### 5.2 `FindSkillDir`：向上查最多 10 层

```go
// internal/config/loader.go:214-229
func FindSkillDir(startDir string) (string, bool) {
    dir := filepath.Clean(startDir)
    for depth := 0; depth <= maxSkillDirSearchDepth; depth++ {
        if _, err := os.Stat(filepath.Join(dir, "SKILL.md")); err == nil {
            return dir, false
        }

        parent := filepath.Dir(dir)
        if parent == dir {
            break
        }
        dir = parent
    }

    return filepath.Dir(startDir), true
}
```

**关键点**：

1. **`maxSkillDirSearchDepth = 10`**（`loader.go:17`）——硬上限，防止在巨型仓库里无限向上找。
2. **`parent == dir` 终止条件**：到达文件系统根（如 `/`），`filepath.Dir("/") == "/"`。
3. **fallback 行为**：找不到时返回 `filepath.Dir(startDir)` 且 `fallback=true`，**不报错**。上层用 `logging.Warnf` 提示，但流程继续——这是「**宽容失败**」设计：允许在非标准目录结构下也能跑。
4. **`SKILL.md` 是「技能根」的锚点**：skill-up 的目录约定是 `skill-root/SKILL.md` + `skill-root/evals/eval.yaml`。SKILL.md 类似 Node 的 `package.json`、Go 的 `go.mod`——**项目根标识符**。

### 5.3 `LoadEvalConfig` + `applyDocumentedDefaults`：默认值的「单一事实源」

```go
// internal/config/loader.go:67-83

// internal/config/loader.go:91-105

    d := DefaultEvalConfig()

        cfg.Cases.Defaults.TimeoutSeconds = d.Cases.Defaults.TimeoutSeconds
    }

```

**注释解释**了为什么只填这 4 个默认（`loader.go:62-66`）：其他未设置的字段保留零值，让 validator 能识别「用户没填」并报错（如 `schema_version` / `environment.type` / `engine.name`）。

**关键设计**：默认值来自 `DefaultEvalConfig()`，而它来自 `//go:embed defaults.yaml`：

```go
// internal/config/defaults.go:60-70

        return nil, err
    }
    return &cfg, nil
}

//go:embed defaults.yaml
var defaultsYAML []byte
```

```yaml
# internal/config/defaults.yaml

  type: none
  workspace_mount: /workspace
  env: {}

mcp:
  servers: []

skills: []

engine:
  name: claude_code
  model: {}

  files: []

    timeout_seconds: 300
    max_turns: 10
  parallelism: 1

  formats: [json]
  artifacts: []
```

**`//go:embed` 的意义**：
1. **编译期嵌入**：`defaults.yaml` 在 `go build` 时被嵌入二进制，运行时不依赖文件系统。
2. **文档与代码不漂移**：README 里写「默认超时 300s、默认 max_turns 10、默认 parallelism 1」，这同一份 yaml 也是代码里的默认值源——**改一处，两边同步**。
3. **没有「魔法数字」**：`300` / `10` / `1` 不散落在 Go 代码里，而是集中在 yaml 里。

> Java 类比：`//go:embed` 类似 Spring Boot 的 `@Value("classpath:defaults.yaml")` 或 `ResourceUtils.readFromJar`。但 Go 的 embed 是**编译期**完成，运行时零开销。

**deep copy 保证不可变**（`defaults.go:21-58`）：

```go
func DefaultEvalConfig() *EvalConfig {
    return deepCopyEvalConfig(defaultEvalConfig)
}

func deepCopyEvalConfig(cfg *EvalConfig) *EvalConfig {
    if cfg == nil {
        return nil
    }
    data, err := yaml.Marshal(cfg)
    if err != nil {
        panic("failed to marshal EvalConfig: " + err.Error())
    }
    var copied EvalConfig
    if err := yaml.Unmarshal(data, &copied); err != nil {
        panic("failed to unmarshal EvalConfig: " + err.Error())
    }
    // Ensure nil slices are initialized to empty slices for consistency
    if copied.MCP.Servers == nil {
        copied.MCP.Servers = []MCPServer{}
    }
    // ... 其他 nil → 空 slice/map ...
    return &copied
}
```

**用 yaml.Marshal/Unmarshal 做 deep copy** 是 Go 里一种取巧但有效的写法：
- 优点：**零反射代码**，任何嵌套结构都能正确拷贝；slice、map、指针全部独立。
- 缺点：性能开销（两次序列化），但默认值加载只在启动时做一次，可接受。
- 替代方案：手写 `clone()` 方法，或用 `github.com/jinzhu/copier`——前者啰嗦，后者增加依赖。

**nil → 空 slice/map 的归一化**：避免调用方对 nil 切片做 `range` 时虽然不 panic 但语义混乱。统一成空 slice 后，业务代码可以放心 `for _, s := range cfg.MCP.Servers`。

`init()` 的 panic 是**故意 fail-fast**（`defaults.go:11-17`）：如果编译期嵌入的 defaults.yaml 都解析不了，那是开发者 bug，运行时没法救——直接 panic 让 CI 红。

### 5.4 `LoadCaseConfig`：路径相对 skillDir、id 文件名兜底、SourceFile 注入

```go
// internal/config/loader.go:108-133
func (l *Loader) LoadCaseConfig(casePath string) (*CaseConfig, error) {
    // casePath is resolved from the skill root so eval configs work the same
    // whether invoked from the skill directory or by passing evals/eval.yaml.
    fullPath := filepath.Join(l.skillDir, casePath)

    data, err := os.ReadFile(fullPath)
    if err != nil {
        return nil, fmt.Errorf("failed to read case file %s: %w", casePath, err)
    }

    var cfg CaseConfig
    if err := yaml.Unmarshal(data, &cfg); err != nil {
        return nil, fmt.Errorf("failed to parse case file %s: %w", casePath, err)
    }

    // Use filename (without extension) as ID if not specified
    if cfg.ID == "" {
        cfg.ID = stripExt(filepath.Base(casePath))
    }

    // Record the source path (as listed in cases.files) so duplicate-case
    // validation can name the offending file even for a filtered subset.
    cfg.SourceFile = casePath

    return &cfg, nil
}
```

**三个细节**：

1. **`filepath.Join(l.skillDir, casePath)`**：case 路径**相对 skill 根**，不相对 eval.yaml 所在目录。注释说明了原因：让「在 skill 目录里跑」和「显式传 `evals/eval.yaml`」两种调用方式**行为一致**。

2. **id 文件名兜底**（`loader.go:124-126`）：如果 case yaml 没写 `id:`，用文件名（去扩展名）做 ID。例如 `cases/basic-test.yaml` 没写 id，自动得到 `basic-test`。这是「**约定大于配置（convention over configuration）**」——Rails、Spring Boot 的核心哲学。

3. **`SourceFile = casePath` 注入**（`loader.go:130`）：把「这个 case 是从 cases.files 里哪个条目加载来的」记录到对象里，供后续去重校验用（§6.5）。注意 `casePath` 是**用户在 eval.yaml 里写的原始字符串**（如 `cases/basic.yaml` 或 `./cases/basic.yaml`），不是 `fullPath`——这样错误信息对用户更友好。

### 5.5 `parseSkillName`：SKILL.md 的 YAML frontmatter 解析

```go
// internal/config/loader.go:240-262
func parseSkillName(skillDir string) (string, bool) {
    data, err := os.ReadFile(filepath.Join(skillDir, "SKILL.md"))
    if err != nil {
        return "", false
    }

    fm, ok := extractFrontmatter(data)
    if !ok {
        return "", false
    }

    var meta skillFrontmatter
    if err := yaml.Unmarshal(fm, &meta); err != nil {
        return "", false
    }

    name := strings.TrimSpace(meta.Name)
    if name == "" {
        return "", false
    }

    return name, true
}

// internal/config/loader.go:269-285
func extractFrontmatter(data []byte) ([]byte, bool) {
    lines := bytes.Split(data, []byte("\n"))

    if len(lines) == 0 || !isFence(lines[0]) {
        return nil, false
    }

    for i := 1; i < len(lines); i++ {
        if isFence(lines[i]) {
            return bytes.Join(lines[1:i], []byte("\n")), true
        }
    }

    return nil, false
}
```

SKILL.md 是 markdown，但开头可以有一段 YAML frontmatter（Hugo / Jekyll 风格）：

```markdown
---
name: my-skill
version: 1.0.0
---

# My Skill

正文...
```

`extractFrontmatter` 的实现细节：
- **必须第一行就是 `---`**——否则视为没有 frontmatter（不尝试在文档中间找）。
- **返回下一个 `---` 之前的所有行**。
- **失败时返回 `false`**，**不会把 markdown 正文喂给 yaml 解析器**（注释 `loader.go:266-268`）——否则 yaml 解析 markdown 表格、标题会得到一堆垃圾字段。

`isFence` 容忍 `---` 后面的尾随空白和 CR（`loader.go:289-291`），兼容 Windows CRLF 行尾。

**为什么从 SKILL.md 读 name？** 因为 skill-up 用 skill name 做：报告目录名、telemetry 属性、artifact 路径。这些都需要一个**稳定的标识符**，而 SKILL.md 是技能的唯一标识文档。

## 6. 分层校验器：多阶段、子集、延迟

`validator.go` 是 config 包最复杂的文件，1200+ 行。它的核心思想是「**分层校验、各司其职**」——不同类型的校验在不同的阶段做，避免一个巨型函数。

### 6.1 校验阶段全景表

| 阶段 | 函数 | 校验内容 | 何时触发 |
|------|------|---------|---------|
| **文档级** | `ValidateEvalConfig` | schema_version、environment.type、engine.name、cases.files 非空 | 加载后立即 |
| **类型枚举** | `isValidRuntimeType` / `isValidJudgeType` | Type 字段是合法枚举 | 文档级内 |
| **runtime 特化** | `validateDockerEnvironment` / `validateNetworkPolicy` | docker 必须 image、workspace_mount 绝对、network_policy 配置 | 文档级内 |
| **case 级** | `ValidateCaseConfig` | input 互斥、turn 完整、post_condition、capture、per-turn rules | 加载每个 case |
| **去重** | `duplicateCaseErrors` | case file 路径归一化后去重、case id 去重 | ValidateCases 入口 |
| **judge 合并** | `ValidateCasesWithEvalDefaults` | 用 eval 级 judge 默认合并 case 级后，校验必填字段 | case 校验后 |
| **延迟（customengine）** | `ResolveCustomEngineConfig` | engine.custom 块、env 引用、敏感字段 | CLI override 后 |

### 6.2 `ValidateEvalConfig`：文档级 + 枚举 + 特化

```go
// internal/config/validator.go:53-106
func (v *Validator) ValidateEvalConfig(cfg *EvalConfig) error {
    var errs []string

    if cfg.SchemaVersion == "" {
        errs = append(errs, "schema_version is required")
    } else if cfg.SchemaVersion != "v1alpha1" {
        errs = append(errs, fmt.Sprintf("schema_version must be 'v1alpha1', got '%s'", cfg.SchemaVersion))
    }

    if cfg.Environment.Type == "" {
        errs = append(errs, "environment.type is required (none, opensandbox, docker)")
    } else if !isValidRuntimeType(cfg.Environment.Type) {
        errs = append(errs, "environment.type must be one of: none, opensandbox, docker")
    }

    if cfg.Environment.Type == runtimeTypeDocker {
        errs = append(errs, validateDockerEnvironment(cfg.Environment)...)
    }

    errs = append(errs, validateNetworkPolicy(cfg.Environment)...)

    if cfg.Engine.Name == "" {
        errs = append(errs, "engine.name is required")
    }

    if len(cfg.Cases.Files) == 0 {
        errs = append(errs, "cases.files must contain at least one case file")
    }
    if cfg.Cases.RetryPolicy.MaxRetries > maxRetryPolicyRetries {
        errs = append(errs, fmt.Sprintf("cases.retry_policy.max_retries must be <= %d", maxRetryPolicyRetries))
    }

    errs = append(errs, validateCollectArtifacts("cases.defaults.collect_artifacts", cfg.Cases.Defaults.CollectArtifacts)...)
    errs = append(errs, validateJudgeTypeAndLocalFields(cfg.Judge)...)

    if len(errs) > 0 {
        return fmt.Errorf("validation errors:\n  - %s", strings.Join(errs, "\n  - "))
    }
    return nil
}
```

**核心模式**：
1. **错误累积**（`var errs []string`）——一次性收集所有错误，最后 `Join` 成一条消息。比「发现第一个错就 return」对用户友好得多（修一个跑一次 → 修下一个 vs 一次性看到全部）。
2. **错误格式统一**：`validation errors:\n  - err1\n  - err2`，每条缩进对齐，方便人眼扫读。
3. **特化校验按 type 分发**：`Type == docker` 才查 docker 必填字段。这种「**类型判别 + 字段要求**」模式在 §2.7 提到过。

**注释明说**（`validator.go:71-75`）：
```go
// Docker-runtime fields that would otherwise silently pass `skill-up
// validate` and only fail later when NewDockerRuntime constructs the
// container — catch them at the preflight gate.
```

这是「**前置门（preflight gate）**」模式：把运行期错误提前到加载期。同一个校验在 `runtime/docker.go` 里也会做（运行期兜底），但**两层防御**比单层稳。

### 6.3 `validateDockerEnvironment` + `validateNetworkPolicy`：runtime 特化校验

`validateNetworkPolicy`（`validator.go:717-761`）是更复杂的特化：

```go
func validateNetworkPolicy(env Environment) []string {
    policy := env.NetworkPolicy
    if policy == "" {
        if len(env.AllowedEgress) > 0 {
            return []string{"allowed_egress requires network_policy: allow_declared"}
        }
        return nil
    }
    if policy != "deny_all" && policy != "allow_declared" {
        return []string{"network_policy must be one of: deny_all, allow_declared"}
    }
    if env.Type == runtimeTypeNone {
        return []string{"network_policy requires environment.type opensandbox or docker (none cannot enforce network isolation)"}
    }
    if env.Type == runtimeTypeDocker && policy == "allow_declared" {
        return []string{"network_policy: allow_declared is not supported for environment.type docker (use deny_all or opensandbox)"}
    }

    var errs []string
    switch policy {
    case "allow_declared":
        if len(env.AllowedEgress) == 0 {
            errs = append(errs, "network_policy: allow_declared requires a non-empty allowed_egress list")
        }
        for i, target := range env.AllowedEgress {
            t := strings.TrimSpace(target)
            if t == "" {
                errs = append(errs, fmt.Sprintf("allowed_egress[%d] must not be empty", i))
                continue
            }
            if strings.ContainsAny(t, "/ ") {
                errs = append(errs, fmt.Sprintf("allowed_egress[%d] %q must be a bare FQDN or wildcard domain, not a URL", i, target))
            }
        }
    case "deny_all":
        if len(env.AllowedEgress) > 0 {
            errs = append(errs, "allowed_egress is only valid with network_policy: allow_declared")
        }
    }
    return errs
}
```

**逻辑链**（自顶向下）：
1. 没声明 policy 但填了 allowed_egress → 报错（egress 没意义）。
2. policy 非法值 → 报错。
3. policy 非空但 runtime 是 `none` → 报错（none 没法做网络隔离）。
4. docker + allow_declared → 报错（docker 当前只支持 `--network=none`，即 deny_all；allow_declared 需要 egress 代理，未实现）。
5. allow_declared：必须有非空 allowed_egress，且每条不能是 URL（不能含 `/` 或空格）。
6. deny_all：不允许声明 allowed_egress（矛盾配置）。

**这条链的精妙之处**：注释 `validator.go:731-737` 解释了 docker 拒绝 allow_declared 的原因——「**Reject early so users do not get a silent 'all egress allowed' container at run time**」。如果不前置校验，docker 容器实际跑起来是「全开 egress」，但用户以为是白名单——**安全语义错位**比报错更可怕。

### 6.4 `ValidateCaseConfig`：case 级完整校验

```go
// internal/config/validator.go:109-163
func (v *Validator) ValidateCaseConfig(cfg *CaseConfig) error {
    var errs []string

    if cfg.Input.Prompt == "" && len(cfg.Input.Turns) == 0 {
        errs = append(errs, "input.prompt or input.turns is required")
    }
    if cfg.Input.Prompt != "" && len(cfg.Input.Turns) > 0 {
        errs = append(errs, "input.prompt and input.turns are mutually exclusive")
    }

    for i, turn := range cfg.Input.Turns {
        if turn.Role == "" {
            errs = append(errs, fmt.Sprintf("input.turns[%d].role is required", i))
        } else if turn.Role != "user" {
            errs = append(errs, fmt.Sprintf("input.turns[%d].role must be \"user\", got %q", i, turn.Role))
        }
        if turn.Content == "" {
            errs = append(errs, fmt.Sprintf("input.turns[%d].content is required", i))
        }
        if turn.TimeoutSeconds < 0 {
            errs = append(errs, fmt.Sprintf("input.turns[%d].timeout_seconds must be non-negative", i))
        }
        if turn.PostCondition != nil {
            errs = append(errs, validatePostCondition(i, turn.PostCondition)...)
        }
        for j, cr := range turn.Capture {
            errs = append(errs, validateCaptureRule(i, j, cr)...)
        }
    }

    turnsTotal := len(cfg.Input.Turns)
    if judgeNeedsLocalValidation(cfg.Judge) {
        errs = append(errs, validateJudgeTypeAndLocalFields(cfg.Judge)...)
    }
    var allRules []Rule
    allRules = append(allRules, cfg.Judge.Success...)
    allRules = append(allRules, cfg.Judge.Failure...)
    errs = append(errs, validatePerTurnRules(allRules, turnsTotal)...)

    errs = append(errs, validateCollectArtifacts("collect_artifacts", cfg.CollectArtifacts)...)
    errs = append(errs, validateCaseMCP(cfg.MCP)...)

    if len(errs) > 0 {
        return fmt.Errorf("validation errors:\n  - %s", strings.Join(errs, "\n  - "))
    }
    return nil
}
```

**逐项要点**：

1. **input XOR 校验**（§3.1 已讲）。
2. **turn.role 必须是 "user"**：当前 MVP 只支持 user 输入（不支持 assistant 注入），注释明说。其他 role（system/assistant）保留扩展空间。
3. **turn.content 必填**：空内容的 turn 没意义。
4. **turn.timeout_seconds 非负**：负数无意义（0 表示「不限制」，由 max_turns 兜底）。
5. **PostCondition/Capture 子结构校验**：递归调用专门的校验函数。
6. **per-turn rules 校验**（`validatePerTurnRules`，`validator.go:646-663`）：检查 `turn_response_contains.turn` / `tool_called_in_turn.turn` 等「**按 turn 索引**」的规则，turn 号不能超过总 turn 数。`turnsTotal == 0` 时不检查（prompt 模式下这些规则本就无意义）。
7. **case-level MCP 校验**（§6.5 已讲 validateCaseMCP，§7 详述语义）。

### 6.5 去重校验：路径归一化与 case 子集正确性

```go
// internal/config/validator.go:420-425
func duplicateCaseErrors(cases []*CaseConfig) []string {
    var errs []string
    errs = append(errs, duplicateCaseFileErrors(cases)...)
    errs = append(errs, duplicateCaseIDErrors(cases)...)
    return errs
}

// internal/config/validator.go:431-452
func duplicateCaseFileErrors(cases []*CaseConfig) []string {
    counts := make(map[string]int, len(cases))
    for _, c := range cases {
        if c.SourceFile == "" {
            continue
        }
        counts[path.Clean(c.SourceFile)]++
    }
    var errs []string
    reported := make(map[string]bool)
    for _, c := range cases {
        if c.SourceFile == "" {
            continue
        }
        norm := path.Clean(c.SourceFile)
        if counts[norm] > 1 && !reported[norm] {
            errs = append(errs, fmt.Sprintf("cases.files lists %q %d times (after path normalization); each case file must appear once", norm, counts[norm]))
            reported[norm] = true
        }
    }
    return errs
}

// internal/config/validator.go:457-477
func duplicateCaseIDErrors(cases []*CaseConfig) []string {
    idFiles := make(map[string][]string, len(cases))
    var order []string
    for _, c := range cases {
        src := c.SourceFile
        if src == "" {
            src = "<unknown source>"
        }
        if _, seen := idFiles[c.ID]; !seen {
            order = append(order, c.ID)
        }
        idFiles[c.ID] = append(idFiles[c.ID], src)
    }
    var errs []string
    for _, id := range order {
        if srcs := idFiles[id]; len(srcs) > 1 {
            errs = append(errs, fmt.Sprintf("duplicate case id %q used by %d case files: %s", id, len(srcs), strings.Join(srcs, ", ")))
        }
    }
    return errs
}
```

**两层去重**：

1. **文件级去重**：`cases.files` 里同一个文件不能列两次。关键点是 **`path.Clean`**——`cases/a.yaml` 和 `./cases/a.yaml` 经 Clean 后都是 `cases/a.yaml`，被认为是同一个文件。这就是 §5.4 把原始 `casePath` 存进 `SourceFile` 的用意：**保留原始字符串用于错误消息，但去重时归一化**。

2. **ID 级去重**：不同文件可能产生同一个 ID（用户显式写了 `id: foo`，或两个文件名去扩展名后相同）。这种情况会**静默覆盖报告**——skill-up 用 case id 做 artifact 目录名、telemetry 属性 key，重复 id 会导致前一个 case 的结果被后一个覆盖。

**`SourceFile` 的关键作用**（注释 `validator.go:416-419`）：
> skill-up writes reports and artifacts keyed by case ID and runs one case per cases.files entry, so a collision would silently overwrite results or double-run a case.

**为什么必须在 case 子集上也能工作？** 看 `ValidateCases` 的注释（`validator.go:359-368`）：
> `skill-up run` calls this with only the cases left after include/exclude filters, so an invalid unselected case never blocks a filtered run; `skill-up validate` passes every case (via ValidateAll) for full-suite validation.

如果去重逻辑依赖「全量 cases 的顺序索引」，过滤后的子集就会漏判。`SourceFile` 是**每个 case 自带的元数据**，子集校验依然正确——这是「**子集校验正确性**」的关键。

```go
    if caseLevel.Type != "" {
        merged := caseLevel
        if merged.Model == "" {
            merged.Model = global.Model
        }
        if merged.PassThreshold == nil {
            merged.PassThreshold = global.PassThreshold
        }
        if merged.TimeoutSeconds == nil {
            merged.TimeoutSeconds = global.TimeoutSeconds
        }
        return merged
    }
    return global

```

**合并语义**：
- case 级有 `type` → 以 case 级为主体，model/pass_threshold/timeout_seconds 字段级 fallback 到 eval 级。

这正是 §3.5 提到的「case 级覆盖 eval 级」的实现。**注意：合并是「为校验构造的临时视图」，不会写回原 config**——避免污染原对象。

## 7. MCP 合并语义：按 name 整条替换 + 不可变

`mcp_merge.go` 实现 case 级 MCP 覆盖 eval 级的合并逻辑。

### 7.1 `MergeCaseMCP`：五种语义

注释 `mcp_merge.go:14-28` 明确列了 5 条语义：

```go
// Merge semantics (SUP-0003):
//  1. If the case declares no servers, the eval-level config is returned as a
//     deep copy (inheritance, unchanged behavior).
//  2. Servers are merged by name while preserving eval-level order: a case-level
//     entry whose name matches an eval-level server replaces that entire entry;
//     a new name is appended to the end.
//  3. Replacement is whole-entry, not a field-level deep merge.
//  4. Duplicate server names within either level are rejected.
//  5. In the MVP, every case-level server must use mode: mocked.
//
// The returned MCPConfig is a fresh value; callers cannot mutate the original
// eval or case configuration through it.
```

实现：

```go
// internal/config/mcp_merge.go:29-74
func MergeCaseMCP(evalMCP MCPConfig, caseMCP MCPConfig) (MCPConfig, error) {
    if len(caseMCP.Servers) == 0 {
        return cloneMCPConfig(evalMCP), nil
    }

    merged := cloneMCPConfig(evalMCP)

    indexByName := make(map[string]int, len(merged.Servers))
    for i, server := range merged.Servers {
        if strings.TrimSpace(server.Name) == "" {
            return MCPConfig{}, errors.New("eval-level mcp server name is required")
        }
        if _, exists := indexByName[server.Name]; exists {
            return MCPConfig{}, fmt.Errorf("duplicate eval-level mcp server name %q", server.Name)
        }
        indexByName[server.Name] = i
    }

    seenCaseNames := make(map[string]struct{}, len(caseMCP.Servers))
    for _, server := range caseMCP.Servers {
        if server.Name == "" {
            return MCPConfig{}, errors.New("case-level mcp server name is required")
        }
        if _, exists := seenCaseNames[server.Name]; exists {
            return MCPConfig{}, fmt.Errorf("duplicate case-level mcp server name %q", server.Name)
        }
        seenCaseNames[server.Name] = struct{}{}

        if server.Mode != mcpModeMocked {
            return MCPConfig{}, fmt.Errorf("case-level mcp server %q must use mode: mocked", server.Name)
        }
        if server.Name != builtinFilesystemMCPServer && strings.TrimSpace(server.ConfigRef) == "" {
            return MCPConfig{}, fmt.Errorf("case-level mcp server %q mocked mode requires config_ref", server.Name)
        }

        cloned := cloneMCPServer(server)
        if idx, ok := indexByName[server.Name]; ok {
            merged.Servers[idx] = cloned
            continue
        }
        merged.Servers = append(merged.Servers, cloned)
        indexByName[server.Name] = len(merged.Servers) - 1
    }

    return merged, nil
}
```

**逐段拆解**：

1. **case 无 server**：直接返回 eval 的 deep copy（语义 1）。
2. **建索引**：eval 级 server 按 name 建索引 `indexByName`，顺便校验 eval 级重名（语义 4）。
3. **遍历 case 级**：每个 case server 必须：
   - 有 name
   - case 内不重名
   - mode 必须是 mocked（语义 5，MVP 限制）
   - mocked 必须有 config_ref（除了内置的 `filesystem`）
4. **合并**：name 在 eval 里存在 → **整条替换**（`merged.Servers[idx] = cloned`）；不存在 → **追加**（语义 2 和 3）。

### 7.2 「整条替换」vs「字段级 deep merge」的设计权衡

语义 3 明确选了**整条替换**。对比两种方案的优劣：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 整条替换（当前） | 简单可预测、易调试、行为清晰 | 想改一个字段得重写整条 |
| 字段级 deep merge | 改字段精细 | 合并语义复杂、易出 bug、调试困难 |

skill-up 选前者——**配置合并的「最小惊讶原则」**：用户写一条 case-level server，就能确定它最终长什么样，不用脑内做字段级 merge 推演。

### 7.3 不可变（immutable）：deep copy 的两层保障

```go
// internal/config/mcp_merge.go:78-96
func cloneMCPConfig(cfg MCPConfig) MCPConfig {
    if cfg.Servers == nil {
        return MCPConfig{}
    }
    servers := make([]MCPServer, len(cfg.Servers))
    for i, server := range cfg.Servers {
        servers[i] = cloneMCPServer(server)
    }
    return MCPConfig{Servers: servers}
}

func cloneMCPServer(server MCPServer) MCPServer {
    cloned := server
    if server.Args != nil {
        cloned.Args = append([]string(nil), server.Args...)
    }
    return cloned
}
```

**为什么必须 deep copy？** 因为：
- `MCPServer` 里有 `Args []string`、`Command string`——slice 是引用类型。
- 如果浅拷贝，case 修改 `merged.Servers[0].Args[0] = "new"`，**eval 级原对象的 Args 也会被改**——配置污染，bug 排查噩梦。

`cloneMCPServer` 的细节：
- `cloned := server` 复制 struct 本身（值类型字段全部拷贝）。
- `cloned.Args = append([]string(nil), server.Args...)` 单独 deep copy slice——这是 Go 里拷贝 slice 的惯用法，分配新底层数组。

> Java 类比：这等价于实现 `Cloneable` 并重写 `clone()` 做 deep clone，或用 copy constructor。Go 没有内置 clone机制，只能手写。

### 7.4 MVP 限制：case 级必须 mocked

语义 5 是 MVP 阶段的限制——case 级 server 不能用 real MCP（只能用 fixture mock）。理由：
- real MCP server 在 case 级声明会导致不同 case 启动不同真实服务，并发跑时端口/资源冲突。
- mocked 用 fixture，可控可复现。

未来扩展：放开限制时，只需要改 `mcp_merge.go:57-59` 的检查，schema 不动。

## 8. customengine.go 配置安全：把凭证挡在命令行之外

这是整个 config 包里**安全意识最强**的文件。背景：skill-up 支持自定义 Agent 引擎，用户的 eval.yaml 可能这么写：

```yaml
engine:
  name: my-custom
  custom:
    transport: local
    local:
      command: my-agent
      args:
        - "--token=${API_KEY}"        # ← 危险！API_KEY 会进 ps/进程追踪
        - "--token=sk-ant-xxx"        # ← 更危险！明文凭证写死
```

`customengine.go` 的使命是：**在校验期就把这种事故拦下来**。

### 8.1 敏感变量名识别：`sensitiveEnvNamePattern`

```go
// internal/config/customengine.go:18-24
var sensitiveEnvNamePattern = regexp.MustCompile(
    `(?i)(^|_)(API_?KEY|ACCESS_?KEY|KEY|TOKEN|SECRET|PASSWORD|PASSWD|CREDENTIALS?|AUTHORIZATION)(_|$)`,
)

func isSensitiveEnvName(name string) bool {
    return sensitiveEnvNamePattern.MatchString(name)
}
```

**正则拆解**：
- `(?i)`：大小写不敏感（`API_KEY` / `api_key` / `Api_Key` 都命中）。
- `(^|_)`：前面必须是字符串开头或下划线——**单词边界**。
- `(API_?KEY|ACCESS_?KEY|KEY|TOKEN|SECRET|PASSWORD|PASSWD|CREDENTIALS?|AUTHORIZATION)`：一组敏感词，`_?` 兼容 `APIKEY` 和 `API_KEY` 两种写法，`CREDENTIALS?` 兼容单复数。
- `(_|$)`：后面必须是下划线或字符串结尾。

**单词边界的作用**（注释 `customengine.go:16-17`）：
> Word boundaries avoid false positives like MONKEY_PATH.

如果不用 `(^|_)`/`(_|$)`，`MONKEY_PATH` 会被命中（含 `KEY`）——典型误报。用边界约束，只匹配完整的单词 `KEY`。

### 8.2 凭证形状识别：`secretLiteralPatterns`

```go
// internal/config/customengine.go:30-41
var secretLiteralPatterns = []*regexp.Regexp{
    // Vendor prefixes (Anthropic sk-ant-, OpenAI sk-, GitHub ghp_/gho_/ghu_/
    // ghs_/ghr_, Google AIza, Slack xox[abp]-, AWS AKIA/ASIA) — case-sensitive
    // on purpose: lowercase prefixes match real keys, uppercase ones AWS IDs.
    regexp.MustCompile(`(?:^|[^A-Za-z0-9_])sk-[A-Za-z0-9_\-]{16,}`),
    regexp.MustCompile(`(?:^|[^A-Za-z0-9_])gh[pousr]_[A-Za-z0-9]{20,}`),
    regexp.MustCompile(`(?:^|[^A-Za-z0-9_])AIza[A-Za-z0-9_\-]{20,}`),
    regexp.MustCompile(`(?:^|[^A-Za-z0-9_])xox[abposr]-[A-Za-z0-9\-]{10,}`),
    regexp.MustCompile(`(?:^|[^A-Za-z0-9_])(?:AKIA|ASIA)[A-Z0-9]{16}`),
    // JWT: three base64url segments separated by dots.
    regexp.MustCompile(`(?:^|[^A-Za-z0-9_])ey[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]{10,}`),
}
```

**为什么是大小写敏感？** 注释明说：
- 小写前缀（`sk-`、`ghp_`）匹配真实 key。
- 大写前缀（`AKIA`、`ASIA`）匹配 AWS Access Key ID。

如果大小写不敏感，`SK-ANT-...` 这种本来就非法的字符串也会被命中——产生误报。

**JWT 模式**：`eyXXX.YYY.ZZZ`——三个 base64url 段用点分隔。`ey` 是 `{"a"` base64url 编码的开头（JWT payload 都是 JSON），所以 JWT 几乎都以 `ey` 开头。这是非常**精巧的启发式**。

**`(?:^|[^A-Za-z0-9_])` 前缀**：要求凭证前面是字符串开头或非字母数字下划线——避免 `mysk-...` 这种普通字符串误报。

### 8.3 `looksLikeSecret` + `rejectIfSecretLiteral`：严格模式拒绝凭证

```go
// internal/config/customengine.go:70-80
func looksLikeSecret(s string) bool {
    if s == "" {
        return false
    }
    for _, re := range secretLiteralPatterns {
        if re.MatchString(s) {
            return true
        }
    }
    return false
}

// internal/config/customengine.go:49-63
func rejectIfSecretLiteral(name, value string, rejectSecrets, fromDefault bool) error {
    if !rejectSecrets || !looksLikeSecret(value) {
        return nil
    }
    if fromDefault {
        return fmt.Errorf(
            "${%s:-...} default value looks like a credential; pass secrets via engine.custom.env, not as inline command-line defaults",
            name,
        )
    }
    return fmt.Errorf(
        "environment variable %q resolves to a value that looks like a credential; reference it from engine.custom.env instead of inline in a command line",
        name,
    )
}
```

**两个错误消息的设计**：
- `fromDefault = true`（用户在 `${X:-sk-ant-...}` 里写死凭证字面量）：消息提示「pass secrets via engine.custom.env」——告诉用户**正确做法**，不只是报错。
- `fromDefault = false`（环境变量本身解析出凭证形状）：消息提示「reference it from engine.custom.env」——同一个目标，但措辞针对「引用」场景。

**注释明说**（`customengine.go:65-69`）：
> It is intentionally conservative — only well-known credential shapes trigger — so legitimate default values (paths, model names, URLs) pass through.

「**故意保守**」——只匹配确凿的凭证形状，宁可漏报也不能误报正常值。这跟 §8.1 的「单词边界」思路一致：**安全检查的误报会训练用户忽略警告，最终失效**。

### 8.4 命名归一化：`normalizeKeyForSensitiveCheck`

用户可能用各种命名风格写 kwargs key：

```yaml
custom:
  kwargs:
    api-key: ...        # kebab-case
    apiKey: ...         # camelCase
    api.key: ...        # dotted
    bearerToken: ...    # camelCase
```

直接用 `isSensitiveEnvName` 检查会漏报（这些都不是 `^..._..._$` 格式）。所以先归一化：

```go
// internal/config/customengine.go:104-126
func normalizeKeyForSensitiveCheck(key string) string {
    var sep strings.Builder
    sep.Grow(len(key))
    for _, r := range key {
        if unicode.IsLetter(r) || unicode.IsDigit(r) {
            sep.WriteRune(r)
        } else {
            sep.WriteByte('_')
        }
    }
    normalized := sep.String()
    var b strings.Builder
    b.Grow(len(normalized) + 4)
    prevLower := false
    for _, r := range normalized {
        if prevLower && unicode.IsUpper(r) {
            b.WriteByte('_')
        }
        b.WriteRune(r)
        prevLower = unicode.IsLower(r)
    }
    return strings.ToUpper(b.String())
}
```

**两阶段归一化**：

1. **非字母数字 → `_`**：`api-key` → `api_key`，`api.key` → `api_key`。
2. **camelCase 拆词**：在「小写→大写」的转换点插入 `_`。`apiKey` → `api_Key`（第一遍），最后 `ToUpper` → `API_KEY`。`bearerToken` → `bearer_Token` → `BEARER_TOKEN`。

归一化后用 `isSensitiveEnvName` 检查：
- `api-key` → `API_KEY` ✓ 命中
- `apiKey` → `API_KEY` ✓ 命中
- `bearerToken` → `BEARER_TOKEN` → 含 `TOKEN` ✓ 命中

**精妙之处**：通过归一化把所有命名风格统一到「`UPPER_SNAKE_CASE`」，再用一份正则检查——避免写多份正则应对不同风格。

### 8.5 `isSensitiveTemplateVar` + `ResolveCustomEngineConfig`：完整解析流程


**内置模板变量**（运行时由 skill-up 注入）：
- `api_key`：直接是凭证。
- `kwargs` / `kwargs_json`：整个 kwargs map，**可能**包含敏感 key（aggregate 视为敏感）。
- `session_input` / `session_input_json`：整个 session 输入，同上。

**`kwargs.<key>`**：用 `normalizeKeyForSensitiveCheck` 归一化后检查。

`ResolveCustomEngineConfig` 是入口：

```go
    errs = append(errs, resolveStringMapEnvStrict("kwargs", custom.Kwargs)...)

    case customTransportLocal:

        }
    case customTransportHTTP:
```

**关键区分：Strict vs 非 Strict**

| 字段 | 模式 | 理由 |
|------|------|------|
| `local.command` / `local.args` / `local.cwd` | **Strict** | 进命令行，凭证会进 `ps` |
| `kwargs.*` | **Strict** | 能被 `${kwargs.key}` 展开进命令行 |
| `env.*` | 非 Strict | 环境变量本就是放凭证的地方 |
| `http.url` / `http.headers` | 非 Strict | URL 里可能有 token，但 headers 是合法凭证位置 |
| `model.*` | 非 Strict | 模型字段一般不含凭证 |

**`resolveLocalEnv`** 的实现（`customengine.go:274-289`）：
```go
func resolveLocalEnv(l *customengine.LocalConfig) []string {
    var errs []string
    errs = append(errs, resolveScalarEnvStrict("local.command", &l.Command)...)
    errs = append(errs, resolveScalarEnvStrict("local.cwd", &l.Cwd)...)
    errs = append(errs, resolveScalarEnvStrict("local.input_file", &l.InputFile)...)
    errs = append(errs, resolveScalarEnvStrict("local.output_file", &l.OutputFile)...)
    for i := range l.Args {
        rv, err := resolveEnvRefsStrict(l.Args[i])
        if err != nil {
            errs = append(errs, fmt.Sprintf("engine.custom.local.args[%d]: %s", i, err))
            continue
        }
        l.Args[i] = rv
    }
    return errs
}
```

**command / cwd / input_file / output_file / args 全部走 Strict**——这些字段最终都拼成进程的命令行，凭证进去就会出现在 `ps`、/proc、容器 exec 日志里。

### 8.6 `resolveEnvRefsStrict`：迭代展开 + 深度上限

```go
// internal/config/customengine.go:397-410
func resolveEnvRefsStrict(s string) (string, error) {
    const maxStrictExpansionDepth = 10
    for range maxStrictExpansionDepth {
        resolved, err := resolveEnvRefsWith(s, true)
        if err != nil {
            return "", err
        }
        if resolved == s || !strings.Contains(resolved, "${") {
            return resolved, nil
        }
        s = resolved
    }
    return "", errors.New("strict env resolution exceeded maximum depth (possible reference cycle)")
}
```

**为什么迭代？** 注释 `customengine.go:392-396`：
> The resolver iterates: if the produced value itself embeds further ${...} references (a wrapper env var whose value is "${CUSTOM_AGENT_TOKEN}"), the next pass re-checks them, so a non-sensitive wrapper cannot smuggle a sensitive name through to run-time rendering.

**攻击场景**：用户设置环境变量 `INNOCUOUS_NAME=${API_KEY}`（API_KEY 是敏感的，INNOCUOUS_NAME 不是）。一次解析会得到 `${API_KEY}`——这时候如果不迭代，**凭证名就漏过去了**。迭代后第二遍解析发现 `${API_KEY}`，命中敏感检查，拒绝。

**`maxStrictExpansionDepth = 10`**：防止恶意构造的循环引用（`A=${B}`、`B=${A}`）导致无限循环。Go 1.22+ 的 `for range N` 语法，简洁。

### 8.7 `resolveEnvRefsWith`：扫描 + 替换 + 双重检查

```go
// internal/config/customengine.go:417-471
func resolveEnvRefsWith(s string, rejectSecrets bool) (string, error) {
    if s == "" {
        return s, nil
    }
    if !strings.Contains(s, "${") {
        // No env reference to expand. In strict mode the raw literal still
        // needs to be checked — `args: ["--token", "sk-ant-..."]` would
        // otherwise hand the credential straight to process.command tracing.
        if rejectSecrets && looksLikeSecret(s) {
            return "", errors.New(
                "value looks like a credential literal; pass secrets via engine.custom.env instead of inline command-line literals",
            )
        }
        return s, nil
    }

    var b strings.Builder
    for i := 0; i < len(s); {
        open := strings.Index(s[i:], "${")
        if open < 0 {
            b.WriteString(s[i:])
            break
        }
        b.WriteString(s[i : i+open])
        start := i + open
        closeIdx := strings.IndexByte(s[start:], '}')
        if closeIdx < 0 {
            b.WriteString(s[start:])
            break
        }
        inner := s[start+2 : start+closeIdx]
        value, leaveIntact, err := resolveEnvToken(inner, rejectSecrets)
        if err != nil {
            return "", err
        }
        if leaveIntact {
            b.WriteString(s[start : start+closeIdx+1])
        } else {
            b.WriteString(value)
        }
        i = start + closeIdx + 1
    }
    out := b.String()
    // Even after expansion, a mixed input like `Bearer ${TOKEN_PREFIX}sk-ant-real-key`
    // can resolve to a string whose suffix is a credential literal. Run the
    // final check so strict-mode callers get a consistent guarantee:
    // no credential-shaped literal reaches a command line.
    if rejectSecrets && looksLikeSecret(out) {
        return "", errors.New(
            "resolved value looks like a credential literal; pass secrets via engine.custom.env instead of inline command-line literals",
        )
    }
    return out, nil
}
```

**三重防御**：

1. **入口检查**（行 425-431）：字符串里没有 `${` 但本身长得像凭证（明文写死）→ 拒绝。
2. **token 检查**（行 449，调 `resolveEnvToken`）：每个 `${VAR}` token 单独检查 VAR 名是否敏感。
3. **出口检查**（行 465-469）：展开后的最终结果里若仍含凭证字面量（如 `Bearer ${PREFIX}sk-ant-real`）→ 拒绝。

**为什么三重？** 因为攻击面是组合的：
- 入口防「明文凭证」。
- token 防 `${SENSITIVE_VAR}` 直接引用。
- 出口防「拼接后凑成凭证」（如前缀变量 + 后缀字面量）。

这是**深度防御（defense in depth）**的典范。

### 8.8 `resolveEnvToken`：内置变量保留 + 敏感拒绝

```go
// internal/config/customengine.go:479-515
func resolveEnvToken(inner string, rejectSecrets bool) (value string, leaveIntact bool, err error) {
    tok := customengine.ParseTemplateToken(inner)

    if IsBuiltinTemplateVar(tok.Name) {
        if rejectSecrets && isSensitiveTemplateVar(tok.Name) {
            return "", false, fmt.Errorf(
                "secret-like template variable ${%s} must not be referenced in a command line; pass credentials via engine.custom.env instead",
                tok.Name,
            )
        }
        return "", true, nil   // ← leaveIntact: 留给运行时解析
    }

    if rejectSecrets && isSensitiveEnvName(tok.Name) {
        return "", false, fmt.Errorf(
            "secret-like environment variable %q must not be referenced in a command line; pass credentials via engine.custom.env instead",
            tok.Name,
        )
    }

    if v := os.Getenv(tok.Name); v != "" {
        if err := rejectIfSecretLiteral(tok.Name, v, rejectSecrets, false); err != nil {
            return "", false, err
        }
        return v, false, nil
    }
    if tok.HasDefault {
        if err := rejectIfSecretLiteral(tok.Name, tok.Default, rejectSecrets, true); err != nil {
            return "", false, err
        }
        return tok.Default, false, nil
    }
    if tok.HasErrForm {
        return "", false, tok.RequiredErr()
    }
    return "", false, fmt.Errorf("environment variable %s is required but not set", tok.Name)
}
```

**4 种分支**：

1. **内置模板变量**（`${workspace}` / `${prompt}` / `${kwargs.x}` 等）：保留原样（`leaveIntact=true`），由运行时 agent 自己解析。但**敏感的内置变量**（`${api_key}` 等）在 strict 模式下直接拒绝。
2. **敏感环境变量名**（`${API_KEY}` 等）：strict 模式拒绝。
3. **普通环境变量 + 有值**：替换为 `os.Getenv` 的值，但值本身若是凭证形状（如变量值是 `sk-ant-xxx`）也拒绝。
4. **未设置的变量**：根据形态报错——`${X:-default}` 用 default、`${X?msg}` 报 msg、`${X}` 报「required but not set」。

**`${X:-default}` 和 `${X?msg}` 两种语法**在 `customengine/template_token.go:27-35` 解析：

```go
func ParseTemplateToken(inner string) TemplateToken {
    t := TemplateToken{Name: inner}
    if before, after, found := strings.Cut(inner, ":-"); found {
        t.Name, t.Default, t.HasDefault = before, after, true
    } else if before, after, found := strings.Cut(inner, "?"); found {
        t.Name, t.ErrMsg, t.HasErrForm = before, after, true
    }
    return t
}
```

这是 bash 风格的两种变量语法：
- `${X:-default}`：X 未设置或空时用 default。
- `${X?msg}`：X 未设置时报错（msg 可选）。

注释 `template_token.go:25-26` 强调「**`:-` 在 `?` 之前匹配**」——所以 `${X:-a?b}` 把 `a?b` 当 default，而不是把 `a` 当 default、`b` 当错误消息。

## 9. 关键设计点（带 Java 类比）

### 9.1 配置即代码（Configuration as Code）

YAML 不是被运行时随手读的字符串，而是先经过 schema 对齐、默认值注入、分层校验、敏感字段脱敏，再以「干净对象」进入业务层。等价于 Spring Boot 的：

```java
@ConfigurationProperties(prefix = "eval")
@Validated  // ← 触发 JSR-303
public class EvalConfig {
    @NotBlank
    @Pattern(regexp = "v1alpha1")
    private String schemaVersion;

    @NotNull
    @Valid  // ← 级联校验嵌套对象
    private Environment environment;
    // ...
}
```

skill-up 用纯 Go 手写了 Spring 这套机制——好处是没有反射魔法，所有逻辑可见、可调试。

### 9.2 多阶段分层校验（@Valid + Validator）

校验按「文档级 → 类型枚举 → runtime 特化 → case 级 → 去重 → judge 合并 → 延迟」分层，每层只做自己擅长的检查。等价于 Java 里：

- `@NotNull` / `@NotBlank` → 文档级（required）
- 自定义 `@ConstraintValidator` → 类型枚举 + 特化
- `@Valid` 级联 → case 嵌套校验
- `@GroupSequence` → 分阶段（先 required 再 cross-field）

**好处**：单层函数不会膨胀到无法维护；新增检查只加一个 `validateXxx` 函数；错误消息分层聚合。

### 9.3 不可变配置（deep copy everywhere）

`DefaultEvalConfig()` 和 `MergeCaseMCP()` 都返回 deep copy，调用方无法通过返回值污染内部状态。等价于 Java 的：

```java
public class EvalConfig {
    private final List<MCPServer> servers;  // final 字段
    public EvalConfig(List<MCPServer> servers) {
        this.servers = List.copyOf(servers);  // 不可变拷贝
    }
    public List<MCPServer> getServers() {
        return servers;  // 已经是不可变 List
    }
}
```

Go 没有 `final` 字段和不可变集合，所以靠**约定 + deep copy 函数**保障。`defaults.go` 用 yaml.Marshal/Unmarshal 做拷贝是取巧但有效的写法。

### 9.4 延迟校验（Late Binding）

`engine.custom` 的校验延迟到 `--engine` override 应用后——因为最终 engine name 决定了 custom 块是否生效。等价于 Spring 的 `@ConditionalOnProperty`：

```java
@Configuration
@ConditionalOnProperty(name = "engine.name", havingValue = "custom")
public class CustomEngineConfig { ... }
```

skill-up 没有 IoC 容器，所以靠**显式的两阶段调用**：先 `ValidateEvalConfig`（不含 custom），再 `ResolveCustomEngineConfig`（含 custom）。`cli/run.go:193-207` 和 `cli/validate.go:28-36` 都遵循这个顺序。

### 9.5 默认值「单一事实源」（//go:embed defaults.yaml）

README 里写的默认值（超时 300s、max_turns 10、parallelism 1）和代码里跑的默认值是**同一份 yaml**——避免「文档说 300，代码改成了 600」的漂移。等价于 Spring Boot 的 `application.yml` + `@PropertySource("classpath:defaults.yml")`。

`//go:embed` 比 `classpath:` 更强：**编译期嵌入**，运行时零文件 IO，不会因为打包漏了 yaml 而崩溃。

## 10. 面试 Q&A

### Q1：为什么 v1alpha1 强制要求 `schema_version`？多此一举吗？

**A**：不是多此一举。`schema_version` 是 k8s 风格的 API 版本化约定，作用是：
1. **未来升级预留入口**：当 schema 不兼容地变更时，新增 `v1beta1` 分支，loader 按版本路由——老文档继续用老 schema，新文档用新 schema。
2. **明确兼容性承诺**：`alpha` 告诉用户「可能 break」，不要在生产里强依赖。
3. **校验前置**：缺 `schema_version` 直接报错，避免「默写了一个字段名拼写错误的 YAML」被静默接受。

当前虽然只有一个版本，但**版本号字段的存在本身就是设计契约**——它是 schema 演进的基础设施。

### Q2：case 级 judge 怎么和 eval 级 judge 合并？为什么要构造「临时合并视图」而不是直接改原对象？

**A**：合并语义在 `validator.go:399-414` 的 `mergeJudgeConfigForValidation`：
- case 级有 `type` → 以 case 为主体，`model` / `pass_threshold` / `timeout_seconds` 字段级 fallback。
- case 级没 `type` → 完全继承 eval 级。

**不写回原对象**的原因：原 `CaseConfig.Judge` 是用户写的「**意图**」，运行时还要再次合并（因为 eval 级 Judge 可能在 CLI override 中变化）。如果校验期就把合并结果写回，会污染原对象、丢失意图，下次校验/合并的基础就错了。「**为校验构造临时视图**」是函数式编程的思想——纯函数，无副作用。

### Q3：为什么 `engine.custom` 的校验要延迟？不能在 LoadEvalConfig 里一次做完？

**A**：因为最终 engine name 受 CLI override 影响。考虑：

```yaml
engine:
  name: claude_code        # ← 加载期看到这个名字
  custom:
    transport: local       # ← claude_code 是内置引擎，custom 块本该被忽略
    local:
      command: broken-cmd  # ← 但加载期不知道用户会不会 --engine my-custom
```

如果加载期立即校验 custom，用户用 `skill-up run --engine claude_code` 时会被 broken-cmd 阻塞——但这个 custom 块根本不会被使用。**只有 `--engine` 应用后，才知道 custom 是否生效**，这时候校验才有意义。

所以流程是：`LoadEvalConfig`（跳过 custom）→ `ValidateEvalConfig`（跳过 custom）→ 应用 `--engine` → `ResolveCustomEngineConfig`（校验 custom）。`cli/validate.go:34` 也调用同一函数，保证 validate 命令不漏报。

### Q4：MCP 合并为什么选「整条替换」而不是「字段级 deep merge」？

**A**：整条替换有三个优势：
1. **可预测**：用户写一条 case-level server，最终结果就是这条，不用脑内做字段 merge。
2. **易调试**：日志里看到的 case 级 server 就是最终生效的 server。
3. **避免「半合并」bug**：字段级 merge 的语义复杂（覆盖？追加？深拷贝？），易出 bug。

字段级 merge 唯一的好处是「**改一两个字段不用重写整条**」，但 skill-up 团队认为这个便利不值得换来语义复杂度。这是「**最小惊讶原则**」在配置合并上的应用。

### Q5：customengine.go 的「凭证检查」为什么要三重（入口/token/出口）？

**A**：因为攻击面是组合的：
1. **入口检查**防「明文凭证字面量」（`args: ["--token", "sk-ant-..."]`）。
2. **token 检查**防「直接引用敏感变量」（`${API_KEY}`）。
3. **出口检查**防「拼接后凑成凭证」（`Bearer ${PREFIX}sk-ant-real`，前缀变量不敏感但后缀字面量敏感）。

加上 `resolveEnvRefsStrict` 的**迭代展开**（防「`INNOCUOUS=${API_KEY}`」间接引用），构成「**深度防御**」。

单一检查总有盲区——比如只做 token 检查会漏掉明文字面量，只做出口检查会漏掉变量名直接引用。三重检查对应三种攻击向量，缺一不可。这是安全代码的典型思路：**Never trust a single layer**。

### Q6（一句话总结）

> `internal/config` 把 eval.yaml 从「**字符串文档**」变成「**强类型 + 默认值 + 多阶段校验 + 不可变 + 安全脱敏**」的运行时对象——它是 skill-up 整个系统的「类型系统」和「安全门」，所有运行期模块都消费这份被精心校验过的配置，因此业务代码可以放心假设「配置就是对的」。
