> 面向 Java 后端/全栈工程师。本文把 skill-up 里「同时跑很多用例、跑挂了能重试、跑久了能停下、停下了不漏孙子进程」这四件事，从源码层面一行一行讲透。

## 0. 一句话定位 + 三件事的关系

**skill-up 的 `Evaluator` 是一个「带限流的并发任务执行器 + 重试/超时包装层」**：它把 N 个测试用例（可选地乘以 `with_skill`/`without_skill` 两种配置）展开成一张任务列表，用信号量控制并发数，每个任务套上「case 级总预算超时 + 失败重试 + 指数退避」，最底层靠进程组把超时命令连同它的子孙进程一起收掉。

三件事不是孤立的，是**一条调用链上的三层包装**：

```
EvaluateAll（并发层：信号量 + WaitGroup）
   └── 每个 task 一个 goroutine
        └── executeCase（重试层：maxAttempts 循环 + 指数退避 + retry_on 白名单）
             └── withCaseTimeout（超时层：context.WithTimeout，case 级 > defaults 级）
                  └── executeCaseOnce（业务层：runtime 准备 → Agent.Run → Judge 打分）
                       └── NoneRuntime.Exec（进程清理层：进程组 SIGTERM→SIGKILL）
```

- **并发**回答「同时跑几个」；
- **重试**回答「跑挂了怎么办」；
- **超时**回答「跑久了怎么办」，并且**重试就是由超时触发的**（超时被识别为 `timeout` 重试理由）；
- **进程清理**是超时落地时「物理层面真的把进程杀干净」的兜底。

> Java 类比：相当于你写了一个 `ThreadPoolExecutor`（并发）+ `@Retryable`（重试）+ `@Timeout`（超时）+ `Process.destroyForcibly()`（进程清理）的组合，只不过 Go 用 `context.Context` 一根线把它们串起来，比 Java 的注解模型更显式、也更可控。

## 1. 并发模型：`EvaluateAll` 逐段讲

核心代码在 `internal/evaluator/evaluator.go:180-237`。这是整份代码里最值得在面试里画出来的一段。

### 1.1 任务展开：`cases × {with_skill[, without_skill]}`

```go
// evaluator.go:195-206
configCount := 1
if e.withBaseline {
    configCount = 2
}

tasks := make([]task, 0, len(cases)*configCount)
for _, c := range cases {
    tasks = append(tasks, task{caseCfg: c, configName: "with_skill"})
    if e.withBaseline {
        tasks = append(tasks, task{caseCfg: c, configName: "without_skill"})
    }
}
```

- `e.withBaseline` 来自 `evalCfg.Benchmark.Enabled`（`runner.go:164` 传入），即 eval.yaml 里的 `benchmark.enabled: true`。
- 关键设计：**把「同一个 case 跑两次（带技能 / 不带技能）」做成两个独立的 task**，而不是 case 内部的两阶段。好处是两条任务可以**并发跑**（受同一个信号量约束），而不是串行。
- `task` 结构体（`evaluator.go:113-116`）只有两个字段：`caseCfg *config.CaseConfig` + `configName string`，后者取值 `"with_skill"` / `"without_skill"`，最终会写进 `EvalResult.Configuration` 字段，供报告分组用。

> Java 类比：相当于把 `List<Case>` flatMap 成 `List<Task>`，每个 Task 带一个 `variant` 标签。后面 `groupResultsByCase`（`runner.go:283-297`）再按 `caseID` 把结果聚回 `{withSkill, withoutSkill}` 一对，用来算 A/B 基线对比。

### 1.2 预分配结果数组 + 信号量 + WaitGroup

```go
// evaluator.go:208-212
results := make([]EvalResult, len(tasks))
sem := make(chan struct{}, e.concurrency)
totalCases := len(tasks)

var wg sync.WaitGroup
```

三个并发原语，一行一个：

1. **`results` 预分配数组**（不是 slice append）：每个 goroutine 用自己的下标 `idx` 写 `results[idx]`，**互不重叠，无需加锁**。这是 Go 并发编程的经典技巧——用「索引分区」代替「共享 slice + mutex」。
   > Java 类比：相当于 `EvalResult[] results = new EvalResult[n]`，每个线程写自己的槽位，比 `synchronizedList.add()` 快得多。
   
2. **`sem := make(chan struct{}, e.concurrency)`**：带缓冲 channel 当信号量。缓冲大小 = 并发上限。这是 Go 的惯用法：channel 不仅能传值，还能当「令牌桶」。
   > Java 类比：等价于 `java.util.concurrent.Semaphore(concurrency)`。`sem <- struct{}{}` = `semaphore.acquire()`，`<-sem` = `semaphore.release()`。

3. **`var wg sync.WaitGroup`**：等所有 goroutine 跑完。`wg.Add(1)` 在起 goroutine 前，`defer wg.Done()` 在 goroutine 退出前。
   > Java 类比：相当于 `CountDownLatch(n)`，或者更贴切的 `CompletableFuture.allOf(...).join()`。Go 的好处是你不需要提前知道 n，可以循环里 `Add(1)`。

### 1.3 循环里起 goroutine：先抢令牌再 `go`

```go
// evaluator.go:213-233
for i, t := range tasks {
    wg.Add(1)
    sem <- struct{}{}          // (A) 主 goroutine 在这里阻塞，直到有空闲令牌
    caseNum := i + 1
    go func(idx int, tk task, cn int) {
        defer wg.Done()
        defer func() { <-sem }()  // (B) 子 goroutine 退出时归还令牌
        if e.observer != nil {
            e.observer.OnCaseStart(cn, totalCases, tk.caseCfg.ID, tk.caseCfg.Title)
        }
        results[idx] = e.executeCase(ctx, tk.caseCfg, tk.configName, nil, nil)
        if e.observer != nil {
            res := results[idx]
            passRate := float64(-1)
            if res.Grading != nil {
                passRate = res.Grading.Summary.PassRate
            }
            e.observer.OnCaseComplete(cn, totalCases, tk.caseCfg.ID, res.Status, passRate)
        }
    }(i, t, caseNum)
}
wg.Wait()
```

几个值得抠的细节：

**(A) `sem <- struct{}{}` 在 `go` 之前，且在主 goroutine 里。**  
这一步**在主 goroutine 阻塞**，而不是子 goroutine 里。意味着：当并发数达到上限，**主 goroutine 会停下来不继续 `go`**，从而把「在飞的任务数」精确锁在 `e.concurrency`。
- 如果把 `sem <- struct{}{}` 放进子 goroutine 里，会发生什么？主 goroutine 会瞬间 `go` 出 N 个 goroutine，每个 goroutine 再去抢令牌——结果 N 个 goroutine 全创建了（占内存/调度压力），只是挤在信号量前排队。当前写法「先抢令牌再 go」更省资源。
- 另一个隐含约束：`sem` 的缓冲大小就是并发上限，**所以主 goroutine 最多积压 `concurrency` 个未消费的令牌写入**，不会无限阻塞导致内存膨胀。

**(B) `defer func() { <-sem }()` 在子 goroutine 里。**  
保证**无论 `executeCase` 是正常返回还是 panic，令牌都会归还**。注意 defer 的 LIFO 顺序：`defer wg.Done()` 先注册，`defer func() { <-sem }()` 后注册，所以**先归还令牌，再 `Done`**——这个顺序很重要：如果先 `Done`（`wg.Wait()` 返回）再归还令牌，`wg.Wait()` 之后 `sem` 可能还没满，调用方如果复用 `sem` 会出问题。当前顺序是安全的。

**闭包变量捕获：`go func(idx int, tk task, cn int)(i, t, caseNum)`。**  
这是 Go 最经典的坑：如果直接在闭包里用循环变量 `i`、`t`，所有 goroutine 会共享同一份变量（Go 1.22 之前），大概率全拿到最后一个值。这里用「把变量作为函数参数传进去」的方式，**在 `go` 的瞬间拍快照**，每个 goroutine 拿到自己的副本。
> Java 类比：相当于 lambda 捕获外层变量必须 effectively final 的限制，Go 没有这个限制所以更容易踩坑，这里用参数化规避。

**`ProgressObserver` 回调：**  
`e.observer` 是个接口（`evaluator.go:43-46`），两个方法 `OnCaseStart` / `OnCaseComplete`。注释明确写了「Implementations must be safe for concurrent use」（必须线程安全）。在 `cli/run.go:310-318` 里，`uiProgressObserver` 把回调转给 `ui.CaseStart` / `ui.CaseComplete`——也就是终端进度条。这里之所以用接口注入而不是直接调 `ui.XXX`，是为了**把进度展示和评测逻辑解耦**（测试时可以传 mock observer）。

### 1.4 `wg.Wait()` 之后返回

```go
// evaluator.go:234-236
wg.Wait()
return results, nil
```

`wg.Wait()` 阻塞到所有 `wg.Done()` 都调用完，此时 `results` 数组每个槽位都填好了，直接返回。**无锁、无 copy、无 channel drain**——这是 Go 并发编程里最干净的「fan-out → fan-in」模式之一。

> Java 类比总结：这套 `Semaphore + CountDownLatch + 预分配数组槽位` ≈ Java 的 `ThreadPoolExecutor(semaphore) + Future.allOf(latch) + 结果数组`，但 Go 用 channel + WaitGroup 把代码量压到了 20 行。

## 2. `parallelism` 来源链：CLI > eval.yaml > 默认 1，上限 256

`cases.parallelism` 是 eval.yaml 里的顶层配置项。

### 2.2 Runner 把配置传给 Evaluator

### 2.3 Evaluator 构造函数兜底默认 1

`concurrency <= 0`（包括 YAML 没写、写了 0、写了负数）都兜底成 1。**默认串行**——这是安全的保守策略，避免用户写错配置意外打爆 API 配额。

### 2.4 CLI `--parallelism` 覆盖 + 校验

```go
// run.go:33-41
const (
    modelFormatParts       = 2
    maxParallelismOverride = 256
    ...
)

// run.go:112
runCmd.Flags().Int("parallelism", 0, "Override cases.parallelism. Must be between 1 and 256 when specified")
```

```go
// run.go:529-546
parallelismFlag := cmd.Flags().Lookup("parallelism")
if parallelismFlag == nil || !parallelismFlag.Changed {
    return nil  // 没传 --parallelism，保留 eval.yaml 的值
}

parallelism, err := strconv.Atoi(parallelismFlag.Value.String())
if err != nil {
    return fmt.Errorf("read --parallelism: %w", err)
}
if parallelism < 1 {
    return fmt.Errorf("invalid --parallelism %d: must be >= 1", parallelism)
}
if parallelism > maxParallelismOverride {
    return fmt.Errorf("invalid --parallelism %d: must be <= %d", parallelism, maxParallelismOverride)
}

evalCfg.Cases.Parallelism = parallelism
```

三个要点：

1. **`parallelismFlag.Changed`**：Cobra 提供的标志，告诉你这个 flag 是用户显式传了，还是只是默认值。只有用户**显式传了** `--parallelism` 才覆盖 eval.yaml，否则不动。这避免了「CLI 默认值 0 覆盖了 YAML 里的 8」这种事故。
2. **下界校验 `< 1`**：拒绝 0 和负数（虽然 `NewEvaluator` 也会兜底，但这里**在配置阶段就报错**，比运行时静默修正更明确）。
3. **上界校验 `> 256`**：`maxParallelismOverride = 256`。为什么是 256？这是个工程经验值——再大容易把本地 Agent CLI（claude_code/codex 这些进程）打爆，也会瞬间打爆模型 API 的 RPM/TPM 配额。**面试可以讲**：这是「保护下游」的限流，相当于 sentinel 里的「并发数限流」。

> 优先级总结：`--parallelism`（CLI）> `cases.parallelism`（eval.yaml）> `1`（默认）。这跟 `--engine`/`--model` 的优先级链完全一致，是整个 skill-up 的设计惯例。

## 3. 重试策略：`executeCase` 的 attempt 循环

核心代码在 `evaluator.go:289-331`。这是「重试层」。

```go
// evaluator.go:289-291
func (e *defaultEvaluator) executeCase(ctx context.Context, caseCfg *config.CaseConfig, configName string, overrideRT runtime.Runtime, overrideAgent agent.Agent) EvalResult {
    maxAttempts := max(e.evalCfg.Cases.RetryPolicy.MaxRetries+1, 1)
```

### 3.1 `maxAttempts = MaxRetries + 1`

`RetryPolicy` 定义在 `schema.go:138-141`：

```go
type RetryPolicy struct {
    MaxRetries int      `yaml:"max_retries,omitempty"`
    RetryOn    []string `yaml:"retry_on,omitempty"` // timeout, error
}
```

- `MaxRetries` 是「**额外**重试次数」，所以总尝试次数 `maxAttempts = MaxRetries + 1`（首次 + 重试 N 次）。
- `max(..., 1)` 兜底：即使 `MaxRetries` 没配或配 0，**至少跑一次**（首次尝试必须执行）。

> Java 类比：Spring 的 `@Retryable(maxAttempts = 3)` 里 `maxAttempts` 是「总次数」（含首次），skill-up 用「重试次数」（不含首次），所以 +1。两种惯例都常见，关键是注释清楚。

### 3.2 attempt 循环：每次都重建超时 context

```go
// evaluator.go:292-328
var result EvalResult
for attempt := 1; attempt <= maxAttempts; attempt++ {
    attemptCtx, cancel, timeoutSource, timeoutSec := withCaseTimeout(ctx, e.evalCfg.Cases.Defaults.TimeoutSeconds, caseCfg.Constraints.TimeoutSeconds)
    result = e.executeCaseOnce(attemptCtx, caseCfg, configName, overrideRT, overrideAgent)
    // 决定是否标注 timeout：必须在 cancel() 之前
    if errors.Is(attemptCtx.Err(), context.DeadlineExceeded) && ctx.Err() == nil {
        annotateCaseTimeoutError(&result, timeoutSource, timeoutSec)
    }
    cancel()

    retryReason, ok := retryReasonForResult(result)
    if !ok || !retryAllowed(e.evalCfg.Cases.RetryPolicy, retryReason) || attempt == maxAttempts {
        return result
    }

    logging.WarnContextf(
        ctx,
        "Runner: case %s (%s) attempt %d/%d hit %s, retrying after %s",
        caseCfg.ID, configName, attempt, maxAttempts, retryReason, retryBackoffDelay(attempt),
    )
    if err := sleepWithContext(ctx, retryBackoffDelay(attempt)); err != nil {
        return result
    }
}
```

四个关键点逐一拆：

#### (1) 每次尝试都调 `withCaseTimeout` 重建 context

**为什么不在循环外建一次 context？** 因为超时是「**单次尝试**的预算」，不是「所有重试加起来的总预算」。如果第一次跑超时了（context 已经 DeadlineExceeded），第二次重试必须用**新的 context**才能真的再跑一次。所以每次循环都 `withCaseTimeout` 新建一个 `attemptCtx`，跑完 `cancel()` 释放。

#### (2) `annotateCaseTimeoutError` 必须在 `cancel()` 之前

代码里那段长长的注释（`evaluator.go:296-304`）解释了顺序的微妙：

```go
// 决定是否标注 *before* cancel() 这样：
// (a) cancel() 不会把 Err 改写成 Canceled 抹掉信号；
// (b) 父 context 的 deadline（比如调用方给 EvaluateAll 套了 context.WithTimeout）
//     触发时，不会把 attemptCtx.Err() 错标成 case 超时——那会让用户去看错误的 YAML 旋钮。
// 一个更紧的子 deadline（比如 judge.timeout_seconds）得到同样的保护，
// 因为当 case 级 deadline 从未触发时 attemptCtx.Err() 保持 nil。
```

如果先 `cancel()` 再检查：`cancel()` 会把 `attemptCtx.Err()` 设成 `context.Canceled`，覆盖掉原本的 `DeadlineExceeded`，于是 `errors.Is(..., DeadlineExceeded)` 失败，超时标注就丢了。**顺序错了，错误信息就变了**——这是个很容易踩的坑，源码用注释 explicitly 标了出来。

#### (3) `retryReasonForResult` + `retryAllowed`：白名单制重试

```go
// evaluator.go:897-905
func retryReasonForResult(result EvalResult) (string, bool) {
    if result.Status != judge.StatusError || result.Error == nil {
        return "", false
    }
    if isTimeoutError(result.Error) {
        return "timeout", true
    }
    return "error", true
}

// evaluator.go:885-895
func retryAllowed(policy config.RetryPolicy, reason string) bool {
    if reason == "" || policy.MaxRetries <= 0 {
        return false
    }
    for _, allowed := range policy.RetryOn {
        if strings.EqualFold(allowed, reason) {
            return true
        }
    }
    return false
}
```

- **只有 `StatusError` 才考虑重试**：PASS / FAIL / SKIP 都不重试。这是个重要设计：**FAIL（断言不过）是确定性失败，重试也不会变**，重试只对「不确定的执行错误」（超时、进程崩、网络抖动）有意义。
- 错误被归为两类：`timeout`（链路里有 `context.DeadlineExceeded`）或 `error`（其他所有）。
- `retryAllowed` 是**白名单**：YAML 里 `retry_on: [timeout]` 表示只重试超时，不重试普通错误；`retry_on: [timeout, error]` 都重试；不写 `retry_on` 则**什么都不重试**（即使 `MaxRetries > 0`）。
- `strings.EqualFold` 大小写不敏感，YAML 里写 `Timeout` / `TIMEOUT` 都行。

#### (4) `retryBackoffDelay` 指数退避 + `sleepContext` 可取消

```go
// evaluator.go:939-944
func retryBackoffDelay(attempt int) time.Duration {
    if attempt < 1 {
        attempt = 1
    }
    return time.Duration(1<<attempt) * time.Second
}
```

`1<<attempt` = 2 的 attempt 次方：
- attempt=1 → 2s
- attempt=2 → 4s
- attempt=3 → 8s
- attempt=4 → 16s

经典指数退避（exponential backoff）。**为什么这么做？** 重试失败往往是因为下游过载（API 限流、容器还没起好），指数退避给下游恢复时间，同时避免重试本身又打爆下游。
> Java 类比：Spring Retry 的 `@Backoff(delay = 1000, multiplier = 2)`，或者 Resilience4j 的 `ExponentialBackoff`。

```go
// evaluator.go:946-956
func sleepContext(ctx context.Context, delay time.Duration) error {
    timer := time.NewTimer(delay)
    defer timer.Stop()

    select {
    case <-ctx.Done():
        return ctx.Err()
    case <-timer.C:
        return nil
    }
}
```

**关键：sleep 是可取消的。** 不是 `time.Sleep(delay)`，而是 `select { ctx.Done() / timer.C }`。区别在于：如果用户在重试等待期间按了 Ctrl+C（父 context 被取消），`time.Sleep` 会**继续睡完**才退出，而 `sleepContext` 会**立刻在 `<-ctx.Done()` 分支返回**。这是 Go 里写「可中断 sleep」的标准范式。
- `defer timer.Stop()` 防止 timer 泄漏（虽然这个 timer 一次性，但 Stop 是好习惯）。
- 父 context 取消时返回 `ctx.Err()`，调用方（`executeCase`）拿到错误直接 `return result`，不再重试。

`executeCase` 用的是 `var sleepWithContext = sleepContext`（`evaluator.go:35`）这个变量——是个**可替换的函数指针**，方便测试 mock（测试里不想真等 2 秒就替换掉）。

### 3.3 重试决策的三个退出条件

```go
// evaluator.go:310-313
retryReason, ok := retryReasonForResult(result)
if !ok || !retryAllowed(e.evalCfg.Cases.RetryPolicy, retryReason) || attempt == maxAttempts {
    return result
}
```

任一满足即**不重试**，直接返回当前结果：

| 条件 | 含义 |
|---|---|
| `!ok` | 不是 Error 状态（PASS/FAIL/SKIP），没有重试理由 |
| `!retryAllowed(...)` | 是 Error，但 `retry_on` 白名单不包含该理由 |
| `attempt == maxAttempts` | 重试次数用完了 |

这三个条件用 `||` 短路，从左到右依次判断，符合「快速失败」原则。

## 4. 超时控制：`withCaseTimeout` —— case 级总预算

### 4.1 优先级：case 级 > defaults 级

```go
// evaluator.go:873-883
func withCaseTimeout(ctx context.Context, defaultTimeoutSec, caseTimeoutSec int) (context.Context, context.CancelFunc, string, int) {
    if caseTimeoutSec > 0 {
        c, cancel := context.WithTimeout(ctx, time.Duration(caseTimeoutSec)*time.Second)
        return c, cancel, "case.constraints.timeout_seconds", caseTimeoutSec
    }
    if defaultTimeoutSec > 0 {
        c, cancel := context.WithTimeout(ctx, time.Duration(defaultTimeoutSec)*time.Second)
        return c, cancel, "cases.defaults.timeout_seconds", defaultTimeoutSec
    }
    return ctx, func() {}, "", 0
}
```

- **优先 case 自己的 `constraints.timeout_seconds`**，没配（=0）才回退到 `cases.defaults.timeout_seconds`，都没配就**不设超时**（返回原 ctx + 空 cancel）。
- 注意返回值里的 `string`（source）和 `int`（seconds）：这是**为了给超时错误信息标注「哪个配置项导致的」**。这是关键设计——下文 4.3 讲。

辅助函数 `caseTimeoutSeconds`（`evaluator.go:262-267`）做同样的优先级判断，但只返回秒数（给 `agent.ExecOptions.TimeoutSec` 用，让 Agent 自己实现超时）。

### 4.2 「超时是 agent + judge 的总预算」——这是个核心设计

看 `executeCaseOnce` 里超时是怎么用的：

```go
// evaluator.go:294
attemptCtx, cancel, timeoutSource, timeoutSec := withCaseTimeout(...)
result = e.executeCaseOnce(attemptCtx, ...)  // 整个 once 都在这个 ctx 下
```

而 `executeCaseOnce` 内部（`evaluator.go:333-481`）会顺序做：
1. 准备 runtime（`prepareRuntimeForCase`）
2. Agent 执行（`runAgent.Run(agentCtx, ...)`）
3. （可选）judge 打分（`evaluateCaseSession` → `runJudgePhase` → `j.Evaluate(ctx, ...)`）

**这三步全部跑在同一个 `attemptCtx` 下**。意味着：如果 timeout=60s，Agent 跑了 55s，judge 就只剩 5s——一旦超时，整个 attempt 失败，触发 `timeout` 重试理由。

证据在 `handleExecutionResult`（`evaluator.go:907-930`）的注释里写得很直白：

```go
// handleExecutionResult finalises the EvalResult when the agent run returned an
// error. Any execErr (including ctx.DeadlineExceeded) terminates the case as
// ERROR: the case timeout is treated as a single budget for agent + judge, so
// we do not try to salvage partial output by running the judge against a
// truncated agent transcript.
```

**为什么这么设计？** 假设超时是「agent 单独的预算」，agent 跑超时了还让 judge 去评一个被截断的输出，judge 会基于残缺数据打分，结果可能误导（给一个本应失败的 case 打 PASS）。**总预算模式下，超时 = 整个 attempt 失败 = 触发重试**，语义干净。

> Java 类比：相当于给「整个 HTTP 请求处理链路」设一个总 timeout（包括下游调用 + 业务逻辑 + 持久化），而不是每步分别设 timeout。Spring Cloud Gateway 的 `timeout` 就是这种总预算语义。

### 4.3 `annotateCaseTimeoutError`：超时错误信息标注来源

```go
// evaluator.go:859-867
func annotateCaseTimeoutError(result *EvalResult, source string, seconds int) {
    if result == nil || result.Error == nil || source == "" || seconds <= 0 {
        return
    }
    if !errors.Is(result.Error, context.DeadlineExceeded) {
        return
    }
    result.Error = fmt.Errorf("%w (case timeout %ds via %s)", result.Error, seconds, source)
}
```

把原始的 `context.DeadlineExceeded` 包成：

```
context deadline exceeded (case timeout 60s via case.constraints.timeout_seconds)
```

三个看点：

1. **`%w` 包装错误**（不是 `%s`）：保留原始错误链，下游 `errors.Is(err, context.DeadlineExceeded)` 仍然能匹配。Go 1.13 的错误包装范式。
2. **`via case.constraints.timeout_seconds`**：直接告诉用户「去改这个 YAML 字段」。这是**可定位性（debuggability）**——面试时可以强调：超时错误不仅报「超时了」，还报「是哪个配置项设的超时」。
3. **多重 guard**（`source == "" || seconds <= 0`）：防御式编程，避免把空 source 拼进去生成奇怪的错误信息。

调用方的判断（`evaluator.go:305`）：

```go
if errors.Is(attemptCtx.Err(), context.DeadlineExceeded) && ctx.Err() == nil {
    annotateCaseTimeoutError(&result, timeoutSource, timeoutSec)
}
```

**`ctx.Err() == nil` 这个条件非常关键**：它排除「父 context 超时」的情况。如果调用 `EvaluateAll` 的人在外面套了一个 `context.WithTimeout(parentCtx, 5*time.Minute)`，那个父超时触发的 `DeadlineExceeded` 不应该被标成「case timeout」——那会误导用户去改 case 的 YAML，而真正的问题是整体运行时间太长。所以只有「**case 自己的 deadline 触发，且父 context 还活着**」才标注。

### 4.4 `isTimeoutError` 与 `handleExecutionResult`

```go
// evaluator.go:932-937
func isTimeoutError(err error) bool {
    if err == nil {
        return false
    }
    return errors.Is(err, context.DeadlineExceeded)
}
```

判断逻辑非常简单：只要错误链里有 `context.DeadlineExceeded`，就算超时。注意 `annotateCaseTimeoutError` 用 `%w` 包装后，链仍然能匹配——这就是为什么前面强调一定要用 `%w`。

```go
// evaluator.go:912-930
func (e *defaultEvaluator) handleExecutionResult(_ context.Context, _ *config.CaseConfig, configName string, startTime time.Time, result *EvalResult, execErr error) bool {
    if execErr == nil {
        return false
    }
    if result.DurationMs == 0 {
        result.DurationMs = time.Since(startTime).Milliseconds()
    }
    result.Status = judge.StatusError
    result.Error = fmt.Errorf("agent execution failed: %w", execErr)
    result.Configuration = configName
    return true
}
```

`handleExecutionResult` 是 `executeCaseOnce` 里 Agent.Run 出错时的统一收口：
- 把 `execErr`（可能是 `context.DeadlineExceeded`，也可能是其他 exec 错误）统一包装成 `"agent execution failed: %w"`。
- 标记 `Status = StatusError`，这就是 `retryReasonForResult` 判断「是否 Error」的来源。
- 返回 `true` 表示「应该 early return」（不再继续 judge 阶段）。

**关键：`%w` 包装意味着 `errors.Is(result.Error, context.DeadlineExceeded)` 仍然成立**，所以即使是 Agent.Run 抛出的超时，后续 `retryReasonForResult` 也能正确识别为 `timeout` 理由。整条错误链是连通的。

## 5. 进程清理：`NoneRuntime.Exec` 的进程组 SIGTERM→SIGKILL

这是最容易在面试里被追问「孙子进程怎么办」的部分。代码在 `internal/runtime/none.go` + 两个平台分支文件。

### 5.1 问题背景：为什么 `exec.CommandContext` 不够用？

Go 标准库的 `exec.CommandContext` 在 ctx 取消时**只 kill 直接子进程**。但 skill-up 的执行模型是：

```
skill-up (Go 进程)
  └─ shell (bash/cmd)            ← exec.Command 直接启动的
       └─ agent CLI (claude_code)
            └─ git / sleep / ping / node ...   ← 孙子进程
```

如果只 kill shell，**孙子进程会变成孤儿进程继续跑**，可能：
- 继续写 workspace 文件，污染下一个 case；
- 占着端口/锁，让下个 case 起不来；
- 在 CI 里挂住，让整个 pipeline 卡死。

所以必须**杀整棵进程树**。

### 5.2 POSIX 实现：进程组 + SIGTERM → 1s → SIGKILL

`internal/runtime/none_exec_unix.go`（build tag `//go:build unix`）：

```go
// none_exec_unix.go:18
const noneExecKillGrace = 1 * time.Second

// none_exec_unix.go:31-58
func configureProcessGroup(cmd *exec.Cmd, done <-chan struct{}) {
    cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}
    cmd.Cancel = func() error {
        if cmd.Process == nil {
            return nil
        }
        pid := cmd.Process.Pid
        // 进程是 group leader（Setpgid），所以负 PID 会给整组发信号
        if err := signalGroupOrProcess(cmd, pid, syscall.SIGTERM); err != nil {
            return err
        }
        // 在另一个 goroutine 里升级到 SIGKILL，这样 Cancel 立即返回，
        // os/exec 可以开始它的 WaitDelay 计时器。goroutine 在进程被回收后
        // （done 关闭）退出，所以它不会给一个被回收复用的 PID 发信号。
        go func() {
            timer := time.NewTimer(noneExecKillGrace)
            defer timer.Stop()
            select {
            case <-done:
            case <-timer.C:
                _ = signalGroupOrProcess(cmd, pid, syscall.SIGKILL)
            }
        }()
        return nil
    }
}

// none_exec_unix.go:62-67
func signalGroupOrProcess(cmd *exec.Cmd, pid int, sig syscall.Signal) error {
    if err := syscall.Kill(-pid, sig); err != nil {
        return cmd.Process.Signal(sig)
    }
    return nil
}
```

逐点拆：

**(1) `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}`**  
让子进程成为**新进程组的 leader**（process group ID = 子进程 PID）。此后该进程及其所有后代都属于同一个进程组。
> 这是 POSIX 的 `setpgid(0, 0)` 系统调用，等价于 shell 里的 `setsid`。Java 的 `ProcessHandle` 在 JDK 9+ 才有，且跨平台支持有限——这是 Go 在系统编程上的优势。

**(2) `syscall.Kill(-pid, sig)`：负 PID = 整组**  
`kill(2)` 系统调用的约定：PID 为负数时，信号发给「绝对值那个 PGID」的所有成员。所以 `-pid` 就是「给整棵进程树发信号」，包括所有孙子进程。
- fallback：`cmd.Process.Signal(sig)` 给单个进程发，作为组信号失败的兜底（极少触发）。

**(3) SIGTERM 先行，1s 后 SIGKILL 升级**  
`cmd.Cancel` 是 Go 1.20+ `exec.Cmd` 的新字段：当 ctx 取消时被调用。这里 Cancel 先发 **SIGTERM**（优雅终止信号），让 shell 和孩子们有时间跑 trap handler、释放锁、flush 数据。如果 1s（`noneExecKillGrace`）后还没退出，**升级到 SIGKILL**（不可捕获、不可忽略）强制杀。
> 这是 Unix 进程管理的标准最佳实践，等价于 Kubernetes 的 `terminationGracePeriodSeconds` + SIGTERM/SIGKILL 流程，也等价于 `docker stop` 默认 10s grace。

**(4) 为什么 SIGKILL 在 goroutine 里「out of band」发？**  
注释写得很清楚：「so Cancel returns immediately and os/exec can start its WaitDelay timer」。`cmd.Cancel` 必须快速返回（让 `os/exec` 框架继续干活），不能阻塞 1s 等升级。所以把「等 1s 再 SIGKILL」扔进一个 goroutine 异步执行。

**(5) `done` channel 防止给回收的 PID 发信号**  
这是个**TOCTOU（time-of-check-time-of-use）安全**细节：如果进程被杀后，操作系统把那个 PID 复用给了一个完全无关的新进程，再发 SIGKILL 就会误杀。所以 `runCmd`（`none.go:289-295`）在 `cmd.Wait()` 返回后 `defer close(done)`，通知升级 goroutine「进程已经回收，别再发信号」：

```go
// none.go:289-295
func runCmd(cmd *exec.Cmd, done chan<- struct{}) error {
    defer close(done)
    if err := cmd.Start(); err != nil {
        return err
    }
    return cmd.Wait()
}
```

`select { case <-done: case <-timer.C: }`——谁先到听谁的：`done` 先到（进程提前退出）就停 timer，`timer.C` 先到（1s 到了进程还在）就发 SIGKILL。优雅且安全。

### 5.3 Windows 实现：无进程组，靠 `WaitDelay`

`internal/runtime/none_exec_other.go`（build tag `//go:build !unix`）：

```go
//go:build !unix

package runtime

import "os/exec"

// configureProcessGroup 在没有 POSIX 进程组的平台上是 no-op。
func configureProcessGroup(_ *exec.Cmd, _ <-chan struct{}) {}
```

**Windows 没有 `setpgid` / `kill(-pid)` 等价物**，所以这里是个空函数。那 Windows 上孙子进程怎么办？

答案在 `none.go` 的 `Exec` 函数里，**两个平台都设置了 `cmd.WaitDelay`**：

```go
// none.go:20-31
const (
    noneDirMode  = 0o755
    noneFileMode = 0o600
    // noneExecWaitDelay 限制 Exec 在 ctx-cancel 后等多久再强制关闭
    // 子进程的 stdio 管道。POSIX 上 configureProcessGroup 会杀整棵树，
    // 所以短 grace 足够。Windows 上没有进程组等价物，Git Bash 的孙子进程
    // (ping/sleep/git) 可能仍占着 stderr 管道；这个延迟最终会关闭管道，
    // 让读管道的 goroutine 解除阻塞，使 Exec 在 deadline 内返回。
    noneExecWaitDelay = 2 * time.Second
)

// none.go:216
cmd.WaitDelay = noneExecWaitDelay
```

`cmd.WaitDelay` 是 Go 1.20+ 的另一个新字段：`cmd.Wait()` 在子进程退出后，最多再等 `WaitDelay` 时间让 stdio 管道排空；超时就**强制关闭管道**，让 `Wait` 返回。

为什么 Windows 需要这个？因为 Git Bash 的 `ping`/`sleep`/`git` 孙子进程会**占着 stderr 管道不放手**（即使 shell 父进程已经退出），导致读 stderr 的 goroutine 永远阻塞。`WaitDelay` 强制关管道，goroutine 解除阻塞，Exec 才能返回。

> 注意数值关系：`noneExecKillGrace = 1s` < `noneExecWaitDelay = 2s`。注释里 explicit 说明：「It must stay comfortably below noneExecWaitDelay (2s) so the escalation fires — and the group is gone — before Exec's WaitDelay force-closes the stdio pipes」。POSIX 上 1s 内进程组必死，2s 时关管道只是兜底；Windows 上没有组杀，只能靠 2s 关管道。

### 5.4 build tag 切换：Go 跨平台编译的经典范式

两个文件用 `//go:build unix` 和 `//go:build !unix` 互斥的 build tag，编译时 Go 工具链会**自动选择对应平台的实现**：

- `none_exec_unix.go`：在 linux/darwin/freebsd 等 POSIX 系统编译进二进制；
- `none_exec_other.go`：在 windows 上编译进二进制。

两个文件**函数签名完全一致**（都是 `configureProcessGroup(cmd *exec.Cmd, done <-chan struct{})`），调用方 `none.go` 不用关心平台差异，直接 `configureProcessGroup(cmd, done)` 即可。
> Java 类比：相当于 Maven 的 profile 或 GraalVM 的 `@TargetPlatform`，但 Go 的 build tag 是源码级的、零运行时开销，更接近 C 的 `#ifdef`。

### 5.5 `classifyExecError`：四态错误分类

`none.go:307-334`，把 `cmd.Run()` 的错误翻译成 `(exitCode, error)` 对：

```go
// 优先级（匹配旧的 inline 行为）：
//
//	nil err                            → (0, nil)
//	*exec.ExitError + ctx.Err() == nil → (exitCode, nil)
//	*exec.ExitError + ctx.Err() != nil → (exitCode, ctxErr)   // 进程被 ctx 杀
//	exec.ErrWaitDelay (无 ExitError)   → (0, nil)             // 进程退出 0，只是管道没关
//	非 ExitError                       → (-1, ctxErr or err)
func classifyExecError(ctx context.Context, runErr error) (int, error) {
    if runErr == nil {
        return 0, nil
    }
    // 当 context 终止进程时，无论 OS 报告什么退出码都强制 -1。
    // POSIX 上被杀的 sleep 传播为 -1（信号），但 Windows bash 的 sleep
    // 被 ctx-cancel 杀掉却表现为 exit 1——会和正常失败混淆。
    // -1 + ctxErr 是「被 context 杀」的规范信号，调用方（和 Exec 里的 switch）都看它。
    if ctxErr := ctx.Err(); ctxErr != nil {
        return -1, ctxErr
    }
    var exitErr *exec.ExitError
    if errors.As(runErr, &exitErr) {
        return exitErr.ExitCode(), nil
    }
    // exec.ErrWaitDelay（无 ExitError 包装）意味着进程本身成功退出，
    // 只是 Wait 关闭了被后台子孙进程占着的 stdio 管道。捕获到的
    // stdout/stderr 仍是有效输出——这里当作正常 exit 0，而不是 exec 失败。
    if errors.Is(runErr, exec.ErrWaitDelay) {
        return 0, nil
    }
    return -1, runErr
}
```

四种状态总结：

| 场景 | exitCode | error | 含义 |
|---|---|---|---|
| `runErr == nil` | 0 | nil | 正常成功 |
| ctx 被取消/超时 | **-1** | ctxErr | 被框架杀掉（无论 OS 报什么码） |
| `*exec.ExitError`（ctx 还活着） | 真实退出码 | nil | 脚本本身失败（业务错误） |
| `exec.ErrWaitDelay`（无 ExitError） | 0 | nil | 进程正常退出，只是管道慢关 |

几个精妙处：

**(1) ctx 取消时强制 -1。** 注释解释：POSIX 上被信号杀的进程报 -1 是惯例；但 Windows bash 的 `sleep 1` 被 ctx 杀会报 exit 1，**和脚本正常失败无法区分**。所以无论平台，只要 `ctx.Err() != nil`，统一改成 -1，作为「被 context 杀」的规范信号。下游 `Exec` 函数的 switch（`none.go:248`）就靠这个识别。

**(2) `exec.ErrWaitDelay` 当作 exit 0。** 这是个**关键的宽容设计**：进程已经正常退出（没有 ExitError），只是 stdio 管道被后台孙子占着没及时关闭。如果把这当 exec 失败，会让「Agent 本身跑成功了，只是后台有个 sleep 没退」的 case 被误判为失败。所以源码选择信任已捕获的输出，按 exit 0 处理。

**(3) `errors.As` 而非 type assertion。** `errors.As(runErr, &exitErr)` 会沿着错误包装链查找，比 `runErr.(*exec.ExitError)` 更健壮（能处理被 `fmt.Errorf("%w")` 包装过的错误）。

### 5.6 `Exec` 函数里的 switch：消费这四个状态

```go
// none.go:247-280
switch {
case result.ExitCode == -1 && ctx.Err() != nil:
    // 进程因为父 context 被取消或超时被杀。
    // -1 是哨兵值，不是真实退出码，附上完整命令源（"exited with code -1: set -e ..."）会误导。
    // 当这确实是 deadline（不是手动取消）时，附上 "deadline elapsed by Xs"。
    reason := ctx.Err().Error()
    if errors.Is(ctx.Err(), context.DeadlineExceeded) {
        if deadline, ok := ctx.Deadline(); ok {
            reason = fmt.Sprintf("%s (deadline elapsed by %s)", reason, time.Since(deadline).Round(time.Millisecond))
        }
    }
    logging.ErrorContextf(ctx, "command killed by context (%s); command: %s", reason, maskCommand(command))
    ...
case result.ExitCode != 0:
    logNonZeroExit(ctx, result.ExitCode, command)
    ...
case result.Stderr != "":
    logging.WarnContextf(ctx, "stderr: %s", result.Stderr)
}
```

- 第一个 case（被 ctx 杀）：错误信息会算出「**超出了 deadline 多少**」（`time.Since(deadline)`），方便日志关联——比如「deadline elapsed by 3.2s」说明超时 3.2 秒才被杀掉。
- `maskCommand(command)`（`none.go:336-343`）：把超长命令截断到 200 字符，避免日志爆炸。

## 6. 多轮对话的 per-turn timeout

多轮对话（`input.turns`）场景下，除了 case 级总预算，**每一轮还能单独设超时**。代码在 `internal/evaluator/multiturn.go:156-178`：

```go
// executeSingleTurn 给一轮对话调用 agent，可选地施加 per-turn 超时。
func executeSingleTurn(
    ctx context.Context,
    resumer agent.SessionResumer,
    rt runtime.Runtime,
    opts agent.ExecOptions,
    content string,
    turnNum int,
    timeoutSec int,
    sessionID string,
) (*agent.SessionResult, error) {
    msg := transcript.Message{Role: transcript.RoleUser, Content: content, Turn: turnNum}

    turnCtx := ctx
    var cancel context.CancelFunc
    if timeoutSec > 0 {
        turnCtx, cancel = context.WithTimeout(ctx, time.Duration(timeoutSec)*time.Second)
    } else {
        cancel = func() {}
    }
    defer cancel()

    return resumer.RunTurn(turnCtx, rt, opts, msg, sessionID)
}
```

`timeoutSec` 来自 `Turn.TimeoutSeconds`（`schema.go:295`）：

```go
type Turn struct {
    Role           string         `yaml:"role"`
    Content        string         `yaml:"content"`
    PostCondition  *PostCondition `yaml:"post_condition,omitempty"`
    Capture        []CaptureRule  `yaml:"capture,omitempty"`
    TimeoutSeconds int            `yaml:"timeout_seconds,omitempty"`
}
```

要点：

1. **`turnCtx` 是 `ctx`（即 case 级 attemptCtx）的子 context**——子超时不能超过父超时。如果 case timeout=60s，turn1 用了 30s，turn2 设了 timeout=40s，那 turn2 实际最多只能跑 30s（因为父 context 只剩 30s）。Go 的 `context.WithTimeout` 会自动取 min。
2. **`timeoutSec <= 0` 时不设超时**（用父 context），用空 cancel 函数兜底避免 nil 调用 panic。
3. **`defer cancel()`**：即使没设 WithTimeout，也调空 cancel——这是 Go context 的最佳实践，避免静态分析工具（如 `lostcancel`）报警，也避免未来重构时漏掉。

> 这套「case 总预算 + 单轮预算」的双层超时，在 Java 里需要手动用两个嵌套的 Future + timeout 组合实现，Go 用 context 嵌套天然支持。

## 7. 关键设计点（带 Java 类比）

### 7.1 信号量限流：channel 当令牌桶

```go
sem := make(chan struct{}, e.concurrency)
sem <- struct{}{}      // 获取
defer func() { <-sem }()  // 归还
```

**为什么不用 `sync.Mutex + 计数器`？** 因为 channel 天然带阻塞语义，且能配合 `select` 实现超时/取消。Mutex + 计数器要自己写 wait/notify，容易出 bug。
> Java 类比：`java.util.concurrent.Semaphore`。但 Go 的 channel 信号量还顺带解决了「主 goroutine 在哪阻塞」的问题——主 goroutine 写 channel 时阻塞，自然就限制了起 goroutine 的速度。

### 7.2 context 贯穿：一根线串起所有超时/取消

`ctx` 从 `cli/run.go` 进来，经过 `Runner.Evaluate` → `EvaluateAll` → `executeCase` → `withCaseTimeout` → `executeCaseOnce` → `Agent.Run` → `NoneRuntime.Exec` → `cmd.Run`。**整条链路任何一个环节取消，下游全部感知**。

这是 Go 并发编程的核心哲学，与 Java 的「Thread.interrupt() 几乎没人响应」形成鲜明对比：
> Java 类比：相当于 `java.util.concurrent.Future.cancel(true)` + 各处 `Thread.currentThread().isInterrupted()` 检查，但 Go 的 context 是**显式参数传递**，比 Thread 的隐式中断更可控。

### 7.3 超时即总预算 + 可定位

- **总预算**（4.2）：case timeout 覆盖 agent + judge，避免对截断输出误判。
- **可定位**（4.3）：错误信息标注 `via case.constraints.timeout_seconds`，用户一眼知道改哪个旋钮。

这两点合起来回答了「为什么超时不是分阶段设」的设计权衡。

### 7.4 进程组优雅终止：SIGTERM→1s→SIGKILL + done channel 防 PID 复用

5.2 节详述。核心是：
- **进程组**杀整棵树（防孙子进程逃逸）；
- **SIGTERM 先行**给清理时间；
- **异步 goroutine 升级 SIGKILL**（不阻塞 Cancel 返回）；
- **done channel** 防止给回收的 PID 发信号（TOCTOU 安全）。

> Java 类比：`Process.destroy()` (SIGTERM) → `Process.destroyForcibly()` (SIGKILL)。但 Java 没有「进程组」一等概念，杀子孙进程要用 `ProcessHandle.descendants()`（JDK 9+）手动遍历，且 Windows 支持有限。Go 这里用 `Setpgid + kill(-pgid)` 更可靠。

### 7.5 错误分类：四态区分 + 平台抹平

5.5 节详述。`classifyExecError` 把模糊的 OS 退出码（POSIX 的 -1 vs Windows 的 1）统一成 `(exitCode, error)` 规范对，让下游业务逻辑不用关心平台差异。特别是把 `exec.ErrWaitDelay` 当作 exit 0 的宽容设计，避免「Agent 成功但后台 sleep 没退」被误判失败。

## 8. 面试 Q&A

### Q1：skill-up 怎么做并发？为什么不用线程池？

**A**：用 goroutine + 带缓冲 channel 当信号量。具体在 `EvaluateAll`（`evaluator.go:180-237`）：先把 cases × {with_skill, without_skill} 展开成任务列表，每个任务起一个 goroutine；并发上限用 `sem := make(chan struct{}, concurrency)` 控制——主 goroutine 在 `sem <- struct{}{}` 阻塞，子 goroutine 退出时 `<-sem` 归还令牌；用 `sync.WaitGroup` 等全部完成。结果用预分配数组 `results[idx]` 写，每个 goroutine 写自己的槽位，无锁。

为什么不用「线程池」？Go 的 goroutine 是用户态轻量级线程（2KB 起始栈），开 10 万个也不心疼；而 Java 式线程池主要为了复用昂贵的内核线程。skill-up 的任务数（cases）通常几十到几百，直接每任务一 goroutine + 信号量限流，代码更直观。信号量本质上是「虚拟的线程池」，只是调度交给 Go runtime。

### Q2：超时怎么控制？为什么说 case 超时是「总预算」？

**A**：用 `context.WithTimeout` 给每个 attempt 建一个 `attemptCtx`（`evaluator.go:294` 的 `withCaseTimeout`）。优先级是 case 级 `constraints.timeout_seconds` > defaults 级 `cases.defaults.timeout_seconds`。

「总预算」指的是这个 context 同时绑定了 `Agent.Run` 和后续的 `Judge.Evaluate`——两者共用一个 deadline。`handleExecutionResult`（`evaluator.go:907`）的注释 explicit 说明：超时直接判 ERROR，不试图用截断输出跑 judge。原因：judge 基于残缺 transcript 打分会误导（给本应失败的 case 打 PASS）。总预算语义让「超时 = 整次失败 = 触发 timeout 重试」，逻辑干净。

而且错误信息会标注来源：`annotateCaseTimeoutError` 把 `context.DeadlineExceeded` 包成 `"context deadline exceeded (case timeout 60s via case.constraints.timeout_seconds)"`（`evaluator.go:866`），用户直接知道去改哪个 YAML 字段。

### Q3：重试策略是什么？怎么避免重试打爆下游？

**A**：在 `executeCase`（`evaluator.go:289-331`）里循环 `maxAttempts = MaxRetries + 1` 次。重试决策三层：

1. **状态过滤**：只有 `StatusError` 才考虑重试（PASS/FAIL 不重试，因为断言不过是确定性失败）。
2. **理由分类 + 白名单**：错误被分成 `timeout` / `error` 两类，YAML 里 `retry_on: [timeout]` 控制重试哪些——白名单制。
3. **指数退避**：`retryBackoffDelay = 2^attempt` 秒（2s/4s/8s/16s），给下游恢复时间。

防打爆下游：（a）指数退避本身就是去拥塞信号；（b）`parallelism` 上限 256 在配置层硬限并发；（c）退避期间用 `sleepContext`（`select` 而非 `time.Sleep`），父 context 取消立刻返回，不会「用户已经 Ctrl+C 了还在重试」。

### Q4：孙子进程怎么清理？为什么 `exec.CommandContext` 不够？

**A**：`exec.CommandContext` 在 ctx 取消时只 kill 直接子进程，但 skill-up 的进程树是 `shell → agent CLI → git/sleep/ping`，孙子进程会变孤儿继续跑，污染 workspace、占端口、卡 CI。

解决方案在 `none_exec_unix.go`（POSIX）：`cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` 让子进程成为新进程组 leader，然后 `cmd.Cancel` 里用 `syscall.Kill(-pid, SIGTERM)` 给**整组**发信号。SIGTERM 后启一个 goroutine 等 1s（`noneExecKillGrace`），没退就升级 `SIGKILL`。goroutine 用 `done` channel 知道进程何时被回收，**避免给被操作系统复用的 PID 误发信号**（TOCTOU 安全）。

Windows 没有 `setpgid`/`kill(-pid)` 等价物（`none_exec_other.go` 是空实现），靠 `cmd.WaitDelay = 2s` 在子进程退出后强制关闭 stdio 管道，让读管道的 goroutine 解除阻塞。两个平台用 build tag `//go:build unix` / `!unix` 切换。

### Q5：`classifyExecError` 为什么要分四种状态？

**A**：因为 `cmd.Run()` 的错误信号有歧义，必须翻译成规范对 `(exitCode, error)` 才能让业务层正确判断。四种状态：

1. `nil err` → `(0, nil)` 正常成功；
2. ctx 取消 → `(-1, ctxErr)` 强制 -1，**抹平平台差异**（POSIX 进程被信号杀报 -1，但 Windows bash 的 sleep 被 ctx 杀报 exit 1，会和脚本正常失败混淆）；
3. `*exec.ExitError`（ctx 活着）→ `(真实退出码, nil)` 业务级失败，交给 expect/judge 处理；
4. `exec.ErrWaitDelay`（无 ExitError）→ `(0, nil)` **宽容设计**：进程已成功退出，只是 stdio 管道被后台孙子占着没及时关闭，按 exit 0 处理，避免误判。

特别是第 4 种，如果不特殊处理，会让「Agent 跑成功了但后台有个 sleep 没退」的 case 被标成失败——这对用户体验伤害很大。

---

## 9. 一句话总结

> skill-up 的并发/重试/超时/清理是一套「层层包装」的设计：**信号量限并发（channel 当令牌桶）→ context 贯穿（attemptCtx 重建支持重试）→ case 总预算超时（agent + judge 共用 deadline，且错误标注来源旋钮）→ 进程组 SIGTERM→SIGKILL（done channel 防 PID 复用，build tag 分平台）**。整条链路用 `context.Context` 一根线串起来，从用户 Ctrl+C 到底层 `kill -9`，任何一层取消都能秒级传导到所有下游——这是 Go 在系统编程上比 Java 显式且可控的地方，也是这份代码最值得在简历/面试里讲的设计。
